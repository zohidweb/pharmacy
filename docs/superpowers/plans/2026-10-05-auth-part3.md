> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Новые тесты не пишутся до готовности MVP** (решение пользователя 2026-10-05). В плане нет шагов
> RED/GREEN. Существующие наборы должны оставаться зелёными: тест, сломанный изменением сигнатуры
> или каталога, исправляется, а не удаляется. Непокрытое перечислено в разделе «Долг по тестам».

**Goal:** оператор платформы входит в админку по своему логину и паролю. Маршруты `/api/v1/operator/*`
доступны только с сессией оператора, по его правам, и каждое его действие пишется в журнал платформы.

**Architecture:**
- **Второй контур принципала (ADR-0013).** У оператора свои таблицы класса `platform`: `operators`,
  `operator_credentials`, `platform_audit_log`. Доступ к ним только через `PlatformDatabase`
  (роль `pharmacy_platform`, код в `app/platform/**`).
- **Сессия.** Хранится в Redis отдельным портом `OperatorSessionStore`. JWT с `aud=admin` в cookie
  `__Host-op_sid`.
- **Контур выбирает `SessionMiddleware` по пути.** На `/operator/*` он строит `OperatorPrincipal`,
  на остальных маршрутах — `EmployeePrincipal`, как сейчас. Токен чужого контура не принимается.
- **Права оператора.** Задаются в коде, проверяются `OperatorPermissionsGuard` и
  `@RequireOperatorPermission`. Маршрут оператора без декоратора по умолчанию получает отказ.

**Tech Stack:** NestJS 11, Kysely + pg (`PlatformDatabase`), node-pg-migrate (только Up),
node-redis 6, `@nestjs/jwt`, `PasswordHasher` из части 1.

**Spec:** `docs/superpowers/specs/2026-10-02-auth-design.md`. Нужные разделы:
- §9 — оператор;
- §4 — два контура;
- §5 и §7 — токен и проверка запроса;
- §11 — ошибки и конфигурация.

Части 1 и 2 уже в `main` (PR #8, #9).

## Global Constraints

- **Ветка и коммиты.** Ветка `feature/auth-part3` от актуального `main`. Conventional Commits. Подпись
  GPG не обходить.
- **Сессия оператора.**
  - JWT: `aud: 'admin'`, `iss: 'pharmacy-api'`. Claims: `jti`, `sub` (operatorId), `iat`, `exp`.
    `tid` нет.
  - Cookie `__Host-op_sid` с атрибутами `Secure; HttpOnly; SameSite=Strict; Path=/`. При
    `AUTH_TEST_COOKIES=true` — `op_sid`.
  - `OPERATOR_SESSION_IDLE_SECONDS` = 1800, `OPERATOR_SESSION_ABSOLUTE_SECONDS` = 28800.
- **Контуры.**
  - Контур оператора — ровно маршруты `/api/v1/operator/*`.
  - CSRF для них сверяет `Origin` с `ADMIN_ORIGIN`, для остальных маршрутов — с `WEB_ORIGIN`.
- **Вход оператора** устроен как вход сотрудника в части 1:
  - `login` — рабочий e-mail в нижнем регистре;
  - лимит `LOGIN_MAX_FAILURES` / `LOGIN_LOCK_SECONDS` по ключу `operator:<sha256(login)>`;
  - фиктивный хеш для неизвестного логина;
  - выравнивание неудачи по `LOGIN_FAILURE_FLOOR_MS`;
  - один ответ `401 invalid_credentials` на любую неудачу.
- **Журнал.** `platform_audit_log` только дополняется: триггер `forbid_mutation`, как у `audit_log`.
  Пароли, коды и токены в него не попадают.
- **Ограничения.**
  - Оператор не получает доступа к тенантным таблицам. Вход «от имени» и выдача кодов через API
    вне этой части (решения P2, P3).
  - Новые зависимости не добавляются. Docker-контейнеры не создаются. `.env` не читается и не
    правится.
- **Проверки каждой задачи:**
  - всегда — `npx nx lint api`, `npx tsc -b apps/api/tsconfig.spec.json`, `npx nx test api`;
  - для задачи с миграцией ещё `api:migrate`, `api:db-types` и `api:integration`;
  - `run-many` и `npm run check` запускает пользователь.

## Review Focus

Тестов нет. Поэтому это список для финального ревью и ручной проверки (задача 5):

1. **Чужой контур.**
   - Cookie сотрудника на `/operator/*` → 401.
   - Cookie оператора на `/me`, `/sessions/current` → 401.
   - JWT с `aud=web`, подложенный в `op_sid`, → 401.
2. **Запрет по умолчанию.** Маршрут `/operator/*` без `@RequireOperatorPermission` и без `@Public` →
   403. Оператор не проходит `PermissionsGuard` тенанта, сотрудник не проходит `OperatorPermissionsGuard`.
3. **Перебор и тайминг входа оператора.**
   - Неизвестный логин, неверный пароль и заблокированный оператор неразличимы.
   - 5 неудач → `429 login_locked`.
4. **CSRF админки.**
   - `Origin: WEB_ORIGIN` на `POST /operator/...` → `403 csrf_rejected`.
   - `Origin: ADMIN_ORIGIN` на маршрутах тенанта → тоже отказ.
5. **Блокировка оператора.** После `status = 'blocked'` следующий запрос его живой сессии → 401.

## Решения, принятые при составлении плана

- **P1. Первый оператор получает одноразовый код активации, а не пароль в консоли.**
  - Код выдаёт скрипт `create-operator.mjs`. Пароль оператор задаёт сам через
    `POST /operator/activations`, тем же механизмом, что владелец в части 1 (128 бит, base32,
    в БД только SHA-256).
  - Причина: иначе скрипту пришлось бы повторять scrypt + pepper вне `PasswordHasher`. Это дубль
    криптокода и риск расхождения форматов PHC.
  - Это расходится со спекой (§9: «пароль вводится в консоли без эха»), поэтому спека правится в
    задаче 5.
- **P2. Управление сетями вне части 3.** Сюда относятся создание сети, блокировка тенанта с закрытием
  его сессий и выдача кода владельцу через API. Это модуль «сети» админки, у него будет свой план.
  - Выдача кода владельцу пишет в `employee_credentials` тенанта. Роль `pharmacy_platform` таких прав
    не имеет (ADR-0013), а давать их — тот же вопрос доверия, что и вход «от имени».
  - Пока остаётся скрипт `create-activation-code.mjs`.
  - Открытый пункт части 1 «блокировка тенанта закрывает его сессии» переносится в план модуля сетей.
- **P3. Профиль, команда и журнал оператора вне части 3.** Сюда относятся `/operator/me`, смена пароля
  оператора, список операторов и `GET` журнала. Спека (§9) их не включает, админка остаётся на моках.
- **P4. Статус оператора проверяется на каждом запросе.** Это одно чтение `operators.status` через
  `PlatformDatabase`. Операторов единицы, кэш не нужен, а блокировка действует сразу.
- **P5. В БД статус `active` / `blocked`** (модель данных 01). В DTO `PlatformOperator.status`
  `blocked` отдаётся как `disabled`.
