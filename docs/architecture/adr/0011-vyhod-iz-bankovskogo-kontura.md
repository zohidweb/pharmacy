# ADR-0011: Проект вне банковского контура — отказ от техрадара и банковских согласований

- **Статус:** accepted
- **Дата:** 2026-09-29
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy

## Контекст

Фаза проектирования Pharmacy прошла по шаблону ai-project-start с банковским процессом управления:
техрадар банка как закон, одноразовые исключения из радара (ADR-0003/0004/0005), Архитектурный
комитет и апрув ИБ (APPROVAL.md), запрет технологий из «категорий на утверждении». Сам продукт —
внешняя SaaS-платформа для аптечных сетей и не связан с инфраструктурой банка (C4 context).
Команда решила вести проект вне банковского контура: банковские правила и согласования больше не
применяются, но инженерная дисциплина и защита данных тенантов должны сохраниться.

## Рассмотренные варианты

1. **Оставить банковский процесс** — техрадар, исключения, комитет и ИБ. Минусы: процесс рассчитан
   на внутрибанковские системы; запрещает целые классы инструментов (CI/CD, мониторинг, брокеры,
   хранилище секретов), которые продукту понадобятся к prod; согласования вне команды тормозят срок.
2. **Полностью убрать правила** — выбор технологий без записи решений. Минусы: теряется история
   решений и контроль над стеком; растёт риск утечки данных тенантов.
3. **Выйти из банковского контура, сохранив ADR-процесс и базовые правила проекта** — решения
   команды фиксируются в ADR, ревью делает архитектор проекта, четыре правила защиты данных и
   интеграций остаются обязательными.

## Решение

Выбран вариант 3.

- Техрадар банка (`tech-radar/`), команда `/update-radar`, процедура исключений, Архитектурный комитет
  и апрувы ИБ удаляются из проекта. Файлы доступны в истории git.
- Ревью архитектуры и перевод ADR из `proposed` в `accepted` — **архитектор проекта Zohid Saidov**
  (docs/architecture/APPROVAL.md).
- Новая технология, библиотека уровня фреймворка, интеграция или компонент — только через ADR (`/03-adr`).
- Остаются обязательными правила проекта:
  1. никакой самописной криптографии — только проверенные библиотеки и алгоритмы;
  2. персональные и клиентские данные не отправляются во внешние LLM и SaaS;
  3. никаких внешних SaaS-БД для данных тенантов — только собственная PostgreSQL;
  4. закрытый список интеграций (1С, фискализация, курсы НБТ, синхронизация офлайн-точек); новая
     интеграция — через ADR.
- Снимаются запреты бывших «категорий на утверждении» (брокеры сообщений, CI/CD, мониторинг,
  библиотеки логирования, хранилище секретов, криптобиблиотеки в рамках правила 1, API gateway,
  push). Такие технологии вводятся обычным ADR. До соответствующего ADR действуют текущие решения:
  очереди-таблицы в PostgreSQL (ADR-0002), ручной прогон проверок (`npm run check`), встроенный
  Nest Logger, env-файлы для секретов.
- ADR-0001, 0003, 0004, 0005 переоформлены как обычные решения о выборе технологий; их выводы
  (NestJS, Next.js, Docker) не меняются.

## Последствия

- Положительные: решения принимаются внутри команды без внешних согласований; к prod можно выбрать
  CI/CD, мониторинг и хранилище секретов; история решений сохраняется в ADR.
- **Отрицательные (обязательно):**
  - один человек принимает архитектурные решения — нет независимой проверки; риск ошибок и
    «слепых зон», особенно в безопасности (аутентификация ADR-0008, изоляция тенантов);
  - нет внешнего контроля защиты персональных данных — ответственность за соответствие
    законодательству РТ (локализация ПДн, вопрос № 1 stack.md) целиком на команде и заказчике;
  - снятие запретов расширяет выбор, но и риск «зоопарка» технологий — дисциплина держится только
    на ADR-процессе и ревью архитектора;
  - переоформлены принятые ADR (0001, 0003–0005): историческая формулировка «исключений из радара»
    видна только в истории git.
