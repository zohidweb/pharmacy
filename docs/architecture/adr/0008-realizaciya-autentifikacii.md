# ADR-0008: Реализация самописной аутентификации — scrypt из `node:crypto` (Node 22 и 24), сессионная cookie на одном origin, device-cookie терминала, `redis` (node-redis)

- **Статус:** accepted (2026-09-30, архитектор проекта — APPROVAL.md; только аутентификация)
- **Дата:** 2026-09-30
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

**Граница решения.** ADR-0008 решает только **аутентификацию** — кто пользователь и как он
входит (хеширование, сессии, CSRF, терминал, «от имени»). **Авторизация** — модель прав «модуль ×
действие × охват точек», роли, проверка прав (guards) — решается **отдельным ADR**. Имена прав в
этом документе (`pos:terminal-bind`, `platform:impersonate`) — рабочие обозначения; их модель и
хранение определит ADR об авторизации.

Модель аутентификации уже зафиксирована (stack.md, раздел 2–3; APPROVAL.md,
2026-09-29): логин + пароль, PIN ≥ 4 цифр для переключения кассира на привязанном к точке
терминале, серверные сессии в Redis, idle-таймаут — настройка сети тенанта, вход оператора
платформы «от имени» с аудитом, автономная офлайн-точка в Docker на ПК аптеки без интернета
(ADR-0005). Скил `nestjs-api` (`reference/nestjs-security-auth.md`) уже содержит проект
реализации (порт `PasswordHasher`, `SessionStore`, guards), но помечает как «требует ADR»
четыре детали: алгоритм/библиотеку хеширования, транспорт сессии и CSRF, протокол
привязки терминала, механику входа «от имени»; к ним добавляется выбор Redis-клиента и
хранилища throttler. Этот ADR их закрывает.

Ограничения, которые определяют выбор:

- Правило проекта: никакой самописной криптографии — только проверенные библиотеки и
  алгоритмы. Каждая сторонняя криптобиблиотека — дополнительная supply-chain-поверхность и
  объём security-ревью; выбор фиксируется этим ADR, решение принимает архитектор проекта.
- Keycloak отклонён ранее (stack.md, раздел 3): не применим к внешним тенантам и к
  офлайн-точке без интернета.
- PIN из 4 цифр — пространство 10⁴: при утечке БД любой хеш перебирается мгновенно, онлайн —
  за ≤ 10⁴ попыток; защищают только лимиты/блокировки, привязка к терминалу и серверный
  секрет (pepper), а не стойкость хеша.
- Развёртывание (c4/deployment.md): reverse proxy — единственная точка входа, отдаёт статику
  `apps/web` / `apps/admin` (Next.js static export) и проксирует `/api`; админка — отдельный
  поддомен. Офлайн-точка: браузер → `localhost` того же ПК; **Redis на офлайн-точке не
  устанавливается** (c4/container.md).
- Nest 12 (актуальная линия `@nestjs/core` 12.1.x); **API должен работать на Node.js 22 LTS и 24 LTS**
  (требование архитектора проекта 2026-09-30); нагрузка — до 50
  одновременных кассиров, касса ≤ 1 сек, запас ×5.

## Рассмотренные варианты

Решение многоосевое; ниже — варианты по каждой оси (минимум два на ключевых).

**Ось A. Алгоритм и реализация хеширования паролей и PIN**

Ориентир параметров — OWASP Password Storage Cheat Sheet: Argon2id — первый выбор,
минимальные эквивалентные конфигурации `m=47104 (46 MiB), t=1, p=1` / `m=19456 (19 MiB), t=2,
p=1` / `m=12288, t=3` / `m=9216, t=4` / `m=7168, t=5`; scrypt (если Argon2id недоступен) —
`N=2^17, r=8, p=1` / `N=2^16, r=8, p=2` / `N=2^15, r=8, p=3` / `N=2^14, r=8, p=5` /
`N=2^13, r=8, p=10`; bcrypt — только legacy, work factor ≥ 10 и ограничение пароля 72 байтами;
pepper — секрет, хранимый отдельно от хешей (defense in depth).

1. **Argon2id через npm `argon2` (node-argon2, 0.45.x, MIT)** — нативный аддон с prebuilt-
   бинарями (`node-gyp-build`), PHC-строка, `verify`/`needsRehash` из коробки; зрелый и самый
   распространённый в Node. Минусы: **новая сторонняя криптобиблиотека**, нативный код и транзитивные зависимости (`@phc/format`, `node-addon-api`) —
   supply-chain-поверхность; мейнтейнер сам планирует превратить пакет в тонкую обёртку над
   встроенным `crypto.argon2` по мере распространения Node + OpenSSL ≥ 3.2 (issue #469).
2. **Argon2id через `@node-rs/argon2` (2.2.x, MIT)** — Rust/N-API, без зависимостей, prebuilt
   под платформы, быстрый. Минусы: та же **новая сторонняя криптобиблиотека**, реализация
   Argon2 не из OpenSSL (отдельная кодовая база для security-ревью), меньше распространён;
   платформенные бинари нужно проверять для образа офлайн-точки (Linux в WSL2).
3. **bcrypt (npm `bcrypt` 6.x / `bcryptjs`)** — зрелый, простой. Минусы: не memory-hard
   (дешевле перебор на GPU), ограничение 72 байта, OWASP относит к legacy; всё равно **новая
   сторонняя библиотека**. Отклонён.
4. **scrypt из встроенного `node:crypto`** (`crypto.scrypt`, есть с Node v10.5.0, stable).
   Плюсы: **никакой новой npm-криптобиблиотеки** — примитив рантайма (OpenSSL), который уже
   используется проектом (`randomBytes`, `createHash`); memory-hard; зрелость. Минусы:
   OWASP ставит scrypt вторым после Argon2id; нет встроенного PHC-формата и `needsRehash` —
   тонкую обёртку (кодирование параметров/соли, сравнение `timingSafeEqual`) пишем сами;
   дефолт `maxmem` = 32 MiB (ошибка, если `128·N·r > maxmem`) — для `N=2^16/2^17` задавать
   `maxmem` явно; pepper — только через отдельный HMAC-шаг.
5. **Argon2id из встроенного `node:crypto`** (`crypto.argon2('argon2id', …)`: добавлен в
   v24.7.0, помечен Stable в v24.19.0 от 2026-08-03; реализация — OpenSSL ≥ 3.2, в
   официальных сборках Node 24 бандлится OpenSSL 3.5.x). Плюсы: OWASP-первый выбор **без новой
   npm-криптобиблиотеки**; pepper поддержан штатно параметром `secret` (не хранится с хешем);
   тот же рантайм, что уже выбран (ADR-0003). Минусы: свежий в Node-API (стабилен ~2 месяца; в
   v24.20.0 исправлены «Argon2 validation errors» и «Argon2 bypassing FIPS mode»); требует
   Node ≥ 24 (Node 22 LTS не имеет) и сборки с OpenSSL ≥ 3.2 (дистрибутивные сборки с
   shared OpenSSL < 3.2 метода не имеют); PHC-обёртку, как и в варианте 4, пишем сами.

**Ось B. Транспорт идентификатора сессии и CSRF**

1. **HttpOnly-cookie на одном origin (reverse proxy)** — `Set-Cookie: __Host-sid=…; Secure;
   HttpOnly; SameSite=Strict; Path=/`. Плюсы: токен недоступен JS (XSS не может его
   эксфильтровать); не нужен CORS; `__Host-` — host-only, защищает от подмены cookie с
   соседнего поддомена (admin/web — same-site). Минусы: нужна CSRF-защита; фронтенд и API
   обязаны жить на одном origin (proxy); Chrome не принимает префикс `__Host-` на
   `http://localhost` (атрибут `Secure` на localhost Chrome ≥ 89 и Firefox ≥ 75 принимают) —
   для офлайн-точки другое имя cookie.
2. **Opaque-токен в заголовке `Authorization: Bearer`** (хранение в памяти / `sessionStorage`
   SPA). Плюсы: CSRF невозможен по конструкции; работает при фронтенде на отдельном origin.
   Минусы: токен читаем из JS — любая XSS (в т.ч. через npm-зависимость фронтенда) уносит
   сессию за пределы браузера; хранение в памяти теряет сессию при перезагрузке кассы, в
   `localStorage` — долгоживущий секрет в JS; фронтенд на отдельном origin требует CORS.
3. **Cookie + synchronizer/double-submit CSRF-токен** — классика, но при same-origin +
   `SameSite=Strict` + Fetch Metadata избыточна: лишний раунд за токеном и состояние на
   клиенте. Отклонён как избыточный.

**Ось C. Привязка терминала к точке и PIN-переключение**

1. **Device-cookie терминала** — при привязке сервер выдаёт случайный credential (256 бит),
   кладёт в HttpOnly-cookie `__Host-term` (офлайн: `term`), в БД — только SHA-256. Плюсы: JS
   не читает; простая ротация/отзыв; браузерная касса без агентов. Минусы: очистка данных
   браузера = отвязка (повторная привязка заведующим); cookie переносима при физическом
   доступе к профилю браузера.
2. **Токен терминала в `localStorage`/IndexedDB + заголовок** — читаем из JS: XSS = клон
   терминала навсегда (до отзыва). Отклонён.
3. **Неэкспортируемый ключ WebCrypto (ECDSA P-256) в IndexedDB + challenge-response** —
   сильнее (ключ не извлекаем даже XSS), примитив браузера, не библиотека. Минусы: сложнее
   протокол и тесты, нестабильность IndexedDB в kiosk-профилях. Кандидат на усиление после MVP.
4. **Клиентские TLS-сертификаты** — операционно неподъёмно для десятков ПК аптек (выпуск,
   установка, отзыв). Отклонён.

**Ось D. Redis-клиент и хранилище throttler**

1. **`ioredis` (6.0.x)** — API, на котором написаны примеры скила; де-факто стандарт в
   NestJS-сообществе; для throttler есть `@nest-lab/throttler-storage-redis`. Минусы: README
   `ioredis` прямо говорит, что сопровождение — best effort, и для новых проектов рекомендует
   node-redis; `@nest-lab/throttler-storage-redis` 1.2.0 в peer-зависимостях объявляет
   `@nestjs/common` только до `^11` — с Nest 12 формально несовместим.
2. **`redis` (node-redis, 6.2.x, официальный клиент Redis)** — активно развивается,
   рекомендован Redis для новых проектов, типизированные команды. Throttler: либо
   `@nestjs-redis/throttler-storage` (2.0.x, поддерживает Nest 12 и `redis` ^5/^6, но пакет
   одного мейнтейнера), либо **собственная реализация интерфейса `ThrottlerStorage`**
   (`@nestjs/throttler` 6.x) на `MULTI`/Lua-скрипте — десятки строк без новой зависимости.
   Минусы: примеры скила переписывать; меньше готовых Nest-примеров.

**Ось E. Вход оператора платформы «от имени» тенанта**

1. **Переиспользовать сессию оператора в `apps/web`** (оператор с op-cookie ходит в
   tenant-API, guard подставляет тенант). Минусы: смешение пространств сессий и прав,
   размытый аудит, cookie оператора на origin клиентского продукта. Отклонён.
2. **Отдельная impersonation-сессия тенанта** — выдаётся по запросу из админки через
   одноразовый handoff-код, живёт в пространстве tenant-сессий с флагом, `actingOperatorId`,
   `impersonationId`, жёстким абсолютным TTL без продления, ограниченным набором прав и
   баннером в UI. Минусы: дополнительный протокол handoff и таблица `impersonations`.
3. **Отдельный «сервисный» сотрудник в каждом тенанте** с паролем у оператора — общий
   секрет, нет персональной ответственности, противоречит аудиту «кто». Отклонён.

## Решение

Выбрано по итогам обсуждения с архитектором проекта 2026-09-30 (детали — таблица ниже): **A4** — scrypt из встроенного `node:crypto` с pepper
(HMAC-SHA-256) за портом `PasswordHasher`: работает на Node 22 и 24 без сторонних
npm-криптобиблиотек и нативных аддонов, что минимизирует supply-chain-поверхность; A5 (Argon2id
из `node:crypto`) отложен до отказа от Node 22 — переход без сброса паролей через `needsRehash`; **B1** — HttpOnly-cookie на одном origin + CSRF через `SameSite=Strict`, Fetch
Metadata и проверку `Origin`; **C1** — device-cookie терминала с PIN-переключением и
многоуровневыми лимитами; **D2** — `redis` (node-redis) и собственный `ThrottlerStorage`;
**E2** — отдельная ограниченная по времени impersonation-сессия. Определяющие факторы:
минимальная новая криптоповерхность (только OpenSSL рантайма, уже выбранного вместе с
NestJS), недоступность секретов сессии и терминала для JS, работа тех же механизмов на
офлайн-точке без Redis и интернета.

| Тема | Решение |
|---|---|
| Хеш пароля и PIN | `crypto.scrypt`, параметры по OWASP: **`N=2^15, r=8, p=3`** (эквивалент минимума OWASP с меньшей памятью — 32 MiB на проверку вместо 128 MiB у `N=2^17, p=1`; важно для ПК офлайн-точки и одновременных входов), `keylen` = 32, соль — 16 случайных байт на хеш, `maxmem` задаётся явно (≥ 128·N·r·2). Pepper — `HMAC-SHA-256(pepper, secret)` перед scrypt. Хранение — PHC-строка `$scrypt$ln=15,r=8,p=3$<salt>$<hash>` + версия pepper; `needsRehash` при смене параметров, алгоритма или pepper — перехеширование при следующем успешном входе. Сравнение — `crypto.timingSafeEqual`. Параметры повышаются по замеру на целевой VM и ПК офлайн-точки |
| Будущий алгоритм | Argon2id из `node:crypto` (`crypto.argon2`, есть с Node 24.7; стабилизирован в 24.19–24.20) — после отказа от поддержки Node 22: новый `PasswordHasher` + `needsRehash` переводят хеши на Argon2id при входе, без массового сброса. Отдельный ADR не нужен — смена параметров за портом, отметка в APPROVAL.md |
| Рантайм | **Node.js 22 LTS (≥ 22.20) или 24 LTS**; `package.json` `engines` — обе линии; Docker-образ — Node 24. Самопроверка на старте `apps/api`: тест-вектор scrypt (RFC 7914) и доступность `crypto.scrypt`/`timingSafeEqual` — иначе процесс не стартует. e2e аутентификации прогоняются на обеих версиях Node |
| Pepper | 256 бит, свой на каждое развёртывание: облако — один (из переменных окружения, пока ADR не выберет хранилище секретов; открытый вопрос № 8 stack.md); **каждая офлайн-точка — собственный**, генерируется при установке и в облако не передаётся; с версией для ротации. Бэкап pepper — отдельно от бэкапов БД |
| Пароль | Длина/сложность — политика паролей проекта; верхний предел длины (защита от DoS дорогим хешем) — в DTO. Неизвестный логин и неверный пароль неразличимы (ответ и порядок времени: при отсутствии логина — хеширование по фиктивному хешу) |
| PIN | ≥ 4 цифр по ТЗ; **по умолчанию — 4**, сеть тенанта может повысить минимальную длину. Запрет тривиальных PIN (повторы, последовательности: 1111, 1234, 0000…). PIN — не идентификатор: кассир выбирается (список кассиров точки на привязанном терминале или табельный код), затем PIN. PIN принимается **только** с привязанного терминала |
| Лимиты PIN | Счётчик по `(tenant, employee, terminal)`: **после 3 неудачных попыток** — блокировка PIN сотрудника (вход только паролем; разблокировка — заведующим или успешным входом по паролю с заменой PIN) + аудит. Счётчик по `terminal`: после `TERMINAL_PIN_MAX_FAILURES` (по умолчанию 10) неудач по разным кассирам за 15 мин — временная блокировка PIN-входа на терминале на 15 мин + уведомление заведующему (против перебора одного PIN по всем кассирам) |
| Лимиты пароля | `@nestjs/throttler` по IP/маршруту + счётчик по `(tenantCode, login)` с прогрессивной блокировкой; все неудачи и блокировки — в аудит без секретов |
| Транспорт (облако) | `__Host-sid` (`Secure; HttpOnly; SameSite=Strict; Path=/`) на origin `apps/web`; оператор — `__Host-op_sid` на origin `apps/admin`. Токен — `randomBytes(32)`, в Redis ключ — SHA-256 токена. Tenant-cookie принимается только с origin web, operator-cookie — только с origin admin. CORS выключен |
| Транспорт (офлайн) | `http://localhost`: cookie `sid` / `term` с `Secure; HttpOnly; SameSite=Strict` (без префикса `__Host-`, который Chrome на http-localhost отклоняет). Доступ к офлайн-точке с других ПК по LAN — вне этого ADR (потребует TLS в LAN и отдельного решения) |
| CSRF | Для небезопасных методов: `Sec-Fetch-Site` должен быть `same-origin` (если заголовок есть), иначе `Origin` обязан совпасть с разрешённым origin; тело только `application/json` (формы и «простые» запросы отклоняются); `GET` без побочных эффектов |
| Жизнь сессии | Idle-TTL = таймаут сети тенанта, зажатый в `[SESSION_IDLE_TIMEOUT_MIN, MAX]`; абсолютный срок; новый токен при входе, PIN-переключении и смене привилегий (защита от фиксации); смена пароля / блокировка сотрудника — `destroyAllFor` |
| Step-up | Привязка/отвязка терминала, управление сотрудниками и ролями, смена своего пароля — только в сессии, открытой паролем (не PIN), не старше `STEP_UP_MAX_AGE` |
| Привязка терминала | Сотрудник с `pos:terminal-bind` входит паролем на этом ПК → `POST /api/v1/terminals` (точка из его охвата, имя терминала) → сервер создаёт `terminals` (`tenant_id`, `store_id`, `credential_hash`, `bound_by`, `bound_at`, `last_seen_at`, `revoked_at`), ставит device-cookie, пишет аудит. Отзыв — `revoked_at`, действует немедленно: проверяется при каждом PIN-входе и на каждом запросе PIN-сессии (кэш статуса в Redis с инвалидацией). Ротация credential — при повторной привязке |
| PIN-переключение | `POST /api/v1/terminal-sessions` `{ employeeId|employeeCode, pin }` + device-cookie → проверки (терминал не отозван, сотрудник активен и имеет доступ к точке терминала, PIN не заблокирован, PIN верен) → предыдущая PIN-сессия на этом терминале уничтожается, создаётся новая с `terminalId`, охват = только точка терминала |
| Хранилище сессий | Порт `SessionStore`: облако — Redis; **офлайн-точка — PostgreSQL-таблица сессий** (Redis там нет; переживает перезапуск контейнера). Throttler офлайн — встроенное in-memory хранилище (один процесс) |
| Учётные данные офлайн-точки | **Отдельные от облака.** Сотрудники, роли и права приходят синхронизацией (ADR-0014) **без** хешей паролей и PIN; на точке пароль и PIN задаются локально: первый вход — одноразовый код, который выдаёт заведующий/владелец на точке (или оператор при установке), затем сотрудник задаёт пароль и PIN. Сброс — локально. Кража ПК точки не раскрывает облачные учётные данные |
| Redis-клиент | `redis` (node-redis 6.x) — единственный клиент проекта; throttler — собственная реализация `ThrottlerStorage` на node-redis (атомарно: `MULTI`/Lua) |
| «От имени» | Оператор с правом `platform:impersonate` и свежим step-up в админке → `POST /api/v1/operator/impersonations` `{ tenantId, reason }` → запись `impersonations` + одноразовый handoff-код (TTL ≤ 60 с, однократный, в Redis только хеш) → админка делает top-level `POST` формы на origin web (код — в теле, **не в URL**) → сервер выдаёт tenant-сессию с `actingOperatorId`, `impersonationId`: абсолютный TTL 60 мин без продления; **права — только просмотр** (любые изменяющие запросы `POST/PUT/PATCH/DELETE` к прикладным ресурсам отклоняются guard'ом на уровне сессии, а не набором ролей); постоянный баннер в UI; начало/конец сессии и все просмотры чувствительных разделов — в аудите тенанта с `acting_operator_id` и `impersonation_id`; владелец тенанта видит их в аудите. Отзыв сессии оператора каскадно гасит его impersonation-сессии |
| Секреты вне логов | Пароль, PIN, токены сессий/терминала, handoff-код, pepper — никогда в логах, аудите, ответах об ошибках, URL |

## Последствия

- Положительные:
  - в проект не входит ни одна сторонняя npm-криптобиблиотека: вся криптография — OpenSSL
    через `node:crypto` рантайма, уже выбранного вместе с NestJS (ADR-0003); меньше
    supply-chain-поверхность и security-ревью;
  - memory-hard scrypt с параметрами OWASP и pepper: утечка одной только БД не раскрывает ни
    пароли, ни (при сохранности pepper) 4-значные PIN; один код на Node 22 и 24;
  - токены сессии и терминала недоступны JS — XSS не выносит их за пределы браузера;
  - один механизм для облака и офлайн-точки (разница — имя cookie и хранилище сессий за
    портом);
  - вход «от имени» персонален, ограничен по времени и правам, полностью виден в аудите
    тенанта;
  - порт `PasswordHasher` с PHC-форматом и `needsRehash` позволяет сменить алгоритм или
    параметры без массового сброса паролей.
- **Отрицательные (обязательно):**
  - **scrypt — второй выбор OWASP** после Argon2id: при той же стоимости слабее против
    атак с компромиссом время/память; принято ради поддержки Node 22; переход на Argon2id — при
    отказе от Node 22 (строка «Будущий алгоритм»);
  - в Node `crypto.scrypt` выполняет параметр `p` последовательно в одном потоке libuv-пула:
    `p=3` — втрое больше CPU на проверку; под нагрузкой входов нужен размер пула
    (`UV_THREADPOOL_SIZE`) и throttling; параметры откалибровать на ПК офлайн-точки;
  - две поддерживаемые версии Node — двойная матрица проверки (e2e аутентификации на 22 и 24);
  - «без библиотеки» ≠ «без своего кода»: кодирование/разбор PHC-строки, `needsRehash`,
    фиктивный хеш для неизвестного логина пишем сами — это не самописная криптография, но
    код, требующий отдельного security-ревью;
  - **pepper — новый критичный секрет** (хранилище секретов не выбрано):
    на MVP — переменные окружения, пока ADR не выберет хранилище; потеря pepper = недействительны все пароли и PIN
    развёртывания (массовый сброс); для офлайн-точки потеря ПК/тома = локальный сброс
    учёток; ротация pepper — только постепенная, при входе пользователя;
  - учётные данные офлайн-точки отдельные от облака: сотруднику точки нужен свой пароль и PIN,
    их заведение и сброс — локальная процедура заведующего (одноразовый код); это трение для
    людей, работающих и в облачных, и в офлайн-точках;
  - 4-значный PIN по умолчанию слаб против подсматривания и физического доступа к терминалу;
    блокировка после 3 неудач даёт DoS-вектор (коллега может заблокировать чужой PIN) и чаще
    срабатывает от опечаток на сенсоре — обходится входом по паролю, но это трение на кассе;
  - memory-hard хеш стоит CPU/RAM на каждый вход и PIN-переключение (≈19 MiB на одновременную
    проверку); без throttling эндпоинты входа — DoS-вектор; параметры надо откалибровать на
    ПК офлайн-точки (от 8 ГБ ОЗУ, вместе с PostgreSQL и Docker);
  - cookie-транспорт жёстко связывает фронтенды и API одним origin через reverse proxy:
    вынести статику на CDN/отдельный домен без перепроектирования нельзя; две конфигурации
    cookie (облако `__Host-*` / офлайн без префикса) — обе нужно покрыть e2e-тестами;
    доступ к офлайн-точке по LAN не поддерживается;
  - device-cookie: очистка данных браузера или смена профиля отвязывает терминал —
    повторная привязка заведующим; браузеры касс нужно настраивать (не чистить cookie);
    при физическом доступе к профилю браузера credential копируется (усиление — вариант C3
    после MVP);
  - node-redis вместо ioredis: примеры скила и большинство Nest-примеров в сети — на ioredis;
    собственный `ThrottlerStorage` — наш код на сопровождении;
  - две реализации `SessionStore` (Redis и PostgreSQL) — дублирование логики TTL и тестов;
  - impersonation добавляет протокол handoff, таблицу, read-only-guard и баннер в UI; режим
    «только просмотр» не позволяет оператору исправить данные за клиента — исправления делает сам
    тенант (или отдельное решение, если понадобится);

Решено архитектором проекта 2026-09-30 (бывшие спорные моменты):

1. PHC-обёртка, `needsRehash` и фиктивный хеш поверх примитивов `node:crypto` — прикладной код, а
   не собственная криптография; проходит отдельное ревью безопасности.
2. Основной алгоритм — scrypt из `node:crypto` (A4): API должен работать на Node 22 и 24;
   Argon2id (A5) — после отказа от Node 22, переход через `needsRehash`.
3. PIN по умолчанию — 4 цифры, блокировка после 3 неудач.
4. Учётные данные офлайн-точки — отдельные, заводятся на точке.
5. Режим «от имени» — только просмотр.
