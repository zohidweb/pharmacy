# Выбор стека — Сервис уведомлений клиентов

## 1. Профиль проекта

| Параметр | Значение |
|---|---|
| Класс проекта | Full — продуктовая система |
| Тип проекта | веб-приложение (SPA + API) |
| Назначение (1–2 предложения) | Формирует и отправляет клиентам СМС- и push-уведомления о движениях по счёту (списания, зачисления, отказы операций). |
| Пользователи и пиковая нагрузка | 50 000 клиентов банка; пиковая нагрузка — 20 уведомлений/сек |
| Критичность | Tier 2 — важная внутренняя система (не платёжный тракт, но задержка/потеря уведомлений напрямую влияет на доверие клиентов) |
| Категория данных | персональные данные (ФИО, номер телефона, маскированный номер счёта, тип и сумма операции) |
| Объём данных и срок хранения | история уведомлений по 50 000 клиентам; хранится 3 года (регуляторное требование банка) |
| Доступность (SLA) | 99,5% 24×7 |
| RTO / RPO | RTO 4 часа / RPO 15 минут |
| Ограничения | персональные данные не покидают контур банка; обмен с СМС-шлюзом — только через DMZ-прокси; прямой доступ к БД АБС запрещён |

## 2. Чек-лист безопасности

| Вопрос | Ответ |
|---|---|
| Какие категории данных обрабатываются? | ФИО, номер телефона клиента, маскированный номер счёта, тип и сумма операции |
| Где хранятся секреты (пароли, ключи, строки подключения)? | НЕ в коде и не в git — в хранилище секретов инфраструктуры, доступ по ролям |
| Как аутентифицируются пользователи? | Оператор банка (единственный UI-пользователь сервиса) — через корпоративный SSO банка; клиенты сервисом напрямую не аутентифицируются, они только получатели уведомлений |
| Как аутентифицируются сервисы между собой? | Взаимный TLS + токен, выданный API-gateway; каждый вызов несёт correlation ID |
| Что уходит за контур банка (данные, вызовы)? | Текст уведомления и номер телефона клиента — на СМС-шлюз (внешний провайдер), только через DMZ-прокси |
| Что шифруется (при передаче / при хранении)? | При передаче — TLS 1.2+ на всех вызовах; при хранении — шифрование на уровне диска для PostgreSQL (персональные данные) |

**Флаг апрува ИБ:** ДА

## 3. Выбор стека

Только технологии из tech-radar/RADAR.md со статусом «Утверждено» (при наличии — «Приоритет»).

| Слой | Технология | Статус в радаре | Обоснование | Альтернатива из радара и почему нет |
|---|---|---|---|---|
| Backend | C# (.NET, актуальная LTS) | Утверждено | В команде-примере есть компетенции в .NET; единая экосистема с существующими банковскими сервисами упрощает поддержку | PHP отклонён — нет компетенций в команде-примере |
| Frontend | Angular | Приоритет | Приоритетная технология радара; нужен только простой административный интерфейс оператора (шаблоны, мониторинг доставки) | React отклонён — Angular приоритет радара |
| БД | PostgreSQL | Утверждено | Единственная утверждённая СУБД радара; подходит для хранения клиентов, шаблонов и истории уведомлений | Альтернативы в радаре нет |
| Кэш | Redis | Утверждено | Единственный утверждённый кэш радара; используется также как очередь задач на отправку | Альтернативы в радаре нет |
| API | REST | Утверждено | Простой синхронный обмен с АБС и SPA, не требует потоковой передачи или строгой типизации схемы | gRPC отклонён — нет внешних клиентов, которым нужна бинарная эффективность, у команды нет опыта |
| Очередь сообщений | RabbitMQ | Исключение (ADR-0003, approve одноразовое) | асинхронная отправка критичных уведомлений (отказ операции) | из радара нет утверждённого брокера («На утверждении») |

## 4. Интеграции

Правила: только через утверждённый API-слой; прямой доступ к БД АБС запрещён;
для финансовых операций — идемпотентность и correlation ID.

| Система | Протокол | Формат | Владелец | SLA |
|---|---|---|---|---|
| АБС | REST | JSON | Управление ИТ | 99,9% |
| СМС-шлюз | REST | JSON | внешний провайдер | 99,5% |
