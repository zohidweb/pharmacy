# Нагрузочный прогон кассы

Прогон проверяет, выдерживает ли облачный API кассы нагрузку пилота с ростом ×5 на данных за год работы сети
(ADR-0009, ось «Ж»). Бюджеты — из раздела «Бюджеты API кассы» ADR-0009, профиль и решения — в плане
`docs/superpowers/plans/2026-11-04-pos-load-test.md` (R1–R18). Прогон ручной, перед пилотом и после изменений
горячего пути кассы; в CI не входит.

## Что нужно

- `npm run dev:deps` — PostgreSQL и Redis разработки в Docker. Прогон работает только с базой `pharmacy_load` этого
  контейнера и логической БД Redis 13: dev-база `pharmacy`, `pharmacy_test`, стенд и прод не затрагиваются, скрипты
  отказываются работать с базой под другим именем.
- `.env` разработки (раздел «Local development secrets» CLAUDE.md). Скрипты читают его сами и значения не печатают.
  Из worktree без своего `.env` — путь к нему в переменной `LOAD_ENV_FILE`.
- Собранный API: `npx nx build api`. Прогон запускает `apps/api/dist/main.js` с настройками прода по умолчанию (пул 10,
  один процесс), `NODE_ENV=production`, в контейнере `pharmacy-load-api` образа Node из `apps/api/Dockerfile`
  (`node:24.21.0-alpine` по digest) в сети `pharmacy-dev_default` — рядом с PostgreSQL и Redis, как в compose test и
  prod; снаружи — `127.0.0.1:3010`. Старт около двух минут: `node_modules` читается через общую папку Docker Desktop.
- Генератор нагрузки (`tools/load/driver.mjs`) тоже работает в контейнере этой сети. С Windows замер не годится: запрос
  к PostgreSQL через порт Docker Desktop стоит ≈ 3 мс против ≈ 0,2 мс внутри сети, а петлевой интерфейс ПК держит
  клиента на сотнях запросов в секунду (пустой `/health`: ≈ 360 запросов/с с Windows против ≈ 6 000 изнутри).
  `--api host` и `--driver host` оставлены для сравнения и отладки.
- Место: база полного объёма (`--scale 1`) занимает около 18 ГБ: на `--scale 0.02` — 0,85 ГБ, из них 0,4 ГБ от масштаба
  не зависят. Генератор требует не меньше 30 ГБ свободно на диске виртуального диска Docker (на Windows — `C:`, другой —
  в `LOAD_DOCKER_DISK`), иначе останавливается; тогда — `--scale 0.5`, в отчёте пометка «объём ниже ADR».

## Порядок

```bash
node tools/load/db.mjs create
node tools/load/db.mjs generate --scale 1
node tools/load/db.mjs verify
node tools/load/run.mjs --scenario all
node tools/load/db.mjs drop
```

- `create` — пустая база, `docker/postgres/initdb/02-database.sql`, все миграции.
- `generate` — год истории сети «Нагрузка»: 30 точек `L01`…`L30`, 3000 товаров, около 5,5 млн чеков и 10 млн движений;
  около часа (`--scale 0.02` — полторы минуты). Работает суперпользователем в `docker exec … psql`, по одному месяцу в
  транзакции; печатает месяц и размер базы. Каждый случайный выбор — хеш его позиции, поэтому повтор на том же масштабе
  даёт те же счётчики. Обрыв (диск, перезапуск) оставляет загруженные месяцы: `verify` скажет, какой последний, а
  следующий `generate` продолжит с него.
- `verify` — счётчики, остатки партий не ниже нуля, суммы чеков и оплат, уникальность номеров, висячие ссылки.
- `run.mjs` — поднимает API, собирает парк кассиров (250 кассиров на своих терминалах, 5 заведующих) и гонит сценарии.
  Повторный запуск на той же базе переиспользует владельца, терминалы и смены. Подготовка парка — около 6 минут: входы
  по PIN идут не чаще 55 в минуту (лимит 60 с одного адреса). Для пробы: `--minutes N` укорачивает сценарии,
  `--cashiers N` берёт меньше кассиров (сначала по одному на точку), `--pause S` — пауза между сценариями.
  `--factor F` умножает темп всех потоков профиля: `--scenario profile --factor 2 --minutes 5` — запас ×2 по ADR-0009.
- `size` — размер базы и десяти самых больших таблиц.
- `drop` — удаляет базу и `tools/load/.state/`.

## Сценарии

| Сценарий | Что делает | Гейт |
|---|---|---|
| `profile` | 15 минут: чеки 5/с, изменения снимка 9/с и текущая смена 5/с от 250 кассиров; поиск каталога по штрихкоду 3/с и по тексту 3/с, поиск остатков 3/с от 5 заведующих | бюджеты ниже, 0 ответов 5xx, 0 ответов 429 |
| `hot` | 3 минуты: 5 кассиров точки `L01` продают одну партию, до 20 чеков/с | бюджет чека, остаток партии = приход − продано |
| `stress` | 5 минут: чеки на 250 соединениях по 4 в секунду (каждый кассир — не больше 240 в минуту при лимите 300) и GET-потоки на 50 соединениях с тем же темпом, без общего ограничения | ≥ 10 чеков/с, ≥ 50 GET/с, 0 ответов 5xx |
| `replay` | повтор 200 принятых чеков тем же ключом и телом, тот же ключ с другим телом, 50 одновременных пар | 201 и тот же номер, 409, по одному чеку на ключ |
| `all` | все четыре подряд с минутой паузы | все гейты |

## Бюджеты (ADR-0009)

| Поток | p97.5 | p99 |
|---|---|---|
| Чек `POST /receipts` | 300 мс | 600 мс |
| Товар по штрихкоду `GET /catalog/products?q=<штрихкод>` | 100 мс | 250 мс |
| Текстовый поиск `GET /catalog/products?q=`, `GET /stores/{id}/stock-products?query=` | 200 мс | 400 мс |
| Изменения снимка, текущая смена | флаг при p97.5 > 300 мс (бюджета в ADR нет, R2) | — |

Касса сканирует и ищет по своему снимку каталога, поэтому бюджеты поиска проверяются на поиске бэк-офиса (R1). Время
меряется у генератора нагрузки в сети Docker — от отправки запроса до конца ответа, без интернета и Caddy прода.
Поток с темпом N — это N соединений по запросу в секунду, их старты разнесены по секунде со случайной фазой потока:
одно соединение autocannon с темпом начинает свою секунду в момент старта, и без разноса все запросы секунды уходили
бы в одну миллисекунду. Модель замкнутая: если ответ дольше секунды, темп падает, и сценарий проваливает проверку
«темп выдержан». Касса, как и настоящая, сразу вычитает проданное из партий своего снимка. Перед сценарием `hot`
горячая партия `L01` пополняется до запаса на весь сценарий (`db.mjs`, `topUpHotBatch`), поэтому повторный прогон на той
же базе её не опустошает. Сессия кассира без запросов живёт 15 минут: пауза больше 10 минут между сценариями даст 401.

## Отчёт

`tools/load/results/<время>/summary.md` и `summary.json` (каталог в `.gitignore`; сводка — в описании PR):

- по каждому потоку: ответов, ответов 2xx в секунду (и цель), p50, p90, p97.5, p99, бюджет, итог;
- коды ответов по потокам, 429 — отдельно. Задержки и темп считаются только по ответам 2xx: ошибки не прячутся в
  процентилях и не засчитываются в пропускную способность. Любой ответ не 2xx (5xx, 401, 409, 429) — FAIL сценария;
- инварианты после сценария: новые чеки = ответы 201 с новыми номерами, номера уникальны, остаток горячей партии,
  одно движение на строку чека;
- железо (CPU, ОЗУ, версии Node и PostgreSQL), размер базы, параметры прогона, итог PASS или FAIL.

Промах бюджета или 5xx — находка: `EXPLAIN (ANALYZE, BUFFERS)` медленного запроса на `pharmacy_load`, ожидания в
`pg_stat_activity`, пул и блокировки. Исправления — отдельным планом. Медленные запросы прогона показывает журнал
PostgreSQL: перед прогоном `alter database pharmacy_load set log_min_duration_statement = 200` (суперпользователем;
настройка уходит вместе с базой), после — `docker logs --since <начало> pharmacy-dev-postgres-1`. `EXPLAIN` — от роли
`pharmacy_app` с `app.tenant_id`, как его выполняет API, и с моментом-значением, а не `now()`: API передаёт его
параметром, и партиции отсекаются ещё при планировании.

## Секреты

Значения `.env` не печатаются. Пароль владельца, пароли заведующих и cookie устройств лежат в `tools/load/.state/`
(в `.gitignore`, только для этой базы, удаляются `drop`). Cookie и PIN в отчёты не попадают; парк уходит генератору
нагрузки через stdin контейнера, не файлом. Пока API прогона работает, `docker inspect pharmacy-load-api` показывает
переменные dev `.env` — как у любого контейнера с `-e`; это только dev.

Если `.state/fleet.json` потерян, а база осталась, `run.mjs` восстанавливает парк сам: владелец получает новый
одноразовый код прямо в `pharmacy_load`, заведующие — новые пароли, а терминалы с потерянными cookie отзываются и
привязываются заново (их открытые смены владелец сначала закрывает принудительно).

Ctrl+C останавливает прогон и удаляет его контейнеры (`pharmacy-load-api`, `pharmacy-load-driver`); контейнер,
оставшийся после аварийного выхода, следующий запуск удаляет сам.

## Сжатие диска Docker на Windows

Виртуальный диск Docker Desktop (`%LOCALAPPDATA%\Docker\wsl\disk\docker_data.vhdx`) после `drop` сам не уменьшается.
Сжать его:

1. `docker system df` — убедиться, что база удалена; закрыть Docker Desktop.
2. `wsl --shutdown`.
3. В PowerShell от администратора:
   - Windows Pro с Hyper-V: `Optimize-VHD -Path "$env:LOCALAPPDATA\Docker\wsl\disk\docker_data.vhdx" -Mode Full`;
   - иначе `diskpart`: `select vdisk file="<путь к vhdx>"`, `attach vdisk readonly`, `compact vdisk`, `detach vdisk`, `exit`.
4. Запустить Docker Desktop и `npm run dev:deps`.

Хвосты трёх прогонов ×2 различаются в разы из-за стенда, медианы — нет. Главный результат A/B — изменения снимка:
p50 106 → 37 мс при 18 запросах в секунду, то есть они держат в среднем не ≈ 1,9, а ≈ 0,7 соединения из пула 10. С
прежним кодом любое замедление базы накапливалось в пуле: 2026-11-05, сразу после полного прогона, при ×2 на изменения
пришлись 595 из 614 медленных запросов, а хвост чека дошёл до 1,1 с.

Находки:

1. **Исправлена 2026-11-09: изменения снимка считали остаток всей точки.** `PosStock.batchesWithStock` для списка до
   200 товаров суммирует движения только их партий — подзапрос на партию по индексу партии, как
   `StockRepository.batchStock`. Список длиннее и полный снимок идут прежним проходом по точке: на списке около 300
   товаров подзапросы по партиям ещё быстрее прохода по точке, а примерно с 1000 уже медленнее. `EXPLAIN ANALYZE` на
   `L01`, строки совпадают с прежним запросом:

   | Изменения | Прежний запрос | Новый |
   |---|---|---|
   | товары последних 40 продаж точки (30 шт.) | 100 мс | 28 мс |
   | 3 самых продаваемых | 109 мс | 15 мс |
   | 50 случайных | 103 мс | 9 мс |
   | 200 самых продаваемых | 87 мс | 64 мс |

   Остаётся цена истории ходовых товаров: три самых продаваемых — около 21 % движений точки, и их сумма растёт с
   историей. Полностью это снимает только находка 2.
2. **Полный снимок точки суммирует всю историю.** Без изменений; под нагрузкой до 5,1 с на запрос. Хранить остатки или
   итоги закрытых месяцев — отступление от правила «остатки выводятся из движений», только через ADR.
3. **Планирование запросов к движениям.** У `stock_movements` 38 секций, 27 из них пустые, до 2028-12. В покое
   планирование — 2–5 мс; под нагрузкой 2026-11-05 было 10–33 мс. Не перемерялось.
4. **Под перегрузкой чтение уступает чекам.** Без изменений: пул 10 обслуживает запросы по очереди, ответов 5xx нет. При
   64 чеках в секунду за двухминутное окно изменений точка продаёт больше 200 товаров, и изменения идут проходом по
   точке.
5. **Горячая партия чувствительна к задержке коммита.** Чеки одной партии выстраиваются в очередь за её блокировкой
   (`FOR UPDATE` до коммита). При 20 чеках в секунду на чек остаётся 50 мс, а медиана — 48 мс: запаса нет, и любое
   замедление `fsync` растит очередь. 2026-11-05 хвост был 48 мс, 2026-11-09 — 730 мс. На VPS это зависит от диска:
   до пилота стоит замерить там задержку коммита (`pg_test_fsync`).
6. **Стенд на Windows.** Замер с Windows не годится: запрос к базе через порт Docker Desktop стоит 3 мс вместо 0,2 мс,
   петля ПК держит клиента на ≈ 360 запросах в секунду, а `fetch` добавляет ≈ 10 мс. Поэтому API и генератор — в сети
   Docker. Но и там диск ВМ — диск Windows: `fsync` контрольной точки доходил до 10 с, и хвосты двух одинаковых прогонов
   различаются в разы. Сравнивать — только A/B на одном стенде.
