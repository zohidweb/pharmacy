## 1. Профиль проекта

| Параметр | Значение |
|---|---|
| Класс проекта | Full — продуктовая система |
| Тип проекта | Веб-приложение: клиентский продукт (касса, склад, кабинет владельца) и административный продукт (админка оператора платформы). Офлайн-дистрибутив точки — та же система, разворачиваемая локально (Docker) |
| Репозитории кода | Единый репозиторий `pharmacy` (ADR-0010, 2026-09-29): Nx-монорепо в корне — `apps/api` (NestJS, единый бэкенд обоих продуктов), `apps/web` (клиентский продукт), `apps/admin` (админка оператора), `libs/*` (общие типы, DTO, доменная логика, UI-кит) — и архитектурные артефакты (`docs/architecture/`: stack.md, C4, ADR, APPROVAL; `tech-radar/`). Отступление от практики «один деплой-юнит = один репозиторий» обосновывается в ADR-0002 и ADR-0010. ~~Отдельный кодовый репозиторий `pharmacy-app`~~ — заменено ADR-0010 |
| Назначение (1–2 предложения) | Мультитенантная SaaS-платформа автоматизации аптечных сетей Таджикистана: складской учёт по партиям (FEFO, сроки годности), касса с офлайн-режимом, закупки и долги поставщикам, цены/скидки, возвраты, отчёты, выгрузка в 1С — плюс административный контур оператора (тенанты, биллинг, лицензионные ключи офлайн-точек, услуги) |
| Пользователи и пиковая нагрузка | Из ТЗ: на старте 3 тенанта, ~30 точек, до 50 одновременно работающих кассиров; операции кассы ≤ 1 сек; архитектура обязана выдержать рост ×5 без переработки |
| Критичность | Tier 2 — при простое облака в течение дня облачные аптеки не могут штатно продавать (смягчается буфером перебоев связи), владельцы не видят отчёты; офлайн-точки продолжают работать. Подтверждено командой |
| Категория данных | Персональные данные: ФИО и учётные записи сотрудников тенантов, контакты поставщиков, поля рецептов ПКУ (состав уточняется заказчиком). Розничный покупатель анонимен. Банковской тайны нет |
| Объём данных и срок хранения | Оценка (подтверждена командой): ~3–9 тыс. чеков/день на платформу; за 3 года ~5–10 млн чеков и ~30–50 млн строк движений по партиям; суммарно десятки ГБ, до ~100 ГБ с учётом роста ×5. Аудит-журналы неизменяемы, хранение ≥ 3 лет; бэкапы облачной БД ежедневно, хранение 30 дней |
| Доступность (SLA) | 99,5% в рабочие часы тенантов; плановые работы ночью с уведомлением (из ТЗ) |
| RTO / RPO | RTO 4 часа / RPO 24 часа (из ТЗ) |
| Ограничения | Срок — запуск до конца 2026 года. Компетенции команды: NestJS, Next.js, Angular (нет .NET/PHP). Валюта TJS, автозагрузка курсов НБТ; локализация RU/TJ; фискализация РТ (в MVP — адаптер-заглушка); место хостинга — открытый юридический вопрос; офлайн-точки требуют Docker (категория радара «На утверждении») |

## 2. Чек-лист безопасности

| Вопрос | Ответ |
|---|---|
| Какие категории данных обрабатываются? | Персональные данные (сотрудники тенантов, контакты поставщиков, поля рецептов ПКУ); финансовые данные тенантов (продажи, долги, счета) — не банковская тайна. Покупатель анонимен |
| Где хранятся секреты (пароли, ключи, строки подключения)? | НЕ в коде и не в git; на MVP — переменные окружения среды деплоя. Категория «Управление секретами» в радаре «На утверждении» — выбор инструмента в открытых вопросах (№ 8) |
| Как аутентифицируются пользователи? | Самописная аутентификация по ТЗ: логин + пароль (хеш), PIN ≥ 4 цифр для переключения кассира на привязанном к точке терминале, таймаут сессии (настройка сети). Радар: «Утверждено, не рекомендуется» → обязательное согласование с ИБ (флаг ниже) |
| Как аутентифицируются сервисы между собой? | Внутри облака — модульный монолит, внешних межсервисных вызовов нет. Синхронизация офлайн-точка ↔ облако — HTTPS + уникальный лицензионный ключ точки |
| Что уходит за контур банка (данные, вызовы)? | Продукт — внешняя SaaS-платформа для аптек (не внутрибанковская система); данные тенантов живут в облаке платформы, место хостинга — открытый вопрос № 1. Входящие внешние вызовы: курсы НБТ. Банковские данные банка не задействованы |
| Что шифруется (при передаче / при хранении)? | При передаче — HTTPS на всех соединениях (из ТЗ). При хранении — пароли/PIN хешируются; шифрование БД и бэкапов — уточнить требования с ИБ при согласовании |
| Хранение данных на устройстве (для мобильных) | Не применимо (веб). Для офлайн-точки: локальная БД на ПК точки; ответственность за сохранность несёт тенант (фиксируется в договоре, из ТЗ) |
| Биометрия и fallback-вход (для мобильных) | Не применимо |
| Certificate pinning (для мобильных) | Не применимо |
| Root/jailbreak-детект (для мобильных) | Не применимо |
| Удалённый сброс при утере устройства, MDM (для мобильных) | Не применимо. Аналог для терминалов: отвязка терминала заведующим/владельцем, мгновенная блокировка сотрудника (из ТЗ) |

**Флаг апрува ИБ:** ДА — обрабатываются персональные данные, плюс самописная аутентификация;
в APPROVAL.md обязателен апрув ИБ.

## 3. Выбор стека

Только технологии из tech-radar/RADAR.md со статусом «Утверждено» (при наличии — «Приоритет»).
⚠️ Backend и Frontend выбраны командой ВНЕ радара — оформлены как запросы исключений
(ADR-0003, ADR-0004 в статусе proposed); использование до апрува Архкомитета запрещено.

| Слой | Технология | Статус в радаре | Обоснование | Альтернатива из радара и почему нет |
|---|---|---|---|---|
| Backend | NestJS (Node.js, TypeScript) — **предлагается, ожидает исключения (ADR-0003)** | Вне радара | Единственный бэкенд-стек, которым владеет команда; срок до конца 2026; единый TypeScript и общие типы с фронтендом в Nx-монорепо | C# (.NET LTS), PHP — «Утверждено», отклонены: команда ими не владеет, обучение с нуля срывает срок |
| Frontend | Next.js (React, TypeScript) — **предлагается, ожидает исключения (ADR-0004)** | Вне радара | Решение команды: единая TS/React-экосистема с бэкендом, компетенции команды. Риск отказа комитета зафиксирован — есть утверждённые альтернативы | Angular («Приоритет», команда владеет), React — отклонены решением команды в пользу единой Next.js-экосистемы |
| БД | PostgreSQL | Приоритет | Реляционная модель из ТЗ (партии, движения, документы), мультитенантная изоляция (RLS), та же БД в Docker-дистрибутиве офлайн-точки | Другая СУБД — не рассматривалась, PostgreSQL подходит полностью |
| Кэш | Redis | Утверждено | Сессии и PIN-сессии терминалов, кэш каталога/цен для скорости кассы (≤ 1 сек) | — (единственный в категории) |
| API-стиль | REST | Утверждено | Браузерные клиенты и синхронизация офлайн-точек; простота отладки | gRPC — не нужен: нет внешних высоконагруженных потребителей |
| Аутентификация | Самописная (логин+пароль, PIN, привязка терминала) | Утверждено (не рекомендуется) | Требования ТЗ не ложатся на SSO: PIN-переключение кассиров на терминале, мультитенантные кастомные роли «модуль × действие × охват точек», офлайн-вход на автономной точке | Keycloak («Приоритет») — корпоративный SSO банка не применим к внешним тенантам-аптекам; офлайн-точка без интернета не может ходить в централизованный IdP. Согласование с ИБ обязательно |
| Язык фронтенда | TypeScript | Утверждено | Обязателен для нового фронтенд-кода | — |
| Инструмент сборки / организация кода | Nx (монорепо) | Категории в радаре нет (тулинг) | Общие типы и библиотеки между `api`, `web`, `admin`; кэширование сборок | Фиксируется в ADR-0002; подтверждается Архкомитетом на ревью |
| Контейнеризация (офлайн-дистрибутив, волна 3) | Docker — **ожидает утверждения категории (ADR-0005)** | Категория «На утверждении» | Требование ТЗ: офлайн-точка = Docker-образ на ПК точки (Windows 10/11 + WSL2, Linux) | Альтернатив в радаре нет — категория целиком не утверждена |

## 4. Интеграции

Правила: только через утверждённый API-слой; прямой доступ к БД АБС запрещён;
для финансовых операций — идемпотентность и correlation ID.

| Система | Протокол | Формат | Владелец | SLA |
|---|---|---|---|---|
| 1С:Бухгалтерия 8 для Таджикистана | Файловый обмен, выгрузка вручную за период | CommerceML/XML | Бухгалтерия заказчика | Нет (офлайн-обмен); тестовая база заказчика нужна к приёмке W2-05 |
| Фискализация (онлайн-ККМ / виртуальная касса) | Адаптер отправки чека; в MVP — заглушка (логирует и возвращает успех) | По требованиям вендора ККМ | Вендор не выбран (открытый вопрос № 9) | Замена заглушки на реального вендора не должна менять кассу |
| Курсы валют НБТ | Исходящий запрос курса на дату операции (REST/HTML — уточнить при реализации) | JSON/HTML | Национальный банк Таджикистана | Ежедневная загрузка; ручная корректировка при недоступности |
| Банковский эквайринг | БЕЗ интеграции в MVP: отдельный банковский терминал, кассир указывает способ оплаты; сверка вручную по итогам смены | — | Банк-эквайер заказчика | — |
| Синхронизация офлайн-точек | HTTPS, очередь операций, идемпотентность (из ТЗ: повторная отправка без дублей) | JSON | Собственный компонент платформы | Расписание по умолчанию раз в сутки + ручной запуск |
