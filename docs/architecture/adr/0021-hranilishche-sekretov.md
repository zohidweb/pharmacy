# ADR-0021: Хранилище секретов — файлы секретов на хосте среды и compose secrets

- **Статус:** accepted (2026-10-27, архитектор проекта — APPROVAL.md)
- **Дата:** 2026-10-27
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

Вопрос № 8 stack.md «хранилище секретов — до прод-деплоя» открыт. Решение 7.1 ревью безопасности 2026-10-22 включает
его в условия до первых реальных данных пилота. Сейчас все секреты среды лежат в одном env-файле на хосте
(`docker/env/<env>.env`, права 0600):
- пароли суперпользователя и ролей БД (`pharmacy_owner`, `pharmacy_app`, `pharmacy_platform`, `pharmacy_backup`),
  пароль Redis;
- ключи подписи сессий и pepper паролей и PIN (ADR-0008: потеря pepper делает недействительными все пароли и PIN);
- ключ S3 бакета копий (ADR-0020).

Compose подставляет эти значения в окружение контейнеров и в командные строки, поэтому они видны (находка S6 ревью):
- в `docker inspect` и `docker compose config`. Эти команды оператор и AI-ассистенты разработки запускают при
  выкладке и диагностике, а их вывод попадает в чаты и в контекст внешней LLM. Правила проекта запрещают передавать
  секреты в запросы к AI;
- в списке процессов хоста: `redis-server --requirepass …`, `psql -v …` в скрипте ролей;
- в окружении каждого процесса контейнера.

Кроме того, `docker compose build` подставляет весь env-файл, поэтому открытый env-файл prod лежит и на машине
архитектора, где собираются образы.

Ограничения:
- один VPS Contabo (ADR-0020), Docker Compose без оркестратора (ADR-0005), без CD;
- команда из одного-двух человек;
- закрытый список интеграций (ADR-0011), новая технология — только через ADR.

Копия env-файла уже шифруется `age` и лежит в бакете под Object Lock (`env-push`, спецификация
`2026-10-23-offsite-backups-design.md`, O13). Захват хоста (root или группа `docker`) раскрывает все секреты и все
данные при любом хранилище на этом же хосте. От этого не защищает ни один из вариантов ниже.

## Рассмотренные варианты

1. **Env-файл на хосте как сейчас, плюс записанные правила доступа, ротации и копии.**
   - Плюсы: без изменений кода.
   - Минусы: S6 остаётся — секреты по-прежнему в `docker inspect`, в `docker compose config` и в аргументах процессов.
     Открытый env-файл prod остаётся на машине сборки. По сути это сегодняшнее состояние, которое ревью назвало «до
     хранилища секретов».
2. **Файлы секретов на хосте среды, в контейнеры — через compose secrets.** Каждый секрет — отдельный файл в каталоге
   среды на хосте. Compose монтирует в контейнер только секреты этого сервиса в `/run/secrets/<имя>`, а приложения
   читают `<ПЕРЕМЕННАЯ>_FILE`. Env-файл остаётся для несекретной конфигурации. Каталог копируется в бакет,
   зашифрованный `age`.
   - Плюсы: штатный механизм Compose (ADR-0005), без новых инструментов и сервисов. Секретов нет в окружении
     контейнеров, в `inspect`, в `compose config` и в аргументах процессов. Права каждого сервиса явно записаны в
     compose. Для сборки образов секреты среды не нужны.
   - Минусы: см. «Последствия».
3. **SOPS + `age`: зашифрованный файл секретов в git, расшифровка при выкладке.**
   - Плюсы: история изменений секретов в git; ключи `age` у хранителей уже есть.
   - Минусы:
     - новый инструмент — бинарник вне npm и официальных образов;
     - шифротекст всех секретов навсегда остаётся в истории репозитория: утечка ключа хранителя раскрывает и прошлые
       значения;
     - после расшифровки на хосте — то же окружение контейнеров, то есть S6 без варианта 2 не закрывается.
4. **HashiCorp Vault или OpenBao на том же VPS.**
   - Плюсы: аудит чтения секретов, динамические пароли БД, аренда и отзыв.
   - Минусы:
     - ещё один сервис с состоянием: свои копии, обновления и поверхность атаки;
     - распечатывание после каждой перезагрузки или автораспечатывание через внешний KMS;
     - на одном хосте от захвата root не защищает;
     - для одной-двух аптек и одного администратора избыточно.
5. **Внешний менеджер секретов: Doppler, Infisical Cloud, Bitwarden Secrets Manager или облачный KMS.**
   - Плюсы: секреты вне хоста, аудит, ротация из интерфейса.
   - Минусы:
     - новая интеграция вне закрытого списка (ADR-0011) и ещё один иностранный обработчик — тот же вопрос юриста, что
       у хостинга;
     - старт стека зависит от внешнего сервиса;
     - токен доступа к этому сервису всё равно остаётся секретом на хосте.

## Решение

Выбран **вариант 2**. Детали — в спецификации, которая следует за этим ADR.

1. **Где живут секреты.** В test и prod — каталог секретов среды рядом с её env-файлом, вне git, с правами 0700.
   Каждый секрет — отдельный файл. Открытые значения секретов prod есть только на хосте prod и в зашифрованной копии.
   Сборка образов секретов не требует: на машине архитектора остаётся env-файл без секретов.
2. **Как секреты попадают в контейнеры.** Только через `secrets:` Compose, и каждому сервису — только его секреты. Не
   через `environment:` и не через аргументы команд. API, его скрипты, PostgreSQL, Redis и сервис копий читают секрет
   из файла: `<ПЕРЕМЕННАЯ>_FILE`, `POSTGRES_PASSWORD_FILE` официального образа, у Redis — файл конфигурации или ACL
   вместо `--requirepass`.
3. **Env-файл** хранит только несекретную конфигурацию: адреса, режимы, порты, имя бакета, открытые ключи `age`,
   идентификатор ключа S3. Проверки `stack.mjs` (S2: заглушки, слабые пароли) переносятся на файлы секретов.
4. **Создание.** Секреты создаются на хосте среды случайными значениями, как сейчас создаёт `stack init`. Для test
   хост — машина разработчика, для prod — VPS, где секреты генерирует скрипт из образа `pharmacy/postgres`: Node на
   VPS нет.
5. **Копия.** Env-файл и каталог секретов уходят в бакет копий одним архивом, зашифрованным `age` открытыми ключами
   хранителей (развитие `env-push`, O13; Object Lock). Копию делают на хосте среды после каждого изменения. Без неё
   потеря диска означает потерю pepper (ADR-0008).
6. **Доступ.**
   - root и группа `docker` на VPS — только у названных людей (архитектор и второй хранитель ключа), вход только по
     SSH-ключам; список людей — в руководстве по выкладке.
   - Секреты не печатаются и не попадают в git, чаты, тикеты и запросы к AI-ассистентам.
7. **Ротация** — по процедурам руководства: пароли ролей, ключи сессий, pepper, Redis, ключ S3. После взлома меняется
   всё сразу (раздел «После взлома сервера»). Для ключей сессий и pepper ротация без массового сброса уже
   поддерживается: кольцо ключей и версии pepper, ADR-0008.
8. **dev** не меняется: корневой `.env` с dev-значениями. Код принимает и `<ПЕРЕМЕННАЯ>`, и `<ПЕРЕМЕННАЯ>_FILE`.
9. **Пересмотр** — при втором сервере, появлении CD или росте команды: внешнее хранилище (Vault, OpenBao или облачный
   KMS) — отдельным ADR.

После принятия:
- вопрос № 8 в stack.md закрывается;
- в ADR-0008 строка «Pepper — из переменных окружения, пока ADR не выберет хранилище» заменяется ссылкой на этот ADR;
- CLAUDE.md («Local development secrets», «Environments», «Бэкапы») и `docs/guides/deploy-vps.md` описывают
  каталог секретов.

## Последствия

- Положительные:
  - закрыты находка S6 и условие решения 7.1 «хранилище секретов»;
  - секретов нет в `docker inspect`, в `docker compose config`, в окружении контейнеров и в списке процессов, поэтому
    эти команды можно запускать при диагностике, в том числе AI-ассистентам;
  - права сервисов на секреты записаны в compose явно;
  - на машине сборки нет открытых секретов prod;
  - конфигурация среды восстанавливается из бакета одной процедурой;
  - без новых технологий и внешних сервисов.
- **Отрицательные (обязательно):**
  - Объём работы и риск регрессий. Затрагиваются:
    - чтение `_FILE` в API и скриптах образа `api`;
    - init-скрипты ролей и `04-backup-role.sql`;
    - Redis и сервис копий;
    - `stack.mjs` (`init`, проверки S2, `env-push`), compose-файлы, CLAUDE.md, руководства.

    Существующие env-файлы test придётся перенести. Значения сохраняются, поэтому пароли ролей в базе менять не нужно.
  - От захвата хоста решение не защищает: файлы на диске не зашифрованы, root и группа `docker` читают их, как и
    env-файл сейчас. В памяти процессов секреты остаются.
  - Нет аудита чтения секретов, динамических паролей и автоматической ротации, которые дал бы Vault. Ротация остаётся
    ручной, по процедурам.
  - Конфигурация среды — в двух местах (env-файл и каталог секретов), поэтому шагов выкладки больше. Забытый файл
    останавливает старт сервиса, а не проходит молча.
  - dev и test/prod читают секреты разными путями (переменная или файл): путь `_FILE` проверяется только на стенде
    test.
  - Compose без Swarm монтирует секреты как файлы хоста: права и владельцев задаёт хост, а их ошибки видны только при
    старте контейнера.
  - rclone получает ключ S3 из своей переменной окружения. Внутри процесса копирования ключ окажется в окружении,
    хотя в `inspect` его не будет.
  - Со вторым сервером или CD решение придётся пересматривать.
