# ADR-0003: Исключение из техрадара — RabbitMQ для отправки критичных уведомлений

- **Статус:** accepted
- **Дата:** 2026-09-01
- **Авторы:** команда «Сервис уведомлений клиентов» (пример)

## Контекст

Часть уведомлений (например, об отказе в операции) критична: потеря такого сообщения — риск
для доверия клиента. Сейчас очередь задач на отправку реализована на Redis (см. ADR-0001),
но Redis не даёт полноценного dead-letter и гарантированного подтверждения обработки. Категория
«Брокеры сообщений» в tech-radar/RADAR.md имеет статус «На утверждении» — использовать её
до решения архитектора нельзя без прохождения процедуры исключения (tech-radar/EXCEPTIONS.md).

## Рассмотренные варианты

1. **Redis (уже в стеке)** — минимальные изменения, но нет dead-letter queue и надёжного
   at-least-once с подтверждением обработки для критичных сообщений.
2. **RabbitMQ** — зрелый брокер с DLQ и подтверждениями доставки, широко используется в
   индустрии для похожих задач, но требует исключения из радара (категория «На утверждении»).
3. **Kafka** — избыточен для объёма 20 сообщений/сек и разового сценария; тоже не утверждён
   радаром, выше порог входа для команды такого размера.

## Решение

Выбран RabbitMQ — но только как разовое, одноразовое исключение для этого проекта, до
момента утверждения категории «Брокеры сообщений» в радаре. Используется исключительно для
очереди критичных уведомлений (отказ операции); обычные уведомления по-прежнему идут через
Redis.

## Последствия

- Положительные: надёжная доставка критичных уведомлений с DLQ и явным подтверждением
  обработки, снижение риска «потерянного» уведомления об отказе операции.
- **Отрицательные (обязательно):** в инфраструктуру добавляется ещё один компонент вне
  утверждённого стека — дополнительные расходы на эксплуатацию, мониторинг и отдельные
  компетенции по RabbitMQ; привязка к конкретному брокеру, если категория так и не будет
  утверждена радаром.

## Только для исключений из техрадара

- Альтернативы из радара и почему не подходят: Redis (уже в стеке) — недостаточно надёжен
  для критичных уведомлений (нет DLQ, нет гарантированного подтверждения обработки); других
  утверждённых брокеров сообщений в радаре нет — вся категория «На утверждении».
- **Апрув Архитектурного комитета:** А. Архитекторов (пример), 2026-09-01
- **Апрув ИБ** (для security-категорий): И. Безопасников (пример), 2026-09-01 — получен
  дополнительно, так как сервис обрабатывает персональные данные (см. stack.md, «Флаг апрува
  ИБ: ДА»), и через очередь проходит текст уведомлений с данными об операциях клиента.
- Исход по EXCEPTIONS.md: approve (одноразовое)
