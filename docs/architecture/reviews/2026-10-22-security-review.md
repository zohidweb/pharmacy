- **Дата:** 2026-10-22
- **Подготовил:** архитектор проекта Zohid Saidov (ревью выполнено с помощью AI)
- **Объект:** `main` 80c4973 — `apps/api`, `apps/web`, `apps/admin`, `libs/*`, `docker/`, скрипты `apps/api/scripts`
- **Метод:**
  - пять параллельных аудитов только по чтению кода:
    - вход, сессии и терминал;
    - права и изоляция сетей;
    - ввод, файлы и утечки данных;
    - синхронизация офлайн-точек;
    - фронтенды и развёртывание;
  - каждая находка — отдельная проверка на ложное срабатывание с оценкой уверенности 1–10;
  - в отчёт об уязвимостях идёт уверенность ≥ 8, остальное — ниже порога, с решением.
- **Итог:**
  - уязвимостей с уверенностью ≥ 8 нет;
  - две находки получили 7/10, обе подтвердились на живом API и исправлены в PR `fix/security-review-shift-license`.

## Исправлено

### 1. Открытие смены под терминалом задним числом (7/10, Medium)

- **Где:** `apps/api/src/app/pos/shifts.service.ts`, `pos-context.ts`.
- **Суть.** Без сессии буфер кассы досылается под device-cookie, а автор проверяется правилом P10: держал ли он
  терминал в момент операции. У чека, внесения, изъятия и закрытия этот момент не раньше открытия смены (У7). У
  открытия смены нижней границы не было — только «не старше 30 дней».
- **Что это давало.** Любой у браузера привязанной кассы мог без PIN открыть смену до 30 дней назад от имени кассира,
  который тогда держал терминал. Затем в этой смене — изъятия, чеки, закрытие от его имени. Так обходилось обещание
  ADR-0008 (поправка 2026-10-21, п. 2): подставить можно только того, кто держал терминал в текущей смене.
- **Исправление.** Момент открытия — и для P10, и в `opened_at` — не раньше закрытия последней смены терминала
  (спецификация `2026-10-21-pos-offline-limits`, У17). Более ранний момент сдвигается к закрытию, а не отклоняется.
  По замечаниям ревью ветки:
  - открытие перепроверяет границу в своей транзакции: при параллельном закрытии — 409 `shift_open`;
  - пометка M10 считается по моменту после сдвига;
  - граница не бывает позже приёма.
  - Остаток риска — терминал без закрытых смен (У17).
- **Проверка.** Живой API на временной базе:
  - код `main` открывал такую смену (201);
  - исправленный код отвечает 422 `author_session_missing`;
  - законные открытия под терминалом и по PIN проходят;
  - прежние проверки P10 кассы PR 3 зелёные.

### 2. Лицензионный ключ снова принимал операции после льготного срока (7/10, Medium, пока латентно)

- **Где:** `apps/api/src/app/sync/license-status.ts`, резолвер `resolve_license_key`.
- **Суть.** Льготный срок (30 дней) считался от первого совпавшего по приоритету события, а у блокировки сети — «от
  сейчас». Отсюда два случая:
  - мёртвый истёкший ключ получал новые 30 дней, когда его отзывали при продлении;
  - пока сеть заблокирована, любой не жёстко отозванный ключ её точек принимал операции.
- **Почему латентно.** Офлайн-точек в пилоте нет, пакеты облачной точки получают 409 `store_online`. Риск появится с
  первой офлайн-точкой: у кого осталась копия старого ключа, тот мог бы прислать чеки, списания и приходы от её имени.
- **Исправление** (спецификация `2026-10-16-offline-sync`, §13):
  - срок считается от самого раннего наступившего события: срок ключа, отзыв, закрытие точки, блокировка сети;
  - блокировка считается от `tenants.blocked_at` (миграция `license-key-block-time`);
  - блокировка без времени не принимает ничего.
- **Проверка.**
  - функция на 13 сценариях: код `main` проваливает 6, исправленный проходит все;
  - живой API: старый ключ после продления и при блокировке получает 403, действующий ключ в пределах срока проходит.

## Отсеяно

- **Подделка журнала действий ключом точки** (`audit.service.ts`) — 2/10.
  - ADR-0014 прямо доверяет фактам точки, в том числе её журналу «как есть»; владелец ПК точки и так может записать
    в свою базу что угодно.
  - Решения журнал не принимает: `PinSignIns` читает только `source = 'cloud'`.
  - Возможное усиление (не уязвимость): список действий точки для `audit.recorded`, отметка «с точки» в журнале
    владельца.
- **Закрытая точка оживляет ключ** — ложное срабатывание: закрыть можно только облачную точку, её пакеты получают 409.

## Проверено, уязвимостей нет

- **Сессии:**
  - JWT: только HS256, проверяются `iss` и `aud`, без серверной сессии токен недействителен.
  - Сессия выдаётся заново при каждом входе; при смене пароля, блокировке и смене роли прочие сессии уничтожаются.
  - PIN-сессия привязана к device-cookie.
  - Cookie: `__Host-`, `Secure`, `HttpOnly`, `SameSite=Strict`.
  - CSRF: `Sec-Fetch-Site` или точный `Origin` плюс JSON.
  - Коды активации — 128 бит, одноразовые, в базе только SHA-256.
  - Тестовые cookie вне `APP_ENV=test` и dev-ключи в prod запрещены.
- **Права и изоляция:**
  - У каждого из 67 контроллеров есть маркер прав, маршрут без маркера запрещён.
  - Эскалации нет: роль ограничена правами редактора, роль владельца выдаёт только владелец, свою роль менять нельзя.
  - Охват точек проверяется по точке самой записи.
  - RLS включён с FORCE на всех таблицах сетей. У функций SECURITY DEFINER задан `search_path = ''`, и `EXECUTE`
    отозван у PUBLIC.
- **Ввод и данные:**
  - `sql.raw` и `sql.lit` получают только константы, сортировка — из белого списка.
  - `ValidationPipe` работает с `whitelist` и `forbidNonWhitelisted`.
  - Цены и возвраты пересчитываются на сервере.
  - В ошибках нет стека, в логах нет секретов и ПДн.
- **Синхронизация:**
  - Ключ сверяется в постоянное время.
  - Сеть и точка берутся из ключа; каждый применитель проверяет `sameStore`.
- **Фронтенды и развёртывание:**
  - Нет `dangerouslySetInnerHTML` и вывода HTML-строк; печать идёт через React-портал.
  - Service Worker не кэширует `/api/*`.
  - Рецепты в буфере кассы зашифрованы AES-GCM.
  - Моки выключены по умолчанию.
  - Порты открыты только на `127.0.0.1`, у сервисов нет паролей по умолчанию, `.dockerignore` исключает `.env`.

## Мелкое усиление (не уязвимости, не исправлялось)

- Пароль Redis передаётся в командной строке (`--requirepass`) и виден в `docker inspect`.
- Повтор с тем же ключом идемпотентности (отложенный чек, загрузка, операции кассы и возвратов) возвращает сохранённый
  ответ без повторной проверки охвата точки. Для этого нужен точный UUID ключа.
- Черновик чека с зашифрованным рецептом переживает выход на привязанной кассе — так задумано.
