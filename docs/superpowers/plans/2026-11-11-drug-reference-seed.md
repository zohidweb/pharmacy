# Общий справочник препаратов: загрузка скриптом и подсказка в карточке товара

**Цель.** Названия препаратов (с характеристиками, если они есть) доступны всем сетям: оператор наполняет общий
справочник скриптом, а при создании товара web подсказывает из справочника и заполняет карточку.

**Основание.** Справочник уже принят архитектурой: ADR-0013 (решение 2026-09-30, п. 2 — `drug_reference`, класс
`shared`, ведёт оператор, читают все сети), модель данных `docs/architecture/data-model/02-catalog-prices.md`,
решение D4 (справочник — образец для заполнения; карточка сети хранит свои атрибуты). Новый ADR не нужен: данные
попадают в справочник только от оператора, из каталогов сетей ничего не переносится.

**Стек.** Без новых зависимостей: SQL-миграция node-pg-migrate, Kysely, NestJS, Next.js (static export), скрипт на
`pg` + `uuid`, как `create-operator.mjs`.

## Решения автора

| № | Вопрос | Решение |
|---|---|---|
| R1 | Как наполняется | Скрипт `apps/api/scripts/seed-drug-reference.mjs` ролью `pharmacy_platform` (`PLATFORM_DATABASE_URL`), CSV из `--file <путь>` или из stdin (`docker compose run -T … < файл.csv`: контейнер только для чтения, файл не монтируется). Файл данных в git не попадает. Окно в админке — следующим шагом |
| R2 | Формат файла | CSV UTF-8 (BOM допустим), разделитель `;` или `,` — которого больше в строке заголовков, кавычки по RFC 4180. Заголовки (без учёта регистра): `barcode`, `name_ru` — обязательные; `name_tj`, `inn`, `form`, `dosage`, `manufacturer`, `country` (ISO 3166-1 alpha-2), `prescription` (`none` / `rx` / `controlled`, пусто — `none`). До 10 МБ и 50 000 строк данных |
| R3 | Какие штрихкоды берутся | Только GTIN: 8, 12, 13 или 14 цифр с верной контрольной цифрой. Внутренние коды магазинов не берутся: 13 цифр с префиксом `2`, `02`, `04`; 12 цифр с префиксом `2`, `4`; 8 цифр с префиксом `0`, `2`; у 14 цифр — по 13-значной части — у каждой аптеки они свои и у другой сети означали бы чужой товар. Код хранится в кратчайшей форме: GTIN-14 с индикатором `0` — как GTIN-13, GTIN-8, дополненный нулями до 13, — как 8 цифр; поиск API приводит запрос к той же форме (поправка после ревью). Строка без штрихкода не загружается: справочник ищется сканом |
| R4 | Повторы и конфликты в файле | Штрихкод с разными наименованиями (сравнение без регистра, пробелов по краям и их повторов, `ё`=`е`) — конфликт: код не загружается, строки называются в отчёте. Строки с одинаковым наименованием — одна запись справочника с несколькими штрихкодами; характеристики — из первой строки, где они заданы; отпуск — самый строгий из строк; не больше 20 штрихкодов на запись (как у карточки товара), лишние — в отчёте (поправка после ревью) |
| R5 | Повторный запуск | Штрихкод, который уже есть в справочнике, пропускается: записи не перезаписываются (правки — задача окна оператора). Новый штрихкод для наименования, которое уже есть в справочнике, добавляется к этой записи. Запуск идёт под `pg_advisory_xact_lock`, одной транзакцией |
| R6 | Проверка без записи | `--dry-run`: тот же отчёт, транзакция откатывается. Отчёт — только счётчики и номера строк файла (до 50 на вид проблемы и «ещё N»), без значений: значения могут быть из чужого отчёта |
| R7 | Аудит | Одна запись `platform_audit_log`: `actor_kind = 'system'`, `job = 'seed-drug-reference'`, `action = 'drug-reference.seeded'`, в `details` — счётчики и SHA-256 содержимого файла. Тексты действия и задачи — в журнале операторов админки (RU/TJ) |
| R8 | Схема | `drug_reference` (`name` jsonb с обязательным `ru`, `inn` jsonb, `dosage_form`, `dosage`, `manufacturer`, `country` ISO-2, `is_prescription`, `is_controlled`, `status`, `created_at`, `updated_at`) и `drug_reference_barcodes` (`barcode` — первичный ключ, `drug_reference_id`). Класс `shared`, RLS: `pharmacy_platform` — всё по политике, `SELECT/INSERT/UPDATE`; `pharmacy_app` — только `SELECT`. Индексы trigram по `replace(lower(…), 'ё', 'е')` наименований RU/TJ и МНН, индекс по `drug_reference_id`. Колонку `products.drug_reference_id` пока не добавляем: карточка — копия (D4), а ссылка понадобится вместе с «в справочнике есть обновление»; без неё лента «облако → точка» не тащит ссылку на таблицу, которой на офлайн-точке нет |
| R9 | API для сети | `GET /api/v1/catalog/drug-references?q=&limit=&offset=`, право `catalog:create` (подсказка нужна только тому, кто заводит товар). `q` 2–100 символов: 8–14 цифр — точный поиск по штрихкоду, иначе подстрока в наименовании RU/TJ или МНН (как поиск каталога: `lower(...) like`, `escapeLike`). Только `active`. Порядок: наименование начинается с запроса, затем по наименованию. `limit` 1–20 (по умолчанию 10). Ответ `Page<DrugReferenceItem>`. Только облако (модуль `catalog`) |
| R10 | Где в web | Блок «Общий справочник» сверху формы `ProductForm` только при создании товара — в «Новом товаре» каталога и в создании товара из строки документа (`CreateProductDialog`). В карточке существующего товара блока нет. Блок скрыт, если маршрута нет в текущем режиме (`isApiRouteAvailable`) |
| R11 | Поведение подсказки | Поле «Название или штрихкод», поиск через 300 мс после ввода от 2 символов; Enter сканера — сразу. В создании из документа поле заполнено тем, с чего начали (штрихкод или название), и поиск идёт сразу. До 8 результатов: наименование, строка «форма · дозировка · производитель» (если есть) и штрихкоды, кнопка «Заполнить». Пусто — «В справочнике не найдено, заполните карточку вручную». Ошибка не мешает заполнить карточку руками |
| R12 | Что заполняет «Заполнить» | Наименования RU/TJ, МНН, дозировку, производителя — если в справочнике они заданы; форму — если такая (без регистра) есть в формах сети; страну — если есть в списке стран; отпуск — только строже: `none` справочника значит «не задано»; штрихкоды справочника добавляются к уже введённым без повторов, не больше 20. Повторное «Заполнить» сначала откатывает предыдущее (его штрихкоды и поля, которые пользователь с тех пор не менял). Название, равное тексту, с которого начали заводить товар, заменяется даже пустым значением (поправки после ревью). Категория, единица, фасовка, поштучная продажа, цены и минимальный остаток не меняются. После заполнения — «Заполнено из справочника. Проверьте карточку перед сохранением» |
| R13 | Моки web | В режиме моков — 5 синтетических записей (общие названия, синтетические штрихкоды с верной контрольной цифрой), не данные клиентов |
| R14 | Первое наполнение | Из присланной выгрузки остатков берутся только пары «штрихкод + наименование»; склады, количества и себестоимость не используются. CSV готовится на машине архитектора вне репозитория |
| R15 | Тесты | Новых автотестов нет (правило «тесты отложены до MVP»); проверка живая: скрипт на временной базе (dry-run, запись, повтор), API, экран в браузере. Существующие наборы остаются зелёными (`catalog.int-spec` сверяет манифест классов с базой) |

## Задачи

### 1. Схема
- Миграция по R8; `table-classes.ts`: обе таблицы — `shared`.
- Миграция и `api:db-types` — на временной базе из миграций ветки (не на общей dev-базе); `db-types-verify` зелёный.

### 2. Скрипт
- `seed-drug-reference.mjs` по R1–R7: `--file`, `--dry-run`, `--help`; разбор CSV; проверка GTIN; группировка;
  запись пачками (`jsonb_to_recordset`); отчёт; аудит. Ошибки — фиксированный текст, класс и код ошибки, без значений.
- `webpack.config.js`: скрипт в образе (`scripts/`), как `create-operator.mjs`.
- Тексты действия и задачи в журнале операторов admin (RU/TJ).
- Проверка: временная база — `--dry-run`, запись, повтор (0 новых), файл с конфликтом и внутренними кодами.

### 3. API
- DTO `DrugReferenceItem`, `DrugReferenceQuery`, `DrugReferenceListResponse` в `tenant-catalog.ts`.
- `DrugReferenceQueryDto` (class-validator), репозиторий (чтение в `tenantTransaction`, без фильтра тенанта —
  таблица общая), контроллер `GET catalog/drug-references` с `@RequirePermission('catalog:create')`.
- Проверка: запросы по штрихкоду, по названию, `q` из 1 символа — 400, без права — 403.

### 4. Web
- Маршрут `catalog.drugReferences`, `REAL_API_ROUTES`, мок по R13.
- `DrugReferenceLookup` по R10–R12, хук запроса (TanStack Query, `keepPreviousData` не нужен), подключение в обе
  точки создания; словари RU/TG.
- Проверка в браузере на `127.0.0.1` (режим `partial` с API на временной базе): поиск по названию, по штрихкоду,
  «не найдено», «Заполнить», создание из строки документа со штрихкодом.

### 5. Документы и наполнение
- `CLAUDE.md` (раздел «Containers» — запуск скрипта в dev и в test/prod), модель данных 02 (фактические колонки,
  ссылка карточки — позже), QA.
- CSV из выгрузки (R14) — вне репозитория; `--dry-run` на временной базе, отчёт архитектору.

## На что смотреть ревью

- Внутренние коды и коды с неверной контрольной цифрой не попадают в справочник; GTIN-12 и GTIN-14 не отбрасываются.
- Повторный запуск того же файла ничего не меняет; запуск с новым кодом существующего наименования не создаёт вторую запись.
- Поиск: `%` и `_` в запросе экранируются; запрос из цифр короче 8 ищет по названию; архивные записи не видны.
- «Заполнить» не стирает поля, которых в справочнике нет, и не теряет уже введённые штрихкоды.
- Отчёт и ошибки скрипта не печатают значения файла и строку подключения.
