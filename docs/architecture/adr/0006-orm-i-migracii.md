# ADR-0006: Слой доступа к данным и миграции — Kysely + `pg`, SQL-миграции node-pg-migrate

- **Статус:** accepted (2026-09-30, архитектор проекта — APPROVAL.md)
- **Дата:** 2026-09-29
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI по итогам spike)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

`apps/api` (NestJS, ADR-0003) работает с одной мультитенантной PostgreSQL в облаке и с локальной
PostgreSQL офлайн-точки в Docker (ADR-0005); схема и миграции у них общие. Инварианты проекта
SQL-природные: каждый запрос — в транзакции, которая выставляет `set_config('app.tenant_id', …, true)`
(RLS с `FORCE`, роль приложения `pharmacy_app` не владеет таблицами); остаток — сумма движений по
партиям; партии блокируются `FOR UPDATE` в порядке FEFO; идемпотентность — `ON CONFLICT DO NOTHING
RETURNING`; деньги — `bigint` в дирамах; движения и аудит append-only (`REVOKE` + триггер); очереди —
таблицы со `SKIP LOCKED` (ADR-0002). Команда знакома с Prisma и TypeORM.

Чтобы решать не по документации, 2026-09-29 проведён spike: один и тот же сценарий «продажа N штук»
(tenant-транзакция, идемпотентный чек, FEFO с `FOR UPDATE`, остаток из движений, откат при нехватке,
CRUD-список, изоляция тенантов, две параллельные продажи, запрос без контекста) реализован на
Prisma 7.10, TypeORM 1.1.1, Kysely 0.29.6 и MikroORM 7.2.2 против PostgreSQL 17 с RLS. Все четыре
прошли 6/6 тестов; различаются объёмом ручного SQL, типизацией и найденными ловушками.

## Рассмотренные варианты

Оценки по критериям проекта (1–5): К1 tenant-контекст, К2 блокировки/`ON CONFLICT`, К3 raw SQL,
К4 типобезопасность, К5 миграции с RLS/триггерами, К6 офлайн-образ, К7 удобство CRUD.

| | К1 | К2 | К3 | К4 | К5 | К6 | К7 | Σ |
|---|---|---|---|---|---|---|---|---|
| Prisma 7.10 | 3 | 2 | 4 | 4 | 2 | 3 | 5 | 23 |
| TypeORM 1.1 | 3 | 4 | 3 | 2 | 2 | 5 | 4 | 23 |
| Kysely 0.29 + node-pg-migrate | 4 | 5 | 4 | 4 | 4 | 5 | 3 | 29 |
| MikroORM 7.2 | 4 | 4 | 4 | 3 | 4 | 5 | 5 | 29 |

1. **Prisma 7** — лучший CRUD, команда его знает, `bigint` честно мапится в JS `bigint`. Минусы из spike:
   `FOR UPDATE` и `ON CONFLICT DO NOTHING RETURNING` в API нет — весь критичный путь кассы уходит в
   TypedSQL (preview-фича, генерация требует живой БД); официальный RLS-подход через client extension
   внутри интерактивной транзакции **молча теряет атомарность** (вставка пережила откат); таймаут
   интерактивной транзакции (5 с по умолчанию) не отменяет запрос в PostgreSQL и не отпускает
   блокировку `FOR UPDATE`; `migrate` не видит RLS, политики и CHECK — дрифт не отслеживается; CLI
   миграций требует нативный `schema-engine`, который скачивается из интернета, — отдельная задача для
   офлайн-образа; `@prisma/client` весит ~71 МБ.
2. **TypeORM 1.x** — знаком команде, есть `@nestjs/typeorm`. Минусы из spike: генератор схемы
   (`synchronize` / `migration:generate`) не видит RLS и **собирается удалить `UNIQUE(tenant_id,
   idempotency_key)`**, 8 FK, 4 индекса и 5 CHECK, которых нет в сущностях; `ON CONFLICT (cols) DO
   NOTHING` выражается только хаком `orUpdate([], cols)`; результаты `query()`/`getRaw*()` имеют тип
   `any`, `bigint` по умолчанию — строка; декораторам нужны метаданные (tsx/esbuild их не эмитит);
   генератор сущностей из БД заброшен (2022, критичные уязвимости).
3. **MikroORM 7.2** — ORM-удобства, встроенный RLS (ORM сам выполняет `set_config` после `BEGIN`),
   типизированный Kysely внутри той же транзакции, модель описывает политики, FORCE RLS и триггеры.
   Минусы из spike: **identity map при переиспользовании EntityManager отдаёт данные чужого тенанта без
   SQL** (fail-open; лечится fork на каждый запрос — это дисциплина, а не гарантия); ошибки записи
   всплывают на flush перед `COMMIT`, а не в строке кода; `schema:update` даёт шумный дрифт (FK,
   политики) и удаляет недекларированные индексы; команда инструмент не знает.
4. **Kysely + `pg`, миграции node-pg-migrate** — типизированный query builder без модели и движков.
   Из spike: сгенерированный SQL совпадает с задуманным один к одному; `forUpdate()`, `skipLocked()`,
   `onConflict(…).doNothing().returning()` нативно и типизированно; все найденные обходы tenant-контекста
   — fail-closed (ошибка, а не утечка); типы БД генерируются из реальной схемы (`kysely-codegen`,
   `--verify` ловит дрифт); рантайм — чистый JS (~3,7 МБ). Минусы: нет сущностей и связей — CRUD
   многословнее; версия 0.x; тип `bigint` и парсер `pg` настраиваются в двух местах.

## Решение

Выбран вариант 4: **Kysely поверх `pg` для всего доступа к данным `apps/api` и node-pg-migrate с
SQL-миграциями**. Определяющий аргумент — в мультитенантной системе с персональными данными самый
дорогой класс ошибок — утечка данных чужого тенанта; у Kysely spike не нашёл ни одного такого пути, а
инварианты кассы и склада выражаются без второй парадигмы.

Правила применения:

1. **`DatabaseService.withTenant(tenantId, fn)`** — единственный путь к прикладным таблицам:
   транзакция Kysely на одном соединении пула; первыми операторами — `set_config('app.tenant_id', $1,
   true)`, `SET LOCAL statement_timeout` и `SET LOCAL lock_timeout`. Сервисы и репозитории получают
   `Transaction<DB>` из `withTenant`, но не корневой `Kysely<DB>` — в коде, где есть `trx`, обращение к
   `db` запрещено (правило ревью + архитектурный тест). У пула задан `connectionTimeoutMillis`.
2. **Блокировка отдельно от подсчёта.** Партии блокируются одним оператором (`FOR UPDATE`), остатки
   считаются следующим (`SUM` движений). Объединённый оператор «`FOR UPDATE` + подзапрос `SUM`» в READ
   COMMITTED видит старый снимок и приводит к перепродаже — воспроизведено в spike.
3. **Деньги и `bigint`.** Единый type parser пула (`int8 → BigInt`, `date → строка YYYY-MM-DD`) и тот
   же маппинг в конфиге `kysely-codegen` (`typeMapping: { int8: "bigint" }`); тест сверяет парсер с
   типами. В HTTP-ответах `bigint` сериализуется явно (DTO), `JSON.stringify` по умолчанию на нём падает.
4. **Имена.** База — `snake_case`; в коде — `camelCase` через `CamelCasePlugin` (совпадает с JSON API);
   `kysely-codegen` запускается с `--camel-case`. Алиасы внутри сырых `sql\`…\`` пишутся в `snake_case`.
5. **Типы БД** генерируются `kysely-codegen` из БД после миграций (роль с `USAGE` на схему, фильтр
   схем через `excludePattern`) и хранятся в `apps/api`, не в `libs/shared/*`. `codegen --verify` —
   обязательная проверка перед PR, будущий гейт CI.
6. **Raw SQL** — только через параметризованный тег `sql`; `sql.raw`/`sql.lit` с входными данными
   запрещены. Тип результата `sql<T>` — утверждение разработчика, поэтому raw-запросы покрываются тестом.
7. **Миграции** — `apps/api/migrations/*.sql` для node-pg-migrate, **только Up** (откат — новой
   миграцией или из бэкапа; локальная база пересоздаётся с нуля). `CREATE INDEX CONCURRENTLY` и другие
   операции вне транзакции — отдельной `.mjs`-миграцией с `pgm.noTransaction()` (в `.sql` node-pg-migrate
   оборачивает всё в транзакцию — проверено в spike). Каждая миграция — ревью агентом
   `postgresql-database-reviewer`.
8. **Применение миграций** — роль `pharmacy_owner`, отдельным шагом до старта API (облако — шаг
   выкатки; офлайн-точка — шаг скрипта обновления после обязательного `pg_dump`). Миграции совместимы с
   ещё не обновлёнными точками (expand/contract) из-за синхронизации (ADR-0014).
9. Версии `kysely`, `pg`, `node-pg-migrate`, `kysely-codegen` закрепляются точно; обновление Kysely
   (линия 0.x) — отдельным PR с прогоном e2e.

## Последствия

- Положительные:
  - один путь к данным — tenant-транзакция; неявных запросов (ленивые связи, автосохранение, identity
    map) нет по построению; обходы контекста падают, а не отдают чужие данные;
  - критичный код кассы, склада и очередей — один типизированный API, SQL в логе совпадает с кодом;
  - схема, RLS, гранты, триггеры и индексы — в читаемых SQL-файлах; дрифт типов ловит `codegen --verify`;
  - офлайн-образ без движков и нативных бинарей: мигратор — npm-пакет в том же образе, advisory-лок
    защищает от параллельного запуска.
- **Отрицательные (обязательно):**
  - команда знает Prisma и TypeORM, но не Kysely — нужны обучение и примеры в скиле `nestjs-api`;
  - нет ORM-удобств: связи, вложенные выборки и маппинг в доменные объекты пишутся руками — CRUD
    админки многословнее;
  - все миграции пишутся вручную, цена ошибки в DDL выше — обязательное ревью каждой миграции;
  - типы производны от схемы: забытая регенерация даёт ложную типобезопасность (смягчение — `--verify`);
  - Kysely — линия 0.x: минорные обновления могут ломать API; тяжёлые типы сложных запросов
    замедляют `tsc`; `tsx` типы не проверяет — `tsc --noEmit` обязателен;
  - `bigint`: тип и парсер настраиваются в двух местах — ошибка ломает инвариант «деньги — целые дирамы»;
  - нет официального NestJS-модуля: `DatabaseModule`, завершение пула и логирование SQL (с маскированием
    tenant_id и ПДн в параметрах) пишем сами;
  - только Up: откат неудачной миграции в проде — новой миграцией или из бэкапа.

    `trx`, `sql.raw` со входными данными);
