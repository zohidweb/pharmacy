# ADR-0003: Выбор NestJS для бэкенда

- **Статус:** accepted
- **Дата:** 2026-09-29
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy

## Контекст

Проект Pharmacy — мультитенантная SaaS-платформа автоматизации аптечных сетей (Full, Tier 2,
персональные данные, SLA 99,5% в рабочие часы; см. docs/architecture/stack.md). Жёсткий срок —
запуск первой волны MVP до конца 2026 года. Команда разработки владеет стеком
NestJS / Next.js / Angular (TypeScript) и не владеет ни C#, ни PHP. Архитектура — модульный
монолит в Nx-монорепо (ADR-0002) с двумя TypeScript-фронтендами (ADR-0004); ТЗ требует
строгой доменной модели партий/движений и очереди синхронизации офлайн-точек.

## Рассмотренные варианты

1. **C# (.NET, актуальная LTS)** — Плюсы: зрелая экосистема, строгая типизация, развитый
   инструментарий. Минусы: у команды нулевые компетенции; обучение с нуля при сроке
   «до конца года» — прямой риск срыва срока и низкого качества первого продуктового кода.
2. **PHP (актуальная версия)** — Плюсы/минусы аналогичны: компетенций в команде нет;
   экосистема слабее ложится на задачу (очередь синхронизации офлайн-точек, строгая
   типизация доменной модели партий/движений).
3. **NestJS (Node.js + TypeScript)** — Плюсы: команда владеет; модульная архитектура
   фреймворка ложится на модульный монолит; единый язык TypeScript и общие типы/DTO с обоими
   фронтендами в Nx-монорепо (меньше расхождений контрактов API); зрелая экосистема (ORM,
   валидация, OpenAPI). Минусы: у команды нет накопленной экспертизы эксплуатации и
   сопровождения Node.js-бэкенда в продакшене.

## Решение

Выбран NestJS (актуальная поддерживаемая версия, Node.js LTS, TypeScript) как бэкенд-фреймворк
проекта Pharmacy. Определяющие факторы: компетенции команды при фиксированном сроке до конца
2026 года и сквозной TypeScript от БД-моделей до UI в одном Nx-монорепо. Альтернативы (C#, PHP)
требуют переобучения команды и делают срок нереалистичным.

## Последствия

- Положительные: команда стартует немедленно; общие типы API между `apps/api`, `apps/web`,
  `apps/admin`; один язык — ниже порог взаимозаменяемости внутри команды.
- **Отрицательные (обязательно):**
  - нет существующей экспертизы сопровождения, мониторинга и security-ревью Node-стека —
    её придётся выращивать на этом проекте;
  - зависимость от npm-экосистемы (supply-chain-риски) — потребуется lock-файлы, аудит
    зависимостей и внутренние правила обновлений;
  - однопоточная модель Node.js требует дисциплины при CPU-тяжёлых операциях (отчёты,
    генерация PDF-счетов) — выносить в воркеры.

Управление решениями — ADR-0011 (проект вне банковского контура).
