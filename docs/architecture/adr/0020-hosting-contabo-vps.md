# ADR-0020: Хостинг облачной части на пилоте — один VPS Contabo, домен nurmed.online, копии БД вне хоста

- **Статус:** proposed
- **Дата:** 2026-10-21
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

Место хостинга — открытый вопрос № 1 stack.md, блокер пилота № 2: без хоста нет HTTPS, раздачи web и admin и
внешнего хранилища копий БД. Объём пилота — 1–2 облачные аптеки, офлайн-точек нет. Требования и ограничения:
- ТЗ: SLA 99,5 % в рабочие часы, RTO 4 ч, RPO 24 ч; ежедневная копия БД с хранением 30 дней (C4 `deployment.md`);
- ADR-0011: данные тенантов только в собственной PostgreSQL, без внешних SaaS-БД; новая технология — через ADR;
- ADR-0005: всё запускается Docker Compose; ADR-0012 (proposed, отложен «до выбора хостинга») — Caddy, web и admin
  на поддоменах одного домена;
- ADR-0019 (proposed): ежедневная проверенная копия сервисом `backup` в каталог хоста `BACKUP_DIR`; копию за пределы
  хоста и шифрование копий он оставил этому решению;
- C4 описывает две VM (приложения и БД) в приватной сети; реестра образов и CD нет (ADR-0009: деплой — после выбора
  хостинга).

Архитектор выбрал провайдера и тариф: Contabo, Cloud VPS 6 (6 vCPU, 12 ГБ ОЗУ, 100 ГБ NVMe или 200 ГБ SSD, 300 Мбит/с,
2 снимка диска), и домен `nurmed.online`.

## Рассмотренные варианты

**Размещение**

1. **Один VPS: proxy, API, PostgreSQL, Redis и `backup` в одном Compose-проекте `pharmacy-prod`.**
   - Плюсы: дёшево; топология prod уже описана в `docker/compose*.yml`; PostgreSQL и Redis наружу не публикуются
     (порты только на `127.0.0.1`), приватная сеть — сеть compose.
   - Минусы: одна точка отказа; ночная копия и проверка ADR-0019 нагружают тот же CPU, что и касса; отступление от двух
     VM в C4.
2. **Два VPS (приложения и БД) в приватной сети провайдера, как в C4.**
   - Плюсы: соответствует C4; БД не делит ресурсы с API.
   - Минусы: вдвое дороже и сложнее (приватная сеть, firewall между узлами, два хоста для обновлений) при нагрузке
     пилота в единицы процентов от тарифа; RTO не улучшается — отказ любого узла останавливает продажи.
3. **Хостинг в Таджикистане (местный ЦОД).**
   - Плюсы: данные в стране — снимает юридический вопрос о ПДн за рубежом; меньше задержка.
   - Минусы: архитектор уже выбрал Contabo; местные предложения не сравнивались по цене, SLA и средствам изоляции.
     Остаётся запасным вариантом, если юрист не одобрит хранение за рубежом.

**Копии БД вне хоста** (дополнение к ADR-0019)

1. **Contabo Object Storage (S3-совместимое) в другом регионе, загрузка `rclone`, шифрование `age` до выгрузки.**
   - Плюсы: переживает потерю VPS; провайдер видит только шифротекст; места — сотни ГБ за единицы долларов; хост
     не нужно сопровождать.
   - Минусы: два новых инструмента (`rclone`, `age`); ключ доступа к хранилищу лежит на хосте.
2. **Второй маленький VPS как приёмник копий (`rsync` по SSH).**
   - Плюсы: без S3-клиента.
   - Минусы: ещё один сервер, который нужно защищать и обновлять; при той же учётной записи Contabo — тот же
     провайдер, без выигрыша в независимости.
3. **Автокопии Contabo («VPS with Auto Backup») или снимки диска.**
   - Плюсы: ничего не писать.
   - Минусы: копия всего диска вместе с env-файлом (ключи JWT, pepper, пароли — ADR-0008 требует хранить их отдельно от
     копий БД); восстановление нельзя проверить нашими средствами; снимков всего два.
4. **Забирать копии на компьютер в офисе.**
   - Плюсы: данные у команды.
   - Минусы: зависит от включённого ПК и связи офиса; ручной процесс без контроля.

## Решение

**Размещение — вариант 1.** Среда prod на пилоте — один Cloud VPS 6 Contabo с диском **100 ГБ NVMe** (БД упирается в скорость
диска, места на пилот хватает с запасом) в регионе **EU (Германия)** — наименьшая задержка из Душанбе среди регионов
Contabo. Условие ввода в эксплуатацию: письменное согласие юриста на хранение данных тенантов за пределами РТ; без него
пилот переезжает на вариант 3 той же схемой Compose. Среда test остаётся локальной, как сейчас.

**Домен и сеть.** DNS `nurmed.online`: A-записи `app.nurmed.online` (клиентский продукт и `/api`),
`admin.nurmed.online` (админка), apex — редирект на `app.` — по схеме ADR-0012 B1. Наружу открыты только 80/tcp,
443/tcp и 443/udp (HTTP/3) — для proxy, и 22/tcp — для SSH с адресов команды. TLS — Let's Encrypt через Caddy (профиль
`acme` ADR-0012). `TRUST_PROXY=1`. Этот ADR не принимает ADR-0012 — он лишь снимает причину откладывания.

**Хост.** Ubuntu Server 24.04 LTS; вход по SSH только по ключу, без пароля и без root; `ufw` и firewall панели Contabo
с одинаковым набором портов; автоматические обновления безопасности (`unattended-upgrades`); Docker Engine с
Compose-плагином из официального репозитория Docker. Env-файл `docker/env/prod.env` — на хосте, владелец — служебный
пользователь, права 0600 (вопрос № 8 stack.md остаётся открытым до prod-масштаба).

**Копии вне хоста — вариант 1.** Сервис `backup` ADR-0019 после проверки копии шифрует её `age` открытым ключом
получателя и выгружает `rclone` в бакет Contabo Object Storage в другом регионе (не Германия); хранение — 30 дней,
как в ADR-0019. Закрытый ключ `age` создаётся вне VPS и хранится у архитектора и ещё у одного члена команды; на хосте
его нет, поэтому похищенный хост не открывает свои старые копии. Ключ доступа к бакету — с правами только на этот
бакет. Pepper и env-файл копируются отдельно вручную при каждом их изменении, тоже зашифрованными `age`. Оба
инструмента ставятся пакетами Alpine в образ `pharmacy/postgres`, где уже работает `backup`.

**Выкладка на пилоте** (до отдельного ADR о CD): образы собирает `npm run prod:build` из чистого дерева на теге `main`
(проверки lint и test обязательны), переносятся на хост `docker save | ssh … docker load`, запускаются
`npm run stack -- prod up` на хосте. Исходного кода, Node.js и npm на хосте нет. Перед выкладкой с миграциями —
снимок диска в панели Contabo для быстрого отката.

## Последствия

- Положительные:
  - Снимаются блокеры пилота № 2 (хостинг, HTTPS) и внешняя часть № 3 (копии вне хоста).
  - Топология prod не меняется: тот же `docker/compose*.yml`, что на test; переезд к другому провайдеру — перенос
    env-файла и восстановление копии.
  - Копии переживают потерю VPS и не читаются ни провайдером, ни тем, кто захватил хост.
  - Ресурсы тарифа покрывают нагрузку ТЗ (до ~30 точек и 50 кассиров), а не только пилот.
- **Отрицательные (обязательно):**
  - **Одна точка отказа.** Отказ VPS или его диска останавливает продажи облачных аптек (буфер кассы ADR-0015 держит
    только чеки и смену). Восстановление на новом VPS — из ночной копии: RPO 24 ч, RTO зависит от ручных шагов и не
    отрепетирован на Contabo — первая репетиция обязательна до пилота.
  - **Юридический риск.** Данные тенантов (ПДн сотрудников, контакты поставщиков, поля рецептов ПКУ) хранятся в ЕС;
    без согласия юриста — переезд.
  - **Провайдер.** Contabo — бюджетный хостинг: возможны колебания производительности соседних VPS и медленная
    поддержка; заявленные 99,9 % — не договорной SLA с компенсацией. Привязка невелика (только Compose и S3).
  - **Ночная нагрузка.** Копия и проверочное восстановление ADR-0019 идут на том же CPU и диске, что API.
  - **Отступление от C4** (две VM): обновить `deployment.md`; разделение на два узла — при росте нагрузки.
  - **Новые инструменты** `age` и `rclone` в образе `pharmacy/postgres` — их нужно обновлять вместе с образом.
  - **Ключи.** Потеря закрытого ключа `age` у обоих хранителей делает все внешние копии бесполезными; ключ бакета и
    пароль `pharmacy_backup` на хосте — чувствительные данные.
  - **Ручная выкладка** с машины архитектора: без CD и реестра; ошибка в переносе образов или env-файла видна только
    после запуска.
  - **Нет мониторинга:** `unhealthy` сервисов и истечение места никто не получает автоматически — оператор проверяет
    вручную каждый день, пока нет решения о мониторинге.
  - **Стоимость:** тариф плюс Object Storage и, при необходимости, доплата за регион; проверить срок договора и плату
    за установку при заказе.
