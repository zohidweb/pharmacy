# Касса и перебой API за reverse proxy: план

**Goal:** касса переживает остановку или перезапуск API так же, как обрыв сети: детектор связи уходит в «Нет связи»,
терминал открывается с запомненным профилем (ADR-0015, ось 3), а экран входа сам перечитывает привязку терминала,
когда связь вернулась.

**Найдено** 2026-10-22 при живой проверке F2/F3 (PR #72):

1. Экран входа держит «Не удалось проверить привязку терминала. Вход по PIN недоступен…» до перезагрузки: запрос
   `terminals.current` остаётся в ошибке, когда связь вернулась.
2. Любой HTTP-ответ считается «связь есть»: `isUnreachable` (`shared/api/client.ts`) — только `network`/`timeout`. За
   Caddy (ADR-0012) остановленный или перезапускающийся API отвечает 502/503/504 без problem+json (в dev — сервер Next
   отвечает 500 вместо прокси на :3000). Детектор остаётся «на связи», запасная запомненная сессия в `fetchSession` не
   срабатывает, касса не открывается во время перебоя API.

Причины п. 1: детектор не уходил в «Нет связи» (п. 2), поэтому не было и возврата связи, по которому TanStack Query
перечитывает запросы; а запросы с `networkMode: 'always'` TanStack Query при возврате связи не перечитывает вовсе (см.
G4). В исправленном детекторе всплывает соседний случай: пока детектор «без связи», запрос привязки
(`networkMode: 'online'`) стоит на паузе в `pending`, и экран входа после выхода при перебое (F3) показывает
бесконечный спиннер.

**Spec:** ADR-0015 (оси 2а, 3; буфер кассы), спецификация `2026-10-21-pos-offline-limits` (P18), план
`2026-10-22-security-session-lock` (S3–S5).

## Решения автора

| № | Вопрос | Решение |
|---|---|---|
| G1 | Что считать «API недоступен» | Сетевая ошибка, тайм-аут или **ответ шлюза**: статус ≥ 500 без `Content-Type: application/problem+json`. `apps/api` отвечает problem+json на любую ошибку (`ProblemDetailsFilter`), значит такой ответ дал посредник вместо API: Caddy (502/503/504, API остановлен или перезапускается) или dev-сервер Next (500, на :3000 никто не отвечает). 4xx без problem+json (например, 413 лимита тела в Caddy) — ответ, а не перебой. 5xx с problem+json (500 `internal`, 503 `imports_busy`) — ответ API: он работает |
| G2 | Как это выглядит в коде | `ApiError` сохраняет настоящий статус, код — `gateway`. Всё, что смотрит на статус, не меняется: буфер повторяет ≥ 500, выход блокирует терминал при ≥ 500, загрузка файла узнаёт 502/504, `QueryState` показывает 503 как обслуживание. Тело ответа шлюза не разбирается |
| G3 | Где действует | Одно правило — `isUnreachable` в `shared/api`: детектор связи (`apiRequest` → «Нет связи», пинг `/health`, `onlineManager`), запасная сессия (`fetchSession`) и смена (`useCurrentShift`), снимок каталога (был свой разбор `network`/`timeout`), выход (F3, уже ≥ 500), проверка сессии перед продажей (`ensureSession` офлайн не проверяет, `recheckSession` любую неудачу считает «не проверено»), тексты ошибок (`useApiErrorMessage`, формы входа по паролю и PIN — «Нет связи с сервером») |
| G4 | Привязка на экране входа | `useBoundTerminal` — `networkMode: 'always'`, как у сессии: при перебое запрос отвечает ошибкой, а не встаёт на паузу (экран входа показывает форму, а не спиннер); при возврате связи перечитывается. У TanStack Query 5 `refetchOnReconnect` по умолчанию — `networkMode !== 'always'`: запросы, работающие и при перебое (сессия, привязка, смена, каталог), при возврате связи не перечитывались вовсе. Поэтому в `AppProviders` — `refetchOnReconnect: true` для всех: устаревший запрос (ошибка без данных, смена старше 30 с) перечитывается, как любой другой; сессия с данными (`staleTime: Infinity`) — нет. Предупреждение уходит само |
| G4а | Снимок каталога после перебоя | Снимок, показанный из IndexedDB при перебое (`stale`), перечитывается сразу при возврате связи (`refetchOnReconnect: 'always'` для него), а не когда ему исполнится минута (`staleTime`): иначе «Нет связи: цены и остатки — из сохранённого каталога» висело до следующего случайного обновления |
| G5 | Вход при перебое | Вход по паролю и по PIN — `networkMode: 'always'`: вход уходит сейчас или получает «Нет связи», но не ждёт связи на паузе и не входит позже, когда кассир уже ушёл. Раньше при обрыве сети так и было; с G1 это стало бы случаться при каждом перезапуске API |
| G6 | Архитектура | ADR не меняется: ADR-0015 задаёт детектор как «пинг `/api/v1/health` + ошибки запросов» и не перечисляет коды; буфер уже повторяет 5xx. Уточнение «ответ шлюза = API недоступен» — для ревью архитектора вместе с PR. Условие для ADR-0012: страницы ошибок прокси не отдают `application/problem+json` (в `docker/proxy/Caddyfile` ветки `feature/hosting-proxy` — так и есть) |

Вне объёма: перебой PostgreSQL или Redis, о котором API сам отвечает 5xx problem+json, — это ответ API, касса
показывает ошибку, как сейчас. Админка: тот же разбор ответа шлюза и текст «Нет связи» — отдельной задачей (у неё нет
детектора и буфера).

## Живая проверка

API останавливается и запускается (в dev сервер Next отвечает 500 text/plain — тот же класс, что 502 Caddy):

- g1 — экран входа на привязанном терминале, API остановлен, перезагрузка → предупреждение о привязке и форма пароля
  (не спиннер); API запущен → не позже чем через ≈ 10 с (пинг) форма PIN без перезагрузки;
- g2 — кассир вошёл по PIN (смена открыта); API остановлен → «Нет связи»; перезагрузка → касса открывается с
  запомненным профилем, сменой и снимком каталога; продажа уходит в буфер; API запущен → «В сети» без перезагрузки,
  предупреждение о сохранённом каталоге уходит, буфер дослан (по своей задержке повтора, до 60 с);
- g3 — API остановлен, «Выйти» → экран входа с формой (не спиннер), терминал заблокирован; API запущен → выход дослан
  (F3);
- g4 — API остановлен, вход по паролю или PIN → «Нет связи с сервером» сразу, без ожидания;
- g5 — ответ API с ошибкой (неверный PIN, 4xx problem+json) — как раньше, связь не теряется.

**Итог 2026-10-23** (web dev :4210 `partial` + API :3000, синтетическая сеть): g1–g5 и G4а пройдены. Первая
проверка g1 не прошла — так нашлось правило `refetchOnReconnect` TanStack Query для `networkMode: 'always'` (G4).
`npx nx run-many -t lint fsd test -p web` — зелёный.
