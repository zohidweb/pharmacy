# ADR-0014: Протокол синхронизации офлайн-точек с облаком

- **Статус:** accepted (2026-09-30, архитектор проекта — APPROVAL.md)
- **Дата:** 2026-09-30
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

Офлайн-точка (волна 3) — та же система (`apps/web` + `apps/api` + локальная PostgreSQL в
Docker на одном ПК аптеки, без Redis; ADR-0002, ADR-0005, C4 container), работающая полностью
автономно. По ТЗ и C4: синхронизация по расписанию (интервал — настройка сети, по умолчанию 15 минут; решение 2026-09-30) и вручную; канал —
HTTPS + уникальный лицензионный ключ точки, отзыв ключа действует при следующей синхронизации;
очередь операций точки (таблица в PostgreSQL) доставляется в облако идемпотентно, без дублей;
справочники и цены подтягиваются из облака; конфликты: цена — решает владелец в облаке, дубль
товара — решает точка (glossary «Конфликт синхронизации»); облако принимает синхронизацию от
старых версий точки с преобразованием на лету; обновление точек — вручную оператором;
первоначальная загрузка — флеш-комплект (образ + снимок каталога и стартовых остатков).

Ограничения, которые решение обязано сохранить: остаток = сумма движений по партиям; чек
(документ) и его движения атомарны; деньги — целые дирамы; аудит, журнал ПКУ и движения —
append-only; финансовые операции и синхронизация — idempotency key + correlation ID (CLAUDE.md);
брокера нет — очереди и outbox являются таблицами со `SKIP LOCKED` (ADR-0002, скил
`postgres-best-practices`: `lock-skip-locked`, `data-idempotency-keys`, `data-stock-from-movements`,
`schema-primary-keys`); облачная PostgreSQL доступна только из приватной сети (C4 deployment);
`tenant_id`/`store_id` для синхронизации берутся из ключа, а не из тела запроса (скил `nestjs-api`,
`nestjs-security-auth.md`). Масштаб: ~30 точек, ~3–9 тыс. чеков в сутки на всю платформу
(≈100–300 чеков в сутки на точку), рост ×5. Слой данных (ADR-0006) и аутентификация (ADR-0008)
ещё `proposed`: протокол не должен зависеть от их выбора. Образ БД — `postgres:17.11-alpine`
(docker/postgres/Dockerfile): встроенной `uuidv7()` нет (она появилась в PostgreSQL 18).

## Рассмотренные варианты

### Ось 1. Модель синхронизации (главное решение)

1. **Репликация строк средствами PostgreSQL (logical replication / CDC)** — точка публикует
   свои таблицы, облако подписывается; облако публикует справочники с фильтром строк по тенанту
   и точке. Плюсы: встроено в СУБД, минимум прикладного кода, порядок транзакций сохраняется.
   Минусы для этого проекта:
   - нужен прямой сетевой доступ PostgreSQL ↔ PostgreSQL (подписчик подключается к
     публикатору): облачная БД пришлось бы открыть наружу или строить VPN до каждого ПК аптеки
     за NAT — противоречит C4 deployment (БД только в приватной сети) и схеме «HTTPS + ключ»;
     лицензионный ключ в механизме не участвует, отзыв превращается в правку `pg_hba`/ролей;
   - слот репликации на стороне публикатора удерживает WAL, пока подписчик недоступен: точка,
     неделю не выходившая на связь, раздувает WAL облака (для публикации справочников);
   - при конфликте (например, нарушение уникальности) применение останавливается до ручного
     вмешательства (`ALTER SUBSCRIPTION … SKIP`) — вся синхронизация точки встаёт;
   - DDL не реплицируется: схемы облака и всех точек должны меняться синхронно, что прямо
     противоречит требованию «облако принимает старые версии точки»;
   - переносятся строки, а не бизнес-операции: облако не может провалидировать операцию,
     записать аудит применения, выделить конфликт цены или дубль товара; RLS и роли
     применения придётся настраивать отдельно для каждой подписки (30 подписок, ×5 при росте).
2. **Снимок + дельта строк по `updated_at` (двусторонний обмен состояниями таблиц, last write
   wins)** — REST, просто для справочников. Минусы: для изменяемых сущностей (документ
   «черновик → проведён», чек «отложен → оплачен → возвращён») обмен состояниями теряет смысл
   переходов и атомарность «чек + его движения» приходится восстанавливать на приёме; LWW
   опирается на часы ПК аптеки (ненадёжны); удаления надо отслеживать отдельно; курсор по
   `updated_at` пропускает строки поздно закоммиченных транзакций; полный снимок точки (за 3 года
   ≈1–2 млн строк движений на точку) регулярно гонять нельзя. Годится только для первоначальной
   загрузки и пересинхронизации справочников.
3. **Журнал операций-фактов точка → облако (transactional outbox → inbox) + курсорная лента
   изменений облако → точка, с явным владельцем каждого класса данных** — точка в той же
   транзакции, что и бизнес-операция, пишет в `sync_outbox` операцию-факт (чек со строками,
   оплатами и движениями; проведённый документ со своими движениями; смену…), облако применяет
   её целиком в одной транзакции с дедупликацией по `operation_id`. Облачные справочники
   отдаются лентой изменений с курсором и tombstones. Плюсы: обычный REST поверх HTTPS + ключ;
   один факт = одна транзакция на обеих сторонах (инварианты сохраняются по построению);
   валидация, аудит, конфликты и версионирование — в прикладном коде; схема БД точки и облака
   может различаться (контракт — DTO протокола, а не таблицы). Минусы: много собственного кода
   (типы операций, преобразователи версий, лента, карантин, UI конфликтов); каждая новая доменная
   функция требует решения «как она синхронизируется».
4. **Готовый движок синхронизации (PowerSync, ElectricSQL, CouchDB/PouchDB-подобные и т.п.)** —
   ориентированы на синхронизацию клиентских реплик (браузер/мобильное, SQLite) с серверной БД, а
   у нас точка — полноценный PostgreSQL + API; вводят новый серверный компонент или внешнюю
   зависимость (новая технология и интеграция — ADR-0011), свою модель конфликтов и прав, не
   знающую наших инвариантов «остаток = сумма движений». Отклонено.

### Ось 2. Что облако делает с операцией точки

- **2а. Команда (облако переисполняет):** точка присылает «продать 2 шт. товара X», облако
  заново делает FEFO и списывает партии. Минус: результат в облаке может отличаться от того,
  что уже напечатано в чеке на точке; при «отрицательном остатке» облако вынуждено отвергать
  продажу, которая физически состоялась.
- **2б. Факт (облако принимает результат):** точка присылает чек вместе с конкретными
  движениями по партиям (с их идентификаторами), облако сохраняет их как есть. Точка — источник
  истины по своим остаткам; облако — их зеркало.

### Ось 3. Применение в облаке

- **3а. Приём в inbox, применение фоновым воркером** — короткий HTTP-запрос, но воркер,
  разбирающий операции всех тенантов, не может работать под RLS одного тенанта: нужна отдельная
  роль и модель её прав (скил `lock-skip-locked`: «требует ADR»).
- **3б. Приём и применение в том же запросе** — контекст тенанта уже известен из ключа, каждая
  операция — собственная tenant-транзакция; неприменимые операции уходят в карантин. Запрос
  длиннее (батч до нескольких секунд), но без межтенантного воркера.

## Решение

Выбираем **вариант 3 оси 1** (журнал операций-фактов + лента изменений, данные разделены по
владельцам), **2б** (облако принимает факты точки, точка — источник истины по своим остаткам) и
**3б** (применение в запросе с карантином). Определяющие аргументы: только эта модель сохраняет
атомарность «чек + движения» и append-only-инварианты на обеих сторонах без распределённых
транзакций, работает поверх уже заданного канала «HTTPS + лицензионный ключ», переживает дни
без связи и разнобой версий точек (контракт — версионированные DTO, а не схема таблиц) и не
вводит новых технологий или компонентов. Детали — ниже.

### 1. Владельцы данных (single writer)

Конфликты исключаются по построению: у каждого класса данных ровно один пишущий.

| Владелец | Данные | Направление |
|---|---|---|
| Облако (владелец сети, оператор) | Настройки сети; карточка точки; каталог (товары, МНН, штрихкоды); цены сети (базовые цены и их изменения); скидочные правила; роли и права; сотрудники (профиль, доступ к точкам, статус блокировки — **без** хешей пароля/PIN, см. ADR-0008: учётные данные точки отдельные); поставщики; входящие перемещения на точку («в пути»); решения по конфликтам цены; статус лицензии и минимальная версия протокола | облако → точка (лента изменений) |
| Офлайн-точка | Чеки (строки, оплаты, движения), возвраты покупателей, проведённые документы склада (приход, списание, инвентаризация, возврат поставщику, ввод начальных остатков, отправка/приём перемещения) и **их партии и движения**, смены (открытие, инкассация, закрытие, Z-отчёт), журнал ПКУ, аудит действий на точке, терминалы точки, локально созданные товары, локальные изменения цены, решения по дублям товара | точка → облако (журнал операций) |

Решение 2026-09-30: офлайн-точка **может сама заводить товары и менять цены** (строки её владения —
«локально созданные товары», «локальные изменения цены»). Конфликт цены (сеть изменила цену товара,
который точка переоценила) попадает в очередь конфликтов в кабинете владельца сети — решает владелец;
продажа по локальной цене — факт, чек не переоценивается. Дубль товара решает точка.

Следствия: в облаке для точки в режиме «офлайн» все операции, меняющие её остатки, **запрещены**
(UI и API облака показывают её склад только на чтение); черновики, отложенные чеки и локальные
сессии не синхронизируются — в журнал попадают только завершённые факты.

### 2. Идентификаторы, идемпотентность, порядок

- Все сущности и операции, возникающие на точке, — **UUIDv7, генерируемые приложением**
  (`schema-primary-keys`; PostgreSQL 17 не имеет `uuidv7()`). Библиотека — по умолчанию `uuid`
  (MIT, `v7()` с версии 10.0.0, актуальная линия 14.x; фиксируется в `libs/shared/util` вместе с
  ADR-0006). Уникальность в облаке обеспечивает первичный ключ `(tenant_id, id)`: коллизия (на
  практике невозможная) даёт ошибку и карантин, а не перезапись. Человекочитаемые номера (чек в
  смене, номер документа) уникальны в пределах `(tenant_id, store_id, …)` и не являются ключом.
- Операция: `operationId` (UUIDv7) — ключ идемпотентности; `storeSeq` — локальный `bigint
  identity` outbox; `payloadHash` — SHA-256 (`node:crypto`) от сериализованного payload;
  `correlationId`; `occurredAt` (часы точки, только информативно); `actor` (сотрудник, терминал).
- Облако: `sync_inbox` с `primary key (tenant_id, store_id, operation_id)`; вставка ключа и
  применение — одна транзакция (`INSERT … ON CONFLICT DO NOTHING RETURNING`). Повтор с тем же
  `operationId` и тем же `payloadHash` → `duplicate` (успех); с другим хешем → `rejected:
  id-reused` (ошибка кода точки, в админку). Ключи в inbox не удаляются (окно повторов — дни и
  недели); тяжёлые payload после применения можно архивировать (п. 8).
- **Порядок.** Точка отправляет одним воркером в порядке `storeSeq`; облако сериализует
  применение операций одной точки `pg_advisory_xact_lock('sync-apply', store)` (`lock-advisory`).
  Строгий «водяной знак» по `storeSeq` не используется: значения identity выдаются до COMMIT, и
  операция с меньшим номером может закоммититься позже большей — дедупликация идёт только по
  `operationId`. Причинные зависимости это не ломает: зависимая операция (возврат по чеку, приём
  перемещения) создаётся после коммита исходной и получает больший номер. Если ссылка всё же не
  найдена (например, исходная в карантине), операция уходит в карантин со статусом
  `pending-dependency` и переприменяется автоматически в конце каждого следующего приёма.

### 3. Облако → точка: лента изменений

- В облаке `sync_changes` (`tenant_id`, `scope_store_id` или `null` = вся сеть, `entity_type`,
  `entity_id`, `change_seq`, `op` = `upsert`/`delete`), запись — в той же транзакции, что и
  изменение справочника (облачный outbox).
- **Курсор без пропусков.** Позицию `change_seq` присваивает не писатель, а единственный
  воркер-«секвенсор» после коммита (раз в несколько секунд, под `pg_advisory_xact_lock`,
  `update … set change_seq = nextval(…) where change_seq is null order by id`). Поэтому
  выдача `change_seq > cursor` не пропускает поздно закоммиченные изменения. (Альтернатива —
  фильтр по `xid8` и `pg_snapshot_xmin(pg_current_snapshot())` — корректна, но завязана на
  внутренности СУБД и поведение при восстановлении; оставлена как запасная.)
- Выдача — **состояние сущности на момент чтения**, а не история её правок: несколько изменений
  одной сущности в странице схлопываются (`distinct on (entity_type, entity_id)`), payload
  сериализуется в версию протокола точки (п. 5). Удаление — tombstone (`op = delete`); на точке
  сущность архивируется, а не удаляется физически, т.к. на неё ссылаются факты (чеки, партии).
  Облако не удаляет физически сущности, на которые могут ссылаться факты точек.
- Точка применяет страницу и сохраняет новый курсор **в одной локальной транзакции** (upsert по
  `id` допустим — это справочники, `data-upsert`), поэтому обрыв посреди выдачи безопасен.
- Лента хранится не меньше максимального окна офлайна (**90 дней**, настройка оператора). Если курсор точки старше горизонта или облако сменило формат набора данных —
  ответ `resync-required`, точка перезагружает облачные наборы полным снимком (они небольшие:
  каталог сети — десятки тысяч строк) и продолжает с курсора снимка.
- Входящее перемещение из облачной точки приходит в ленте как документ «в пути»; приём — уже
  операция точки. Отзыв/блокировка ключа — в каждом ответе (п. 7). Блокировка сотрудника,
  изменение прав и цен вступают в силу на точке **только после синхронизации** (вопрос № 3).

### 4. Точка → облако: применение фактов

- Типы операций (с версией `typeVersion`): `receipt.completed` (чек + строки + оплаты +
  движения + записи ПКУ + аудит), `return.completed`, `document.posted` (с новыми партиями и
  движениями), `transfer.dispatched`, `transfer.accepted`, `shift.opened`, `shift.cash-collected`,
  `shift.closed`, `product.created-locally`, `product.duplicate-resolved`, `price.changed-locally`
  (если разрешено), `terminal.bound`/`terminal.revoked`, `audit.recorded` (действия на точке без
  доменной операции: входы, неверные PIN), `stock.checkpoint`. Одна операция = одна локальная
  транзакция точки = одна tenant-транзакция облака.
- Применение в облаке (в запросе, п. 6): `set_config('app.tenant_id', …)` → advisory-лок точки →
  ворота inbox → валидация (ссылки на тенант/точку/справочники, целые дирамы, суммы строк =
  итог, знаки движений) → вставка строк с **идентификаторами точки как есть** → запись в inbox
  статуса `applied`. Облако **не пересчитывает FEFO и не проверяет остаток**: движения точки
  принимаются как факт, остаток точки в облаке = сумма её движений. Отрицательный остаток на
  точке не возникает штатно (та же логика `FOR UPDATE` + FEFO, что и в облаке); в облаке он
  возможен только при пропущенных операциях и выявляется сверкой, а не отказом в приёме.
- Производные облачные данные (долг поставщику по приходу, отчёты) — из применённых фактов, как
  для облачной точки. Аудит точки вставляется как есть (append-only), облако добавляет одну
  запись `sync.batch-applied` на батч.
- **Карантин.** Операция, не прошедшая валидацию или применение, откатывается целиком, её
  сырой конверт сохраняется в `sync_inbox` со статусом `quarantined` + причина (отдельной
  транзакцией), точке отвечаем `quarantined` — точка считает её доставленной и не повторяет.
  Переприменение — автоматически (зависимости) или кнопкой оператора после исправления кода.
  Автоматической «починки» данных точки облако не делает.
- **Сверка остатков.** Точка при каждой синхронизации отправляет `stock.checkpoint`: на
  позиции `storeSeq` — число партий, сумма остатков и хеш списка `(batch_id, on_hand)`; облако
  сравнивает со своим расчётом по движениям этой точки. Расхождение — красный статус в админке
  (п. 8), без авто-исправления.
- **Конфликты (glossary).** *Цена:* если сеть разрешает точке менять цену, `price.changed-locally`
  несёт `basePriceVersion`; если цена в облаке успела измениться, создаётся конфликт для
  владельца в `apps/web`; решение владельца уходит на точку лентой. Проданные чеки не
  перецениваются никогда — строка чека хранит фактическую цену. *Дубль товара:* облако
  помечает локальный товар, совпавший с карточкой каталога (штрихкод; МНН + форма + дозировка +
  производитель), конфликт приходит на точку лентой; решает точка (`product.duplicate-resolved`:
  «объединить с карточкой X» или «оставить отдельно»). Объединение — запись алиаса
  `local_id → canonical_id`; факты не переписываются, отчёты и остатки агрегируют через алиас.
- **Флеш-комплект и переход точки в офлайн-режим.** Комплект = снимок облачных наборов на
  курсоре `cursor0` + состояние склада точки: партии и по одной переносящей движение
  (`origin = cloud-snapshot`) на партию, равной остатку в облаке на момент выпуска. Переносящие
  движения не попадают в outbox (история уже в облаке) — остаток = сумма движений на обеих
  сторонах. С момента выпуска комплекта облако переводит точку в `offline-pending` (запись
  склада в облаке закрыта). Новая точка без истории заводит начальные остатки обычным
  документом на точке. Потеря ПК = новый комплект из облака; неотправленное пропадает
  (ответственность тенанта, C4 deployment).

### 5. Версионирование протокола

- Уровни: `/api/v1` — версия REST-транспорта (меняется только при несовместимом изменении
  эндпоинтов); `protocolVersion` (целое) в конверте батча и в handshake; `type` + `typeVersion`
  у каждой операции; `appVersion` и `schemaVersion` (последняя применённая миграция) — только
  телеметрия, решений по ним облако не принимает.
- Точка → облако: в облаке цепочка **upcaster'ов** `type@N → type@N+1` — чистые функции в
  `libs` (контракты — `libs/shared/dto`, сериализация — JSON camelCase), каждая покрыта
  фикстурами реальных конвертов. В inbox хранится исходный конверт, upcast — при применении
  (переприменение из карантина возможно после исправления upcaster'а).
- Облако → точка: выдача ленты и снимков в форме версии протокола точки (**downcast**): новые
  поля опускаются, типы сущностей, неизвестные этой версии, не выдаются.
- Окно поддержки: облако поддерживает текущую и минимум две предыдущие версии протокола
  (предложение; не меньше срока, за который оператор успевает обновить все точки вручную).
  Ниже `minSupportedProtocol` — `426` problem+json `code: protocol-unsupported`: точка
  продолжает работать и копить outbox, показывает «требуется обновление».
- Миграции БД — expand/contract (ADR-0006 proposed это уже требует): облако не удаляет поле
  или смысл, пока его может прислать поддерживаемая версия точки.

### 6. Транспорт

| Эндпоинт | Назначение |
|---|---|
| `POST /api/v1/sync/runs` | Handshake: версии точки, курсор ленты, глубина outbox, возраст старейшей неотправленной операции, время точки. Ответ: `syncRunId`, статус лицензии, `minSupportedProtocol`/рекомендуемая версия, лимиты батча, время сервера (сдвиг часов), число операций точки в карантине |
| `POST /api/v1/sync/operations` | Батч операций (≤ 500 операций и ≤ 2 МБ JSON после распаковки); `Idempotency-Key` = `batchId`; ответ — результат по каждой операции: `applied` / `duplicate` / `quarantined` / `rejected` |
| `GET /api/v1/sync/changes?cursor=…&limit=…` | Страница ленты: `items`, `nextCursor`, `hasMore` (keyset-курсор — осознанное исключение из конвенции limit/offset: offset на меняющейся ленте даёт пропуски) |
| `GET /api/v1/sync/snapshots/{dataset}?after=…` | Полный снимок облачного набора постранично (пересинхронизация, установка через интернет); возвращает `cursor` ленты, с которого продолжать |
| `POST /api/v1/sync/runs/{id}/complete` | Итог прогона: счётчики, длительность, ошибки клиента (телеметрия для п. 8) |

- **Батчи и сжатие.** Запрос — `Content-Encoding: gzip` (`node:zlib`, без новых зависимостей);
  body-parser 2.x в составе Express 5 (`@nestjs/platform-express` 11 → express 5.2.1 →
  body-parser 2.3.0) распаковывает gzip/br/deflate сам, а лимит `limit` применяется к
  распакованному телу — защита от «zip-бомбы». Для маршрутов sync задаётся собственный лимит
  (по умолчанию body-parser — 100 КБ); остальные маршруты не меняются. Ответы ленты и снимков —
  gzip при `Accept-Encoding` (на reverse proxy, когда он будет выбран, либо в контроллере через
  `node:zlib`). Оценка объёма: 100–300 чеков в сутки × 2–4 КБ ≈ до 1 МБ в сутки на точку без
  сжатия — неделя офлайна укладывается в несколько батчей.
- **Возобновление.** Точка помечает операции батча `sent` только после ответа; при обрыве после
  COMMIT в облаке повтор даёт `duplicate`. Лента — курсор сохраняется постранично; снимок —
  keyset-токен `after`. Таймаут запроса 60 с, экспоненциальная пауза между попытками,
  circuit breaker клиента (скил `nestjs-api`). Отправку outbox на точке ведёт один воркер
  (порядок `storeSeq`, `SKIP LOCKED` + аренда на случай падения — `lock-skip-locked`); HTTP-вызов
  вне транзакции захвата.
- **Расписание.** Интервал — настройка сети тенанта (от 5 минут до 24 часов, по умолчанию 15 минут) + кнопка «Синхронизировать сейчас» (право
  `sync:run`) на точке; интервал — настройка сети (можно чаще при наличии интернета —
  вопрос № 3). Планировщик — `@nestjs/schedule` по скилу `nestjs-api` (в `package.json` пока нет;
  добавляется при реализации модуля `sync`).
- **Аутентификация ключом.** `Authorization: Bearer <licenseKey>`; ключ — 256 бит из
  `crypto.randomBytes(32)`, base64url, с открытым префиксом-идентификатором
  (`phk_<keyId>_<secret>`) для поиска записи. В облаке хранится `keyId` + SHA-256 секрета
  (высокая энтропия — медленный хеш не нужен; тот же приём, что для credential терминала в
  ADR-0008 proposed), сравнение — `crypto.timingSafeEqual`. Самописной криптографии нет —
  только примитивы `node:crypto`. `LicenseKeyGuard` (`@Public()` для сессионного guard) кладёт
  `tenantId`/`storeId` точки в контекст; `storeId` в теле, если есть, обязан совпадать.
  Ключ на точке — в env-файле развёртывания (как прочие секреты, открытый вопрос № 8 stack.md),
  в логах, аудите и ошибках — никогда. Ротация: оператор выпускает новый ключ, старый действует
  до первого успешного прогона с новым либо до заданной даты. Ограничение частоты — по `keyId`
  (throttler) и по IP для неудачных попыток.
- **Защита от повтора.** Канал — только HTTPS; повтор записи безвреден по построению
  (идемпотентность по `operationId` и `batchId`). Подпись запросов HMAC и метки времени не
  вводим: ключ остаётся bearer-секретом при любой схеме, а часы ПК аптеки ненадёжны.

### 7. Отзыв ключа и блокировка

- Статусы лицензии в облаке: `active`, `expiring` (≤ N дней до срока), `expired`, `revoked`,
  `revoked-hard` (компрометация ключа), плюс «точка закрыта» и «тенант заблокирован». Статус
  возвращается в handshake и в каждом ответе sync (`Pharmacy-License-Status`).
- `revoked` / `expired` / точка закрыта: облако **продолжает принимать** `POST /sync/operations`
  в течение льготного периода (предложение — 30 дней, настройка оператора), чтобы продажи,
  уже совершённые на точке, не потерялись; лента и снимки не выдаются. Точка, получив статус,
  в одной транзакции записывает его локально и аудит, блокирует новые чеки, документы и смены,
  оставляет просмотр, отчёты и досылку очереди.
- `revoked-hard`: не принимается ничего (`401` problem+json `code: license-revoked`); данные,
  не отправленные до отзыва, остаются на ПК точки.
- Точка хранит срок лицензии из последнего ответа и сама перестаёт продавать после его
  истечения, даже без связи. Защита от правки локальной БД владельцем ПК этим не
  обеспечивается (вне MVP можно выдавать подписанную облаком «аренду» — Ed25519 из
  `node:crypto`, но это новый секрет для хранения, вопрос № 8 stack.md). Без синхронизации точка **не блокируется**: после 7 дней — баннер на кассе и уведомление
  владельцу сети и оператору (решение 2026-09-30).

### 8. Наблюдаемость

- Облако: `sync_runs` (точка, время, версии, отправлено/применено/дубли/карантин, получено
  изменений, байты, ошибки, `correlationId`) и `sync_store_state` (последний успешный приём и
  выдача, последний контакт, глубина outbox и возраст старейшей неотправленной операции по
  данным точки, лаг ленты = голова `change_seq` − курсор точки, статус лицензии, версии,
  сдвиг часов, открытые конфликты, результат сверки остатков).
- `apps/admin` — экран «Синхронизация точек»: зелёный / жёлтый / красный по порогам (нет
  успешной синхронизации > 3 интервалов сети; > 7 дней — красный; есть карантин; есть открытые
  конфликты; версия ниже рекомендуемой; расхождение сверки; сдвиг часов > 5 мин), кнопка
  переприменения карантина. `apps/web` (владелец сети) — время последней синхронизации каждой
  офлайн-точки и очередь конфликтов цены. Точка — страница статуса: последний прогон, очередь,
  ошибки, статус лицензии, кнопка ручного запуска.
- Логи — встроенный Nest `Logger` с `correlationId` (`x-correlation-id` из операции проходит
  в inbox и в логи облака); тела операций, ключи и ПДн (поля рецепта ПКУ) в логи не пишутся.
  Внешняя система метрик и алертинга не выбрана — до её ADR статус строится запросами к этим
  таблицам. Здоровье секвенсора ленты (время последнего присвоения `change_seq`) — отдельный
  показатель: его остановка останавливает выдачу изменений всем точкам.
- Хранение: на точке отправленные строки outbox удаляются через 30 дней (данные остаются в
  доменных таблицах); в облаке ключи `sync_inbox` — бессрочно, сырые payload применённых
  операций — не менее срока поддержки старых версий протокола, с секционированием по месяцам
  (`schema-partitioning`); `sync_runs` — 1 год (предложение).

### Независимость от ADR-0006 и ADR-0008

Протокол задан JSON-контрактами (`libs/shared/dto`) и SQL-таблицами; от слоя данных требуется
только: явная tenant-транзакция на одном соединении, `INSERT … ON CONFLICT DO NOTHING
RETURNING`, `pg_advisory_xact_lock`, `FOR UPDATE SKIP LOCKED` и параметризованный raw SQL. Это
доступно в Kysely и TypeORM штатно, в Prisma и MikroORM — через raw-запросы внутри интерактивной
транзакции; выбор ORM меняет только реализацию репозиториев `sync`. Лицензионный ключ — отдельный
вид учётных данных, определённый здесь; от алгоритма хеширования паролей ADR-0008 он не зависит.

## Последствия

- Положительные:
  - инварианты «остаток = сумма движений», атомарность чека и append-only сохраняются на обеих
    сторонах без распределённых транзакций: один факт — одна транзакция здесь и там;
  - повтор, обрыв, двойной запуск (по расписанию и вручную) безопасны — дедупликация в БД;
  - конфликты сведены к двум, названным в глоссарии; остальное исключено разделением владельцев;
  - точки разных версий синхронизируются одновременно; схема БД точки может отставать;
  - никаких новых технологий, брокеров и открытых наружу портов БД; канал — тот же REST
    `/api/v1` за reverse proxy;
  - прозрачность для оператора: лаг, карантин, сверка остатков, версии — в админке.
- **Отрицательные (обязательно):**
  - большой объём собственного кода и тестов: ~15 типов операций, upcaster'ы/downcaster'ы с
    фикстурами, лента с секвенсором, снимки, карантин, два UI конфликтов; каждая новая доменная
    функция обязана определить своё поведение в синхронизации — риск забыть;
  - облако доверяет фактам точки: ошибка кода точки или правка её БД владельцем ПК попадает в
    облако как истина; защита — валидация, сверка остатков и аудит, но не переисполнение;
  - данные офлайн-точки в облаке отстают до интервала синхронизации (по умолчанию до 15 минут при наличии связи):
    отчёты владельца неполны, блокировка сотрудника, изменение прав и цен, отзыв ключа
    доходят до точки с той же задержкой — ТЗ «мгновенная блокировка» для офлайн-точки
    невыполнима;
  - обязательство поддерживать несколько версий протокола и дисциплина expand/contract в
    миграциях удорожают каждое изменение контрактов;
  - запрет складских операций по офлайн-точке из облака нужно соблюдать во всех путях записи
    облака (UI, API, импорт) — ещё одна проверка в guard'ах и ревью;
  - синхронное применение делает запрос приёма длинным (до нескольких секунд на батч); после
    недель офлайна — десятки батчей подряд; таймауты reverse proxy надо настроить под это;
  - секвенсор ленты — дополнительный фоновый процесс и единая точка задержки выдачи изменений;
  - `sync_inbox` с сырыми конвертами растёт соразмерно всем операциям точек — нужны
    секционирование и регламент архивации;
  - лицензионный ключ — bearer-секрет в env-файле на ПК аптеки: его кража позволяет
    отправлять операции от имени точки до отзыва; `occurredAt` — по часам ПК и ненадёжен;
  - при переходе точки в офлайн история её движений до переноса есть только в облаке (на
    точке — переносящие движения); отчёты точки за прошлые периоды — только в облаке.
- После перевода в `accepted` обновить (в этом ADR не редактируется):
  - `docs/architecture/c4/container.md` и `deployment.md`: эндпоинты `/api/v1/sync/*`,
    `sync_outbox` / `sync_inbox` / `sync_changes`, секвенсор ленты, ключ в env-файле точки,
    режим `offline-pending`, флеш-комплект с переносящими движениями; перерисовать PNG;
  - `docs/architecture/glossary.md`: операция синхронизации (sync operation), лента изменений
    (change feed), курсор, карантин (quarantine), сверка остатков (stock checkpoint),
    переносящее движение, режим точки `offline-pending`;
  - `docs/architecture/stack.md`, раздел 4, строка «Синхронизация офлайн-точек»: ссылка на
    этот ADR, JSON + gzip, батчи; `CLAUDE.md`: правило «складские операции офлайн-точки — только
    на точке; операция синхронизации пишется в outbox в транзакции факта»;
  - скилы: `postgres-best-practices` (`lock-skip-locked`, `data-idempotency-keys` — `payload_hash`,
    статусы inbox, карантин, секвенсор; `schema-primary-keys` — библиотека UUIDv7),
    `nestjs-api` (`nestjs-security-auth.md` — формат ключа и статусы лицензии;
    `nestjs-messaging-basics.md` — `sync.apply` выполняется в запросе, а не воркером;
    `nestjs-debugging-production.md` — запросы к `sync_store_state`; `nestjs-rate-limiting.md` —
    трекер по `keyId`);
  - `docker/`: compose-профиль офлайн-точки (без Redis, `STORE_MODE=offline`, `SYNC_BASE_URL`,
    ключ в env-файле) и пример `docker/env/*.env.example`; `libs/shared/dto` — контракты sync.

### Решено архитектором проекта 2026-09-30

1. Офлайн-точка может заводить товары и менять цены; конфликт цены решает владелец в облаке
   (очередь конфликтов), продажа по локальной цене — факт; дубль товара решает точка.
2. Интервал синхронизации — настройка сети (5 мин – 24 ч, по умолчанию 15 мин) + ручной запуск.
3. Точка без синхронизации не блокируется: через 7 дней — предупреждение на кассе, владельцу и
   оператору.
4. MVP: перемещения между офлайн- и облачными точками (через ленту и журнал, «в пути») и перевод
   точки **офлайн → облако** (финальная синхронизация, остатки становятся облачными, ПК выводится
   из работы). Перевод облако → офлайн — после MVP; новая офлайн-точка ставится с флеш-комплекта.
5. Складские документы офлайн-точки проводятся только на точке; в облаке её склад — просмотр и
   отчёты; входящее перемещение принимается на точке.
6. Учётные данные сотрудников точки — отдельные (ADR-0008); курсов валют нет (ADR-0016).
7. Значения по умолчанию (параметры, меняются без нового ADR): на точке хранится вся её история;
   окно ленты — 90 дней, старше — полный снимок (`resync-required`); после отзыва ключа облако
   принимает данные точки ещё 30 дней, новые продажи блокируются, как только отзыв дошёл до точки;
   облако поддерживает ≥ 2 предыдущие версии протокола; батч — ≤ 500 операций и ≤ 2 МБ.
8. Модель: 2б (точка — источник истины по своим остаткам; облако не переисполняет и не отвергает
   факты — карантин и сверка), 3б (применение в запросе), секвенсор ленты.

## Поправка 2026-10-02

Фиксирует решения, принятые архитектором при утверждении модели данных (2026-09-30 / 2026-10-01,
`docs/architecture/data-model/`). Принцип «один владелец данных» и протокол не меняются.

1. **Лента «облако → точка»** (п. 1, строка «Облако») дополнительно несёт: общие справочники
   `drug_reference` и `services` (ADR-0013 п. 6), `dictionary_values`, `payment_methods`,
   `legal_entities`, `categories`, `tenant_settings`.
2. **Долг поставщику по приходу офлайн-точки** заводит облако при применении `document.posted`
   (запись в `supplier_ledger_entries`); точка долги поставщикам не ведёт.
3. **Заказы поставщикам, оплаты поставщикам и заявки на перемещение** ведутся только в облаке;
   операций синхронизации для них нет.
4. **Отмена проведения** (`unpost`) на офлайн-точке запрещена: операции синхронизации для неё
   нет; правило режима поверх ролей (ADR-0018 п. 5). Пересмотр — отдельной поправкой, если
   заказчик потребует.
5. **`return.completed`** включает автоматическое списание просроченного возвращённого товара:
   движения списания входят в ту же операцию и ту же транзакцию, что и возврат.
