# Копии БД вне сервера: шифрование `age` и выгрузка `rclone`

- **Дата:** 2026-10-23
- **Статус:** утверждена архитектором 2026-10-23 вместе с поправкой ADR-0020 (O5) — APPROVAL.md
- **Основание:** ADR-0020, раздел «Копии вне хоста — вариант 1»; решение 7.1 ревью безопасности 2026-10-22 (пилот —
  это prod: копии вне хоста и их шифрование — до первых реальных данных). Локальные копии — ADR-0019 и спецификация
  `2026-10-21-db-backups-design.md` (B1–B16); эта спецификация их не меняет, а продолжает.

## 1. Цель и критерии успеха

Сейчас проверенная копия лежит только в `BACKUP_DIR` на том же VPS: потеря сервера или его захват уносит и базу, и все
копии. Нужно, чтобы:

1. каждая проверенная копия в течение часа оказывалась вне сервера — зашифрованной, в другом регионе;
2. тот, кто захватил сервер, не мог ни прочитать прежние внешние копии, ни удалить их раньше срока;
3. базу можно было поднять на новом сервере только из внешней копии и копии env-файла;
4. оператор видел состояние внешних копий там же, где локальных (`ps`, `backup-status`).

## 2. Решения автора (на утверждение вместе со спецификацией)

| № | Решение |
|---|---|
| O1 | **Что выгружается.** После каждой проверенной копии (B4) сервис `backup` собирает её каталог (`pharmacy.dump`, `globals.sql`, `manifest.json`) в один tar, шифрует `age` открытыми ключами получателей и выгружает `rclone` как `<среда>/<копия>.tar.age`. Непроверенные и неудавшиеся копии не выгружаются. |
| O2 | **Ключи шифрования.** На сервере — только открытые ключи (`BACKUP_AGE_RECIPIENTS`: архитектор и второй хранитель, ADR-0020). Закрытые ключи создаются `age-keygen` на машинах хранителей и на сервер не попадают; без них внешние копии не читает никто, в том числе захвативший сервер. Потеря обоих закрытых ключей делает внешние копии бесполезными (ADR-0020, «Ключи»). |
| O3 | **Хранилище.** Бакет Contabo Object Storage в регионе US Central (`usc1`) или Singapore (`sin1`) — не EU, где VPS. Регион выбирает архитектор при заказе; в бакете только шифротекст (вопрос юриста о данных за пределами РТ — тот же, что у VPS). |
| O4 | **Защита от удаления — Object Lock.** Бакет создаётся с Object Lock в режиме COMPLIANCE и сроком по умолчанию 30 дней (Contabo включает его только при создании бакета). Удалить или перезаписать копию раньше срока не может никто, в том числе владелец ключа. **Сервер ничего не удаляет во внешнем хранилище:** срок хранения отрабатывает правило бакета (lifecycle, истечение через 31 день). |
| O5 | **Ключ доступа к бакету.** У Contabo одна пара S3-ключей на аккаунт; ограничить ключ одним бакетом можно отдельным пользователем и политикой бакета через API Contabo. Если это удаётся при настройке — серверу выдаётся ключ пользователя с правом только записи и чтения списка в этом бакете. Если нет — на сервере ключ аккаунта, и от удаления защищает только O4. **Поправка ADR-0020**: «ключ только на этот бакет» становится «по возможности; защита от удаления — Object Lock». |
| O6 | **Настройка rclone — только переменными окружения** (`RCLONE_CONFIG_OFFSITE_*`: тип `s3`, провайдер `Ceph`, endpoint `https://usc1.contabostorage.com` или `sin1`, ключи, path-style), без файла `rclone.conf` на сервере. Включается переменной `BACKUP_OFFSITE_BUCKET`; без неё внешней выгрузки нет (как сейчас). |
| O7 | **Проверка выгрузки.** `rclone copyto` сверяет размер и контрольную сумму; затем `rclone lsjson` по объекту подтверждает размер. Только после этого копия считается выгруженной: рядом с её манифестом пишется `offsite.json` (время, объект, размер). |
| O8 | **Неудача выгрузки** не делает копию плохой: она проверена и лежит локально. Демон повторяет выгрузку раз в час для проверенных копий моложе срока хранения, ещё не выгруженных, начиная с самой свежей. |
| O9 | **Здоровье.** При включённой выгрузке `backup` становится unhealthy, если самая свежая выгруженная копия старше 26 ч (после первых 2 ч контейнера) — как для локальных (B8). В prod без настроенной выгрузки `backup` тоже unhealthy («нет копий вне хоста», решение 7.1); в test выгрузка необязательна. |
| O10 | **Состояние.** `backup-status` показывает у каждой копии, выгружена ли она, и самую свежую выгруженную. |
| O11 | **Восстановление из внешней копии** (потеря сервера). Новая команда `pharmacy-backup fetch <копия>`: скачивает объект, расшифровывает закрытым ключом, переданным **через stdin** (ключ не пишется на диск сервера), проверяет архив и кладёт каталог копии в `BACKUP_DIR`; дальше — обычный `restore <копия> --replace-database` (B9). `stack.mjs`: `offsite-fetch <копия> --identity <файл ключа>`. Без Node на VPS: `cat key.txt \| ssh deploy@<IP> "… exec -T backup pharmacy-backup fetch <копия>"` — руководство по выкладке. |
| O12 | **Учебное восстановление** раз в месяц: `offsite-fetch` самой свежей копии на стенде test (или prod в окно), затем `backup-verify <копия>` — восстановление во временный экземпляр. Делает хранитель ключа; это единственная проверка, что внешнюю копию реально можно открыть. *Уточнено при реализации: отдельная команда `verify-offsite <копия>` (`stack offsite-verify`) скачивает, расшифровывает и восстанавливает копию во временный экземпляр, ничего не оставляя на хосте, — на рабочем сервере копия с тем же именем обычно уже лежит, и `fetch` её бы не скачал.* |
| O13 | **Копия env-файла** (ключи JWT, pepper, пароли; ADR-0008, B10). Новая команда `npm run stack -- <env> env-push` на машине архитектора: шифрует env-файл теми же получателями и выгружает в `<среда>/env/<время>.env.age` того же бакета (тем же образом `pharmacy/postgres`, без новых инструментов на машине). Запускать после каждого изменения env-файла; Object Lock защищает и эти копии. |
| O14 | **Инструменты.** `age` и `rclone` — пакетами Alpine в образ `pharmacy/postgres` (ADR-0020), версия — из репозитория базового образа по digest. Обновляются вместе с образом. |
| O15 | **Сеть.** Контейнеру `backup` нужен исходящий HTTPS к endpoint хранилища; входящих портов нет. |
| O16 | **Тесты отложены до MVP** (решение 2026-10-05): без новых автотестов. Проверка — вживую: на временном стеке с удалённым хранилищем rclone типа `local` (каталог на хосте вместо S3 — весь путь шифрования, выгрузки, `fetch` и восстановления без облака), и один прогон на настоящем бакете, когда архитектор его создаст. |

## 3. Шаги выгрузки (`pharmacy-backup push`)

1. Взять блокировку копий (та же, что у `run`): выгрузка не идёт параллельно с копией.
2. Для проверенных копий моложе `BACKUP_RETENTION_DAYS` без `offsite.json`, от самой свежей:
   - `tar -C <копия> -cf - pharmacy.dump globals.sql manifest.json | age -r … -o /scratch/<копия>.tar.age`;
   - `rclone copyto /scratch/<копия>.tar.age offsite:<bucket>/<среда>/<копия>.tar.age`;
   - сверить размер (`rclone lsjson`), записать `offsite.json`, удалить файл в `/scratch`.
3. Ошибка — в лог (без ключей и без ответа хранилища целиком), копия остаётся невыгруженной до следующего часа.

`run` после успешной копии сразу вызывает выгрузку; демон вызывает `push` каждый час, если есть невыгруженные копии.

## 4. Конфигурация (env-файлы test и prod)

| Переменная | Значение |
|---|---|
| `BACKUP_OFFSITE_BUCKET` | имя бакета; пусто — выгрузки нет |
| `BACKUP_AGE_RECIPIENTS` | открытые ключи `age1…` через пробел |
| `RCLONE_CONFIG_OFFSITE_TYPE` | `s3` (в test для проверки — `local`) |
| `RCLONE_CONFIG_OFFSITE_PROVIDER` | `Ceph` |
| `RCLONE_CONFIG_OFFSITE_ENDPOINT` | `https://usc1.contabostorage.com` или `https://sin1.contabostorage.com` |
| `RCLONE_CONFIG_OFFSITE_ACCESS_KEY_ID`, `RCLONE_CONFIG_OFFSITE_SECRET_ACCESS_KEY` | ключи S3 (секрет) |
| `RCLONE_CONFIG_OFFSITE_FORCE_PATH_STYLE` | `true` |

`stack init` добавляет переменные с пустыми значениями; `stack build/up` в prod предупреждает, если выгрузка не
настроена (S2 не трогает пустые необязательные переменные).

## 5. Настройка бакета (один раз, архитектор)

1. В панели или API Contabo — Object Storage в выбранном регионе (O3).
2. Бакет с Object Lock (`--object-lock-enabled-for-bucket`), режим COMPLIANCE, срок по умолчанию 30 дней.
3. Правило lifecycle: истечение объектов через 31 день.
4. По возможности — отдельный пользователь с политикой бакета (O5).
5. Ключи `age-keygen` у двух хранителей; открытые — в env-файл prod; закрытые — в менеджер паролей хранителей, не в
   git и не в чаты.
6. `stack prod env-push`, затем первая копия и `offsite-fetch` + `backup-verify` на test (O12).

## 6. Вне объёма

- Шифрование локальных копий в `BACKUP_DIR` (они на диске сервера, как и сама база).
- Хранилище секретов (вопрос № 8 stack.md) — env-файл по-прежнему на хосте.
- Мониторинг и оповещения — по-прежнему ежедневный `ps` оператором.
- Копии офлайн-точек.
