# ADR-0015: Фронтенд-стек приложений web и admin (данные, формы, i18n, офлайн-буфер, маршрутизация)

- **Статус:** proposed
- **Дата:** 2026-09-29
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (черновик подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

`apps/web` (касса, склад, закупки, возвраты, отчёты, кабинет владельца) и `apps/admin` (оператор
платформы) — Next.js 16 (App Router, React 19, TypeScript strict) в режиме `output: 'export'`
(ADR-0004, `apps/web/next.config.js`): в проде нет серверного рантайма Next.js, статику отдаёт
reverse proxy (c4/deployment.md; конфигурация — ADR-0012, в работе), данные идут только через REST
`apps/api` `/api/v1/…` с одного origin. Сессия — HttpOnly-cookie, CSRF-защита требует тела
`application/json` и `Origin`/`Sec-Fetch-Site` своего origin (ADR-0008, proposed). Контракты API —
`libs/shared/dto` (class-validator); фронтенд импортирует их только через `import type`, иначе
декораторы и `class-validator` попадают в клиентский бандл.

Требования, которые определяют выбор: касса — POS на слабых ПК (Chrome/Edge, две последние версии),
сенсорные экраны от 10″, сканер штрих-кода USB HID (клавиатурный ввод), печать чеков 58/80 мм через
печать браузера; операция кассы ≤ 1 сек, из них клиенту отведено ≤ 150 мс, скан → строка чека
≤ 100 мс, first-load JS кассы ≤ 250 КБ gzip (ADR-0009, proposed). Облачная точка переживает перебои
связи за счёт буфера — очереди операций в браузере с идемпотентной досылкой (c4/container.md, ТЗ
«Административный продукт» п. 4.5). Офлайн-точка (волна 3) открывает ту же сборку `apps/web` через
`localhost` к локальному API в Docker. Локализация RU/TJ, деньги — integer-дирамы, форматтеры — в
`libs/shared/util`. Действуют правила ADR-0011: данные тенантов не уходят во внешние SaaS, закрытый
список интеграций, никакой самописной криптографии. Масштаб: 3 тенанта, ~30 точек, до 50 кассиров
(запас ×5); волна 1 — до конца 2026 года (≈ 3 месяца), команда небольшая.

Сейчас в `apps/web`/`apps/admin` только каркас генератора Nx, а скилы (`web-performance-optimization`,
`ui-standards-tokens`) помечают «только после ADR» обёртки IndexedDB, библиотеки состояния и кэша,
i18n и Service Worker. Этот ADR закрывает эти пометки одним решением по семи осям. Не входит сюда:
CSS и UI-кит (ADR-0007, proposed), e2e и бюджеты (ADR-0009, proposed), конфигурация proxy (ADR-0012,
в работе), выбор ORM (ADR-0006, proposed) — решение от ORM не зависит, потому что фронтенд видит
только `libs/shared/dto`.

## Рассмотренные варианты

Версии, лицензии и даты релизов проверены 2026-09-29 по npm-реестру; размеры (gzip) — по
bundlephobia для указанной версии, это размер всего пакета без tree-shaking, реальный вклад в
бандл меньше и подтверждается замером (ADR-0009, ось З). Где размер не удалось подтвердить, цифра
не приводится. Поведение Next.js проверено по документации 16.3.6 (в репозитории сейчас `next ~16.1.6`).

### Ось 1. Маршрутизация в static export

Факты Next.js 16: в `output: 'export'` не поддерживаются динамические сегменты с
`dynamicParams: true` и динамические сегменты без `generateStaticParams()` — HTML создаётся только
для перечисленных на сборке значений. Пустой массив из `generateStaticParams` в режиме export
приводит к ошибке сборки «missing generateStaticParams()» (vercel/next.js #71862, закрыт как дубль
#61213; поведение в 16.x проверить на scaffold). Rewrites, redirects, headers и proxy (middleware)
в export не работают — это задача reverse proxy. `useSearchParams` в пререндеренной странице
обязан стоять внутри `<Suspense>`, иначе production-сборка падает (missing-suspense-with-csr-bailout).
Документация предлагает раздавать `out/` по правилу `try_files $uri $uri.html $uri/ =404` и
`error_page 404 /404.html`.

1. **Статические маршруты + идентификатор в query (`/receipts/view?id=…`, `/stock?storeId=…&offset=…`).**
   Каждый экран — статическая папка `app/`, один HTML-файл на экран; сущность и фильтры — в
   query-параметрах, которые читает клиентский компонент через `useSearchParams` внутри
   `<Suspense>`. Плюсы: работает в export без обходных путей; proxy нужен только стандартный
   `try_files` без правил на каждый маршрут; `next/link`, prefetch и code splitting по маршрутам
   сохраняются; deep link и F5 работают; Service Worker кэширует конечный список HTML-файлов.
   Минусы: URL менее «красивые»; дисциплина — обёртка `Suspense` у каждого экрана с query
   (иначе ломается сборка), типизированные построители ссылок вместо строк.
2. **Динамический сегмент с заглушкой** (`generateStaticParams → [{ id: '_' }]` + rewrite в proxy
   `/receipts/* → /receipts/_.html`, id берётся из `location`). Плюсы: «красивые» URL. Минусы:
   клиентская навигация `Link` на `/receipts/123` запрашивает RSC-payload несуществующего файла и
   откатывается на полную перезагрузку; параметры из пререндера (`'_'`) расходятся с URL; правило
   proxy на каждый динамический маршрут связывает ADR-0012 с деревом `app/`; Service Worker должен
   повторять те же rewrites. Хрупко.
3. **Catch-all `[[...slug]]` с собственным разбором пути на клиенте.** Одна оболочка на всё
   приложение, proxy отдаёт её на любой путь. Минусы: теряется code splitting и prefetch Next.js
   по маршрутам — весь роутинг и ленивые чанки пишем сами; first-load кассы растёт; по сути свой
   роутер внутри Next.js.
4. **Hash-роутинг (`/#/receipts/123`).** Плюсы: proxy не нужен вовсе. Минусы: вне роутера
   Next.js (`Link`, `usePathname` не работают с hash), свой роутер, неестественные URL и история.
5. **Отдельный клиентский роутер (React Router, TanStack Router) внутри catch-all.** Минусы: два
   роутера и два набора соглашений в одном приложении; если нужен собственный роутер, честнее
   пересмотреть ADR-0004 (React + Vite), а не прятать его внутри Next.js.

### Ось 2. Данные с сервера, кэш и клиент API

**2а. Кэш серверных данных**

1. **TanStack Query v5** (`@tanstack/react-query` 5.104.0, MIT, ≈ 13,8 КБ gzip; релизы
   еженедельно, последний — 2026-09-26). Плюсы: кэш, дедупликация, отмена (`AbortSignal`),
   повторы, инвалидация после мутаций, `placeholderData` для пагинации, `networkMode` и
   `onlineManager` — можно подключить собственный детектор связи вместо ненадёжного
   `navigator.onLine`; devtools по умолчанию попадают только в development-сборку; документация
   Next.js прямо называет SWR и TanStack Query для клиентского фетчинга. Минусы: новая зависимость
   и понятия (query keys, staleTime), которые команде нужно освоить; соблазн хранить в кэше
   Query то, что должно жить в буфере кассы (см. ось 6).
2. **SWR** (`swr` 2.5.1, MIT, Vercel). Плюсы: проще и легче, пример в документации static export.
   Минусы: слабее мутации и инвалидация по ключам, нет `networkMode`; для десятков экранов склада
   с формами и списками придётся дописывать то, что в TanStack Query есть.
3. **RTK Query** (`@reduxjs/toolkit` 2.13.0, MIT). Плюсы: генерация эндпоинтов, строгая модель.
   Минусы: тянет Redux и store как центр приложения — оправдано, только если Redux выбран и для
   клиентского состояния (ось 3), а он не выбран.
4. **Свой fetch-слой без кэша** (`useEffect` + `AbortController`). Плюсы: ноль зависимостей.
   Минусы: дедупликацию, гонки ответов, повторы, инвалидацию и состояние загрузки для каждого
   экрана пишем сами — на объёме склада и отчётов это недели работы и источник дефектов.

**2б. Типизированный клиент API**

5. **Ручной тонкий клиент на `fetch` поверх типов `libs/shared/dto`.** В `libs/shared/dto` — только
   типы и константы: карта маршрутов `ApiRoutes` (`'POST /receipts': { body: CreateReceiptDto;
   response: ReceiptDto }`), без декораторов в рантайме фронтенда; клиент — одна функция
   `apiRequest` в `apps/*/src/app/api` (или общей `libs/web/api-client`): correlation ID,
   `Idempotency-Key`, `application/json`, разбор problem+json, таймаут. Плюсы: без кодогенерации и
   OpenAPI; в монорепо изменение DTO сразу ломает компиляцию фронтенда; axios не нужен (нативный
   `fetch`). Минусы: соответствие пути и метода контроллеру не проверяется компилятором — нужен
   тест соответствия (маршруты Nest ↔ ключи `ApiRoutes`); карту маршрутов поддерживаем руками.
6. **OpenAPI из NestJS (`@nestjs/swagger` 12.0.2, MIT, CLI-плагин с `classValidatorShim`) +
   генерация типов (`openapi-typescript` 7.13.0 + `openapi-fetch` 0.17.0, MIT, ≈ 2,9 КБ gzip) или
   клиента с хуками (`orval` 8.38.0, `@hey-api/openapi-ts` 0.99.0, MIT).** Плюсы: схема — источник
   правды о путях, методах и кодах ответа; документация API; готовые хуки TanStack Query (orval).
   Минусы: CLI-плагин по умолчанию обрабатывает только файлы `*.dto.ts`/`*.entity.ts` компилируемой
   программы — работу с DTO из `libs/shared/dto` при сборке Nx (webpack/ts-loader через
   `getCustomTransformers`) нужно проверить; сейчас скил `nestjs-api` держит Swagger опциональным и
   вне production; появляется шаг генерации, артефакт, который надо держать в синхроне, и дублирование
   с уже общими TS-типами; при `@hey-api/openapi-ts` 0.x API генератора ещё меняется.

### Ось 3. Клиентское состояние (чек кассы, смена, выбранная точка)

Под «клиентским» понимается состояние, которого нет на сервере или которое ещё не отправлено:
черновик чека, активная PIN-сессия и смена на терминале, выбранная точка владельца, режим связи.

1. **Zustand v5** (`zustand` 5.0.15, MIT; релиз 2026-08-13). Плюсы: store вне дерева React —
   обработчик сканера и отправитель буфера меняют чек через `getState()` без хуков и без рендера
   всего экрана; селекторы подписывают компонент только на нужный срез (требование скила
   `web-performance-optimization`: не один большой Context); простой API. Минусы: ещё одна
   зависимость; без правил легко превратить в «глобальную свалку» и продублировать серверные данные.
2. **Jotai** (`jotai` 3.0.0, MIT; мажорный релиз 2026-09-08). Плюсы: атомарные подписки, мелкие
   обновления. Минусы: атомная модель хуже ложится на агрегат «чек» с инвариантами (строки, скидка,
   оплаты, итог в дирамах); 3.0 вышла три недели назад — риск миграций и сырых мест на старте.
3. **Redux Toolkit.** Плюсы: зрелые инструменты, devtools, строгие редьюсеры. Минусы: больше кода
   и веса ради трёх–четырёх срезов состояния; оправдан только в связке с RTK Query.
4. **Только React (`useReducer` + Context, либо свой store на `useSyncExternalStore`).** Плюсы:
   ноль зависимостей; редьюсер чека — чистая функция, тестируется в Jest. Минусы: Context
   перерисовывает всех потребителей при каждом изменении (скан — это изменение); свой
   `useSyncExternalStore`-store — это самописный Zustand, который придётся поддерживать.

### Ось 4. Формы и валидация

Правила валидации уже живут на сервере в DTO `libs/shared/dto` (class-validator) и остаются
источником правды: сервер отвечает 400 problem+json с `errors[]`. Клиентская валидация нужна для
UX (подсказка до отправки), а не для безопасности.

1. **React Hook Form + zod 4** (`react-hook-form` 7.89.0, `@hookform/resolvers` 5.9.1, `zod` 4.6.5 —
   все MIT, активные релизы в сентябре 2026). Плюсы: неконтролируемые поля — мало рендеров на
   слабом POS; zod 4 и valibot реализуют Standard Schema, resolver один; по документации zod
   вклад в бандл — ≈ 5,9–13 КБ gzip для типичных схем, `zod/mini` — ≈ 2–4 КБ; схемы дают типы.
   Минусы: правила дублируются с DTO (длина, диапазоны, обязательность) и могут разойтись.
2. **React Hook Form + valibot** (`valibot` 1.5.0, MIT, ≈ 14,7 КБ gzip весь пакет, модульный —
   в бандл попадают только использованные функции). Плюсы: меньше вес. Минусы: менее привычный
   функциональный API, меньше готовых ответов; выигрыш над `zod/mini` небольшой.
3. **React Hook Form + class-validator на клиенте (`classValidatorResolver`).** Плюсы: одни
   правила для сервера и клиента. Минусы: требует импорта DTO-классов значениями — ломает правило
   `import type` и тянет в бандл `class-validator` (с `validator.js`) и `reflect-metadata`, т.е.
   бьёт ровно по бюджету first-load кассы; сообщения об ошибках — английские, их всё равно
   переводить.
4. **Нативные формы + свой хук валидации.** Плюсы: без зависимостей. Минусы: десятки форм склада,
   закупок, ролей «модуль × действие × охват точек», мастера админки — массивы полей, зависимые
   поля и ошибки сервера придётся писать самим.
5. **zod на обеих сторонах (DTO в zod, `nestjs-zod` на сервере) — одна схема.** Отклонено в этом
   ADR: меняет зафиксированную конвенцию бэкенда (CLAUDE.md, скил `nestjs-api`: DTO на
   class-validator) — это отдельное решение для `apps/api`, а не фронтенд-стека.

### Ось 5. i18n RU/TJ в static export

1. **next-intl с маршрутизацией по локали** (`next-intl` 4.14.8, MIT, активная разработка).
   По документации без middleware (static export) обязателен префикс локали в URL (`/ru/…`,
   `/tg/…`), нельзя согласовать локаль на сервере, нельзя использовать `pathnames`, нужен
   корневой редирект на локаль по умолчанию. Плюсы: зрелая библиотека, ICU-сообщения, типизация
   ключей. Минусы: каждый экран собирается дважды, локаль живёт в URL (смена языка кассиром —
   навигация на другой HTML), удваивается список файлов для proxy и Service Worker; режим
   «без i18n routing» из документации читает локаль в `i18n/request.ts` через `cookies()` —
   это серверный рантайм, в export недоступен.
2. **use-intl — ядро next-intl, только на клиенте** (`use-intl` 4.14.8, MIT, тот же мейнтейнер
   и релизный цикл). `IntlProvider` в клиентском корневом провайдере, локаль — из настройки
   сотрудника/терминала (API) с запасным значением в `localStorage`, словари грузятся динамическим
   `import()` только для активной локали. Плюсы: те же `useTranslations`, ICU-синтаксис
   (plural/select) и типизация ключей, что у next-intl, но без префиксов URL; путь к next-intl
   открыт, если когда-нибудь появится серверный рантайм. Минусы: при пререндере в HTML попадают
   строки локали по умолчанию (или скелет) — первая отрисовка до загрузки словаря требует
   заглушки; меньше примеров «use-intl без Next.js», чем для next-intl.
3. **i18next + react-i18next** (`i18next` 26.4.2 ≈ 13,7 КБ gzip, `react-i18next` 17.0.15
   ≈ 10,2 КБ gzip, MIT). Плюсы: самая большая экосистема, загрузка неймспейсов. Минусы: самый
   тяжёлый вариант; собственный формат интерполяции и плюралов (ICU — через дополнительный плагин);
   много необязательных плагинов (детекторы, бэкенды), каждый — ещё зависимость.
4. **Lingui** (`@lingui/core`/`@lingui/react` 6.8.0, MIT). Плюсы: компиляция сообщений на сборке,
   маленький рантайм, извлечение строк CLI. Минусы: макросы требуют SWC/Babel-плагина компиляции —
   совместимость плагина с версией SWC внутри Next.js ломается при обновлениях Next (а Next.js и
   так «ломающе быстрый», ADR-0004); ещё один шаг сборки.
5. **FormatJS / react-intl** (`react-intl` 12.1.3, BSD-3-Clause). Плюсы: эталонный ICU. Минусы:
   тяжелее use-intl; для компактности нужна прекомпиляция сообщений отдельным CLI.
6. **Свой словарь ключей в `libs/shared/util`** (текущая временная норма скила
   `ui-localization-formatting`). Плюсы: ноль зависимостей. Минусы: плюралы (в русском три
   формы), подстановки, типизация ключей и загрузка по локали пишутся самими; поддержка `tg` в
   `Intl.PluralRules` браузера не гарантирована и требует проверки.

Форматирование денег, дат, количеств — по любой оси **не** через i18n-библиотеку, а через
собственные утилиты `libs/shared/util` (`formatMoney`, `parseMoneyToMinor`, `formatDateOnly`,
`formatDateTime` с `Asia/Dushanbe`): одинаково на экране и в печати чека, integer-дирамы без float,
группировка через `Intl.NumberFormat('ru-RU')`, потому что ICU браузера для `tg` не гарантирован.

### Ось 6. Офлайн-буфер кассы

**6а. Доступ к IndexedDB**

1. **`idb`** (8.0.3, ISC, ≈ 1,4 КБ gzip; автор — Jake Archibald; последний релиз 2025-05-07 —
   стабильная, редко меняющаяся обёртка). Плюсы: промисы вместо событий, типизированная схема
   хранилищ (`DBSchema`), явные транзакции, минимальный вес; модель и ограничения — ровно
   нативного IndexedDB. Минусы: низкая активность проекта; ловушки транзакций IndexedDB остаются
   (нельзя ждать не-IDB промисы внутри транзакции — она автоматически закроется).
2. **Dexie 4** (`dexie` 4.4.6, Apache-2.0, ≈ 31,1 КБ gzip, активная разработка). Плюсы: запросы
   по индексам, `liveQuery` (реактивные выборки), миграции схемы, хорошая документация. Минусы:
   в ≈ 20 раз тяжелее `idb` на маршруте кассы; облачная синхронизация Dexie Cloud — внешний SaaS
   для данных тенантов, запрещён ADR-0011 (правило 3), нужна договорённость не подключать её.
3. **localForage** (1.10.0, Apache-2.0; последний релиз 2021-08-18). Только ключ–значение, без
   индексов и транзакций на несколько хранилищ; проект фактически не развивается. Отклонён.
4. **Нативный IndexedDB API** (текущая норма скила). Плюсы: ноль зависимостей. Минусы:
   событийный API, многословный и ошибкоопасный в самом критичном для денег коде; `idb` — это
   ≈ 1,4 КБ, снимающие этот риск.

**6б. Service Worker (оболочка приложения при перебое)**

Без Service Worker уже открытая касса переживает перебой, пока вкладку не перезагрузили. Но
перезагрузка страницы, перезапуск ПК или обновление Windows во время перебоя — и приложение не
откроется, продажи встанут; ленивые чанки маршрутов, которые ещё не загружались, тоже недоступны.

5. **Без Service Worker.** Плюсы: нет риска «застрявших» старых версий. Минусы: буфер защищает
   только от перебоя без перезагрузки; требует предзагрузки всех чанков кассы при старте смены.
6. **Свой минимальный Service Worker без зависимостей** (≈ 100–150 строк) + скрипт после
   `next build`, строящий манифест файлов `out/` с хешами. Стратегии: precache оболочки
   `apps/web` (HTML экранов кассы, `/_next/static/*`, шрифты, словари), cache-first для
   хешированных ассетов, network-first с откатом на кэш для навигаций, очистка старых кэшей при
   `activate`; `/api/*` не кэшируется никогда. Плюсы: не зависит от сборщика Next.js
   (Turbopack/webpack) — работает с уже готовым `out/`; поведение полностью наше и проверяется
   Playwright (`context.setOffline`). Минусы: свой код в самом опасном месте (ошибка SW может
   «закрепить» сломанную версию у всех касс) — нужен kill-switch и строгий порядок обновления.
7. **Serwist** (`serwist`, `@serwist/build`/`@serwist/cli` 9.5.12, MIT; форк Workbox, активен) или
   **Workbox** (`workbox-build` 7.4.1, MIT). Плюсы: проверенные стратегии, генерация манифеста
   (`injectManifest` по каталогу `out/`). Минусы: интеграция `@serwist/next` для Turbopack строится
   на route handler `app/serwist/[path]/route.ts` — совместимость с `output: 'export'` в
   документации не подтверждена; для наших 4–5 правил кэширования библиотека избыточна.

**6в. Идемпотентная досылка и конфликты**

Ключ операции генерируется на клиенте в момент её создания и передаётся в `Idempotency-Key` при
каждой попытке; сервер дедуплицирует через `UNIQUE (tenant_id, idempotency_key)` и возвращает
исходный результат, другой payload с тем же ключом — 409 (скилы `nestjs-api`,
`postgres-best-practices/data-idempotency-keys`). Для генерации UUIDv7: `crypto.randomUUID()`
выдаёт только v4, поэтому варианты:

8. **`uuid`** (14.0.2, MIT, ≈ 3,8 КБ gzip весь пакет; только ESM; активен) — `v7()` по RFC 9562;
   та же функция в `libs/shared/util` для `apps/api` (правило `schema-primary-keys`: UUIDv7
   генерирует приложение). Минус: ESM-only — для Jest нужен `transformIgnorePatterns`.
9. **Своя реализация UUIDv7 на `crypto.getRandomValues`.** Отклонена: ошибки в монотонности и
   битах версии/варианта в ключе денежных операций дороже 4 КБ; дух правила «не писать самим то,
   что есть в проверенной библиотеке».

Способ отправки:

10. **«Сначала буфер» (outbox-first) — каждая буферизуемая операция сначала записывается в
    IndexedDB, затем сразу отправляется.** Один путь кода для онлайна и перебоя, обрыв «после
    COMMIT, но до ответа» обрабатывается так же, как отсутствие связи. Минус: запись в IndexedDB
    (единицы–десятки мс) входит в клиентский бюджет 150 мс.
11. **Прямой запрос, в буфер — только при ошибке сети.** Минус: два пути кода, потеря операции,
    если вкладка закрылась между ошибкой и записью; неоднозначность «дошёл ли чек».
12. **Paused mutations TanStack Query + persister.** Минус: сериализация мутаций требует
    `setMutationDefaults` на каждый тип, хранилище и порядок — чёрный ящик библиотеки в денежном
    коде; нет явного карантина и порядка FIFO.

### Ось 7. Сканер штрих-кода

1. **Собственный обработчик клавиатурного потока** (набросок `useBarcodeScanner` уже в скиле
   `web-performance-optimization`): буфер в `ref`, порог интервала между символами, минимальная
   длина, суффикс Enter, ноль `setState` на символ. Плюсы: ≈ 50–100 строк, полный контроль, нет
   зависимостей. Минусы: краевые случаи — наши (раскладка, фокус в поле, медленный ПК).
2. **Библиотеки: `onscan.js`** (1.5.2, MIT, последний релиз 2020-05), **`use-scan-detection`**
   (0.2.3, MIT, 2023), **`@point-of-sale/keyboard-barcode-scanner`** (1.1.4, MIT, 2025-06).
   Плюсы: готовая эвристика. Минусы: первые две не развиваются; все решают ту же задачу на
   50–100 строк и всё равно требуют настройки под наши сканеры и раскладки.
3. **WebHID/Web Serial (сканер не как клавиатура).** Плюсы: нет путаницы с ручным вводом, можно
   передать GS1-разделители. Минусы: разрешение браузера на каждом ПК, сканер надо переводить в
   HID-POS/COM-режим, поддержка — только Chromium; для EAN-13 в MVP не нужно.

## Решение

Выбираем минимальный набор библиотек, где своя реализация была бы дороже и опаснее, и
собственный код там, где задача укладывается в десятки строк.

React Hook Form и полный `zod` загружаются в чанках экранов склада, закупок и админки.

**Правила применения.**

- **Маршрутизация и proxy (требования к ADR-0012).** `trailingSlash: false` (по умолчанию),
  раздача `out/` как есть, включая RSC-payload-файлы (`*.txt`) для prefetch; правило
  «путь → путь.html → 404.html» (синтаксис — по серверу, выбранному в ADR-0012; черновик ADR-0012
  уже предусматривает это и отказ от SPA-fallback на `index.html`); HTML, `*.txt` и `sw.js` —
  `Cache-Control: no-cache`, `/_next/static/*` — `immutable`; `/api` — на тот же origin (ADR-0008).
  Admin — отдельный поддомен, та же схема без SW.
- **Клиент API.** Все запросы — через `apiRequest`: `credentials: 'same-origin'`, тело только
  `application/json`, `X-Correlation-Id` на каждый запрос (скил `react-dev`), `Idempotency-Key` —
  для финансовых операций, таймаут `AbortSignal.timeout`, разбор problem+json в типизированный
  `ApiError { status, code, correlationId, errors[] }`; 401 — глобальный переход на вход/PIN.
  ПДн и тела ответов не логируются в консоль. Импорт из `libs/shared/dto` во фронтендах — только
  `import type` (правило ESLint `@typescript-eslint/no-restricted-imports` с `allowTypeImports: true`
  для `@pharmacy/shared-dto` и полный запрет `class-validator`/`class-transformer` в `apps/web`,
  `apps/admin`, `libs/ui`).
- **Состояние.** В Zustand не копируются серверные списки; черновик чека сохраняется в IndexedDB
  (переживает F5); редьюсер чека (строки, скидка, оплаты, итог в дирамах) — чистые функции в
  `apps/web/src/features/pos` с порогом покрытия ADR-0009 для буфера и мапперов.
- **Формы.** Сообщения ошибок zod — ключи i18n, не английские тексты; для каждой пары
  «DTO ↔ схема формы» — общий набор допустимых/недопустимых примеров, который прогоняется и через
  `class-validator` (в тесте `libs/shared/dto`), и через zod (в тесте фронтенда): расхождение
  правил ловится тестом, а не в проде.
- **i18n.** Ключи — английские идентификаторы, словари `messages/ru.json`, `messages/tg.json` в
  `libs/shared/util` (или `libs/web/i18n`), типизация через объявление `Messages`; строки
  примитивов UI-кита (ADR-0007) — тоже из словарей; нормализация `NFC` перед поиском и печатью.
- **Буфер кассы.**
  - Что буферизуется в MVP: продажа (чек и его оплаты) и кассовые операции смены (открытие,
    внесение/изъятие, закрытие) — в одной очереди, чтобы сохранить порядок. Склад, закупки,
    возвраты, отчёты при отсутствии связи недоступны (явное сообщение в UI).
  - Локальный снимок каталога и цен точки (версия + дельты от API) — в IndexedDB и в памяти как
    `Map<barcode, product>`; поиск и скан работают по нему и при перебое.
  - Операция получает UUIDv7 при нажатии «Оплатить», записывается в хранилище `outbox` одной
    транзакцией вместе с изменением черновика, затем отправляется. Отправитель один на терминал
    (`navigator.locks`), операции уходят строго по одной в порядке FIFO; повтор при сетевой ошибке,
    таймауте и 5xx — экспоненциальная задержка с джиттером (до 60 с), чтобы 30 точек после
    восстановления облака не пришли одновременно.
  - Ответы: 2xx (в том числе повтор, вернувший исходный результат) — операция доставлена,
    удаляется из `outbox`; 401/403 — очередь на паузе до восстановления сессии, данные не
    теряются; 409 (ключ с другим payload) и 400/422 — **карантин**: операция не удаляется, ключ не
    перегенерируется автоматически, заведующий видит список «требует разбора»; ни одна операция не
    удаляется молча.
  - Бизнес-конфликты после восстановления связи (партия закончилась, цена или скидочное правило
    изменились, товар заблокирован) решаются **сервером** по правилу «продажа, совершённая
    физически, — факт»: чек принимается с ценой из снимка (`priceListVersion` в payload) и
    пометкой расхождения для заведующего; отклонение (422) — только для нарушений, которые нельзя
    принять задним числом. Точная политика — в модуле `pos`/`sync` API (скил `nestjs-api`),
    клиент лишь показывает статус.
  - Буфер браузера облачной точки и протокол синхронизации офлайн-точки (ADR-0014, proposed) —
    разные каналы, но одни принципы: `operationId` (UUIDv7 из `uuid`) как ключ идемпотентности,
    карантин вместо удаления, совместимые статусы результата (доставлено / дубль / карантин /
    отклонено); если ADR-0014 будет принят с другими названиями, буфер берёт их.
  - Операция несёт `tenantId`, `storeId`, `terminalId`, `employeeId`, `occurredAt` (часы ПК) —
    сервер хранит и `receivedAt`; имя базы IndexedDB включает тенант и точку терминала, чтобы
    буфер одной точки не был отправлен в другую.
  - Счётчик неотправленных операций виден кассиру всегда; выход из системы, закрытие смены и
    отвязка терминала при непустом буфере — только с предупреждением. Вызывается
    `navigator.storage.persist()`, чтобы браузер не вытеснил данные при нехватке места.
- **Service Worker.** Регистрируется только в облачной сборке `apps/web` (флаг времени выполнения —
  по ответу API о типе развёртывания; офлайн-точке SW не нужен — API на `localhost`). Новая версия
  активируется только когда чек пуст (или при старте смены) — никогда посреди продажи. Kill-switch:
  выкладка «пустого» `sw.js`, который удаляет кэши и снимает регистрацию. Офлайн-сценарии
  (перебой, F5 при перебое, обновление версии) — обязательные e2e Playwright (ADR-0009, ось Д).
- **Сканер.** Буфер по `event.code` (`Digit0`…`Digit9`, `KeyA`…), а не `event.key`: при русской или
  таджикской раскладке сканер в режиме клавиатуры выдаёт кириллицу вместо латиницы Code128;
  порог интервала и минимальная длина — настройки терминала (на слабом ПК события приходят
  пачками); сканер настраивается с суффиксом Enter; скан при фокусе в поле поиска распознаётся
  тем же обработчиком и не попадает в текст поля; метки `pos:scan` → `pos:scan-to-line` (ADR-0009).

**Контракт API (OpenAPI) предлагается решать отдельным ADR** «Контракт REST API и документация»:
он затрагивает `apps/api` (Swagger в production или нет, CLI-плагин и `libs/shared/dto`, версия
контракта для офлайн-точек старых версий — c4/deployment.md, «облако принимает синхронизацию от
старых версий»), а не только фронтенд. Триггеры: первый внешний потребитель API, расхождения карты
маршрутов, которые не ловит тест соответствия, или решение отдавать документацию тенантам. Ручной
клиент этого ADR спроектирован так, что его сигнатура `apiRequest(route, params)` заменяется на
`openapi-fetch` без правок экранов.

Согласуемые этим ADR зависимости (версии фиксируются в корневом `package.json`, single-version
policy Nx; ни одна не делает сетевых вызовов, кроме запросов к собственному `apps/api`):
`@tanstack/react-query`, `zustand`, `react-hook-form`, `@hookform/resolvers`, `zod`, `use-intl`,
`idb`, `uuid` — runtime; `@tanstack/react-query-devtools`, `fake-indexeddb` — dev. `stack.md` не
меняется: это библиотеки внутри слоя «Frontend: Next.js» (как в ADR-0007).

## Последствия

- Положительные:
  - маршрутизация не требует ни обходных путей Next.js, ни правил proxy на каждый экран; один
    и тот же набор HTML-файлов работает в облаке, на офлайн-точке и в кэше Service Worker;
  - касса продолжает продавать при перебое связи, в том числе после перезагрузки страницы или ПК;
    дубли чеков исключены на уровне БД, операция никогда не теряется молча (карантин вместо
    удаления), порядок операций смены сохраняется;
  - вес на маршруте кассы минимален: из новых библиотек там только TanStack Query, Zustand, `idb`,
    `uuid`, use-intl — все MIT/ISC, с понятной активностью; формы и полный zod — в чанках других
    экранов;
  - типы API — общие с бэкендом без кодогенерации; изменение DTO ломает компиляцию фронтенда в
    том же MR (единый репозиторий, ADR-0010);
  - все пометки «только после ADR» в скилах по данным, состоянию, i18n, IndexedDB и Service Worker
    закрываются одним решением;
  - решение не зависит от ORM (ADR-0006) и CSS-подхода (ADR-0007): фронтенд видит только
    `libs/shared/dto` и компоненты `libs/ui`.
- **Отрицательные (обязательно):**
  - восемь новых runtime-пакетов и два dev-пакета — supply-chain-поверхность и обновления,
    которые надо отслеживать; TanStack Query и zod выпускают релизы часто;
  - URL вида `/receipts/view?id=…` вместо `/receipts/123`; каждый экран с query обязан иметь
    `<Suspense>`-обёртку — забытая обёртка ломает production-сборку (зато не прод);
  - ручная карта маршрутов `ApiRoutes` — поддерживается руками; без теста соответствия путь и
    метод могут разойтись с контроллером; документации API для внешних потребителей нет до
    отдельного ADR;
  - правила валидации дублируются в DTO (class-validator) и схемах zod; тест-«двойник» снижает,
    но не исключает расхождения; поддерживать его — дополнительная работа;
  - use-intl без Next.js-интеграции: при пререндере в HTML нет строк активной локали, до загрузки
    словаря показывается скелет; меньше готовых примеров;
  - свой Service Worker — самый рискованный код решения: ошибка может закрепить сломанную версию
    на всех кассах; нужны kill-switch, дисциплина версий и обязательные офлайн-e2e; кэшированная
    старая версия может несколько часов работать с новым API — API обязан быть обратно
    совместимым минимум на одну версию фронтенда;
  - буфер живёт в профиле браузера: очистка данных сайта, смена профиля или сбой диска удаляют
    неотправленные операции (как и device-cookie терминала, ADR-0008); `storage.persist()` в Chrome
    выдаётся по эвристикам и не гарантирован; браузеры касс нужно настраивать;
  - продажа при перебое опирается на снимок каталога, цен и остатков — возможны продажи сверх
    фактического остатка и по устаревшей цене; разбор расхождений ложится на заведующего и
    требует доработки API (флаги расхождений, список «требует разбора»);
  - outbox-first добавляет запись в IndexedDB в критический путь каждого чека (в пределах
    клиентского бюджета 150 мс ADR-0009, но на слабом ПК это надо замерить);
  - часы POS-ПК могут быть неверны — `occurredAt` операций из буфера нельзя считать доверенным;
  - `uuid` 14 — только ESM: конфигурация Jest (`transformIgnorePatterns`) в `apps/web` и `apps/api`;
  - собственный обработчик сканера требует настройки под конкретные модели сканеров и ручной
    проверки на эталонном POS-ПК; 2D-коды с GS1-разделителями через режим клавиатуры надёжно не
    передаются — при появлении маркировки понадобится отдельный ADR (WebHID/Serial).
- **Что обсудить с архитектором и заказчиком до `accepted`:**
  - досылка после истечения PIN-сессии: под чьей сессией уходят операции прежнего кассира
    (предложение: device-cookie терминала + любая активная сессия этой точки, сервер проверяет
    права автора операции на момент `occurredAt`) — затрагивает ADR-0008;
  - продажа ПКУ при перебое: поля рецепта — ПДн, хранить их в IndexedDB нежелательно;
    предложение — ПКУ только онлайн;

  - политика сервера для бизнес-конфликтов при досылке («продажа — факт» или отклонение).
