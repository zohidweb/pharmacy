# Остаток в изменениях снимка кассы: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** изменения снимка кассы (`GET /stores/{id}/catalog-snapshot?sinceVersion=`) считают остаток только партий своих
товаров, а не все движения точки за год (находка 1 нагрузочного прогона 2026-11-05), и прогон показывает новый запас:
профиль ×1, ×2 и перегрузка.

**Architecture:**
- Меняется один запрос — ветка изменений в `PosStock.batchesWithStock` (`apps/api/src/app/inventory/pos-stock.ts`).
  Полный снимок (`productIds === null`) оставляет сумму по всей точке за один проход: ему нужны все партии, а хранение
  остатков — отдельное решение через ADR (находка 2).
- Изменения сначала выбирают партии своих товаров по индексу партий `(tenant_id, store_id, product_id, expiry_date)`, а
  движения суммируют только по ним — индексом движений `(tenant_id, store_id, batch_id) include (qty_delta_pieces)` в
  каждой месячной секции, без чтения таблицы.
- Ответ API не меняется: те же партии, те же поля, тот же порядок. Миграций, новых индексов и зависимостей нет.

**Tech Stack:** NestJS + Kysely (`sql`-тег), PostgreSQL 17.11, инструменты прогона `tools/load/` (autocannon 8.0.0).

**Spec:** находка 1 руководства `docs/guides/load-test.md` («Последний прогон») и бюджеты ADR-0009
(`docs/architecture/adr/0009-instrumenty-testirovaniya-i-porogi-kachestva.md`, «Бюджеты API кассы»). Отдельной
спецификации нет: исправление локальное, поведение API не меняется.

## Уточнения при планировании

| № | Что нашлось | Решение | Цена ошибки |
|---|---|---|---|
| P1 | `batchesWithStock` один и для полного снимка, и для изменений. Полному снимку нужны все партии точки | Меняется только ветка со списком товаров. Полный снимок — прежний запрос (находка 2 — отдельный ADR) | Нет |
| P2 | Две формы «только партии своих товаров»: подзапрос на каждую партию (`join lateral`, как `StockRepository.batchStock`) и сумма движений с `batch_id = any(array(<партии товаров>))`. Замер — ниже, «Замер форм» | Форма `any`: на коротком списке она наравне с `lateral` (4,6 против 3,1 мс), на 50 товарах — не хуже, а на всём каталоге — 56 мс против 84 у прежнего запроса, тогда как `lateral` — 452 мс: на каждую партию он заново обходит все 38 секций. Фильтр по товарам переезжает из внешнего `where` внутрь суммы движений; полный снимок — тот же запрос без фильтра | На полном объёме короткий список может стоить 10–15 мс, а не 3–5: популярные товары — это и большинство движений. Всё равно в 6–9 раз быстрее прежних 87–93 мс |
| P3 | Прежний запрос отбирал движения по точке движения, новый — партии по точке партии | Партия принадлежит одной точке, её движения — движения этой точки (модель данных 03: `batches.store_id`, `stock_movements.store_id` — «точка партии»; перемещение создаёт новую партию получателя). Совпадение строк проверяется на `pharmacy_load` (`except all` в обе стороны) | Партия с движениями чужой точки пропала бы из изменений; проверка её поймает |
| P4 | Список товаров изменений бывает большим: загрузка каталога или массовая переоценка меняют тысячи товаров, а за годы у точки копятся партии | Товары — один параметр-массив `= any(${sql.val([...productIds])}::uuid[])`, как в `catalog.repository.ts` и `purchase-prices-source.ts`; список партий не уходит в параметры. Лимита в 65 535 параметров нет | Нет |
| P5 | Тесты отложены до MVP (решение пользователя) | Совпадение строк и планы проверяет одноразовый скрипт на `pharmacy_load`, в репозиторий он не попадает. Долг — в тексте PR | Регрессия формы запроса до MVP ловится только прогоном |
| P6 | Сравнимость с замером 2026-11-05 | Тот же стенд и тот же прогон: `--scale 1`, `run.mjs --scenario all`, затем `--scenario profile --factor 2 --minutes 5`, журнал запросов дольше 200 мс | Нет |
| P7 | При ×2 может упереться в следующую находку (3 — планирование 38 партиций, 4 — пул 10) | Здесь не чинится. Прогон называет следующее узкое место по журналу медленных запросов, исправление — следующим планом | Запас ×2 может остаться FAIL — это результат, а не провал плана |

## Замер форм (`--scale 0.1`, точка `L01`)

2026-11-05, при планировании: `pharmacy_load` на `--scale 0.1` (у `L01` 40 638 движений и 8 947 партий),
`explain (analyze, buffers)` под `pharmacy_app` с RLS, второй прогон каждого запроса. Время исполнения, мс;
планирование у всех форм — 2–5 мс.

| Товаров в изменениях | Партий в ответе | Прежний запрос | `lateral` | `any` |
|---|---|---|---|---|
| 3 самых продаваемых | 4 | 18,4 | 3,1 | 4,6 |
| 50 самых продаваемых | 76 | 25,3 | 13,5 | 12,9 |
| 50 случайных | 123 | 34,4 | 9,9 | 5,1 |
| все 3000 | 6 476 | 84,3 | 452,1 | 56,1 |

Строки обеих новых форм совпали с прежними во всех наборах (`except all` в обе стороны — 0). План формы `any`:
`InitPlan` выбирает партии по индексу партий, затем в каждой секции движений — `Index Only Scan` с
`batch_id = ANY ((InitPlan …).col1)` в `Index Cond`, `Heap Fetches: 0`. Товаров с нулевым остатком генератор не создаёт
(у каждого есть последняя партия), поэтому этот случай проверяется на полном объёме отдельно (Task 1, Step 4).

**Исполнение, 2026-11-09: форма пересмотрена по замеру полного объёма.** На `--scale 1` форма `any` не прошла порог
Step 4: 3 товара — 32 мс (порог 15), весь каталог — 278 мс против 199 у прежнего запроса. На изменениях, которые касса
шлёт на самом деле (товары последних продаж точки — самые ходовые), `lateral` вдвое быстрее `any`: 40 против 89 мс на
30 товарах. Прежний запрос он обгоняет до 300 товаров и уступает ему с ≈ 1000. Принята гибридная форма: до 200 товаров
— `lateral`, длиннее и полный снимок — прежний проход по точке, товары — одним параметром `uuid[]` (P4). Порог «3 товара
≤ 15 мс» исходил из ошибочной оценки: 3 самых ходовых товара — около 21 % движений точки, одна их сумма стоит ≈ 15–20 мс
в любой форме. Новый порог: те же строки во всех наборах, реалистичные изменения и 3 товара — не больше половины
прежнего запроса, 200 товаров — быстрее него. Числа — в журнале исполнения и в руководстве. После финального ревью
порог считает партии товаров изменений, а не товары: не больше 600 партий (≈ 200 самых ходовых товаров на данных
прогона), иначе — проход по точке. Подзапрос стоит 50–80 мкс на партию, а партии ходового товара копятся с каждой
поставкой, и порог в товарах на реальной истории сделал бы изменения медленнее прохода по точке.

## Review Focus

1. Товар изменений, у которого все партии точки на нуле или в минусе, приходит с пустым списком партий — касса должна
   их стереть, а не оставить старые: та же выдача, что у прежнего запроса (набор `edge` скрипта сравнения).
2. Изменения после загрузки каталога — тысячи товаров: новый запрос не медленнее прежней суммы по точке (набор `all`).
3. Товар без партий на точке и неизвестный id — без строк и без ошибки (набор `edge`).
4. Повторяющиеся id товаров в списке не дублируют партии (набор `edge`).
5. Запрос под ролью `pharmacy_app` и RLS (как в API), а не под суперпользователем: сравнение и планы — после
   `set role pharmacy_app` и `set_config('app.tenant_id', …)`.

- Produces: `PosStock.batchesWithStock(trx, tenantId, storeId, productIds: readonly string[] | null):

- [ ] **Step 1: Фильтр по товарам — внутрь суммы движений**

  Один запрос для обоих случаев. Внешний `where b.product_id in (…)` удаляется; при `productIds !== null` в `where`
  подзапроса суммы добавляется фрагмент:

```sql
and m.batch_id = any(array(
  select x.id from pharmacy.batches x
  where x.tenant_id = ${tenantId} and x.store_id = ${storeId}
    and x.product_id = any(${sql.val([...productIds])}::uuid[])))
```

  При `null` фрагмент пустой — полный снимок получает прежний запрос. Ранний `return []` для пустого списка
  остаётся. Комментарий над запросом — по смыслу: полный снимок суммирует движения точки за один проход, изменения —
  только движения партий своих товаров (нагрузочный прогон 2026-11-05, находка 1).
