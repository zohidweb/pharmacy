# ADR-0023: Публичный сайт продукта — Next.js с серверной отрисовкой, публичный контур API

- **Статус:** proposed
- **Дата:** 2026-10-28
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)
- **Поправляет:** ADR-0004 (режим отрисовки — для нового приложения), ADR-0005 (новый образ), ADR-0012 (корневой
  домен), ADR-0020 (apex больше не редирект)
- **Спецификация:** `docs/superpowers/specs/2026-10-28-public-site-design.md`

## Контекст

У продукта два приложения: клиентское (`app.nurmed.online`) и админка оператора (`admin.nurmed.online`), оба —
static export Next.js (ADR-0004). Корневой `nurmed.online` перенаправляет на `app.` (ADR-0012, ADR-0020).

Нужен публичный сайт для продаж: главная, тарифы и услуги, публичная оферта и политика ПДн, блог, заявка на
подключение. Требования пользователя (2026-10-28):

- **индексация поисковиками обязательна** — страницы, и прежде всего статьи блога, должны приходить готовым HTML;
- статьи, документы и настройки сайта (название, логотип, контакты) правит оператор в админке, без разработчика и
  без выкладки;
- заявки с сайта разбирает оператор в админке.

Static export отдаёт готовый HTML только для того, что известно при сборке. Статья, опубликованная в админке, при
static export появится в HTML только после новой сборки и выкладки.

## Рассмотренные варианты

1. **Next.js с серверной отрисовкой** — новое приложение `apps/site`, `next start` в своём контейнере, кеш страниц
   по времени (ISR). Плюсы: готовый HTML для поисковиков; публикация видна через минуту без сборки; тот же стек,
   кит `libs/ui` и токены. Минусы: ещё один постоянный процесс и образ; сервер Next.js нужно своевременно обновлять
   ради исправлений безопасности.
2. **Static export с пересборкой при публикации** — Плюсы: ADR-0004 не меняется, на сервере только файлы. Минусы:
   `next build` на продуктовом сервере — контейнер-сборщик с исходниками и зависимостями, минуты сборки, память у API;
   ломает правило «образ собран заранее и только запускается»; ошибка сборки ломает публикацию.
3. **Конструктор сайтов или внешняя CMS (Tilda и т. п.)** — Плюсы: быстро. Минусы: ПДн заявок уходят во внешний SaaS
   (ADR-0011); редактор не в нашей админке.
4. **HTML-шаблоны в NestJS** — Плюсы: нет нового процесса. Минусы: новая библиотека-шаблонизатор, второй способ
   вёрстки и дублирование стилей; кит React не переиспользуется.

## Решение

Выбран вариант 1.

1. **`apps/site`** — Next.js (App Router) с `output: 'standalone'`, запуск `next start`; страницы с данными API
   кешируются на 60 с (`revalidate = 60`), при сборке образа к API не обращаются. Стек — как у web и admin:
   React, TypeScript strict, Tailwind v4 на токенах `--ph-*`, `libs/ui`, FSD (ADR-0017), use-intl. `apps/web` и
   `apps/admin` остаются static export.
2. **Запрещено в `apps/site`:** Server Actions; middleware; Route Handlers, кроме metadata-маршрутов (`sitemap.xml`,
   `robots.txt`); `dangerouslySetInnerHTML`; оптимизация картинок `next/image` (нужна библиотека `sharp`) — картинки
   `unoptimized`. Новые зависимости — через ADR, как везде.
3. **Сайт не имеет доступа к базе, Redis, секретам и cookie сотрудников и операторов.** Данные он читает у API через
   публичный контур — тот же, что видит любой посетитель; сеть compose, адрес `SITE_API_INTERNAL_URL`.
4. **Публичный контур API `/api/v1/public/*`** — без сессии: чтение опубликованного (настройки сайта, тарифы,
   статьи, документы, картинки, sitemap) и приём заявки на подключение. Защита приёма — лимиты по IP, общий суточный
   предел, поле-ловушка, время заполнения; без внешней капчи (ADR-0011). Проверка `Origin` — по `SITE_ORIGIN`.
5. **Данные сайта — в PostgreSQL платформы** (роль `pharmacy_platform`, `app/platform/**`, ADR-0013), картинки — в
   `bytea`; всё попадает в ежедневные копии (ADR-0019).
6. **Текст статей и документов — ограниченный Markdown**, разбираемый своим парсером в `libs/shared/util` в дерево
   блоков и отрисовываемый React-элементами. HTML в тексте не поддерживается; ссылки — `https:`, `http:`, `mailto:`
   и относительные.
7. **Контейнер `site`** (образ `pharmacy/site`, ADR-0005): non-root, только для чтения, кеш страниц — `tmpfs`, без
   capabilities, `no-new-privileges`, в test и prod; в dev — `npx nx dev site`.
8. **Прокси (поправка ADR-0012 и ADR-0020):** корневой домен отдаёт сайт; на нём же `/api/v1/public/*` идёт в API.
   На `app.` и `admin.` публичный контур закрыт (404). `www.` — редирект на корневой домен. В test robots.txt
   запрещает индексацию.
9. **Веб-аналитика** в это решение не входит — второй этап, своим ADR (внешние счётчики — вопрос ADR-0011).

## Последствия

- **Положительные:** у продукта есть индексируемый сайт; публикация без разработчика; тот же стек и кит;
  ПДн заявок остаются в нашей базе; данные сайта в копиях без отдельной настройки.
- **Отрицательные (обязательно):**
  - ещё один постоянно работающий процесс на VPS (ориентир — до 256 МБ памяти) и ещё один образ в сборке и выкладке;
  - сервер Next.js — новая поверхность атаки: обновления безопасности Next.js нужно отслеживать и выкатывать (раньше
    уязвимости сервера Next.js проект не касались — использовался только static export);
  - публичный контур API без сессии — новая поверхность: спам заявок и нагрузка на чтение ограничиваются лимитами;
  - свой парсер Markdown нужно сопровождать; его ошибка — риск подмены ссылок, поэтому HTML не поддерживается вовсе;
  - картинки в базе увеличивают размер копий (до 2 МиБ на картинку).

Управление решениями — ADR-0011 (проект вне банковского контура).
