# Сотрудники, роли и терминалы владельца — спецификация

Дата: 2026-10-06. Статус: утверждено архитектором 2026-10-07. Связано: ADR-0018 (модель авторизации), ADR-0008
(аутентификация; дополнение 2026-10-06 — подтверждение паролем), ADR-0013 (дополнение 2026-10-06 —
роли по умолчанию при создании сети), спецификации `2026-10-02-auth-design.md` (версия прав, свежий
вход, PIN), `2026-10-05-tenants-module-design.md` (`provision_tenant`),
`2026-10-06-owner-stores-design.md` (режим `partial` web).

## 1. Цель и критерии успеха

Владелец (и заведующий с нужными правами) собирает команду сети: заводит сотрудников с паролем и
PIN, назначает одну роль и охват точек, правит, сбрасывает пароль и PIN, блокирует; ведёт роли из
каталога прав; видит и отвязывает терминалы своих точек. Экран «Сотрудники и роли» `apps/web`
работает с настоящим API.

Успех:
- новая сеть сразу имеет четыре роли: «Владелец», «Заведующий точкой», «Фармацевт-кассир»,
  «Бухгалтер»;
- никто не выдаёт права шире своих и охват шире своего, не меняет собственные роль и охват; в сети
  всегда остаётся активный владелец (ADR-0018, п. 2–4);
- смена роли, её прав, охвата или статуса действует на следующем запросе сотрудника; блокировка и
  сброс пароля завершают его сессии;
- действия с сотрудниками и ролями после 15 минут сессии не требуют выхода: окно «Подтвердите
  пароль» продлевает свежесть входа;
- каждое изменение — в журнале сети (`audit_log`).

## 2. Решения, принятые при обсуждении (2026-10-06)

| # | Вопрос | Решение |
|---|---|---|
| E1 | Объём | Все три вкладки экрана: сотрудники, роли, терминалы (у терминалов — новый список, отвязка уже есть) |
| E2 | Роли новой сети | `provision_tenant` создаёт четыре роли. «Владелец» — системная (как сейчас). Три остальные — **обычные роли сети** без связи с шаблоном (`template_key` пустой): их переименовывают и меняют как любую роль. Наборы прав по умолчанию — `roleTemplates` из `libs/shared/domain`, только как начальные значения |
| E3 | Свежий вход | `POST /sessions/current/confirmation` с паролем продлевает свежесть сессии; web показывает окно и повторяет действие |
| E4 | PIN сотрудника | Новый `POST /employees/{id}/pin`: руководитель задаёт или меняет PIN, блокировка PIN после трёх ошибок снимается (ADR-0008) |

## 3. Роли по умолчанию (дополнение поправки ADR-0013 от 2026-10-05)

- `provision_tenant` получает параметр `p_default_roles jsonb` — массив `{ id, name: {ru, tj},
  permissions: string[] }` трёх обычных ролей; функция вставляет их в `roles` (`is_owner = false`,
  `template_key = null`) и права в `role_permissions` в той же транзакции. Роль «Владелец» —
  как сейчас (`is_owner = true`, `template_key = 'owner'`, без строк `role_permissions`: у владельца
  все права каталога).
- Формат проверяет функция (массив объектов с этими ключами), допустимость строк прав —
  ограничение `role_permissions.permission`; список и названия задаёт приложение
  (`TenantsService`): права — `roleTemplates.manager / cashier / accountant`, названия RU/TJ —
  «Заведующий точкой» / «Мудири нуқта», «Фармацевт-кассир» / «Фармасевт-хазинадор»,
  «Бухгалтер» / «Муҳосиб» (таджикские названия — на проверку носителю языка).
- `pharmacy_provisioner` получает `INSERT` в `role_permissions` и политику RLS для своей роли;
  каталог-тест (`PROVISIONING_FUNCTIONS`) не меняется по составу, проверяет новую сигнатуру.
- Уже созданные сети dev/test получают три роли миграцией, если у сети нет ни одной обычной роли
  (идемпотентно); продовых сетей нет.

## 4. API (`apps/api/src/app/staff`, только `TenantDatabase`)

Модуль не регистрируется на офлайн-точке (сотрудники и роли — данные облака, приходят лентой
изменений, ADR-0014 — отдельной задачей). Все мутации — `@RequireFreshAuth()`.

| Маршрут | Право | Ответ |
|---|---|---|
| `GET /employees?storeId=&roleId=&status=&limit=&offset=` | `employees:view` | `200 EmployeeListResponse` |
| `GET /employees/{id}` | `employees:view` | `200 EmployeeCard` (последние 20 действий сотрудника из `audit_log`) |
| `POST /employees` | `employees:create` | `201 EmployeeCard` |
| `PUT /employees/{id}` | `employees:update` (+ `employees:assign-role` при смене роли или охвата) | `200 EmployeeCard` |
| `POST /employees/{id}/password` | `employees:update` | `204` |
| `POST /employees/{id}/pin` | `employees:update` | `204` |
| `POST /employees/{id}/status` | `employees:update` | `200 EmployeeCard` |
| `GET /roles` | `roles:view` | `200 Role[]` |
| `POST /roles` | `roles:manage` | `201 Role` |
| `PUT /roles/{id}` | `roles:manage` | `200 Role` |
| `GET /terminals` | `terminals:view` | `200 TenantTerminal[]` — терминалы точек охвата |

Правила (ADR-0018; совпадают с моками `apps/web/src/shared/api/mocks/handlers-staff.ts`):
- **Видимость.** Сотрудник виден, если его охват пересекается с охватом смотрящего; сотрудника с
  охватом «вся сеть» видит только смотрящий с охватом «вся сеть». Невидимый → 404.
- **Назначение** (создание, смена роли или охвата): права роли ⊆ права редактора → иначе 403
  `permission_escalation`; роль «Владелец» назначает только владелец (403 `permission_escalation`);
  охват ⊆ охват редактора → иначе 403 `store_not_in_scope`; у роли «Владелец» охват всегда «вся
  сеть»; охват-список не пустой и из активных точек сети (400 `validation_failed`).
- **Своё.** Собственные роль, охват и статус менять нельзя → 403 `own_assignment`; свою роль
  редактировать нельзя → 403 `own_assignment`.
- **Владелец.** Последнего активного владельца нельзя перевести на другую роль или заблокировать →
  409 `last_owner`; роль «Владелец» не редактируется → 409 `system_role`.
- **Роль.** Название 1–60 символов, уникально среди ролей сети без учёта регистра (409
  `role_name_taken`); права — строки каталога (`permissions` в shared-domain), без дублей; права ⊆
  права редактора (403 `permission_escalation`). Название сохраняется одинаковым для RU и TJ; ответ
  отдаёт название на языке сотрудника.
- **Сотрудник.** ФИО 1–200; логин, телефон (E.164), e-mail — по правилам `normalizeIdentifier`,
  уникальны на платформе → 409 `login_taken` / `phone_taken` / `email_taken` (по имени индекса, как в
  модуле «сети»); язык `ru` / `tg`; пароль — `passwordProblems` (422 `password_policy`); PIN —
  `checkPin` с `tenant_settings.pin_min_length` (422 `pin_length` / `pin_trivial` у поля, как у смены своего PIN), пустой — без PIN. Хеши — тот же
  `PasswordHasher` (scrypt + pepper), что у входа; ответы не несут паролей и PIN.
- **Последствия.** Смена роли, охвата, статуса и изменение прав роли увеличивают
  `employees.permissions_version` (у роли — всем её сотрудникам) в той же транзакции и после коммита
  пишут версию в кэш (как в спецификации аутентификации). Блокировка, сброс пароля → все сессии
  сотрудника завершаются (`destroyAllFor`). Новый PIN снимает `pin_locked_at` и счётчик ошибок.
- **Аудит** в той же транзакции: `employee.created`, `employee.updated`, `employee.assignment-changed`
  (роль, охват), `employee.password-reset`, `employee.pin-set`, `employee.blocked` /
  `employee.unblocked`, `role.created`, `role.updated`. В деталях — идентификаторы и названия, без
  паролей и PIN.

## 5. Подтверждение паролем (дополнение ADR-0008 от 2026-10-06)

`POST /sessions/current/confirmation { password }` (контур web; `@Authenticated()`):
- только сессия, открытая паролем (PIN-сессия → 403 `password_session_required`);
- пароль проверяется тем же путём, что вход (scrypt, pepper); верный → `authenticatedAt` записи
  сессии = сейчас, `204`; неверный → 422 `invalid_current_password` у поля `password` (как у смены
  своего пароля);
- неудачи считаются в том же лимите, что вход по логину (`LoginLimiter`, ключ — сотрудник); после
  лимита → 429 `login_locked`;
- аудит: `auth.reconfirmed` / `auth.reconfirm-failed`.

## 6. Контракт (`libs/shared/dto`)

- `EmployeeListItem.pinLocked: boolean` — PIN заблокирован после трёх ошибок.
- `SetEmployeePinRequest { pin: string }` — `POST /employees/{id}/pin`.
- `ConfirmSessionRequest { password: string }` — `POST /sessions/current/confirmation`
  (`tenant-auth.ts`).
- Остальные типы `tenant-staff.ts` — без изменений; JSDoc дополняется кодами ошибок раздела 7.

## 7. Web (`apps/web`)

1. `REAL_API_ROUTES` + `employees.*`, `roles.*`, `terminals.list`, `employees.setPin`,
   `sessions.confirm`.
2. Один код ошибки свежего входа: моки и тексты переходят с `step_up_required` на
   `fresh_auth_required`; ошибка проверки в моках — 400 `validation_failed` (как API); конфликты
   логина, телефона, e-mail — у полей.
3. **Фича `features/confirm-password`:** `withFreshAuth(action)` — на 403 `fresh_auth_required`
   открывает окно «Подтвердите пароль» (монтируется один раз в оболочке приложения), вызывает
   `sessions.confirm` и один раз повторяет действие; закрытие окна отменяет действие без ошибки;
   неверный пароль и 429 — в окне; в PIN-сессии окно предлагает войти паролем. Обёртку получают
   мутации сотрудников, ролей, отвязки терминала и смены своего пароля и PIN в профиле.
4. Карточка сотрудника: действие «Задать PIN» (окно, минимум длины — из настроек сети) и отметка
   «PIN заблокирован».
5. Вкладка «Роли»: колонка «Тип» — «Системная» у владельца, «Обычная» у остальных (без «Шаблон»).
6. Моки — новые маршруты и коды; тексты RU/TJ; существующие тесты экрана сотрудников и профиля
   правятся под новые коды.

## 8. Ошибки

| Статус | Коды |
|---|---|
| 400 | `validation_failed` с `errors[]` |
| 403 | `permission_escalation`, `store_not_in_scope`, `own_assignment`, `fresh_auth_required`, `password_session_required` |
| 404 | `not_found` — сотрудник, роль или терминал вне охвата или нет |
| 409 | `last_owner`, `system_role`, `role_name_taken`, `login_taken`, `phone_taken`, `email_taken` |
| 422 | `password_policy`, `pin_length`, `pin_trivial`, `invalid_current_password` (подтверждение) |
| 429 | `login_locked` |

## 9. Вне объёма

Удаление и архив сотрудников и ролей; синхронизация сотрудников на офлайн-точку и их локальные
учётные данные (ADR-0008, ADR-0014); журнал сети как экран; подтверждение паролем для оператора
админки (позже, на той же основе); привязка терминала из web (маршрута нет).

## 11. Проверка

Новые автотесты не пишутся до MVP (решение 2026-10-05); существующие наборы — зелёные (каталог-тест
— под новую сигнатуру и права). Ручная проверка:
- curl: новая сеть → четыре роли; владелец создаёт заведующего (охват — одна точка) и кассира;
  заведующий: видит только сотрудников своей точки, роль шире своих прав → 403, чужая точка → 403,
  своя роль → 403; последний владелец → 409; блокировка кассира → его сессия 401; смена прав роли
  → сессия сотрудника видит новые права на следующем запросе; PIN после трёх ошибок → новый PIN
  снимает блокировку; подтверждение паролем: неверный → 422, верный → действие проходит;
- браузер (`web:dev-api`, API с коротким `STEP_UP_MAX_AGE_SECONDS`): владелец заводит команду, окно
  «Подтвердите пароль» появляется после истечения свежести и действие выполняется; вкладки «Роли» и
  «Терминалы» на настоящих данных.
