# ADR-0002: Стиль архитектуры — модульный монолит в Nx-монорепо

- **Статус:** accepted
- **Дата:** 2026-09-29
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy

## Контекст

Платформа обслуживает на старте 3 тенанта / ~30 точек / до 50 одновременных кассиров с
запасом роста ×5 — это малая нагрузка для одного приложения. Разработку ведёт одна небольшая
команда со сроком до конца 2026 года. Ключевая особенность из ТЗ: офлайн-точка — это та же
система, устанавливаемая целиком на один ПК аптеки (Docker) и синхронизируемая с облаком;
брокеры сообщений радаром не утверждены. Доменные модули жёстко очерчены ТЗ и бэклогом:
каталог, склад/партии, касса/смены, закупки, цены/скидки, возвраты, биллинг, синхронизация,
фискализация, экспорт 1С, аудит.

## Рассмотренные варианты

1. **Модульный монолит** (одно NestJS-приложение с явными границами модулей) — минимум
   операционной сложности для команды без DevOps-штата; транзакции между складом, кассой и
   аудитом — локальные ACID в одной PostgreSQL (критично: остатки выводятся из движений,
   чек списывает партии атомарно); офлайн-дистрибутив = тот же артефакт, развёрнутый локально.
2. **Микросервисы** — независимое масштабирование и деплой, но: нагрузка их не требует;
   распределённые транзакции для «чек → движения партий → аудит» резко усложняют главный
   инвариант системы; межсервисное взаимодействие потребовало бы брокера (категория радара
   не утверждена); офлайн-точку из набора сервисов на один ПК аптеки не поставить разумным
   образом; эксплуатационная нагрузка непосильна для команды и срока.
3. **Два раздельных монолита** (клиентский и административный бэкенды) — изоляция продуктов,
   но оба работают с одной мультитенантной моделью (тенанты, точки, счета, ключи):
   дублирование доменной логики и две точки согласованности данных без выгоды.

Организация кода: **Nx-монорепо** `pharmacy-app` (`apps/api`, `apps/web`, `apps/admin`,
`libs/*`) против практики банка «один деплой-юнит = один репозиторий» — рассмотрено на
шаге /01: общие TypeScript-типы и DTO между API и двумя фронтендами, одна команда,
синхронные релизы волн MVP перевешивают; отступление фиксируется здесь.

## Решение

Модульный монолит на NestJS с границами модулей по доменам ТЗ; единая PostgreSQL с изоляцией
тенантов на уровне данных; очередь синхронизации офлайн-точек — таблицы в PostgreSQL (без
брокера). Три деплой-юнита (api, web, admin) в одном Nx-монорепо; офлайн-дистрибутив
собирается из тех же приложений. Горизонтальное масштабирование — добавлением stateless-
инстансов API (сессии в Redis); запас ×5 это покрывает.

## Последствия

- Положительные: локальные ACID-транзакции для главного инварианта (остаток = сумма движений);
  один артефакт для облака и офлайн-точки; минимальная эксплуатация; быстрый старт; явные
  границы модулей оставляют путь к выносу сервисов при реальном росте за пределы ×5.
- **Отрицательные (обязательно):**
  - масштабирование только целиком: нельзя отдельно масштабировать «тяжёлые» модули
    (отчёты, синхронизацию) — при росте за ×5 потребуется вынос, границы модулей придётся
    дисциплинированно охранять (ревью зависимостей между модулями);
  - единая БД — общая точка отказа и общий бюджет производительности для всех тенантов;
    «шумный сосед» смягчается только на уровне приложения;
  - монорепо отступает от практики банка: общие пайплайны CI, риск взаимных блокировок
    релизов приложений; категория CI/CD радара ещё не утверждена;
  - деплой любого изменения — редеплой всего API, окно обслуживания затрагивает всех
    тенантов (смягчение: плановые работы ночью, из ТЗ).

## Только для исключений из техрадара

Секция не применяется: стиль архитектуры не является технологией радара. Nx — инструмент
сборки вне категорий радара (открытый вопрос № 10 в stack.md), подтверждается Архитектурным
комитетом на ревью; отдельное исключение не подаётся, если комитет не потребует.
