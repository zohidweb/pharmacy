# ADR-0004: Исключение из техрадара — Next.js как фронтенд-фреймворк

- **Статус:** accepted
- **Дата:** 2026-09-29
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy

## Контекст

Проект Pharmacy (см. docs/architecture/stack.md и ADR-0003): два веб-фронтенда — клиентский
продукт (касса/склад, сенсорные POS-экраны, буфер офлайн-операций) и админка оператора
платформы — в Nx-монорепо с бэкендом на NestJS (ожидает исключения, ADR-0003). Техрадар v1.3
в категории Frontend содержит Angular («Приоритет»), React и TypeScript («Утверждено»);
Next.js как фреймворк в радаре отсутствует. Команда владеет и Next.js, и Angular.

Честная фиксация: это самый спорный запрос пакета — утверждённые альтернативы существуют,
и одной из них команда владеет. Решение о подаче принято командой осознанно.

## Рассмотренные варианты

1. **Angular** — «Приоритет» в радаре, команда владеет, в банке есть стандарты
   (`angular-dev`). Плюсы: нулевой риск по радару, готовые конвенции банка. Минусы: второй
   фреймворк в монорепо рядом с React-экосистемой Next.js/NestJS; меньше переиспользования
   кода (формы, стейт, UI-кит) между приложениями; смешанная экосистема повышает стоимость
   сопровождения одной командой.
2. **React (SPA, из радара)** — «Утверждено». Плюсы: та же экосистема, что у Next.js, без
   исключения. Минусы: «голый» React требует самостоятельной сборки инфраструктуры
   (роутинг, сборка, code-splitting), которую Next.js даёт из коробки; но это наиболее
   вероятная альтернатива при отказе комитета.
3. **Next.js (React-фреймворк)** — вне радара. Плюсы: команда владеет; единая
   React/TypeScript-экосистема с NestJS-бэкендом и общими библиотеками в Nx; готовая
   инфраструктура (роутинг, сборка, оптимизация). Минусы: вне радара; серверная часть
   Next.js (SSR) для внутренних приложений (касса, админка) не нужна — используется как
   статический/клиентский фреймворк, что ослабляет аргументацию.

## Решение

Предлагаем утвердить Next.js (актуальная стабильная версия, режим SPA/static для кассы)
для `apps/web` и `apps/admin`. Определяющий аргумент — единая React/TypeScript-экосистема
с бэкендом и максимальное переиспользование кода в монорепо одной командой при сроке до
конца 2026 года. Команда понимает, что при отказе комитета альтернатива — React (из радара)
или Angular («Приоритет»), и готова к этому исходу: смена фронтенд-фреймворка на этапе
проектирования не влияет на модель данных и API.

## Последствия

- Положительные: один UI-стек на оба приложения; общий UI-кит и формы в `libs/*`;
  ускорение разработки командой с существующими компетенциями.
- **Отрицательные (обязательно):**
  - обходится приоритетная рекомендация радара (Angular) при наличии компетенций — создаёт
    прецедент «выбор по предпочтению команды», который комитет может счесть нежелательным;
  - высокая вероятность отказа: решение по фронтенду блокируется до вердикта комитета
    (SLA 3 раб. дня), при отказе — переключение на React/Angular;
  - Next.js развивается быстро и ломающе (App Router и т.п.) — стоимость обновлений выше,
    чем у Angular LTS;
  - SSR-возможности фреймворка в проекте не используются — платим сложностью фреймворка
    за инфраструктуру сборки.

## Только для исключений из техрадара

- Альтернативы из радара и почему не подходят: Angular («Приоритет») — команда владеет, но
  второй фреймворк рядом с React-экосистемой бэкенда дробит монорепо и переиспользование;
  React («Утверждено») — приемлемая запасная альтернатива, уступает Next.js только готовой
  инфраструктурой сборки. Подробнее — «Рассмотренные варианты».
