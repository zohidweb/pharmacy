# Project Starter — как начать проект правильно

Шаблон Банка Эсхата для проектов с AI-разработкой (вайбкодингом). Он проводит команду по
одинаковым шагам проектирования и не даёт уйти от технологического радара банка.

Версия шаблона — в файле `VERSION`, история изменений — в `CHANGELOG.md`.

## Мини-словарь

| Термин | Что значит |
|---|---|
| Tech radar (техрадар) | утверждённый список технологий банка: `tech-radar/RADAR.md` |
| Stack (стек) | набор технологий проекта: язык, фреймворк, БД и т.д. |
| Gate (гейт) | контрольная точка: дальше нельзя без апрува |
| NFR | нефункциональные требования: нагрузка, доступность, восстановление |
| RTO / RPO | за сколько восстановимся / сколько данных можем потерять |
| Tier | класс критичности системы: 1 — платежи/клиенты … 3 — вспомогательные |
| ИБ | Служба информационной безопасности |
| hook (хук) | автоматическая проверка Claude Code — скрипт, который срабатывает при записи файлов |
| merge request (MR) | запрос на слияние изменений в GitLab, аналог pull request |
| slash-команда | команда, которую вы набираете в чате Claude Code, начинается с / |

## Быстрый старт

1. Создайте репозиторий проекта из этого шаблона («Use this template» / копия без git-истории
   шаблона). Полный `git clone` не используйте.
2. Откройте проект в Claude Code. При первом запуске Claude Code спросит разрешение на
   project-hooks — **согласитесь**: это предохранитель, который блокирует написание кода до
   завершения проектирования и правки радара. Это безопасно: hook — небольшой скрипт из этой
   же папки (`.claude/hooks/guard.ps1`), он только проверяет пути записываемых файлов, ничего
   не отправляет наружу и не трогает файлы за пределами проекта.
3. Команды вида `/01-…` набираются прямо в поле чата Claude Code (как сообщение) и запускаются
   клавишей Enter. Выполняйте шаги по порядку:

| Шаг | Что делаете | Результат |
|---|---|---|
| 1 | `/01-select-stack` — интервью о проекте и выбор стека | `docs/architecture/stack.md` |
| 2 | `/02-c4-model` — диаграммы системы | `docs/architecture/c4/…` |
| 3 | `/03-adr` — фиксация решений (минимум ADR-0001; для Full также ADR-0002) | `docs/architecture/adr/…` |
| 4 | **Ревью архитектуры** (человек!) — см. ниже | `docs/architecture/APPROVAL.md` |
| 5 | `/04-generate-claude-md` — финализация | новый `CLAUDE.md` проекта |

4. После шага 5 — новая сессия (`/clear`) и можно вайбкодить. Правила зафиксированы в новом
   CLAUDE.md; новое архитектурное решение по ходу разработки = сначала `/03-adr`, потом код.

**Прототип или внутренняя утилита?** На шаге 1 выберите класс **Lite** — сокращённый путь
(~1–2 часа): короткий stack.md → одна Context-диаграмма → ADR-0001 → `/04`. Ревью — пост-фактум.
Если прототип идёт в прод — проходите полный путь. Post-factum ревью — не формальность: при
финализации проект вносится в реестр в GOVERNANCE.md с дедлайном, комитет отслеживает его на
квартальных пересмотрах.

**Монорепо или несколько репозиториев?** Обычная практика банка — отдельные репозитории
по компонентам (backend и frontend отдельно; мобильные — свои репо). Тогда репозиторий из
этого шаблона становится «репозиторием архитектуры» системы: здесь живут stack.md, C4, ADR
и APPROVAL, а `/04` генерирует отдельный CLAUDE.md для каждого кодового репозитория
(docs/architecture/generated/) — его копируют в корень соответствующего репо вместе со
скиллом стека. Монорепо допустим для небольших систем и Lite. Решение фиксируется на
интервью /01 (строка «Репозитории кода») и в ADR-0002.

**Скиллы стеков.** В шаблоне лежат конвенции банка по каждому стеку (`.claude/skills/`) —
Claude подхватывает их автоматически при вайбкодинге, без отдельной команды. После
финализации (`/04`) остаются только скиллы вашего стека, скиллы остальных стеков удаляются.
Конвенции — v1, черновик до утверждения Архитектурным комитетом.

**Не пользуетесь Claude Code?** Те же шаги вручную или с другим AI-инструментом:
чек-листы в `docs/guides/`. Артефакты и их структура — те же.

**Пример как должно получиться:** `examples/demo-project/` — полностью заполненный
эталонный проект «Сервис уведомлений клиентов». Сомневаетесь, как выглядит хороший
артефакт — смотрите туда.

## 15 минут теории

### Что такое C4

C4 — четыре уровня «карты» системы, от общего к частному. Нам нужны первые два-три:
**Context** — система как один квадрат: кто ей пользуется и с какими внешними системами она
говорит. Отвечает на вопрос «что это и для кого».
**Container** — из каких крупных частей состоит система (приложения, сервисы, БД, кэш) и как
они связаны. Отвечает на вопрос «из чего это сделано».
**Deployment** — где каждая часть работает (сервер, кластер, контур сети). Отвечает на
вопрос «где это живёт» — в банке от этого зависят доступы и согласования.
Диаграммы рисуются в Mermaid прямо в Markdown — их видно в Git и легко править.

### Зачем ADR

ADR (Architecture Decision Record) — короткая запись одного решения: контекст → варианты →
что выбрали → чем платим. Через полгода никто не помнит, ПОЧЕМУ выбрали модульный монолит, —
ADR помнит. Плохой ADR: «Решили использовать PostgreSQL, потому что он хороший». Хороший ADR:
«Рассматривали PostgreSQL и хранение в АБС; выбрали PostgreSQL, потому что отчётные запросы
нагружали бы АБС; платим за это синхронизацией справочников (см. риск в разделе Последствия)».

## Ревью архитектуры (шаг 4)

Ревью проводит **Архитектурный комитет** (комитет может делегировать ревью
peer-архитектору). SLA — 3 рабочих дня.

**Как подать на ревью:** issue в центральном репозитории ai-project-start
(https://gitlab.eskhata.com/zsaidov/ai-project-start) с меткой `review-request` и ссылкой
на репозиторий проекта, либо сообщение в канал «Архитектура».

Чек-лист ревьюера:

- [ ] stack.md заполнен, версия радара указана, технологии — только «Утверждено» (или есть
      апрув исключения в ADR);
- [ ] профиль проекта и чек-лист безопасности не пустые; открытые вопросы — адекватные;
- [ ] C4: context + container + deployment (для Lite — только context), внешние системы
      совпадают с разделом «Интеграции»;
- [ ] ADR-0001 существует (для Full также ADR-0002), у решений заполнены отрицательные
      последствия;
- [ ] при «Флаг апрува ИБ: ДА» — получен апрув ИБ.

Результат ревьюер записывает в `docs/architecture/APPROVAL.md` строго в формате:

    # Architecture Review
    Статус: APPROVED
    Архитектурный комитет: <представитель, Имя Фамилия>
    Дата: YYYY-MM-DD
    ИБ: <Имя Фамилия — обязательно при «Флаг апрува ИБ: ДА»; иначе «не требуется»>
    Комментарии: <опционально>

(Для Lite допустимо `Статус: APPROVED (post-factum)` — в этом случае обязательна ещё одна
строка: `Дедлайн фактического ревью: YYYY-MM-DD`; без неё `/04` откажет.) Без этого файла
`/04` не сработает.

Важно: строка статуса — ровно `Статус: APPROVED` (английское слово). «Утверждено» или
«approved» строчными `/04` не примет и объяснит, чего не хватает.

## Технология вне радара?

Не спорьте с Claude — он обязан отказать. Процедура: `tech-radar/EXCEPTIONS.md`
(ADR-обоснование → заявка → апрув Архитектурного комитета, для security-категорий + ИБ →
SLA 3 дня).

## Частые вопросы

**Почему Claude отказывается писать код?** — проектирование не завершено: нет какого-то
артефакта или APPROVAL.md. Спросите его: «какие шаги остались?».
**Хук заблокировал запись файла — это баг?** — нет, это предохранитель. Он снимается сам
после `/04-generate-claude-md`. Вы увидите сообщение `BLOCKED: …` — это нормально, ничего не
удалено и не сломано; файл просто не был записан.
**Радар устарел / нужной категории нет?** — `/update-radar`; если категория «На утверждении» —
заявка через EXCEPTIONS.md ускорит её утверждение.
**Guard защищает от всего?** — нет: это предохранитель от случайных ошибок при работе Claude
через инструменты записи. Намеренный обход возможен, и его ловит не hook, а ревью
Архитектурного комитета и человеческое код-ревью.
