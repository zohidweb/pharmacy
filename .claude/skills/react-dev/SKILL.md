# Конвенции Банка Эсхата — React (v1, черновик до утверждения Архитектурным комитетом)

## 1. Структура проекта

- Внутри `src/`:
  - `features/<feature-name>/` — бизнес-фичи: компоненты, хуки, состояние и API-вызовы одной
    фичи живут рядом. Фичи НЕ импортируют друг друга напрямую — общая логика выносится в
    `shared/`.
  - `shared/` — переиспользуемые компоненты, хуки, утилиты без бизнес-логики конкретной
    фичи.
  - `app/` (или `core/`) — точка входа, роутинг, провайдеры на всё приложение (auth,
    HTTP-клиент с correlation ID).
- TypeScript обязателен для всего нового фронтенд-кода (tech-radar/RADAR.md); `.jsx`/`.js`
  для нового кода не используется.

## 2. Нейминг

- Идентификаторы кода и комментарии — на английском.
- Компоненты — PascalCase, файл называется так же, как компонент (`OrderList.tsx`).
- Хуки — camelCase с префиксом `use` (`useOrderList`).
- Переменные, параметры, обычные функции — camelCase.
- Не-компонентные файлы (утилиты, типы) — kebab-case или camelCase, единообразно в пределах
  проекта.
- REST-пути на бэкенде, которые вызывает фронтенд, — kebab-case
  (`/api/notification-templates`).

## 3. Тесты

- Раннер де-факто — Jest (или Vitest) для unit/component-тестов, Playwright для e2e
  (кандидаты в радар, до утверждения комитетом; не менять без ADR).
- Обязательно покрывать: хуки и функции с бизнес-логикой (мапперы данных с бэкенда,
  валидация), каждый компонент — минимум рендер + основной пользовательский сценарий.
- Тестируется поведение (что видит пользователь), а не детали реализации компонента.

## 4. Логирование и ошибки

- Логи на фронтенде — структурные там, где уходят на бэкенд/в систему мониторинга; в проде —
  минимум, без утечки данных в консоль браузера.
- Каждый исходящий HTTP-вызов к бэкенду несёт correlation ID (`X-Correlation-Id`),
  выставляется единым слоем в `app/`/`shared/` (интерцептор HTTP-клиента).
- Запрещено логировать ПДн, банковскую тайну, секреты — включая в `console.log` и в тела
  ошибок, показываемых пользователю.
- Ошибки запросов не проглатываются молча — есть error boundary на уровне приложения и/или
  явная обработка в месте вызова, с понятным пользователю сообщением.

## 5. Запреты (из радара)

- Самописная криптография — запрещена (tech-radar/RADAR.md, раздел «Запрещено»).
- Аутентификация: приоритет — корпоративный Keycloak (SSO банка); самописная реализация
  не рекомендуется, для систем с ПДн / банковской тайной — согласовать с ИБ.
- Секреты (ключи API, токены) — не в коде и не в репозитории; конфигурация окружения — через
  `.env.local` (в `.gitignore`), коммитится только `.env.example`.
- Внешние вызовы — только к системам из раздела «Интеграции» проектного CLAUDE.md.
- Технологии, библиотеки — только из tech-radar/RADAR.md со статусом «Утверждено»; категории
  «На утверждении» (CI/CD, мониторинг и т.д.) использовать нельзя, пока Архитектурный комитет не
  переведёт их в «Утверждено» — когда категория будет утверждена, конвенции этого файла
  дополняются.

## 6. Перед коммитом

- `npm run build` (или эквивалент) — без ошибок.
- `npm test` — все тесты зелёные.
- `npm run lint` — без ошибок линтера.
- MR — по правилам корневого CLAUDE.md проекта (ветка `feature/<task-id>-<slug>`,
  Conventional Commits, human-ревью обязательно, метка `ai-assisted` для MR с участием AI).
