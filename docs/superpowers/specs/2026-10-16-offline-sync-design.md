# Офлайн-точка и синхронизация — спецификация

Дата: 2026-10-16. Статус: утверждена архитектором 2026-10-16 (вместе с решениями автора E1–E41).

Основа — ADR-0014 (протокол синхронизации, accepted, с поправкой 2026-10-02). Связано:
- модель данных `docs/architecture/data-model/` (06 — таблицы синхронизации, 01 — `license_keys`, 02 — алиас
  дубля, 03/04/05 — владение данными);
- ADR-0005 (Docker, дистрибутив точки), ADR-0008 и спецификация `2026-10-02-auth-design.md` §10 (вход на точке,
  часть 4 — сделана), ADR-0012 (раздача статики, `proposed`), ADR-0013 (кросс-тенантный доступ, резолверы),
  ADR-0015 (web, буфер перебоев облачной точки — не путать с офлайн-точкой), ADR-0018 (права, «правила режима»).

## 1. Цель и критерии успеха

Аптека с ненадёжным интернетом работает на своём ПК как самостоятельная копия продукта: продаёт, принимает товар,
проводит документы склада и смены без связи. Когда связь есть, она отправляет в облако завершённые факты и получает
изменения справочников. Владелец сети видит офлайн-точку в облаке так же, как облачную, — с задержкой синхронизации.

Успех:
- точка дни и недели работает без связи; при появлении связи все её факты попадают в облако ровно один раз, в любом
  порядке обрывов и повторов;
- в облаке остаток офлайн-точки равен остатку на точке (сверка), отчёты, долги поставщикам и журнал включают её факты;
- изменения каталога, цен, скидок, сотрудников, ролей, поставщиков и настроек сети доходят до точки за один прогон;
- конфликт цены решает владелец в облаке, дубль товара — точка; ни один факт не теряется молча (карантин);
- точку можно поставить с нуля (по сети или с флешки) и перевести обратно в облако;
- протокол целиком соответствует ADR-0014; новых технологий, кроме названных в ADR (`@nestjs/schedule`), нет.

## 2. Решения, принятые при обсуждении (2026-10-16)

| # | Тема | Решение |
|---|---|---|
| S1 | Объём | Протокол целиком по ADR-0014. Пилотной аптеки пока нет — делаем полный протокол, а не узкий путь «только продажи» |
| S2 | Этапы | 1) облако принимает операции точки; 2) облако отдаёт ленту и снимки; 3) сама точка; 4) кабинет владельца; 5) установка и переход; 6) экраны админки — позже, вместе с остальной админкой |
| S3 | Проверка | Второй экземпляр API в режиме точки на отдельной базе в том же контейнере PostgreSQL, новых контейнеров нет. Этапы 1–2 — запросами curl от имени точки, этап 3 и дальше — двумя живыми экземплярами |
| S4 | Биллинг офлайн-точки | Тариф офлайн-точки в счетах платформы — отдельной задачей потом. До неё счета считают только облачные точки (как сейчас) |

## 3. Решения автора (на утверждение вместе со спецификацией)

### 3.1 Общее

| # | Тема | Решение |
|---|---|---|
| E1 | Один код | Точка — тот же `apps/api` с `STORE_MODE=offline` и та же схема БД. Доменные модули, которые нужны точке, регистрируются и на ней (раздел 6.1); факты на точке пишут те же сервисы, что и в облаке |
| E2 | Запись операции | Новый модуль ядра `SyncJournal` (`apps/api/src/core/sync`, как `AuditModule` — им пользуются все): `record(trx, operation)`. В облаке — пустая реализация, на точке — строка `sync_outbox` в той же транзакции. Каждый сервис факта (раздел 4.2) в конце своей транзакции вызывает `record` с полным содержимым факта: строки с id, которые он только что записал |
| E3 | Применение в облаке | Модуль `sync` (облако) принимает батч, а каждую операцию применяет «применитель» модуля-владельца данных — экспорт домена (`PosFacts`, `ReturnFacts`, `StockFacts`, `TransferFacts`, `ShiftFacts`, `TerminalFacts`, `CatalogFacts`, `PriceFacts`, `AuditFacts`). Применитель вставляет строки с id точки как есть, без FEFO и проверки остатка. Граф: `pos`, `returns`, `inventory`, `catalog`, `pricing`, `purchasing`, `terminals`, `audit` ← `sync`; домены зависят только от `SyncJournal`/`SyncChanges` ядра — циклов нет |
| E4 | Запись в ленту | Тот же модуль ядра: `SyncChanges.record(trx, entityType, entityId, scopeStoreId?)`. Облачные писатели справочников (раздел 5.1) вызывают его в своей транзакции; на точке — пустая реализация. Пишем всегда, а не только при наличии офлайн-точек: строка дешёвая, а точка, ставшая офлайн позже, всё равно стартует со снимка |
| E5 | Секвенсор ленты — при чтении | **Уточнение ADR-0014 §3** (на отметку архитектора): номер `change_seq` присваивается не фоновым воркером раз в несколько секунд, а в начале каждого `GET /sync/changes` и снимка — `update … set change_seq = nextval(…) where change_seq is null order by id` под `pg_advisory_xact_lock('sync-feed', tenant)`. Инвариант ADR тот же: номер даёт один исполнитель после коммита, поэтому курсор не пропускает поздно закоммиченные изменения. Выгода: в облаке не появляется первый фоновый процесс и «единая точка задержки ленты». Цена: чтение ленты включает нумерацию накопленного |
| E6 | Фоновые задачи | `@nestjs/schedule` (назван в ADR-0014 §6) добавляется только для точки: прогон синхронизации по `tenant_settings.sync_interval_min`. В облаке фоновых задач нет (E5); секции `sync_inbox` создаются миграцией заранее, как у `stock_movements` |
| E7 | Версии | `protocolVersion = 1`, у всех типов операций и сущностей ленты `typeVersion = 1`. Цепочки upcast/downcast заводятся как пустые реестры (тождество) с местом для фикстур; первая настоящая версия 2 — отдельной задачей |
| E8 | Правила режима | `@CloudOnly()` на маршрутах, которых нет на точке (раздел 6.1): на точке — 404 `not_found` (guard по метаданным, как `@Authenticated`). Обратное правило облака уже есть: запись склада и кассы офлайн-точки — 409 `offline_store_read_only` (`StoreAccess`, `PosContext`); оно распространяется на `offline_pending` и на все пути записи фактов (терминалы точки, смены) |
| E9 | Аудит | `AuditService.appendFact(trx, row)` вставляет строку журнала точки как есть (`source = offline_store`, сотрудник и терминал точки), без контекста запроса; на батч облако добавляет одну запись `sync.batch-applied` |

### 3.2 Облако принимает операции (этап 1)

| # | Тема | Решение |
|---|---|---|
| E10 | Ключ точки | `license_keys` по модели данных 01. Формат `phk_<keyId>_<secret>`, секрет — `randomBytes(32)` base64url, хранится SHA-256, сравнение `timingSafeEqual`. Резолвер `resolve_license_key(key_id)` (SECURITY DEFINER, владелец `pharmacy_resolver`, только чтение `key_hash, tenant_id, store_id, status, valid_until`), вызов — через `ContextResolvers`. `LicenseKeyGuard` (маршруты `/sync/*` облака, `@Public()` для сессий) кладёт сеть и точку в контекст; `storeId` в теле обязан совпасть. Лимит частоты — по `keyId`, неудачные попытки — по IP |
| E11 | Выдача ключа до админки | Скрипт `scripts/issue-license-key.mjs --store <id> --valid-until <дата>` ролью `pharmacy_platform` печатает ключ один раз и пишет `platform_audit_log`; `scripts/revoke-license-key.mjs --store <id> [--hard]` — отзыв. Экраны «Лицензии» — с админкой (S2, этап 6) |
| E12 | Статусы лицензии | `active`, `expiring` (вычисляется: ≤ `notify_before_days`), `expired`, `revoked`, `revoked_hard`, плюс «точка закрыта» и «сеть заблокирована». Возвращаются в handshake и в заголовке `Pharmacy-License-Status` каждого ответа sync. `revoked`/`expired`/закрыта — приём операций ещё `revoked_key_grace_days` (30) дней, лента и снимки не выдаются; `revoked_hard` — 401 `license_revoked` |
| E13 | Настройки платформы | `platform_settings` + `feed_window_days` (90), `revoked_key_grace_days` (30), `min_supported_protocol` (1), `recommended_protocol` (1) — оператор меняет их позже экраном админки; до неё — значения миграции |
| E14 | Применение | По ADR §2, §4: `set_config` сети → `pg_advisory_xact_lock('sync-apply', store)` → `insert … on conflict do nothing returning` в `sync_inbox` → upcast → валидация (раздел 4.3) → применитель → статус `applied`. Повтор с тем же хешем — `duplicate`, с другим — `rejected` (`id_reused`). Одна операция — одна транзакция облака |
| E15 | Карантин и зависимости | Ошибка валидации или применения — откат, затем отдельной транзакцией `quarantined` + причина (код). Не найдена ссылка на факт той же точки (чек для возврата, отправка для приёма, смена для чека) — `pending_dependency`; такие операции точки переприменяются автоматически в конце каждого батча. Переприменение карантина вручную — с экраном админки (этап 6); до него — скрипт `scripts/reapply-quarantine.mjs --store <id>` |
| E16 | Номера документов | Точка нумерует свои документы, чеки и смены своими счётчиками (номер содержит код точки — уникален); облако хранит номера как есть и счётчики офлайн-точки не трогает. При переводе точки в облако счётчики облака для неё выставляются по максимуму применённых номеров (этап 5) |
| E17 | Долг поставщику | Точка долги не ведёт: на точке `SupplierLedger` — пустая реализация (порт). Облако при применении `document.posted` (приход, возврат поставщику) вызывает `SupplierLedger.receiptPosted` / `returnPosted` — тот же код, что у облачной точки |
| E18 | Цены при приходе и перемещении | Розница из строки прихода и копия цены отправителя при приёме перемещения на точке — локальные изменения цены этой точки: они едут в той же операции факта и применяются в облаке как `price.changed-locally` внутри неё (с тем же правилом конфликта, E25) |
| E19 | Сверка остатков | Операция `stock.checkpoint` (каждый прогон): число партий, сумма остатков и SHA-256 отсортированного списка `(batch_id, on_hand)` на позиции `storeSeq`. Облако считает то же по движениям точки до этой позиции; расхождение — `store_sync_status.checkpoint_mismatch` и уведомление (E30), без исправления |
| E20 | Наблюдаемость | `sync_runs` (прогон: версии, отправлено/применено/дубли/карантин, получено изменений, байты, ошибки, `correlationId`) и `store_sync_status` (последний успех, контакт, очередь и возраст старейшей операции по данным точки, лаг ленты, статус лицензии, версии, сдвиг часов, открытые конфликты, сверка). Логи — Nest `Logger` с `correlationId`, без тел операций, ключей и ПДн |

### 3.3 Лента и снимки (этап 2)

| # | Тема | Решение |
|---|---|---|
| E21 | Сущности ленты | Раздел 5.1. Не входят: `services` и биллинг (на точке им нет потребителя), `payment_methods` и `drug_reference` (таблиц нет), учётные данные сотрудников (ADR-0008, на точке свои) |

Курсор старше `feed_window_days` — 410 `resync_required`. Строки старше окна удаляются при нумерации (E5) — без отдельной задачи |

Наборы: `network` (настройки, юрлица, точки, политика возвратов), `catalog` (категории, справочники, товары со штрихкодами), `prices` (цены этой точки), `discounts`, `staff` (роли с правами, сотрудники с охватом), `suppliers`, `orders` (подтверждённые заказы точки), `transfers` (входящие в пути), `stock` (только при установке: партии, переносящие количества, счётчики номеров — E39) |

### 3.4 Точка (этап 3)

| # | Тема | Решение |
|---|---|---|
| E24 | Прогон | `SyncClient` точки: handshake `POST /sync/runs` → отправка outbox батчами (≤ 500 операций, ≤ 2 МБ, gzip) в порядке `storeSeq` → лента страницами (страница и курсор — одна локальная транзакция) → `POST /sync/runs/{id}/complete`. Один исполнитель (`pg_try_advisory_lock` на точке) и аренда строк (`lease_until`); HTTP-вызов — вне транзакции захвата; `fetch` Node с таймаутом 60 с, экспоненциальная пауза. Запуск: по расписанию (E6) и кнопкой «Синхронизировать сейчас» (`sync:run`). После прогона — удаление отправленных строк старше 30 дней. Настройки точки: `SYNC_BASE_URL`, `SYNC_LICENSE_KEY` (env-файл точки, в логи — никогда) |
| E25 | Локальные цены и конфликт | `price.changed-locally` несёт `basePriceVersion` (версию облачной цены, которую видела точка). В облаке версия совпала — цена точки становится ценой облака для этой точки (`price_source = store`); не совпала — облачная цена остаётся, открывается `sync_conflicts` (`price`). Владелец решает в кабинете (`keep: cloud` — облачная цена уходит на точку лентой; `local` — цена точки становится облачной). Проданные чеки не переоцениваются |
| E26 | Локальные товары и дубль | `product.created-locally` создаёт товар в облаке. Совпадение со штрихкодом сети — штрихкод не вставляется; совпадение штрихкода или МНН + форма + дозировка + производитель — `sync_conflicts` (`duplicate_product`), который лентой приходит на точку. Точка решает: «объединить с карточкой X» — алиас `merged_into_product_id` (факты не переписываются, отчёты и остатки агрегируют через алиас) или «оставить отдельно» — при совпавшем штрихкоде он остаётся только на точке. Решение — операция `product.duplicate-resolved` |
| E27 | Применение ленты на точке | Upsert по `id` в те же таблицы; удаление — архивирование. Сотрудник: профиль, охват и блокировка обновляются, учётные данные — нет; изменение роли, охвата или блокировки повышает `permissions_version` — сессии на точке перечитывают права (как в облаке). Входящее перемещение — документ «в пути» с партиями отправителя (номер, срок, цена закупки) для приёма |
| E28 | 7 дней без связи | На кассе и в шапке точки — баннер «Нет синхронизации N дней»; точка не блокируется (решение 2026-09-30). Истёкшая по сроку лицензия (по сроку из последнего ответа) — запрет новых чеков, документов и смен; просмотр, отчёты и досылка очереди остаются (ADR §7) |

### 3.6 Уточнения после проверки спецификации (решения автора)

| # | Тема | Решение |
|---|---|---|
| E34 | Перемещения с офлайн-точкой | Поддерживаются все пары: облако → офлайн, офлайн → облако, офлайн → офлайн. **Отзыв** перемещения, у которого хотя бы одна сторона офлайн, запрещён после отправки (409 `offline_transfer_no_recall`) — иначе отправитель и получатель могут разойтись; ошибочное перемещение исправляется обратным. **Недостача** при приёме списывается у отправителя его же записью: облачный отправитель — облаком при применении `transfer.accepted` (как сейчас); офлайн-отправитель — самой точкой: облако кладёт в ленту отправителя `transfer_result` (принятые количества), точка проводит своё списание `transfer_discrepancy` (операция `document.posted`). Облако склад офлайн-отправителя не пишет и его счётчики не трогает (E16) |
| E35 | Объединение дубля | При «объединить с карточкой X» точка проводит свой документ `product_merge` (операция `document.posted`): остаток каждой партии локального товара уходит с неё и приходит новой партией карточки X с тем же номером, сроком и закупочной ценой. Локальная карточка архивируется (`merged_into_product_id`), дальше на точке действуют цена, минимум и штрихкоды карточки X (из ленты). Касса, FEFO и остатки работают только с карточкой X; через алиас группируется лишь история в отчётах (`coalesce(merged_into_product_id, product_id)`) |
| E36 | Что точка делает со справочниками | Точка **создаёт** товар (`product.created-locally`), но не правит товары, категории, штрихкоды, минимумы и статусы — это `@CloudOnly()`; после синхронизации карточку правит облако, правки приходят лентой. Учётные данные сотрудников точки — её собственные (ADR-0008): сброс пароля, PIN, коды первого входа на точке доступны и не синхронизируются; профиль, роль, охват и блокировка — `@CloudOnly()` |
| E37 | Заказы и заявки | Подтверждённые заказы поставщику этой точки идут на точку лентой (`purchase_order`, только чтение) — приход на точке «по заказу» работает как в облаке; облачный применитель прихода сдвигает статус заказа тем же кодом (`OrderReceiving`). Заявки на перемещение ведутся в облаке; их статус двигают применители отправки и приёма |
| E38 | Цена во время конфликта | Облачная цена, изменённая до прихода локальной, уже в ленте — точка получает её следующим прогоном и продаёт по ней, пока владелец не решит. «Оставить цену точки» делает её облачной и снова отправляет на точку. Продажи по локальной цене до этого — факты |
| E39 | Установка — объём | По ADR-0014 решение 4: **новая офлайн-точка** (заведена в облаке, торговли в облаке не было; остатки вводятся на точке начальными остатками) и **переустановка после потери ПК** (снимок `stock` с переносящими движениями). Переустановка: старый ключ — `revoked_hard`, новый ключ; терминалы точки отзываются; незакрытые смены закрываются облаком с причиной «ПК точки утерян» (аудит); в комплект входят счётчики номеров = максимум применённых (E16). Перевод облачной торгующей точки в офлайн — после MVP |
| E40 | `sync_inbox` без секций | **Поправка модели данных 06** (на отметку архитектора): секции по `received_at` ломают дедупликацию — ключ секционированной таблицы обязан включать `received_at`, и повтор в следующем месяце не попадёт в `on conflict`. Ключ — ровно `(tenant_id, store_id, operation_id)` (ADR §2), таблица без секций; архивация сырых конвертов — позже (раздел 10) |
| E41 | Закрытие офлайн-точки | Сначала перевод в облако (E32), затем обычное закрытие точки. Своего сценария закрытия на точке нет |

## 4. Точка → облако: операции

### 4.1 Конверт

`SyncEnvelope { protocolVersion, batchId, storeId, operations: SyncOperation[] }`;
`SyncOperation { operationId (UUIDv7), storeSeq, type, typeVersion, payloadHash, correlationId, occurredAt, actor
{ employeeId, terminalId }, payload }`. Ответ — `{ results: [{ operationId, status, reason? }] }`, статусы
`applied` / `duplicate` / `quarantined` / `rejected` / `pending_dependency`. Контракты — `libs/shared/dto`
(`sync-protocol.ts`), JSON camelCase.

### 4.2 Типы операций (payload — всё, что факт записал)

| Тип | Сервис на точке | Содержимое |
|---|---|---|
| `receipt.completed` | `ReceiptsService.create` | чек, строки, оплаты, записи ПКУ, движения (партии, количества), аудит |
| `return.completed` | `ReturnsService.create` | возврат, строки, возвраты денег, движения; автосписание брака/истёкшего — документ, строки, движения в той же операции |
| `document.posted` | `DocumentPosting`, `WriteOffPosting`, `StockCountPosting`, `SupplierReturnPosting` | документ со строками, новые партии, движения, цены из строк прихода (E18), аудит |
| `transfer.dispatched` | `TransferPosting.send` | документ, строки, движения отправки |
| `transfer.accepted` | `TransferPosting.accept` | приём: партии получателя, движения, принятые количества (недостача — по E34), копия цены (E18) |
| `shift.opened` / `shift.cash-collected` / `shift.closed` | `ShiftsService` | смена, операции кассы, закрытие и Z-отчёт |
| `product.created-locally` | `ProductsService.create` | товар, штрихкоды |
| `product.duplicate-resolved` | новый маршрут точки | конфликт, решение, карточка |
| `price.changed-locally` | `PricesService.update` (только своя точка) | товар, цена, `basePriceVersion` |
| `terminal.bound` / `terminal.revoked` | `TerminalsService` | терминал |
| `audit.recorded` | `AuditService` (события без доменной операции: входы, неверные PIN, отказы) | строка журнала |
| `stock.checkpoint` | `SyncClient` | сверка (E19) |

Перемещение офлайн-точка ↔ облачная точка: отправка с офлайн-точки приходит `transfer.dispatched`, облачная точка
принимает как обычно; отправка из облака на офлайн-точку уходит лентой «в пути», приём — `transfer.accepted`.
Недостача списывается у отправителя его же записью (E34); отзыв перемещения с офлайн-стороной запрещён.

### 4.3 Валидация в облаке

Сеть и точка из ключа; все ссылки — на сущности этой сети (товары, партии, сотрудники, документы точки); деньги —
целые дирамы; сумма строк = итог; знаки движений по виду; повторный id сущности в другой операции — карантин.
Остаток не проверяется (ADR §4, «продажа — факт»). Дата в закрытом периоде — принимается с пометкой (модель 03).

## 6. Точка

### 6.1 Модули и правила режима

Регистрируются на точке: `stores` (чтение), `staff` (чтение сотрудников и ролей, свои PIN/пароль — уже), `catalog`,
`pricing` (цены своей точки), `inventory`, `pos`, `returns`, `purchasing` (поставщики — чтение), `notifications`,
`reports` (по данным точки), `terminals`, `sync` (клиентская часть).

`@CloudOnly()` (E8): заказы поставщикам, оплаты и расчёты с поставщиками, заявки на перемещение, отмена проведения,
управление сотрудниками, ролями, точками и юрлицами, настройки сети, скидочные правила, цены других точек, прочие
расходы, биллинг и услуги, кабинет оператора. Web точки скрывает их по `deployment.kind = 'offline-store'`
(маршрут `GET /deployment` на точке возвращает этот вид).

### 6.2 Web на точке

Та же сборка `apps/web`. Страница «Офлайн-точка» в виде точки, баннер E28, скрытие облачных разделов. Буфер перебоев
кассы (ADR-0015) на точке не нужен (API локальный), Service Worker — только в облачной сборке (как сейчас).

## 12. Проверка

Новых автотестов нет (решение «тесты до MVP»); существующие наборы — зелёные, `npm run check` — у пользователя.

Живая проверка (S3):
- этапы 1–2: скрипт curl с ключом точки: батч каждого типа — `applied`; повтор — `duplicate`; изменённый payload с тем
  же id — `rejected`; ссылка на чужую сеть — `quarantined`; возврат раньше чека — `pending_dependency`, затем
  `applied`; сверка совпала и не совпала; лента после правки каталога, цены, сотрудника — одна строка на сущность,
  курсор не теряет поздний коммит; `resync_required` по старому курсору; отозванный ключ — приём 30 дней, ленты нет;
  `revoked_hard` — 401;
- этап 3 и дальше: облако `:3000` и точка (второй экземпляр, база `pharmacy_store`): продажа, возврат, приход,
  перемещение в обе стороны, смена на точке без связи → связь → отчёты и остатки облака = точки; правка цены в облаке и
  на точке → конфликт → решение владельца → цена на точке; локальный товар с занятым штрихкодом → дубль → решение на
  точке; блокировка сотрудника в облаке → на точке после прогона.

## 13. Решения при реализации

**PR 2a (2026-10-19, локальные цены и товары):**
- PR 2 разбит на три: 2a — `price.changed-locally`, `product.created-locally`, `product.duplicate-resolved`; 2b —
  `document.posted`; 2c — перемещения и правила режима `offline_pending`.
- Открытый конфликт — не больше одного на (точка, вид, сущность). Повторная правка цены точки по устаревшей версии
  обновляет открытый конфликт; правка по актуальной версии применяется и закрывает его решением `local` (E38).
- Слитая карточка (E35) — `status = archived` + `merged_into_product_id`, отдельного статуса `merged` нет. Её
  штрихкоды переходят на карточку сети, чтобы скан находил тот же товар.
- `merge` возможен только с карточкой, найденной в конфликте (`merge_target_mismatch`).
- Чек с товаром точки ждёт партию (`pending_dependency`), пока её не привезёт `document.posted` (PR 2b).
- Группировка истории отчётов через алиас — с отчётами владельца (PR 5).
