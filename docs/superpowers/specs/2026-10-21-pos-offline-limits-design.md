## 1. Цель и критерии успеха

Касса облачной точки доводится до решений архитектора 2026-09-30 о буфере перебоев (ADR-0015): касса без связи
продаёт ПКУ в пределах, блокирует продажи при переполненном буфере, печатает локальный номер чека и досылает буфер,
даже если PIN-сессия кассира истекла, пока не было связи. Данные рецептов удаляются по сроку хранения сети, журнал
ПКУ показывает время продажи и время получения сервером.

Успех:
- чек без связи печатается с локальным номером терминала в смене и кодом чека; по коду кассир находит чек для
  возврата после его отправки;
- продажа ПКУ без связи разрешена, пока в буфере меньше 20 чеков с ПКУ и самому старому меньше 8 часов (параметры
  сети); после — ПКУ не продаётся до отправки;
- при 500 операциях в буфере или самой старой старше 24 часов (параметры сети) касса не принимает новые чеки до
  отправки; с 80 % любого предела кассир видит предупреждение;
- операции буфера, совершённые при живой сессии кассира, доставляются после восстановления связи без нового входа
  по PIN — в том числе после перезагрузки ПК и при входе другого сотрудника; операция от имени кассира, который не
  держал терминал в момент операции, уходит в карантин; касса без связи не создаёт операций, которые сервер не
  примет по возрасту входа кассира;
- данные рецепта старше срока сети (по умолчанию 90 дней) удаляются в течение часа после истечения срока, строка
  журнала остаётся с пометкой «удалены по сроку»; другие изменения записей ПКУ база по-прежнему запрещает.

## 2. Решения автора (не обсуждались — проверить при чтении)

| # | Вопрос | Решение |
|---|---|---|
| P1 | Экран журнала ПКУ | Отдельного экрана нет: журнал — отчёты владельца «Журнал ПКУ» и «ПКУ: сводка» (O6, право `reports:view`). PR 3 добавляет в «Журнал ПКУ» колонку **«Получено»** — время приёма чека сервером рядом с «Продано» (ADR-0015: журнал «с временем «продано» и «получено»»). Из записи ПКУ отчёт читает только поля рецепта (номер, дата, клиника, врач), данные покупателя не покидают базу |
| P2 | Срок хранения рецептов | `tenant_settings.prescription_retention_days` (есть в БД, 90 дней) выводится на экран «Настройки» владельца: 1–3650 дней, `settings:update` с подтверждением паролем, аудит `settings.updated` |
| P3 | Очистка по сроку | Раз в час таймером процесса API (без библиотеки и без `job_queue`) «по тенанту в цикле» (ADR-0013 §4): у записей ПКУ, проданных раньше срока и ещё содержащих данные, обнуляются `prescription_note` и `prescription_file_id`, ставится `prescription_purged_at`. До 5000 записей сети за проход; первый проход через минуту после старта. Несколько экземпляров API не мешают друг другу: `pg_try_advisory_xact_lock` по сети, обновление идемпотентно. Очищаются сети любого статуса. Поправка ADR-0013 |
| P4 | Запрет изменений | Триггер `controlled_sale_records` разрешает `UPDATE` только трёх колонок и только в сторону очистки (модель 04); `DELETE` и `TRUNCATE` по-прежнему запрещены. `pharmacy_app` получает `update` только на эти три колонки |
| P5 | Рецепты в конвертах офлайн-точек | Тот же проход удаляет данные рецепта из конвертов `sync_inbox` операций `receipt.completed`, полученных раньше срока (до 1000 конвертов сети за проход), — портом модуля `sync`. Копии БД (ADR-0019) хранят очищенные данные ещё до 30 дней: фактический срок — «срок сети + 30 дней», это дописывается в отклонения от ТЗ (п. 7) |
| P6 | Пределы буфера | Параметры сети в `tenant_settings`: общий — **24 часа** (1–72) и **500 операций** (50–2000); ПКУ — **8 часов** (1–24) и **20 чеков** (1–200); пределы ПКУ не больше общих. Касса получает их в `settings` снимка каталога, поэтому знает их без связи; до первого снимка действуют значения по умолчанию |
| P7 | Что считается | Операции буфера терминала в состоянии «ждёт отправки», в том числе на паузе. Карантин не считается: он ждёт разбора, а не связи. Возраст — от времени записи в буфер самой старой операции. Предел ПКУ — чеки буфера хотя бы с одной строкой ПКУ |
| P8 | Что блокируется | Общий предел — новые чеки («Оплатить»); внесение, изъятие и закрытие смены разрешены, чтобы кассир мог сдать кассу. Предел ПКУ — добавление ПКУ в чек и оплата чека с ПКУ. Блокировка не зависит от индикатора связи: при работающей досылке буфер пустеет за секунды. Правило E17 «ПКУ без связи — запрет» заменяется пределом |
| P9 | Досылка под терминалом | Четыре маршрута буфера (`POST /receipts`, `POST /shifts`, `POST /shifts/{id}/cash-movements`, `POST /shifts/{id}/closure`) различают два случая. **Своя операция** — у запроса PIN-сессия этого терминала и автор операции — сотрудник сессии: всё как сейчас (E3, право маршрута у сессии). **Под терминалом** — все остальные запросы с device-cookie неотозванного терминала активной сети: сессии нет, она истекла по простою или по абсолютному сроку, вход по паролю на браузере терминала, PIN-сессия другого кассира. Сеть, точка и терминал берутся из терминала, право маршрута у сессии не проверяется (права автора — K7). Без device-cookie — как сейчас: 401 без сессии, 403 `terminal_required` при входе по паролю. Остальные маршруты не меняются |
| P10 | «Активная сессия автора на момент операции» | Проверяется у каждой операции под терминалом (P9), то есть всегда, когда автор — не сотрудник сессии запроса. Без связи касса не продлевает сессию на сервере, поэтому простой не учитывается. Терминал «держит» тот, кто последним вошёл на нём по PIN (аудит `auth.pin-succeeded` терминала). Операция принимается, если в окне ±5 минут вокруг момента операции (E4, после поправки часов; запас — на скачок часов ПК между продажей и отправкой) терминал держал автор, а его вход не раньше чем за общий предел буфера в часах (P6) до момента операции. Иначе — 422 `author_session_missing`, операция уходит в карантин. Права автора — как в K7: неактивен, вне охвата или без права — пометка `author` |
| P11 | Аудит под терминалом | `employee_id` записи аудита — автор операции, `terminal_id` — терминал, в деталях `via: 'terminal'` |
| P12 | Локальный номер | Порядковый номер чека терминала в смене (1, 2, …). Касса присваивает его всем чекам — со связью и без — при «Оплатить», в той же транзакции IndexedDB, что и запись в буфер. Счётчик ведётся по id смены; при чтении текущей смены он поднимается до «чеков смены на сервере + 1» (на случай очистки данных браузера). В API — `localNumber` чека (у операций, записанных до обновления, его нет), колонка `receipts.local_number` без уникальности |
| P13 | Печать без связи | Чек без номера ЧК печатается с «Чек № {n} · код {XXXXXXXX}» и «номер ЧК — после отправки»; код — последние 8 символов id чека (UUIDv7, случайная часть) заглавными. Чек со связью печатается с номером ЧК, как сейчас |
| P14 | Возврат по коду | `GET /receipts/returnable?number=` принимает и код из 8 шестнадцатеричных символов: ищется чек точки, проданный в пределах срока возврата, id которого оканчивается на код. Не найден — 404, найдено несколько — 409 `receipt_code_ambiguous` (кассир ищет продажу по товару и дате). Карточка чека для возврата показывает «без связи № n», если локальный номер есть |
| P15 | Моки | Моки принимают `localNumber`, код при поиске чека, новые настройки и пределы в снимке. Досылку под терминалом моки не моделируют: в них нет истечения сессий. Мок отчётов перестаёт терять `prescriptionPurged` и `piecesPerPack` строки |
| P16 | Офлайн-точка | Касса точки пока работает без API (модуль `pos` регистрируется только в облаке). Пределы и очистка рецептов на самой точке появятся вместе с её кассой (ADR-0014). Таймер очистки работает только в облаке |
| P17 | Возраст входа кассира | Чтобы касса не копила операции, которые сервер по P10 не примет, она останавливает **все** операции буфера (продажи и операции смены), когда со входа кассира по PIN (`authenticatedAt` сессии) прошёл общий предел буфера в часах. Сообщение: «Вход кассира старше {h} ч — войдите по PIN заново (нужна связь)». Со связью сервер раньше завершает сессию по абсолютному сроку (12 ч), поэтому правило срабатывает только без связи |
| P18 | Досылка с экрана входа | Буфер досылается и без сессии — с экрана входа после перезагрузки страницы или ПК. Среда отправки создаётся по привязанному терминалу, а не только по сессии: `GET /terminals/current` получает `tenantId` (`BoundTerminal.tenantId`), без связи берётся запомненный терминал. Ответ 401 при чтении сессии не удаляет буфер и запомненный терминал |

## 3. Схема — миграция `pos-offline-limits`

Номер миграции — выше всех существующих (последняя на main — `1792556744322_import-jobs`); перед добавлением
сверить ветки, основную папку и общие базы. `set local lock_timeout = '5s'`.

- `tenant_settings`:
  - `pos_buffer_max_hours smallint not null default 24` (1–72);
  - `pos_buffer_max_operations integer not null default 500` (50–2000);
  - `pos_controlled_max_hours smallint not null default 8` (1–24);
  - `pos_controlled_max_operations smallint not null default 20` (1–200);
  - проверка: `pos_controlled_max_hours <= pos_buffer_max_hours` и `pos_controlled_max_operations <=
    pos_buffer_max_operations`.
- `receipts.local_number integer null check (local_number between 1 and 999999)`.
- `controlled_sale_records`:
  - триггер `controlled_sale_records_no_update_delete` заменяется на `controlled_sale_records_no_delete` (`before
    delete`, `pharmacy.forbid_mutation()`) и `controlled_sale_records_purge_only` (`before update`, новая функция
    `pharmacy.controlled_purge_only()`): изменение допускается, только если `old.prescription_purged_at is null`,
    `new.prescription_purged_at is not null`, `new.prescription_note is null`, `new.prescription_file_id is null`, а
    остальные колонки не изменились; иначе ошибка 42501, как у `forbid_mutation()`. `controlled_sale_records_no_truncate`
    остаётся;
  - `grant update (prescription_file_id, prescription_note, prescription_purged_at) to pharmacy_app`;
  - частичный индекс `(tenant_id, recorded_at) where prescription_purged_at is null` для прохода очистки.
- Таблица остаётся в `APPEND_ONLY_TABLES` (строки не удаляются); комментарий манифеста называет исключение очистки.
- Поиск по коду (P14) идёт по чекам точки за срок возврата: при планировании проверить индекс `receipts`
  `(tenant_id, store_id, sold_at)`, при отсутствии — добавить в эту миграцию.

## 4. API (`apps/api`)

### 4.1 Досылка под терминалом (P9–P11)

- `SessionMiddleware`: запрос с device-cookie разрешает терминал (`resolve_terminal`, как `GET /terminals/current`)
  и запоминает его в контексте запроса (сеть, точка, терминал) и тогда, когда действующей сессии нет. Принципала-
  сотрудника у запроса без сессии нет; PIN-сессия с чужим device-cookie по-прежнему уничтожается.
- Маршруты буфера помечаются декоратором (например, `@BufferReplay()`). Случай P9 выбирается по телу операции
  (автор = сотрудник PIN-сессии этого терминала → своя операция, иначе — под терминалом). Под терминалом `AuthGuard`
  пропускает запрос без сессии, а проверка права маршрута у сессии не выполняется: права проверяются у автора (K7).
  Остальные маршруты не меняются. CSRF — как у всех запросов, лимит запросов под терминалом — по терминалу.
- `pos` (`pos-context.ts`): под терминалом точка и терминал тела должны совпасть с терминалом (иначе 409
  `wrong_terminal`), точка — облачная и активная; автор — сотрудник сети (иначе 422 `author_not_allowed`) с
  активной сессией по P10 (иначе 422 `author_session_missing`); пометка `author` — по K7. Дальше операция идёт тем же
  путём, что своя: идемпотентность, момент операции по E4, пометки, аудит (P11). Пометка «онлайн-операция другим
  сотрудником» (E3, 60 секунд) сохраняется.
- Проверка P10 читает `audit_log` по индексу точки: входы `auth.pin-succeeded` этого терминала с `recorded_at` от
  «момент − `pos_buffer_max_hours`» до «момент + 5 минут». Терминал держит автор, если хотя бы в одной точке окна
  «момент ± 5 минут» последним вошедшим был автор.
- `GET /terminals/current` (публичный, по device-cookie) отдаёт и `tenantId` (P18).

### 4.2 Локальный номер и поиск по коду (P12–P14)

- `CreateReceiptRequest.localNumber` — необязательное целое 1–999999; хранится в `receipts.local_number`, попадает в
  детали аудита `receipt.completed`. Чеки офлайн-точек (синхронизация) не меняются: номера ЧК им выдаёт точка.
- `GET /receipts/returnable?number=`: значение из ровно 8 шестнадцатеричных символов — код (P14), иначе — номер ЧК,
  как сейчас. `ReturnableReceipt.localNumber: number | null`.

### 4.3 Настройки и снимок (P2, P6)

- `NetworkSettings` и `UpdateNetworkSettingsRequest` получают `prescriptionRetentionDays`, `posBufferMaxHours`,
  `posBufferMaxOperations`, `posControlledMaxHours`, `posControlledMaxOperations` с границами из раздела 3; пределы
  ПКУ больше общих — 400 `validation_failed` с полем. Сохранение — тот же `PUT /settings` (подтверждение паролем,
  аудит `settings.updated` до и после).
- `PosStoreSettings.bufferLimits: { maxHours, maxOperations, controlledMaxHours, controlledMaxOperations }` в снимке
  каталога (E16) — из настроек сети через тот же порт, что `returnWindowDays`.

### 4.4 Журнал ПКУ (P1)

- Отчёт `controlled`: новая колонка `received` (дата и время, `receipts.received_at`) после `at`. У чеков, принятых
  сразу, значения почти совпадают; у чеков из буфера и офлайн-точек видна задержка.
- Запрос отчёта читает из `prescription_note` только `prescriptionNumber`, `prescriptionDate`, `clinic`, `doctor`.

### 4.5 Очистка рецептов (P3–P5)

- **Оркестратор** — платформенный модуль `app/platform/retention` (только облако). Таймер `setInterval` раз в 60
  минут (`unref()`, первый проход через 60 секунд, наложение проходов исключено флагом процесса). Список сетей
  читается под `pharmacy_platform`, для каждой сети вызываются порты тенантских модулей в `runWithContext({ tenantId,
  correlationId })` и `tenantTransaction` под `pharmacy_app` (как статистика админки). Ошибка одной сети пишется в
  лог и не останавливает цикл.
- **Порт `pos`** (`PrescriptionRetention`): `pg_try_advisory_xact_lock` по сети (занято — пропуск); срок из
  настроек сети; до 5000 записей с `recorded_at < now() − срок`, `prescription_purged_at is null` и непустыми данными
  обнуляются одним `update` по индексу раздела 3.
- **Порт `sync`** (`InboxRetention`): у конвертов `receipt.completed` с `received_at` старше срока из записей ПКУ
  удаляются `prescriptionNote` и `prescriptionFileId`; `payload_hash` не меняется (повтор операции сравнивается с
  исходным хешем).
- **След:** если в сети что-то очищено, в `audit_log` пишется одно событие `controlled.prescriptions-purged` с числом
  записей и конвертов (без данных, `employee_id` пуст); лог — число записей по сети, без данных рецептов.

## 5. Ошибки (RFC 7807)

| Код | Статус | Когда |
|---|---|---|
| `author_session_missing` | 422 | Под терминалом: в момент операции (±5 минут) терминал держал не автор, или вход автора старше предела буфера (P10) |
| `receipt_code_ambiguous` | 409 | Поиск чека для возврата: код подходит к нескольким чекам точки (P14) |

Остальные коды не меняются. В web оба кода показываются понятным текстом: первый — в «Требует разбора» смены
(«В момент операции на этом терминале не было входа этого кассира»), второй — на экране возврата.

## 6. Web (`apps/web`)

- **Буфер** (`shared/lib/offline-queue`): запись буфера получает признак `controlled` (чек со строкой ПКУ; новое
  поле записи не требует новой версии базы IndexedDB); `OutboxCounts` дополняется временем самой старой ожидающей
  операции, числом ожидающих чеков с ПКУ и временем самого старого из них. Чистая функция состояния буфера по
  счётчикам, пределам и текущему времени даёт `ok` / `warn` (от 80 %) / `blocked` отдельно для общего предела и для
  ПКУ.
- **Касса** (`features/pos`, `pages/pos`):
  - «Оплатить» при общем пределе заблокировано с причиной; на экране — плашка «Продажи остановлены: буфер заполнен
    ({n} из {max} или старше {h} ч). Продажи возобновятся после отправки»;
  - ПКУ при пределе ПКУ: добавление и оплата заблокированы с сообщением; проверки «нет связи» E17 удаляются;
  - возраст входа (P17): при `authenticatedAt` старше общего предела в часах заблокированы продажа и операции смены,
    на экране — «Вход кассира старше {h} ч — войдите по PIN заново (нужна связь)»;
  - локальный номер (P12): счётчик в хранилище `state` по id смены, присвоение в транзакции `enqueueSale`, подъём при
    чтении текущей смены;
  - печать (P13): «Чек № {n} · код {XXXXXXXX}» и «номер ЧК — после отправки», если номера ЧК нет.
- **Экран входа и среда отправки** (P18, `entities/terminal`, `pages/login`): среда отправки буфера создаётся по
  сессии или, без неё, по привязанному терминалу (`BoundTerminal.tenantId` и точка; без связи — запомненный терминал
  из `terminal-cache`); на экране входа виден счётчик неотправленных операций. 401 при чтении сессии больше не
  забывает терминал; буфер не удаляется никогда (ADR-0015).
- **Шапка** (`widgets/app-shell/ConnectionStatus`): при `warn` — «Буфер почти заполнен: {n} из {max} · старейшая
  {h} ч»; при `blocked` — «Продажи остановлены: буфер заполнен».
- **Настройки** (`pages/owner/settings`): карточка «Касса без связи и рецепты» — пять полей P2 и P6 с границами и
  подсказкой, что пределы ПКУ не больше общих.
- **Возврат**: поле поиска — «Номер чека или код с чека»; карточка — «без связи № {n}»; ошибка
  `receipt_code_ambiguous`.
- **Отчёты**: колонка «Получено» приходит с сервера (колонки отчёта серверные), в моках добавляется.
- **Моки** — по P15; тексты RU/TJ; ключи RU и TJ совпадают (`messages.spec.ts`).

## 10. Уточнения 2026-10-21 (при планировании и реализации)

Поведение разделов 2–6 не меняется.

- **У1.** Device-cookie разрешает не `SessionMiddleware`, а `BufferReplayInterceptor` модуля `pos`, и только на четырёх
  маршрутах буфера: middleware работает на каждом запросе и обращался бы к базе на каждом гостевом запросе терминала.
- **У2.** Событие `controlled.prescriptions-purged` не входит в группы журнала (`audit-groups.ts`): журнал показывает
  его по собственной подписи.
- **У3.** Поиск по коду (P14) ограничен бизнес-датой «сегодня − срок возврата» и идёт по индексу
  `receipts_store_date_idx`; нового индекса нет.
- **У4.** Лимит запросов под терминалом — по IP, как у гостя, а не по device-cookie (§4.1): лимит проверяется до
  проверки cookie, и ключ по непроверенному cookie позволил бы гостю обходить лимит по IP, подставляя случайные
  значения. Буфер повторяет 429 с задержкой.
- **У5.** Колонка «Получено» журнала ПКУ — ключ `receivedAt`: `received` уже подписан «Приход» в сводке ПКУ, подписи
  колонок общие для отчётов.
- **У6.** Возраст входа (P17) останавливает и операции смены на экране «Смена» (открытие, внесение, изъятие, закрытие).

Уточнения по итогам финального ревью:

- **У7.** Момент проверки P10 — момент E4 с его границами: не позже приёма сервером, не старше 30 дней, а у чека,
  внесения, изъятия и закрытия — не раньше открытия смены операции. Иначе клиент мог бы указать любой прошлый момент
  и выдать операцию за любого, кто когда-либо держал терминал.
- **У8.** Пометка M10 «онлайн-операция другим сотрудником» ставится и под терминалом без сессии: операция, принятая в
  течение 60 секунд после её момента, когда никто не вошёл, помечается `author`. Так виден чек, проданный после
  истечения сессии кассира по простою.
- **У9.** Событие `controlled.prescriptions-purged` пишется в транзакции своей очистки: у записей — `{ records }`, у
  конвертов — `{ envelopes }` (вместо одного события на проход). Сбой очистки конвертов не теряет след очищенных
  записей. Очистку конвертов тоже защищает try-lock по сети.
- **У10.** Очистка конвертов выбирает их предикатом jsonpath, который не падает на конверте другой формы. Под него
  добавлен частичный индекс `sync_inbox_prescription_purge_idx`. Очищаются `controlledRecords` и как список, и как одна
  запись.
- **У11.** Локальный номер есть у всех чеков (P12), поэтому карточка возврата подписывает его «на кассе № n», а не
  «без связи № n» (P14).
- **У12.** С 80 % предела ПКУ в шапке появляется предупреждение «ПКУ без связи: n из max чеков», при пределе — «Продажа
  ПКУ без связи остановлена» (§1).

Уточнения по мелким замечаниям финального ревью:

- **У13.** Смена отдаёт `lastLocalNumber` — наибольший локальный номер своих чеков; касса после очистки данных браузера
  продолжает счёт после него, а не после числа чеков (номер доставленного чека не повторится).
- **У14.** Очищенная запись ПКУ в конверте офлайн-точки получает `prescriptionPurged: true`; конверт, применённый позже
  из карантина, создаёт запись уже очищенной («удалены по сроку»), а не «без данных».
- **У15.** Вход по паролю на браузере терминала тоже отправляет буфер терминала (среда отправки — по привязанному
  терминалу); пока привязка не прочитана, буфер не отправляется — браузер, перепривязанный к другой точке, не шлёт
  буфер старой точки новым device-cookie.
- **У16.** Входы по PIN для проверки P10 читаются по частичному индексу `audit_log (tenant_id, terminal_id,
  recorded_at) where action = 'auth.pin-succeeded'`, только облачные. Проверка `receipts.local_number` добавлена
  `NOT VALID` и проверяется отдельной миграцией.

Уточнение по итогам ревью безопасности 2026-10-22 (`docs/architecture/reviews/2026-10-22-security-review.md`):

- **У17.** Граница У7 есть и у открытия смены: его момент — и для проверки P10, и в `opened_at` — не раньше закрытия
  последней смены терминала. Без неё открытие задним числом (до 30 дней) называло автором любого, кто держал терминал
  тогда, а следующие операции смены наследовали эту границу. Момент раньше закрытия сдвигается к нему, а не
  отклоняется: часы ПК могли уйти назад, а в буфере закрытие прошлой смены всегда идёт до следующего открытия.
  - Если закрытие прошлой смены закоммичено после проверки P10, автор проверен по старой границе. Тогда открытие
    получает 409 `shift_open` (карантин буфера). Законный буфер шлёт закрытие и открытие по очереди и сюда не попадает.
  - Пометка M10 считается по моменту после сдвига: момент, указанный раньше границы, может оказаться «живым».
  - Граница никогда не позже приёма сервером.
  - Остаток риска: у терминала, на котором ещё не закрывали смену, граница прежняя — 30 дней. Вход раньше привязки
    терминала невозможен. Граница «приём − предел буфера» отправила бы в карантин законный буфер, который ждал
    связи дольше предела.
