# Нагрузочный прогон кассы: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** узнать, выдерживает ли облачный API кассы нагрузку пилота с ростом ×5 на данных за год работы сети: бюджеты
ADR-0009 по p97.5 и p99, ни одного 5xx, ни одного дубля чека. Каждый промах — найденная причина (`EXPLAIN`).

**Architecture:**
- Отдельная база `pharmacy_load` в dev-контейнере PostgreSQL, как у интеграционных тестов: пустая база, затем
  `02-database.sql`, затем все миграции. Dev-база не трогается.
- Год истории создаёт SQL-генератор `tools/load/generate.sql`. Он запускается суперпользователем, только в
  `pharmacy_load`, по месяцам.
- PIN, терминалы, смены и сессии создаются через API: хеш PIN требует pepper среды, а cookie устройства — секрет,
  известный только API.
- API — собранный `apps/api/dist/main.js` с настройками прода по умолчанию, свой порт, отдельная логическая БД Redis.
- Нагрузку дают параллельные экземпляры autocannon, по одному на поток запросов. У каждого соединения своя сессия
  кассира или заведующего. Задержки считаются по каждому потоку. Инварианты проверяются SQL-запросами после прогона.

**Tech Stack:** Node.js 24 (`.mjs`, как `tools/scripts`), autocannon 8.0.0 (MIT, dev-зависимость), PostgreSQL 17 (psql
через `docker exec`), Redis 8, собранный API.

**Spec:** ADR-0009, ось «Ж. Нагрузочное тестирование кассы» и раздел «Бюджеты API кассы»
(`docs/architecture/adr/0009-instrumenty-testirovaniya-i-porogi-kachestva.md`). Отдельной спецификации нет:
инструмент, профиль, бюджеты и объём данных решены в ADR. Уточнения при планировании — ниже.

## Global Constraints

- Только база `pharmacy_load` и логическая БД Redis 13. Никогда dev `pharmacy`, `pharmacy_test`, стенд pharmacy-test или
  прод. Скрипт отказывается работать с базой, имя которой не `pharmacy_load`.
- Данные синтетические: имена — «Кассир 001», товары — из списка МНН с выдуманными формами, штрихкоды EAN-13 с
  верной контрольной цифрой из диапазона 290…, ИНН — `9`-значные выдуманные.
- Значения `.env` (пароли БД, ключи JWT, pepper) читаются программно и не печатаются; cookie и PIN в отчёты не
  попадают.
- Зависимость — только `autocannon@8.0.0` точной версией в `devDependencies`. Других нет.
- Тесты отложены до MVP. Это замер, а не автотест; в CI не входит.
- Ни одной миграции. Индексы и исправления по находкам — отдельный план.
- Полный `npm run check` запускает пользователь. Перед просьбой о нём — `npx nx run-many -t typecheck`.
- Коммиты — `--no-gpg-sign`, Conventional Commits, `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Повторный запуск на той же базе.** Владелец уже активирован, терминалы привязаны, смены открыты. Подготовка
   должна пройти снова без ручной чистки. Задача 3, шаг 5.
2. **Лимиты не выдаются за медленный ответ.** 429 считаются отдельно и в задержки не входят. В профиле их должно
   быть 0. Задача 4, шаг 5.
3. **Ошибки не прячутся в процентилях.** Ответы не 2xx исключаются из задержек и считаются по кодам. Один 5xx —
   FAIL прогона. Задача 4, шаг 5.
4. **Кончается диск посреди генерации.** Генерация идёт по месяцам, между ними — проверка размера. Обрыв не
   оставляет базу в неясном состоянии: `verify` говорит, что загружено. Задача 2, шаг 4.
5. **Секреты.** Значения `.env` не печатаются, `.state/` и `results/` в `.gitignore`, в отчётах нет cookie. Задачи 1
   и 4.
