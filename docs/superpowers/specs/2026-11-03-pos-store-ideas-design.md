# Экран покупателя, товар по штрихкоду, история цен, опт, камера и QR оплаты — спецификация

Дата: 2026-11-03. Основа — сравнение с проектом safopharm (SWOT 2026-11-02). Пользователь выбрал идеи 1–6 из этого
сравнения и попросил спецификацию без вопросов. Все решения ниже — решения автора, на утверждение вместе со
спецификацией.

Код safopharm не используется ни в каком виде: это взломанная копия коммерческого скрипта (iNilabs, CodeCanyon). Из
сравнения взяты только идеи, реализация — своя, на стеке проекта.

**Статус:** утверждена архитектором 2026-11-03 (APPROVAL.md). Поправки ADR-0015 и ADR-0022 и ADR-0025 принимаются
отдельно, до кода своих PR. Уточнения, найденные при планировании PR 1, — в плане `2026-11-03-pos-store-ideas-pr1.md`.

## 1. Цель

Шесть доработок кассы и склада для пилота:

## 2. Общие правила

- Права проверяет только сервер; web скрывает недоступное (ADR-0018).
- Новые тексты — RU и TJ, с бюджетом длины +40 %. Цвета и размеры — только токены `--ph-*`.
- Деньги — целые дирамы. Формат на экране — `formatMoney`; в ссылке QR (I6) — сомони с точкой (п. D35).
- Офлайн-точек на пилоте нет (память проекта «Pilot scope»). I4 и I6 работают только в облачных точках; протокол
  синхронизации (ADR-0014) не меняется.
- Тесты отложены до MVP (решение пользователя). Каждый PR перечисляет свой тестовый долг (раздел 13); существующие
  наборы остаются зелёными.

## 3. I1. Экран покупателя

| № | Вопрос | Решение |
|---|---|---|
| D1 | Что это | Второе окно браузера на мониторе, повёрнутом к покупателю. Открывается кнопкой «Экран покупателя» в шапке кассы (только при привязанном терминале). Маршрут `/customer-display?terminal=<id>` — вне оболочки, как `/login`: без меню, без сессии, без запросов к API. Страница статическая и попадает в кеш Service Worker вместе со всем `out/`, поэтому открывается и без интернета |
| D2 | Связь с кассой | `BroadcastChannel` с именем `ph-customer-display:<terminalId>`, только в пределах origin, данные не покидают ПК. Касса шлёт `{ v: 1, kind: 'state', state }` при каждом изменении чека, не чаще раза в кадр. Экран при открытии шлёт `{ v: 1, kind: 'hello' }`, касса отвечает текущим состоянием. Сообщение неизвестной версии экран пропускает. Без `BroadcastChannel` в браузере кнопки нет |
| D3 | Что видит покупатель | Четыре состояния: **ожидание** — название точки и «Добро пожаловать»; **чек** — строки (название, количество с единицей «уп.» / «шт.», цена, сумма) в порядке кассы, последняя изменённая строка подсвечена; ниже подытог, скидка с её процентом и крупно «К оплате»; **оплата** — способы и суммы, для наличных — «Получено» и «Сдача», при QR — код оплаты (I6); **готово** — «Спасибо за покупку!», оплачено и сдача, через 10 с — ожидание. В оптовом чеке (I4) — строка «Оптовая продажа · {организация}» |
| D4 | Чего экран не показывает | Партии и сроки, закупочные цены, данные ПКУ (рецепт, покупатель), отложенные чеки, уведомления и ошибки кассы |
| D5 | Язык и размер текста | Язык печатного чека (`draft.language`). Своя крупная типографика для чтения с 1 м, без кнопок A−/A+: на экране покупателя нет ввода |
| D6 | Полный экран | Fullscreen API требует жеста в этом окне: до первого касания или клика экран показывает «Коснитесь, чтобы развернуть». В руководство QA (`docs/qa`) — запуск без жеста: ярлык Chrome `--app=<адрес>/customer-display?terminal=<id> --start-fullscreen --window-position=<x>,0` |
| D7 | Сброс | Касса шлёт `{ v: 1, kind: 'idle' }` при выходе кассира, закрытии смены и отвязке терминала; экран переходит в ожидание |
| D8 | Оборудование | Любой второй монитор (касание не нужно). Без него касса работает как сейчас |

## 4. I2. Товар по незнакомому штрихкоду

| № | Вопрос | Решение |
|---|---|---|
| D9 | Где | Поиск строки документа `ProductSearch` в приходе и начальных остатках — в документах, которые вносят товар на склад. Списание, перемещение и возврат поставщику работают с остатком точки, им новый товар не нужен. Инвентаризация (найденная строка) — вне объёма |
| D10 | Поток | Скан или ввод 8–14 цифр не нашёл товар — под поиском «Товара со штрихкодом {код} нет в каталоге» и кнопка «Завести товар». Текст, а не цифры, — «Завести товар «{запрос}»». Кнопка есть только с `catalog:create`; без него — «Попросите заведующего завести товар в каталоге» |
| D11 | Окно | Форма каталога «Новый товар» (те же поля и проверки) в диалоге. Штрихкод или название (на языке сети по умолчанию) уже заполнено, фокус — на первом пустом обязательном поле. Сохранение — существующий `POST /api/v1/catalog/products`; созданный товар сразу встаёт строкой документа, как выбранный из поиска. Цена — как у любого товара без цены в приходе. Отмена возвращает в поиск с тем же запросом |
| D12 | FSD | `ProductForm` и её модель переезжают из `pages/catalog/ui` в срез `features/product-form`. Им пользуются страницы каталога и новый `CreateProductDialog` документа. Поведение каталога не меняется |
| D13 | Касса | Товар не создаётся: в чеке нужна партия с остатком. Сообщение «Неизвестный штрихкод» получает подсказку «Заведите товар в каталоге или при приходе» |

API и данные не меняются. Аудит — существующая запись создания товара.

| № | Вопрос | Решение |
|---|---|---|
| D14 | Где | Кнопка «История» в строке товара на странице «Цены и скидки» и в блоке цен карточки товара. Открывает окно «История цен — {товар}»: выбор точки («Все точки» или одна из охвата; по умолчанию — точка сессии, если она есть), таблица от новых к старым — дата и время, точка, вид (розница или опт, после I4), было, стало, изменение в процентах, кто, источник. Список — по 50, с «Показать ещё» |
| D15 | Источник | `price.changed` в журнале действий: старая и новая цена, точка и `source` пишутся в той же транзакции, что и цена (`StorePriceWriter`). Названия источников: `prices` — «Вручную», `document` — «Приход № …» (ссылка на документ), `transfer` — «Перемещение № …», `offline_store` — «На точке». Записи не удаляются (append-only), история полная |
| D16 | API | `GET /api/v1/prices/{productId}/history?storeId=&limit=&offset=` (`pricing:view`). Точки вне охвата — 403 `store_not_in_scope`; без `storeId` — все точки охвата. Чтение — новым читателем модуля `audit` (как `PriceChanges`) по `audit_log_entity_idx`, с фильтром тенанта. Зависимость `audit` ← `pricing` уже есть |
| D17 | Закупочные цены | В истории только цены продажи. Право `finance:view-cost` не нужно |

## 6. I4. Оптовая продажа

| № | Вопрос | Решение |
|---|---|---|
| D18 | Что это | Продажа организации (клиника, другая аптека) через ту же кассу: по оптовой цене точки, с покупателем на чеке и накладной A4. Оплата сразу — наличными, картой, QR или NFC. Продажи в долг нет |
| D19 | Оптовая цена | Цена упаковки по точке: `store_products.wholesale_price_per_pack_dirams` (null — опт этого товара на точке закрыт). Только упаковками: оптовой цены штуки нет |
| D20 | Где задаётся | «Цены и скидки»: переключатель «Розница / Опт» меняет столбцы цен точек. Права те же: `pricing:update-store` / `pricing:update-network`. Отдельный запрос `PUT /api/v1/prices/{productId}/wholesale` `{ prices: [{ storeId, priceMinor \| null }], confirmAboveMax }` |
| D21 | Правила цены | Выше регулируемой максимальной цены упаковки — 422 `above_max_price` без `confirmAboveMax`, как у розницы. Предупреждения (не запрет): `above_retail` — выше розничной цены точки, `below_cost` — ниже последней закупки (по настройке `warnBelowCost`). Аудит `wholesale_price.changed` — те же поля, что у `price.changed`. Версия цены растёт, касса получает цену со следующим снимком |
| D22 | Снимок кассы | `PosProduct.wholesalePriceMinor: number \| null` |
| D23 | Право | Новое специальное право `pos:sell-wholesale` (каталог прав и редактор ролей). Роль владельца получает его как все права, прочим ролям его выдаёт владелец. Шаблоны новых сетей не меняются |
| D24 | Режим кассы | Кнопка «Опт» в чеке (только с правом). Включение спрашивает покупателя: организация (обязательно, до 200 знаков), ИНН (обязательно, 9 цифр — правило ИНН юрлица `LegalEntityInput.taxId`), основание (необязательно, до 200 знаков: договор, доверенность). В оптовом чеке: цена строки — оптовая; товар без оптовой цены не добавляется («Нет оптовой цены на этой точке»); ПКУ не добавляется («ПКУ оптом не продаётся»); только упаковки; скидки сети не применяются; отложить чек нельзя. Рецептурный товар — с обычным предупреждением. Выключение режима с непустым чеком — подтверждение и пересчёт строк по розничной цене |
| D25 | Контракт чека | `CreateReceiptRequest.wholesale: { buyerName, buyerTaxId, basis } \| null`. Проверки сервера — как у розницы, по оптовой цене: цена строки должна быть оптовой ценой точки текущей или действовавшей в окне снимка (история из `wholesale_price.changed`), иначе 422 `price_rules_violated` / `price_not_allowed` с приёмом через `X-Accept-Discrepancy` по правам на цены (ADR-0015, поправка 2026-10-23). Без права автора — 422 `author_not_allowed`. Ошибки 400 `validation_failed`: строка ПКУ — `wholesale_controlled`, штука — `wholesale_piece`, скидка — `discount_not_allowed` |
| D26 | Хранение | `receipts.sale_kind` (`retail` \| `wholesale`, по умолчанию `retail`), `buyer_name`, `buyer_tax_id`, `buyer_basis`. CHECK: `wholesale` ⇔ имя и ИНН заданы |
| D27 | Печать | На чеке — «Оптовая продажа», организация, ИНН и основание. В окне проведённого чека — кнопка «Накладная (A4)» (`SheetPrint` + `InvoiceSheet` UI-кита): продавец (юрлицо точки: название, ИНН, адрес), покупатель, номер и дата (номер чека), строки (товар, партия, срок, упаковки, цена, сумма), итог, способ оплаты, подписи «Отпустил» и «Получил». Повторная печать — вне объёма (раздел 12) |
| D28 | Возврат | Как у любого чека: по чеку, на те же способы оплаты. Экран возврата показывает «Оптовая продажа · {организация}» |
| D29 | Смена и отчёты | Итоги смены по способам оплаты не меняются. В отчёте смены — строка «в т.ч. опт: N чеков, сумма». Отчёт `sales_by_store` получает столбцы «Розница» и «Опт» (и в выгрузке Excel) |
| D30 | Офлайн-точка | На офлайн-точке (`STORE_MODE=offline`) кнопки «Опт» нет, оптовой цены в снимке и ленте `PricingFeed` нет |

## 7. I5. Камера

| № | Вопрос | Решение |
|---|---|---|
| D31 | Где | Кнопка «Камера» рядом с полями, которые принимают скан: подбор товара кассы, поиск строки документа, инвентаризация, поиск чека на экране возврата, поле штрихкода в карточке товара |
| D32 | Поведение | Окно с видео задней камеры (`facingMode: environment`) и рамкой. Распознавание идёт непрерывно; первый верный код закрывает окно и передаётся тому же обработчику, что и скан USB-сканера. Где поддерживается — вибрация и кнопка фонарика. Форматы: EAN-13, EAN-8, UPC-A, Code 128, QR (id чека, ADR-0022) |
| D33 | Ограничения | Нет камеры (`videoinput`) или не защищённый контекст — кнопки нет. Нет разрешения — сообщение, как его дать. Поток останавливается при закрытии окна, уходе со страницы и через 60 с без кода. Кадры обрабатываются только в браузере: ничего не сохраняется и не отправляется |
| D34 | Библиотека | ADR-0025 (новый, создаётся `/03-adr` до кода I5). Требования: 5 форматов из D32 в Chrome и Edge на Windows и Android; файлы со своего origin, без CDN, работа без сети; загрузка только при открытии окна, не в начальном бандле кассы; лицензия MIT, Apache-2.0 или BSD; живой проект; версия закреплена точно. Где есть встроенный `BarcodeDetector` (Android, ChromeOS, macOS) — сначала он, на Windows его нет. Кандидаты для ADR: `zxing-wasm` (через полифил `BarcodeDetector`) и `@zxing/browser` — выбор после проверки версий, размеров и лицензий |
| D35 | Proxy | Поправка ADR-0012 в ADR-0025: `Permissions-Policy` хоста `app.` — `camera=(self)`, хоста `admin.` — прежний `camera=()` (сейчас общий сниппет `static-files`, его нужно разделить). Если выбран WASM — `'wasm-unsafe-eval'` в `script-src` только хоста `app.` |

## 8. I6. QR оплаты

| № | Вопрос | Решение |
|---|---|---|
| D36 | Что это | Способ оплаты «QR» уже есть: деньги идут по QR банка, кассир подтверждает вручную, смена сверяется по итогу банка (`terminalTotals.qr`). Новое — касса сама показывает QR оплаты банка на сумму QR-части. Оплата по-прежнему без интеграции: касса ничего не отправляет в банк и не получает от него (stack.md, «Банковский эквайринг»). Подтверждение — та же кнопка «Оплатить», когда кассир увидел платёж в приложении банка |
| D37 | Настройка | По точке, в карточке точки кабинета владельца — блок «QR для оплаты». Шаблон ссылки: только `https://`, до 500 знаков, без пробелов и управляющих символов; подстановки — `{amount}` (сумма в сомони с точкой и двумя знаками, `125.50`) и `{ref}` (ссылка на чек: `{код точки}-{номер чека терминала}`, до 18 знаков); прочие `{…}` — 400. «Получатель» — до 100 знаков, например «ООО «…», Душанбе Сити»; показывается под QR. Пустой шаблон — QR кассой не показывается (наклейка банка работает как сейчас). Без `{amount}` — QR без суммы, а экран крупно пишет «Сумма к оплате: 125,50 смн» |
| D38 | Кто меняет | `PUT /api/v1/stores/{id}/payment-qr` `{ template, recipient } \| null` — `stores:update` и свежий вход (`fresh_auth_required`), точки охвата. Аудит `store.payment_qr_changed` со старой и новой ссылкой (ссылка не секрет). Новое уведомление владельцу `payment_qr_changed` (включено по умолчанию): подменённую ссылку замечают. Кнопка «Проверить» показывает QR на 1,00 смн — его сканируют приложением банка до сохранения |
| D39 | Доставка на кассу | `PosStoreSettings.paymentQr: { template, recipient } \| null` в снимке каталога. QR строится на ПК без сети |
| D40 | Где показывается | Окно оплаты кассы — при выборе «QR» на всю сумму или на часть. Экран покупателя (I1) — в состоянии «Оплата»: QR крупно, получатель и сумма |
| D41 | Рисунок | `lean-qr` 2.7.4 (ADR-0022) и свой SVG, уровень коррекции M. Поправка ADR-0022: QR рисуется ещё и на экране для оплаты, библиотека та же |
| D42 | Счёт получателя | Подсказка формы: ссылка должна вести на расчётный счёт юрлица точки, выданный банком для приёма оплаты, — не на личную карту. Ответственность за содержимое ссылки — у владельца сети. Платёжная ссылка банка Душанбе Сити, которую safopharm берёт за образец, содержит номер карты и работает по `http://` — такую ссылку форма не примет (раздел 14) |

## 9. API

- `GET /api/v1/prices/{productId}/history?storeId=&limit=&offset=` → 200 `Page<PriceHistoryEntry>`; 403, 404.
  `PriceHistoryEntry`: `at`, `storeId`, `storeName`, `kind` (`retail` \| `wholesale`), `oldPriceMinor` (null — цены не
  было), `newPriceMinor`, `source`, `document` (`{ type, id, number }` \| null), `author` (`{ name }` \| null).
- `PUT /api/v1/prices/{productId}/wholesale` → 200 `StorePrice[]`; 403 `store_not_in_scope`, 409 `product_archived`,
  422 `above_max_price`.
- `StorePrice` получает `wholesalePriceMinor: number | null` и `wholesaleWarnings: PriceWarning[]`; `PriceWarning` —
  значение `above_retail`.
- `PosProduct.wholesalePriceMinor`, `CreateReceiptRequest.wholesale`, `PosStoreSettings.paymentQr`.
- `PUT /api/v1/stores/{id}/payment-qr` → 200 `OwnerStore`; 400 `validation_failed`, 403 `fresh_auth_required`, 404,
  409 `store_closed`. `OwnerStore.paymentQr: { template, recipient } | null`.
- Отчёт `sales_by_store` — столбцы `retailMinor` и `wholesaleMinor`.
- Каталог прав — `pos:sell-wholesale`; виды уведомлений — `payment_qr_changed`.

- `db-types` перегенерируются. Классы таблиц (`table-classes.ts`) не меняются: новые колонки — в существующих таблицах.

## 12. Вне объёма

- Опт: продажа в долг и дебиторская задолженность, справочник покупателей-организаций (подсказка «последние
  покупатели» — позже), счёт-фактура, повторная печать накладной, загрузка оптовых цен из файла, опт на офлайн-точке и
  в выгрузке 1С, оптовая цена на ценнике.
- QR оплаты: обмен с API банка, автоматическое подтверждение платежа.
- Экран покупателя: реклама и слайды, ввод покупателя на экране, логотип сети.
- Камера: админка, несколько кодов в кадре, фото рецептов.
- Идеи сравнения, не выбранные пользователем: места хранения (зоны и ячейки), возврат без чека, ввод итоговой суммы
  кассиром, интернет-магазин, уведомления в Telegram.

## 14. Вопросы к заказчику

Ответы не меняют архитектуру, но нужны до пилота соответствующего пункта:

1. Банк (I6): выдаёт ли он юрлицу ссылку оплаты на расчётный счёт с суммой в параметре и по `https://`.
2. Бухгалтер (I4): форма накладной для оптового покупателя; нужен ли счёт-фактура (НДС).
3. Фармацевт (I4): можно ли продавать рецептурные товары организации без рецепта; ПКУ оптом исключён этим решением.
4. Точки пилота (I1, I5): есть ли второй монитор и планшеты с задней камерой.
