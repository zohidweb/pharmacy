# Мелкие доработки перед пилотом — спецификация

Дата: 2026-10-26. Основа — сверка с ТЗ «Клиентский продукт» v3.1, «Административный продукт» v2.1 и макетами на `main`
8f567c2 (память проекта «Gap analysis 2026-10-26»). Пользователь попросил начать без вопросов: все решения ниже —
решения автора, на утверждение вместе со спецификацией. Новых технологий и ADR нет; модель данных — одна поправка
(раздел «Документы»).

## 1. Цель

Закрыть шесть пробелов размера S, которые видны тестировщику и пилотной аптеке и не требуют решений заказчика:

| № | Пробел | Где |
|---|---|---|
| G1 | Текст внизу чека хранится (`tenant_settings.receipt_footer`) и печатается, но задать его негде | web, API |
| G2 | Недопоставленный заказ поставщику нельзя закрыть вручную | web, API, БД |
| G3 | Заказ поставщику нельзя напечатать (ТЗ §4, макет «Отправить поставщику» → печать, модель данных 05) | web |
| G4 | Экран возврата просит «отсканируйте QR-код с чека», а QR на чеке нет | web |
| G5 | Офлайн-страницы админки открываются по прямой ссылке (404), офлайн-тексты видны без офлайн-точек | admin |
| G6 | Название, город и ИНН сети не исправить после создания; ссылки на счёт с вкладки «Счета» компании нет | admin, API |

## 2. Решения автора

| № | Вопрос | Решение |
|---|---|---|
| P1 | Где задаётся текст подвала чека | «Настройки» владельца, новая карточка «Чек»: два поля — RU и TJ, до 200 символов каждое, обрезка пробелов; переводы строк печатаются отдельными строками, прочие управляющие символы — 400; пустое поле — подвала на этом языке нет. Сохраняется вместе с настройками сети (`PUT /settings`, свежий вход, право `settings:update`), в аудите `settings.updated` — до и после. Касса получает его со следующим снимком каталога (уже так) |
| P2 | Хранение подвала | `tenant_settings.receipt_footer` (jsonb `{ru, tj}`, уже есть): пустые языки не пишутся, оба пустых — `null`. Чек берёт язык кассира, иначе язык сети (уже так) |
| P3 | Кто и когда закрывает заказ | `POST /purchase-orders/{id}/close`, право `purchasing:post` и `finance:view-cost` (ответ — заказ с ценами, как у подтверждения); только `confirmed` / `partially_received` точки из охвата, иначе 409 `order_not_open`; повтор закрытия уже закрытого вручную заказа (потерянный ответ) — 200 с заказом, без второй записи аудита. Причина не спрашивается; аудит `purchase_order.closed` с процентом полученного |
| P4 | Ручное закрытие и пересчёт статуса | Новые колонки `purchase_orders.closed_manually_at`, `closed_manually_by`. Отмена проведения прихода по закрытому вручную заказу допустима, заказ остаётся `closed` (`refreshStatus` его не открывает); новый приход по нему — 422 `order_not_open`, как сейчас. В ответе заказа — `closedBy { name, at }` или `null` |
| P5 | Печать заказа | Без нового маршрута: кнопка «Печать» в окне заказа (любой сохранённый заказ, черновик — с пометкой «Черновик»), A4 через `SheetPrint` + `InvoiceSheet` UI-кита: заказчик (точка), поставщик, строки «товар · кол-во × цена · сумма», итог, ожидаемая дата и комментарий. Цены видит тот, кто видит заказ (`finance:view-cost`) |
| P6 | QR на экране возврата | Подсказка без QR: «Номер напечатан на чеке. У чека без связи — код из 8 знаков». QR на чеке — после ADR о штрихкодах |
| P7 | Офлайн-страницы админки | `/offline/licenses` и `/offline/versions` без своих маршрутов в API показывают «Страница не найдена» (как неизвестный адрес), без запросов к API |
| P8 | Офлайн-тексты админки | Признак «офлайн-раздел доступен» — `isApiRouteAvailable('licenses.list')`. Без него скрываются: темы «Ключи» и «Синхронизация» в уведомлениях, область «Только офлайн-точки» в объявлениях, тип «Ключ» в журнале, части «ключей» и «без синхронизации» в подсказке «Требует внимания» на дашборде, пункт про ключи в промо входа. Текст экрана техработ — без офлайн-точек (верен в любом режиме) |
| P9 | Правка сети | `PATCH /operator/tenants/{id}` `{name, city, inn}` (те же правила, что при создании), право `tenants:manage`, свежий вход; 404, 409 `inn_taken`. Блокированную сеть править можно. Аудит `tenant.updated` с перечнем изменённых полей (без значений). Выставленные счета хранят снимок названия и ИНН и не меняются; новые счета берут новые значения. Контакт и логин владельца не правятся (логин — идентификатор входа) |
| P10 | Ссылка на счёт | На вкладке «Счета» карточки компании номер счёта — ссылка на страницу печати счёта (`/billing/invoice?id=`) |

## 3. API

- `POST /api/v1/purchase-orders/{id}/close` → 200 `PurchaseOrder`; 403, 404, 409 `order_not_open`.
- `PATCH /api/v1/operator/tenants/{id}` `UpdateTenantRequest {name, city, inn}` → 200 `TenantDetails`; 400, 403
  `fresh_auth_required`, 404, 409 `inn_taken`.
- `NetworkSettings.receiptFooter: { ru: string; tj: string }` (чтение и запись `PUT /settings`).
- `PurchaseOrder.closedBy: { name: string; at: string } | null`.

## 4. Документы

- Модель данных `05-purchasing.md`: `closed_manually_at`, `closed_manually_by` у `purchase_orders`.
- Миграция `<ts>_purchase-order-manual-close.sql`: две колонки, составная ссылка на сотрудника с индексом, проверка
  «обе пусты или обе заданы, и тогда статус `closed`».
- `docs/qa/02-granitsy-pilota.md`: убрать «отправка заказа — вне системы» в пользу печати; QR — без изменений.

## 5. Вне объёма

QR и штрихкоды на чеке (ADR), правка контакта владельца, история смен, ценники, выгрузки в Excel.
