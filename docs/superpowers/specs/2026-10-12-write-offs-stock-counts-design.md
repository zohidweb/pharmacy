# Списание и инвентаризация — спецификация

Дата: 2026-10-12. Статус: на утверждении архитектора. Связано: модель данных
`docs/architecture/data-model/03-batches-warehouse.md` (одобрена 2026-09-30), спецификация
`2026-10-09-inventory-purchasing-design.md` (ядро склада: партии, движения, нумерация, `DocumentPosting`), ADR-0002
(границы модулей), ADR-0006 (блокировка отдельно от подсчёта), ADR-0014 (офлайн-точка — склад только на точке),
ADR-0018 (права и охват).

## 1. Цель и критерии успеха

Товар уходит со склада не только продажей: просрочку, бой и брак списывают документом, а расхождения учёта с
полкой выявляет инвентаризация. Оба документа переходят с моков на API (`apps/api`, модуль `inventory`), экраны
«Списание» и «Инвентаризация» `apps/web` работают с API в режиме `partial`.

Успех:
- проведённое списание уменьшает остаток партий движениями `write_off` в одной транзакции с документом; списать
  больше остатка нельзя;
- инвентаризация фиксирует учётный остаток в момент старта, считается несколькими сотрудниками одновременно на
  планшетах со сканером, при проведении приходует излишки и списывает недостачи, а найденный товар без учётной
  партии становится новой партией;
- пока идёт инвентаризация, товары её охвата на точке «заморожены» для складских документов, касса работает;
- отмена проведения обоих документов — сторно движений, запрещена, если по партиям, которые документ двигал, после
  проведения были движения;
- каждое действие — в журнале сети (`audit_log`); контролируемые препараты попадают в журнал ПКУ через движения.

## 2. Решения, принятые при обсуждении (2026-10-12)

| # | Вопрос | Решение |
|---|---|---|
| W1 | Причина списания | **Одна на документ** (по одной причине — отдельное списание). Фиксированный список: `expired`, `broken`, `defect`, `misgrade`, `transfer_discrepancy`. Справочник причин сети (`dictionary_values`) не вводится — поправка модели |
| W2 | Кто списывает | Черновик оформляет фармацевт, проводит заведующий. Акта и подписей нет |
| S1 | Найденный товар без учётной партии | По модели (решение 2026-09-30): строка «найденный товар», срок и закупочную цену вводит сотрудник; без них документ не проводится; при проведении — новая партия |
| S2 | Неполный пересчёт | Проводится **только полностью посчитанная** инвентаризация (факт по каждой строке) |
| S3 | Охват | «Вся точка» или «Категория». «Выборочно» в этой итерации не делается (экран его не предлагает) |
| S4 | Работа точки во время пересчёта | Касса работает; склад **заморожен для товаров охвата**: при «вся точка» — весь склад точки, при «категория» — товары этой категории. Остальные товары принимаются и списываются как обычно |
| S5 | Параллельные инвентаризации | На точке одновременно идёт **одна** инвентаризация (решение исполнителя, принято) |
| S6 | Брошенная инвентаризация | Отмена: документ закрывается без движений, заморозка снимается. Право `inventory:delete` (владелец, заведующий) |
| S7 | Как считают | Сразу на экране, планшет со сканером; **несколько сотрудников одновременно**, количества одного товара из разных мест **складываются**. Печать листа не делается |
| R1 | Права | Фармацевт: черновики списаний и ввод количеств (`inventory:create`, `inventory:update` — добавляются в шаблон «Фармацевт-кассир»); заведующий: проведение, отмена проведения, старт инвентаризации (`inventory:post`, `inventory:unpost`), отмена инвентаризации (`inventory:delete`) |
| B1 | Архивные товары | Остатки архивного товара **можно списать и посчитать**: проверка «товар активен» при проведении остаётся у прихода и начальных остатков, у списания и инвентаризации её нет. Найденный товар — только активный (решение исполнителя) |
| B2 | Что блокирует отмену проведения | Только партии, которые документ **действительно двигал** (у инвентаризации — строки с расхождением и новые партии излишков), и любое их движение после проведения — как правило модели «движения позже проведения» (решение исполнителя) |
| B3 | Дата инвентаризации | При проведении и отмене проведения инвентаризации проверяется только закрытый период; окно «задним числом» не применяется — пересчёт может длиться дольше окна (решение исполнителя) |
| B4 | «Добавить просроченные партии» | `GET /stores/{storeId}/stock-products?expired=true` — все товары точки (и архивные) с просроченными партиями с остатком, без лимита страницы (решение исполнителя) |
| P1 | Разбиение | Одна спецификация, **два плана и два PR**: PR-1 «Списание» (разделы 3.1, 4, 5.1, web PR-1), PR-2 «Инвентаризация» (3.2, 5.2, 5.3, web PR-2) |

### 2.1 Поправки модели данных (утверждаются вместе со спецификацией)

1. `documents.write_off_reason text null` — причина списания на уровне документа (W1); в `write_off_lines` нет
   `reason_code`. Справочник `write_off_reason` в `dictionary_values` не вводится.
2. `write_off_lines.unit` (`pack` / `piece`) — в каких единицах ввели количество (для показа); остаток и движения
   — в штуках, как везде.
3. `documents.status` для инвентаризации дополняется `cancelled` (S6): `draft` (идёт пересчёт) → `posted`;
   `draft` → `cancelled` (конечный). Отмена проведения — снова `draft`, заморозка возвращается.
4. Новая таблица `inventory_count_entries` (S7): запись «посчитал N штук» по строке; факт строки — сумма записей.
   `inventory_lines.counted_qty_pieces` не хранится как ввод, а фиксируется суммой записей при проведении.
5. `batches.origin` дополняется `inventory_surplus` (S1).
6. Правило заморозки (S4) — новое правило проведения складских документов.

## 3. Схема

### 3.1 Миграция PR-1 `write-offs`

- `documents.type` дополняется `write_off`; `documents.write_off_reason text null` с `check` — значение из списка
  W1, обязателен для `write_off`, пуст для остальных типов.
- `write_off_lines` (класс `tenant`): `(tenant_id, id)`, `document_id`, `line_no ≥ 1` (уникален в документе),
  `batch_id`, `product_id` (для показа и поиска; совпадает с товаром партии — проверяет приложение),
  `qty_pieces > 0`, `unit text check in ('pack','piece')`, `created_at`. FK на `documents`, `batches`, `products`;
  индексы `(tenant_id, document_id)`, `(tenant_id, batch_id)`, `(tenant_id, product_id)`.
- `stock_movements.kind` дополняется `write_off`.
- RLS (fail-closed по `app.tenant_id`), гранты `pharmacy_app`, манифест `table-classes.ts`, перегенерация типов
  Kysely.

### 3.2 Миграция PR-2 `stock-counts`

- `documents.type` дополняется `inventory`; `documents.status` — `cancelled` (только для `inventory`, `check`);
  колонки `inventory_scope text null` (`all` / `category`), `inventory_category_id uuid null`,
  `inventory_started_at timestamptz null`, `cancelled_by uuid null`, `cancelled_at timestamptz null`; `check`:
  для `inventory` заполнены `inventory_scope` и `inventory_started_at`, категория — тогда и только тогда, когда
  охват `category`.
- `inventory_lines` (класс `tenant`): `(tenant_id, id)`, `document_id`, `line_no`, `product_id`,
  `batch_id null` (пусто — найденный товар без учётной партии), `book_qty_pieces` (остаток партии в момент старта,
  0 у найденного товара), `counted_qty_pieces null` и `sold_since_start_pieces null` (фиксируются при проведении),
  `is_found boolean`, для найденного товара — `surplus_lot_number null`, `surplus_expiry_date null`,
  `surplus_purchase_price_per_pack_dirams null`, `surplus_batch_id null` (создаётся при первом проведении, при
  повторном — та же партия, как у прихода). Уникальность `(tenant_id, document_id, batch_id)` для строк с партией.
- `inventory_count_entries` (класс `tenant`): `(tenant_id, id)` — `id` = ключ идемпотентности планшета (UUIDv7);
  `document_id`, `line_id`, `qty_pieces integer` (может быть 0 — «посчитал ноль», и отрицательным — поправка),
  `entered_by`, `entered_at`. Удаление записи — `DELETE` (это черновой ввод, не журнал). Индекс
  `(tenant_id, line_id)`.
- `batches.origin` дополняется `inventory_surplus` (`supplier_id` пуст, `source_document_id` — инвентаризация).
- `stock_movements.kind` дополняется `inventory_gain`, `inventory_loss`.
- RLS, гранты, манифест, типы — как в 3.1.

## 4. Списание (PR-1; `apps/api/src/app/inventory`, только облако)

Маршруты и права:

| Маршрут | Право |
|---|---|
| `GET /write-offs?storeId&reason&status&limit&offset` (KPI) | `inventory:view` |
| `GET /write-offs/{id}` | `inventory:view` |
| `POST /write-offs`, `PUT /write-offs/{id}` — только черновик | `inventory:create` / `inventory:update` |
| `POST /write-offs/{id}/posting` | `inventory:post` |
| `POST /write-offs/{id}/unposting` | `inventory:unpost` |
| `GET /stock-documents/write-offs/{id}/unposting-check` | `inventory:unpost` |

- **Закупочные суммы** (`costMinor` строки, `totalMinor`, сумма в KPI) — только с `finance:view-cost`; без права
  поля отсутствуют. В отличие от прихода, запись списания этого права **не требует** (W2: фармацевт не видит цен).
- **Черновик:** точка в охвате, облачная и активная (как у прихода: 403 `store_not_in_scope`, 409
  `offline_store_read_only`); номер `СП-<код точки>-<год>-<6 цифр>` из `document_counters` при создании; дата,
  причина, комментарий ≤ 500; строки 1–500: партия этой точки (иначе 400 у `lines.i.batchId`), количество > 0 в
  упаковках или штуках (штуки — только у делимого товара, иначе 400 у `lines.i.unit`); одна партия — не более одной
  строки. Остаток при сохранении не проверяется (проверка — при проведении).
- **Проведение — одна транзакция:**
  - заголовок `FOR NO KEY UPDATE` (как у прихода после PR #19); архивный товар допустим (B1);
  - проверка заморозки (5.3) — 409 `stock_count_in_progress`;
  - дата: не в будущем, не старше окна задним числом (`tenant_settings.backdating_max_days`), не в закрытом
    периоде юрлица (422 `period_closed`) — те же проверки, что у прихода;
  - партии `FOR UPDATE` одним оператором, затем остатки; строка больше остатка партии → 409 `stock_insufficient`
    (с `errors[]` у строк);
  - движения `write_off` (−штуки) с `business_date` = дата документа; `total_dirams` = Σ штуки ×
    `cost_per_piece_dirams` партии; статус `posted`; аудит `document.posted`.
- **Отмена проведения:** запрещена (409 `unpost_blocked`), если по партиям, которые документ двигал, есть движения,
  записанные после его проведения (`recorded_at` позже последнего проведения; B2). Та же выборка — в
  `unposting-check`; в закрытом периоде — 422 `period_closed`; заморозка —
  409 `stock_count_in_progress`. Сторно — движения `reversal`, статус `draft`.
- **Список и KPI:** документы и сумма списанного за месяц бизнес-даты (сумма — с правом), просроченные и
  истекающие (≤ `expiry_reminder_days`) партии с остатком в точках охвата; поиск по точке и причине.
- **«Добавить просроченные партии»** (B4): `GET /stores/{storeId}/stock-products?expired=true` — товары точки,
  включая архивные, у которых есть партии с остатком > 0 и сроком < бизнес-даты; в ответе только такие партии;
  без лимита страницы и поиска. Обычный режим маршрута не меняется.
- Поле `source_customer_return_id` (автосписание при возврате покупателем) не заполняется — его заполнит модуль
  возвратов.

## 5. Инвентаризация (PR-2; `apps/api/src/app/inventory`, только облако)

### 5.1 Маршруты и права

| Маршрут | Право |
|---|---|
| `GET /stock-counts?storeId&status&limit&offset` | `inventory:view` |
| `GET /stock-counts/{id}` | `inventory:view` |
| `POST /stock-counts` — старт | `inventory:post` |
| `PUT /stock-counts/{id}` — комментарий | `inventory:update` |
| `POST /stock-counts/{id}/entries`, `DELETE /stock-counts/{id}/entries/{entryId}` | `inventory:update` |
| `POST /stock-counts/{id}/found-lines`, `PUT …/found-lines/{lineId}`, `DELETE …/found-lines/{lineId}` | `inventory:update` |
| `POST /stock-counts/{id}/posting` | `inventory:post` |
| `POST /stock-counts/{id}/unposting` | `inventory:unpost` |
| `POST /stock-counts/{id}/cancellation` | `inventory:delete` |
| `GET /stock-documents/stock-counts/{id}/unposting-check` | `inventory:unpost` |

Учётные остатки и количества видны всем с `inventory:view`; стоимость штуки, сумма расхождений и закупочная цена
найденного товара — только с `finance:view-cost` (ввести цену найденного товара тоже можно только с этим правом).

### 5.2 Жизненный цикл

- **Старт** (`storeId`, `scope`, `categoryId`): точка в охвате, облачная, активная; на точке нет другой
  инвентаризации в статусе `draft` (иначе 409 `stock_count_in_progress`); номер `ИН-…`. В той же транзакции —
  снимок: строка на каждую партию точки с остатком > 0 у товаров охвата (категория — по текущей категории товара;
  архивные товары с остатком тоже входят), `book_qty_pieces` — остаток на момент старта; `inventory_started_at` =
  время транзакции. Аудит `stock_count.started`.
- **Пересчёт:**
  - `POST /entries` `{ id, lineId, pieces }` — запись «посчитал N штук»; повтор с тем же `id` и телом — тот же
    ответ, с другим — 409 `idempotency_conflict`; ответ — строка с новым фактом;
  - `DELETE /entries/{entryId}` — своя запись; чужую — с правом `inventory:post`;
  - факт строки = сумма записей; строка «посчитана», если у неё есть хотя бы одна запись; отрицательный итог
    допустим при вводе, но не при проведении;
  - **найденный товар:** `POST /found-lines` `{ productId, batchNumber, expiresOn | null, costMinor | null }` —
    строка без партии с `book_qty_pieces = 0`; срок и цену можно ввести позже `PUT`; удалить — пока у строки нет
    записей; товар активный (409 `product_archived`);
  - ввод возможен только в `draft` (409 `document_posted` / `document_cancelled`).
- **Проведение — одна транзакция:**
  - каждая строка посчитана, итог ≥ 0, у найденного товара есть срок и цена — иначе 422 `validation_failed` с
    `errors[]` у строк (`lines.i.counted`, `lines.i.expiresOn`, `lines.i.costMinor`);
  - дата документа = бизнес-дата старта; проверяется только закрытый период (422 `period_closed`), окно «задним
    числом» — нет (B3); архивный товар в строках с партией допустим (B1);
  - партии `FOR UPDATE`, затем остатки; ожидаемый остаток строки = текущий остаток партии (учётный при старте плюс
    продажи и возвраты кассы за время пересчёта — другие документы по этим товарам заморожены);
    `sold_since_start_pieces` = учётный при старте − ожидаемый; расхождение = факт − ожидаемый;
  - расхождение > 0 — движение `inventory_gain`, < 0 — `inventory_loss` по этой партии; найденный товар — новая
    партия `inventory_surplus` (себестоимость штуки — цена упаковки / штук в упаковке, округление вверх) и движение
    `inventory_gain` на факт;
  - фиксируются `counted_qty_pieces`, `sold_since_start_pieces`; `total_dirams` = Σ |расхождение| × стоимость
    штуки (для отчёта; знак — по сумме излишков и недостач в ответе); статус `posted`; аудит `document.posted`.
- **Отмена проведения** — запрет как у списания (B2: партии строк с расхождением и новые партии излишков; закрытый
  период — B3); статус
  снова `draft`, записи пересчёта сохраняются, заморозка возвращается; на точке не должно быть другой
  инвентаризации в `draft` (409 `stock_count_in_progress`).
- **Отмена инвентаризации** — только `draft`: статус `cancelled`, `cancelled_by/at`, движений нет, заморозка
  снимается; аудит `stock_count.cancelled`.

### 5.3 Заморозка склада

- Товар «заморожен» на точке, если там есть инвентаризация в статусе `draft` с охватом `all` или с охватом
  `category`, совпадающей с текущей категорией товара.
- Проведение и отмена проведения прихода, ввода начальных остатков и списания, в которых есть замороженный товар,
  → 409 `stock_count_in_progress` (с `errors[]` у строк). Черновики сохраняются как обычно. Касса не проверяется.
- Гонка «старт инвентаризации ↔ проведение документа» исключается блокировкой точки: проведение и отмена
  проведения складского документа берут `pg_advisory_xact_lock_shared` по `(tenant, store, 'stock')`, старт,
  проведение, отмена проведения и отмена инвентаризации — исключительную по тому же ключу.
- Проверка — внутренний сервис модуля `inventory` (`StockFreeze`), вызывается из `DocumentPosting` для всех типов.

## 6. Контракт (`libs/shared/dto`)

- `WriteOff`: без изменений по составу; `costMinor` строки и `totalMinor` — только с правом (уже `?`).
  `WriteOffListQuery` — `storeId`, `reason`, `status`, `limit`, `offset`.
- `StockCount`:
  - `status: 'in_progress' | 'posted' | 'cancelled'` (`in_progress` = `draft` в БД);
  - `StockCountLine` получает `lineId`, `barcodes: string[]` (для сканера), `isFound`, `counted: boolean`,
    `entries: Array<{ id; pieces; byName; mine: boolean; at }>`; `batchId`, `batchNumber`, `expiresOn` —
    `string | null` у найденного товара; `factPieces` — сумма записей или `null`; у найденного товара
    `costMinor?: number | null` (цена упаковки, с правом);
  - `StartStockCountRequest` — без `productIds` (охват «Выборочно» убран из `StockCountScope` в этой итерации);
  - `SaveStockCountRequest` → `{ comment }`; новые `StockCountEntryRequest { id, lineId, pieces }`,
    `FoundLineInput { productId, batchNumber, expiresOn, costMinor }`;
  - `StockCountListItem` — без изменений, плюс `status` с `cancelled`.
- `StockDocumentKind` + `'write-offs'`, `'stock-counts'` для проверки отмены.
- JSDoc маршрутов — коды раздела 7.

## 11. Проверка

Новые автотесты не пишутся (тесты отложены до MVP); существующие наборы остаются зелёными. Живая проверка:

- **PR-1, curl:** нумерация; черновик фармацевтом без сумм; проведение заведующим — движения и остаток; больше
  остатка → 409; два одновременных проведения одного документа → одно + 409; дата в будущем, закрытый период →
  422; отмена после продажи по партии → 409, без расхода — сторно; чужая точка → 403, офлайн-точка → 409; KPI.
- **PR-2, curl:** старт и снимок; второй старт на точке → 409; два сотрудника вводят записи одной строки — сумма;
  повтор записи с тем же ключом — без задвоения; удаление своей и чужой записи по правам; найденный товар без
  цены → 422 при проведении; проведение — излишек, недостача, новая партия; заморозка: проведение прихода,
  списания и отмена проведения с товаром охвата → 409, товар вне категории — проходит; отмена инвентаризации
  снимает заморозку; отмена проведения после продажи → 409.
- **Браузер (`partial`):** списание фармацевтом и проведение заведующим; инвентаризация со сканером (ввод
  штрихкода), найденный товар, проведение, отмена.
