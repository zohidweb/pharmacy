# ADR-0009: Инструменты тестирования и измерения, пороги качества, CI (GitHub Actions)

- **Статус:** accepted (2026-09-30, архитектор проекта — APPROVAL.md)
- **Дата:** 2026-09-30
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

Скилы разработки `pharmacy-app` (`nestjs-api`, `web-performance-optimization`, `ui-standards-tokens`,
`react-dev`) опираются на Jest как стандарт монорепо (docs/architecture/generated/CLAUDE.pharmacy-app.md),
но помечают «согласовать» десяток dev-зависимостей — Testcontainers, nock, faker, `@golevelup/ts-jest`,
jest-axe, инструмент нагрузки, bundle-analyzer, web-vitals, виртуализацию списков — и содержат
пороги-заглушки из оригиналов: покрытие 90/80, бюджеты бандла 150/900 КБ gzip, p95 API кассы 150/300 мс.
Пороги должны обеспечивать требования ТЗ из stack.md: операция кассы ≤ 1 сек; до 50 одновременных
кассиров с запасом ×5 (≈ 250); ~3–9 тыс. чеков в день на старте, 30–50 млн движений по партиям за
3 года; POS — Chrome/Edge на слабых ПК с сенсорным экраном от 10″; на офлайн-точке браузер, Docker,
API и PostgreSQL делят один ПК с 8 ГБ ОЗУ (c4/deployment.md). CI до этого ADR не был настроен (проверки
запускались вручную, `npm run check`); после ADR-0011 CI вводится обычным ADR — этот ADR его и вводит
(решение архитектора проекта 2026-09-30); репозиторий — GitHub `zohidweb/pharmacy`; мониторинг не выбран (вводится через ADR), так что RUM
в проде пока нет; отправлять клиентские данные во внешние SaaS запрещено; в тестах только синтетические
данные; волна 1 должна запуститься до конца 2026 года (≈ 3 месяца), команда небольшая. Этот ADR
одним решением закрывает все пометки «согласовать», чтобы зависимости не вводились молча, а пороги
не обсуждались заново в каждом PR.

## Рассмотренные варианты

Оси решения независимы, по каждой рассмотрено не меньше двух вариантов. Лицензии и статус пакетов
проверены 2026-09-29 по npm, GitHub и официальной документации.

### А. PostgreSQL для e2e- и интеграционных тестов API

1. **PostgreSQL из docker compose локальной среды** (`docker/compose.dev.yml`, отдельная БД
   `pharmacy_test`). Плюсы: новых зависимостей нет; compose и так нужен для `nx serve api`
   (ADR-0005); тот же образ, что в облаке и на офлайн-точке. Минусы: состояние БД общее для всех
   прогонов, поэтому нужен сброс (пересоздание схемы и миграции в globalSetup) и `maxWorkers: 1`;
   compose должен быть запущен; при появлении CI вопрос придётся решать заново.
2. **Testcontainers** (`testcontainers` + `@testcontainers/postgresql`, MIT). Плюсы: одноразовый
   контейнер на каждый прогон, изоляция, параллельные прогоны — сильная сторона для CI. Минусы:
   дополнительно запускается служебный привилегированный контейнер Ryuk, образы тянутся с Docker Hub,
   поэтому без доступа к Docker Hub нужен зеркальный реестр (`TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX`); каждый
   прогон дольше стартует на Windows/WSL2; без CI главное преимущество не проявляется.
3. **Эмуляторы PostgreSQL в памяти / SQLite.** Отклонены сразу: на них не проверить RLS,
   `FOR UPDATE SKIP LOCKED`, уникальные ключи идемпотентности и реальные откаты транзакций (это
   правило скила `nestjs-api`).

### Б. Моки внешних HTTP-интеграций (курсы НБТ, адаптер фискализации, синхронизация)

1. **Фейки портов + `jest.spyOn(global, 'fetch')`.** Потребители подменяют порт (`NbtRatesClient`,
   `FiscalRegistrar`, клиент синхронизации) через `useValue`, сам клиент тестируется подменой
   встроенного `fetch` Node LTS с `new Response(...)`. Плюсы: зависимостей нет, подход уже описан в
   скиле. Минусы: подменяется функция, а не протокол, поэтому поведение сокета — таймауты, редиректы,
   TLS — не проверяется; ответы пишутся вручную.
2. **nock 14 (MIT).** Плюсы: декларативные ожидания запросов, `disableNetConnect()` как предохранитель
   от реальной сети. Нативный `fetch` nock перехватывает только с v14, через `@mswjs/interceptors`;
   это крупная переделка внутренностей, и мейнтейнеры сами советовали не спешить с переходом. Минусы:
   глобально патчит http и fetch; при трёх интеграциях по 1–3 эндпоинта себя не окупает.
3. **MSW 2 (`msw/node`, MIT).** Плюсы: перехват на сетевом уровне, одни и те же обработчики для Node
   и браузера. Минусы: для бэкенда избыточен; в связке Jest + jsdom требует донастройки окружения
   (глобальные fetch и streams), а на это при сроке ≈ 3 месяца нет времени.

### В. Фабрики тестовых данных

1. **Свои детерминированные билдеры**: счётчик и явные значения — `buildBatch({ expiresOn })`, EAN-13
   с контрольной цифрой, деньги в дирамах, заведомо синтетические имена вида «Сотрудник-001».
   Плюсы: тесты воспроизводимы, доменные данные точны, на ревью синтетика видна сразу. Минусы: пишет
   и поддерживает команда.
2. **`@faker-js/faker` (MIT)**, детерминизм через `faker.seed()`. Плюсы: быстро даёт правдоподобные
   данные. Минусы: доменные значения (партии, сроки годности и FEFO, дирамы, штрих-коды) всё равно
   пишутся вручную; таджикской локали нет, есть только `ru`; правдоподобные ФИО и телефоны в фикстурах
   и логах хуже отличимы от реальных ПДн при проверке «нет клиентских данных в диффе».

### Г. Моки провайдеров NestJS в unit-тестах

1. **Ручные типизированные фабрики моков** (`createDatabaseServiceMock()`, `{ method: jest.fn() }`
   с `jest.Mocked<T>`). Плюсы: зависимости теста видны явно, пакетов не добавляется. Минусы:
   бойлерплейт на больших интерфейсах; моки `ExecutionContext` для guards и interceptors пишутся
   вручную.
2. **`@golevelup/ts-jest` (MIT, `createMock<T>()`).** Плюсы: автомок всех методов, удобно для guards
   и interceptors. Минусы: версия 0.x, мейнтейнеров немного; вызов незамоканного метода по умолчанию
   не падает, и тест может остаться «зелёным», хотя задета неучтённая зависимость. Для
   тенант-фильтра и транзакций это опасно.

### Д. e2e фронтенда (`apps/web-e2e`, `apps/admin-e2e`)

1. **Playwright** (`@playwright/test` + `@nx/playwright`, Apache-2.0). Плюсы: вариант по умолчанию
   у генератора `@nx/next:application`; поддерживает Chromium и установленные Chrome/Edge
   (`channel: 'chrome' | 'msedge'`), то есть ровно целевые браузеры POS; эмулирует касания, умеет
   замедлять CPU и сеть через CDP; трассы и HTML-отчёт хранятся локально. Минусы: браузерные бинарники
   по умолчанию скачиваются с CDN Microsoft, поэтому нужен внутренний зеркальный хост
   (`PLAYWRIGHT_DOWNLOAD_HOST`) или установленные Chrome/Edge; появляется второй раннер рядом с Jest.
2. **Cypress (MIT).** Плюсы: зрелый DX. Минусы: по умолчанию отправляет crash-reports на
   api.cypress.io (отключается `CYPRESS_CRASH_REPORTS=0`); параллельный запуск и аналитика идут через
   SaaS Cypress Cloud, который запрещён правилом проекта (данные — не во внешние SaaS); у Nx для Next.js он не по умолчанию; тесты с
   несколькими вкладками не поддерживаются.

### Е. Автоматические проверки доступности (WCAG 2.1 AA)

1. **Только ручной аудит** (Lighthouse Accessibility в DevTools, проход клавиатурой). Плюс: без
   зависимостей. Минус: регрессии ловятся поздно и на глаз.
2. **`jest-axe` (MIT) для компонентов `libs/ui`.** Плюсы: быстро, в том же Jest. Минус: в jsdom
   правило `color-contrast` не работает и отключено, контраст токенов этим не проверить.
3. **`@axe-core/playwright` на ключевых экранах в e2e.** Плюс: настоящий браузер, контраст тоже
   проверяется. Минус: работает только в медленных e2e.
   Варианты 2 и 3 используют один движок `axe-core` (Deque, MPL-2.0). Это слабый файловый копилефт:
   для dev-зависимости, которую не изменяют и не распространяют, обязательств он не создаёт.

### Ж. Нагрузочное тестирование кассы

Профиль нагрузки оценён по stack.md. При росте ×5 это ≈ 45 тыс. чеков в день; за 12 рабочих часов
с пиковым коэффициентом 4 выходит ≈ 4–5 чеков/с и ≈ 20–25 запросов поиска/цены в секунду. Та же
оценка получается из 250 кассиров, каждый из которых обслуживает покупателя примерно раз в 60 с.

1. **k6** (Grafana, AGPL-3.0, бинарник на Go). Плюсы: лучшая модель сценариев — открытая модель
   `constant-arrival-rate`, пороги p95 прямо в скрипте, сценарии на JS. Минусы: ставится не через npm,
   то есть мимо lock-файла; AGPL-3.0 нужно проверить по лицензионной политике проекта (для неизменённого
   CLI обязательств обычно нет, но AGPL часто ограничивают политикой); по умолчанию отправляет
   анонимный usage report в Grafana, поэтому обязателен `K6_NO_USAGE_REPORT=true`; k6 Cloud — SaaS,
   запрещён.
2. **autocannon** (MIT, npm, Node; последний релиз 8.0.0 — октябрь 2024). Плюсы: программный API
   вызывается из TypeScript-скрипта в `tools/load/`; массив `requests[]` с `setupRequest`/`onResponse`
   позволяет выстроить цепочку «поиск → чек» с уникальным `Idempotency-Key`; `overallRate` задаёт
   интенсивность; телеметрии нет. Минусы: это бенчмарк HTTP/1.1, а не сценарный движок, поэтому
   кассир с паузами моделируется приближённо; p95 в выводе нет (есть p50/p90/p97.5/p99).
3. **Artillery** (MPL-2.0, npm). Плюсы: сценарии в YAML, фазы нагрузки. Минусы: телеметрия включена
   по умолчанию (`ARTILLERY_DISABLE_TELEMETRY=true`); тяжёлое дерево зависимостей ради облачных
   раннеров; продукт ориентирован на Artillery Cloud. Для 2–3 эндпоинтов выигрыша перед autocannon нет.

### З. Анализ бандла фронтенда

1. **`@next/bundle-analyzer` (MIT)** — обёртка над `webpack-bundle-analyzer`, работает только со
   сборкой webpack. В Next.js 16 по умолчанию собирает Turbopack, так что анализировать пришлось бы
   отдельную сборку `--webpack`, которая отличается от боевой.
2. **Встроенный `next experimental-analyze`** (Next.js ≥ 16.1, Turbopack). Плюсы: без зависимостей,
   показывает граф модулей Turbopack, UI открывается локально (`.next/diagnostics/analyze`, `--serve`
   на localhost). Минусы: функция экспериментальная; совместимость с `output: 'export'` нужно
   проверить на первом замере.
3. **Без анализатора**: размеры `out/_next/static/chunks`, `tools/check-bundle-budget.mjs` и DevTools
   Coverage. Плюс: доступно всегда. Минус: не видно, какой модуль раздул чанк.

### И. Метрики Web Vitals

1. **Встроенные API браузера** (`PerformanceObserver` для `event` и `long-animation-frame`,
   `performance.measure`) плюс DevTools Performance и Lighthouse Timespan. Плюс: без зависимостей.
   Минус: INP вручную считать сложно и неточно.
2. **`web-vitals`** (Google Chrome, Apache-2.0). Плюс: эталонная реализация INP/LCP/CLS с
   attribution. Риски: код может попасть в прод-бандл, и появится соблазн отправлять метрики, а это
   уже RUM, то есть мониторинг, который в стеке не выбран (вводится через ADR).

### К. Длинные списки (каталог, остатки по партиям, отчёты)

1. **Без виртуализации**: серверная пагинация `limit/offset` (стандарт API), «показать ещё» по
   ≤ 50 строк, фильтры, `content-visibility: auto` на блоках. Плюсы: нет зависимостей, сохраняются
   Ctrl+F, печать и доступность. Минус: экраны, где сотни строк действительно нужны одновременно
   (например, лист инвентаризации), могут упереться в рендер на слабом POS.
2. **`@tanstack/react-virtual`** (MIT, v3, headless). Плюсы: библиотека даёт только логику, разметка
   и токены остаются нашими (`libs/ui`); поддерживает динамическую высоту строк. Минус: поиск по
   странице, печать и доступность ломаются, нужна своя обвязка.
3. **`react-window` v2 (MIT).** В 2025 году библиотека переписана (`List`/`Grid`, динамические высоты
   с 2.2): API сменился, а готовые компоненты навязывают свою разметку таблиц.

### Л. Пороги покрытия

1. **Единый глобальный порог 90/90/80/90 (lines/functions/branches/statements, из оригинала скила).**
   Плюс: просто. Минус: при сроке ≈ 3 месяца и небольшой команде он подталкивает писать тесты
   «ради процента» на контроллеры, конфиг и адаптеры-заглушки, а потом порог снижают или обходят
   исключениями.
2. **Дифференцированные пороги по слоям.** Высокие там, где деньги и остатки (чистые функции
   `libs/shared/util`, доменные сервисы кассы, склада, возвратов, цен и биллинга), умеренные
   глобально. Главный гейт при этом — обязательные e2e-кейсы (изоляция тенантов, идемпотентность,
   атомарность, деньги), а не процент. Минус: конфиг сложнее, пороги нужно пересматривать.
3. **Без порогов, только ревью.** Отклонён: пока CI нет, порог покрытия остаётся единственной
   машинной проверкой качества тестов.

### М. Бюджеты производительности кассы

1. **Только сквозной критерий ТЗ ≤ 1 сек.** Плюс: взят прямо из ТЗ. Минус: не делит время между
   бэкендом и фронтендом, поэтому регрессию API на 400 мс не видно, пока её не «съест» сеть.
2. **Декомпозиция 1 сек на бюджеты API (серверное время), сети и клиента.** Плюс: каждую часть можно
   проверить отдельно — API нагрузкой, клиент через Playwright/DevTools. Минус: сетевая часть зависит
   от места хостинга (открытый вопрос № 1 в stack.md).

## Решение

Выбраны варианты без новых зависимостей там, где их хватает для нагрузки ТЗ. Новые dev-зависимости
вводятся только там, где своя реализация была бы дороже и хуже: Playwright, axe-core, autocannon,
web-vitals локально. Главный гейт качества — обязательные e2e-кейсы и дифференцированные пороги
покрытия. Бюджет «≤ 1 сек» разложен на API, сеть и клиент. Гейты PR проверяет CI на GitHub Actions
(раздел «CI» ниже); нагрузочные прогоны и замеры на эталонном ПК — вручную перед релизом.

| Ось | Решение |
|---|---|
| А. БД для e2e | **PostgreSQL из docker compose** — одинаково локально и в CI (compose поднимает наши образы `docker/postgres`, `docker/redis` с init-скриптом ролей и RLS) (отдельная БД `pharmacy_test`, тот же образ, прикладная роль без обхода RLS). Testcontainers не вводим до ADR о CI |
| Б. HTTP-моки | **Фейки портов + `jest.spyOn(global.fetch)`**. В `setupFiles` unit-тестов `apps/api` стоит предохранитель: `fetch` по умолчанию бросает ошибку «реальная сеть в тесте». В `api-e2e` курсы НБТ отдаёт локальный фейк-сервер на `node:http` в globalSetup; фискализация в MVP — заглушка. nock и MSW не вводим |
| В. Фабрики данных | **Свои детерминированные билдеры**, общие для unit и e2e, в новой Nx-библиотеке `libs/shared/testing` (тег `type:testing`: импорт разрешён только из `*.spec.ts` и проектов `*-e2e`, через `@nx/enforce-module-boundaries`). faker не вводим |
| Г. Моки NestJS | **Ручные типизированные фабрики моков** в `libs/shared/testing` / `apps/api/test/mocks`. `@golevelup/ts-jest` не вводим |
| Д. e2e фронтенда | **Playwright** (`@playwright/test`, `@nx/playwright`) в `web-e2e` / `admin-e2e`. Браузеры — установленные Chrome/Edge (`channel`) или внутреннее зеркало. `@testing-library/react` (MIT), который ставится генератором Nx вместе с Jest, считаем частью стандарта Jest |
| Е. Доступность | **`jest-axe`** для компонентов `libs/ui` и **`@axe-core/playwright`** для экранов: вход, касса (скан → оплата), приёмка, возврат. Гейт — 0 нарушений уровня serious/critical. Ручной аудит по скилу `ui-standards-tokens` остаётся обязательным |
| Ж. Нагрузка | **autocannon** (dev-зависимость, скрипты в `tools/load/`). k6 — запасной вариант через новый ADR с проверкой AGPL-3.0 и `K6_NO_USAGE_REPORT=true`, если приближённой модели не хватит. Artillery отклонён |
| З. Анализ бандла | **Встроенный `next experimental-analyze`** при сборке Turbopack. `@next/bundle-analyzer` допускается как dev-зависимость, только если проект собирается webpack. Гейт — скрипт бюджета без зависимостей |
| И. Web Vitals | **`web-vitals` как devDependency**: только в perf-сценариях Playwright (скрипт подключается через `addInitScript`) и в локальной отладочной сборке под флагом. В прод-бандл не попадает и никуда не отправляется. RUM — отдельный ADR о мониторинге, и только на собственный `apps/api` |
| К. Длинные списки | **Без виртуализации** в MVP: пагинация, «показать ещё», `content-visibility`. Если замер (профиль на CPU 4×, приложенный к PR) покажет, что этого не хватает, заранее выбранный кандидат — **`@tanstack/react-virtual`**, с одобрения фронтенд-лида в PR и с обвязкой доступности и печати. `react-window` отклонён |
| Л. Покрытие | Дифференцированные пороги (таблица ниже), только с повышением («храповик») |
| М. Бюджеты | Декомпозиция 1 сек (таблицы ниже) |

**Пороги покрытия** (Jest `coverageThreshold`; functions и statements = lines). Для критичных модулей
ключом служат **пути каталогов**, а не glob: по документации Jest glob-порог применяется к каждому
файлу отдельно, каталог считается агрегатно, а совпавшие пути вычитаются из global.

| Область | Lines | Branches |
|---|---|---|
| `libs/shared/util` (деньги, округление в пользу аптеки, даты) | 95 | 90 |
| `libs/shared/domain`, `libs/shared/testing` (если есть логика) | 90 | 85 |
| `apps/api`: `modules/pos/`, `inventory/`, `returns/`, `pricing/`, `billing/` | 85 | 75 |
| `apps/api`: global (контроллеры, guards, адаптеры, конфиг) | 70 | 60 |
| `apps/web`: буфер офлайн-операций, мапперы и валидация (каталоги фиксируются при scaffold) | 80 | 70 |
| `libs/ui` | 70 | 60 |
| `apps/web`, `apps/admin`: global | 60 | 50 |

Из покрытия исключаются только `main.ts`, `*.module.ts`, `*.dto.ts`. Покрытие e2e в процент не
входит. Чек-лист обязательных кейсов (`nestjs-testing-ci-troubleshooting.md`) — отдельный гейт,
он не зависит от процентов. На релизе 2 пороги пересматриваются в сторону повышения; ориентир —
`apps/api` global 80/70.

**Бюджеты API кассы.** Время серверное (от входа запроса в API до ответа, включая БД), нагрузка —
по профилю оси Ж: 5 чеков/с + 25 поисков/с в течение 15 минут. На горячем SKU 5 кассиров одной
точки одновременно продают одну партию, чтобы проверить конкуренцию `FOR UPDATE`. Объём данных стенда —
не меньше 1 года работы (≈ 10–17 млн движений), целевой — 3 года. Дополнительно — стресс-прогон на
250 соединениях без пауз: запас по пропускной способности должен быть ≥ ×2 от целевой интенсивности.
autocannon не выводит p95, поэтому бюджет проверяется по **p97.5 — это строже p95**.

| Операция | p95 (проверяется по p97.5) | p99 | Обоснование |
|---|---|---|---|
| Товар и цена по штрих-коду (точное совпадение, индекс / кэш Redis) | ≤ 100 мс | ≤ 250 мс | Точечный поиск по индексу. Предложенные агентами 150 мс — слишком мягкий сигнал: seq scan или промах кэша заметнее на 100 |
| Текстовый поиск по каталогу RU/TJ (tsvector / pg_trgm) | ≤ 200 мс | ≤ 400 мс | Ввод с debounce; тяжелее точного поиска |
| Проведение чека (транзакция, FEFO-списание, движения, outbox) | ≤ 300 мс | ≤ 600 мс | Подтверждаем 300 мс — см. разложение ниже |
| Ошибки / дубли | 0 ошибок 5xx; 0 дублей при повторе с тем же `Idempotency-Key` | | Инварианты ТЗ |

Разложение «оплата → чек проведён, печать запущена ≤ 1 сек» для облачной точки: клиент ≤ 150 мс,
сеть — один запрос по keep-alive TLS при RTT ≤ 150 мс, ≈ 200 мс, API ≤ 300 мс; резерв ≈ 350 мс
остаётся на GC, «шумного соседа» и досылку из буфера. Сама физическая печать в бюджет не входит.
Скан, обработанный через API, укладывается в ≈ 400 мс; через локальный индекс каталога — в ≤ 100 мс.
Для офлайн-точки бюджеты API те же, проверка — на эталонном ПК с 8 ГБ ОЗУ, 1–3 кассира, браузер
открыт на том же ПК.

**Клиент (POS).** Замер на production-сборке с замедлением CPU 4× в DevTools, пока нет эталонного
POS-ПК заказчика; затем — на эталонном ПК.

| Метрика | Цель | Статус |
|---|---|---|
| Скан → строка чека (`pos:scan-to-line`) | ≤ 100 мс | гейт для PR, затрагивающих кассу |
| INP на сценариях кассы (скан, количество, оплата) | ≤ 200 мс | гейт |
| Оплата → чек проведён (Playwright, эмуляция RTT 150 мс через CDP, 20 прогонов) | 19 из 20 ≤ 1 с | гейт перед релизом |
| LCP страницы кассы (холодный старт смены) / CLS | ≤ 2,5 с / ≤ 0,1 | гейт |
| Lighthouse Accessibility | ≥ 95 и 0 нарушений axe уровня serious/critical | гейт |
| Lighthouse Performance (desktop) | ≥ 90 | ориентир, не гейт: для SPA за логином оценка нестабильна и не отражает интерактивность |

**Бюджеты бандла.** Порядок такой: (1) сейчас действуют стартовые потолки; (2) когда будет готов
walking skeleton кассы (скан → чек → оплата), делается базовый замер; (3) бюджет = базовый замер
+ 10 %, округлённо до 10 КБ, но не выше потолка; значения фиксируются в `tools/bundle-budget.json`
кодового репозитория с датой и commit; (4) дальше бюджеты только снижаются, повышение — с
обоснованием и выводом анализатора в PR и одобрением фронтенд-лида (нового ADR не требуется).
Передача по сети здесь вторична: статика кэшируется как `immutable`, на офлайн-точке всё идёт через
localhost. Настоящая цена — разбор и компиляция JS на слабом CPU при старте смены и после каждого
деплоя.

| Бюджет (gzip) | Стартовый потолок |
|---|---|
| First-load JS маршрута кассы | ≤ 250 КБ (цель ≤ 200 КБ) |
| Любой отдельный JS-чанк | ≤ 150 КБ |
| Весь JS `apps/web` / `apps/admin` | ≤ 900 КБ каждый |

Скрипт `tools/check-bundle-budget.mjs` из скила нужно доработать под учёт first-load маршрута кассы.

**Внешние сервисы: ни один инструмент не отправляет данные наружу.** Всё запускается локально или
на стендах платформы, отчёты (coverage, трассы Playwright, результаты нагрузки) остаются на машине
разработчика или стенде и в git не коммитятся (`.gitignore`). Обязательные настройки:

| Инструмент / сервис | Что по умолчанию | Правило проекта |
|---|---|---|
| Jest, `@testing-library/react`, axe-core, autocannon, web-vitals | Телеметрии нет | web-vitals ничего не отправляет |
| Playwright | Телеметрии нет; браузеры скачиваются с CDN Microsoft | Установленные Chrome/Edge или внутреннее зеркало. Облачный сервис Playwright (Azure) не используется |
| Next.js | Анонимная телеметрия включена | `NEXT_TELEMETRY_DISABLED=1` в `.env.example` и у всех разработчиков |
| Nx | Предлагает подключить Nx Cloud (удалённый кэш) | Nx Cloud не подключается, `nxCloudId` в `nx.json` отсутствует |
| Lighthouse | — | Только встроенный в DevTools; PageSpeed Insights / CrUX не используются |
| Отклонённые варианты | Cypress (crash-reports), k6 (usage report), Artillery (телеметрия), их облака | Не используются. При пересмотре — сначала отключить телеметрию |

### CI (GitHub Actions)

| Что | Решение |
|---|---|
| Платформа | GitHub Actions, GitHub-hosted раннеры `ubuntu-latest`; self-hosted не используются (публичный репозиторий: чужие PR выполняли бы код на своей машине) |
| `ci.yml` — триггеры | `pull_request` в `main` и `push` в `main` |
| Job **checks** (Node 24) | `npm ci` → `npx nx affected -t lint typecheck test build` (base — `main`) с порогами покрытия; `kysely-codegen --verify` (когда появится слой данных, ADR-0006); скрипт бюджета бандла |
| Job **api-e2e** (матрица Node 22 и 24, ADR-0008) | `docker compose -f docker/compose.yml -f docker/compose.dev.yml up -d --wait postgres redis` с env из примера → миграции (node-pg-migrate) → `npx nx e2e api-e2e`; обязательные кейсы: изоляция тенантов, идемпотентность, атомарность чека, деньги |
| Job **web-e2e** (Node 24) | Playwright с установленным на раннере Chrome (`channel: 'chrome'`), сценарии: вход, касса (скан → оплата), приёмка, возврат; `@axe-core/playwright` — 0 нарушений serious/critical |
| Гейты слияния PR | **checks, api-e2e (обе версии Node), web-e2e** — обязательные; настраиваются в правилах защиты ветки `main` (GitHub → Settings → Branches) владельцем репозитория |
| `nightly.yml` (по расписанию) | `npm audit --audit-level=high` и сканирование Docker-образов **Trivy** (Apache-2.0; скачивает базу уязвимостей, данные проекта не отправляет); падение — уведомление, не блок PR |
| Dependabot | Обновления npm, Docker-образов и GitHub Actions — отдельными PR, проходят те же гейты |
| Безопасность CI | Actions закреплены по commit SHA; `permissions: contents: read` по умолчанию; секретов в CI нет (данные синтетические, env из `*.example`); PR из форков — без секретов и без записи |
| Кэш | Локальный кэш Nx (`.nx/cache`) и npm через `actions/cache`; Nx Cloud не подключается |

## Последствия

- Положительные: все пометки «согласовать» в скилах закрыты одним решением, и агенты перестают
  останавливаться на каждой зависимости; новых npm-пакетов добавляется минимум (Playwright, axe-core
  в двух обёртках, autocannon, web-vitals — все dev-only, лицензии MIT / Apache-2.0 / MPL-2.0);
  бюджеты производительности можно проверить по частям, и регрессия API видна до того, как её «съест»
  сеть; пороги покрытия соответствуют сроку и концентрируют усилия на деньгах и остатках; данные
  не покидают контур.
- **Отрицательные (обязательно):**
  - CI на GitHub-hosted раннерах: при переводе репозитория в приватный — лимит бесплатных минут
    (2000/мес на бесплатном тарифе); матрица Node 22/24 для api-e2e и Playwright — самые дорогие job'ы,
    экономия — `nx affected` и кэш; при превышении — self-hosted раннер только для приватного репозитория;
  - гейты работают, только если владелец включит правила защиты `main` с обязательными проверками;
    нагрузочные прогоны и замеры на эталонном ПК по-прежнему ручные — перед релизом;
  - код проекта выполняется на инфраструктуре GitHub (раннеры, Dependabot); клиентских данных там нет,
    но CI — ещё одна поверхность supply-chain (actions третьих сторон — только по SHA);
  - общая тестовая БД в compose: e2e идут последовательно (`maxWorkers: 1`) и медленно растут с
    числом тестов; при заметном росте времени CI — пересмотреть ось А (Testcontainers, шардирование);
  - свои билдеры, моки и фейк-сервер НБТ — это бойлерплейт, который команда поддерживает сама;
    подмена `fetch` не проверяет таймауты, TLS и редиректы клиента НБТ — они проверяются только
    на стенде;
  - autocannon моделирует кассира приближённо и проверяет p97.5 вместо p95; если модели не хватит,
    понадобятся новый ADR на k6 и юридическая проверка AGPL-3.0;
  - нагрузочный стенд с данными за 1–3 года требует генератора синтетических данных (десятки
    миллионов движений) и ресурсов стенда — это отдельная задача в бэклоге волны 1;
  - Playwright требует внутреннего зеркала браузеров или установленных Chrome/Edge на машинах
    разработчиков; второй раннер — это второй конфиг и второй набор навыков;
  - `jest-axe` не проверяет контраст, а автоматические проверки в целом покрывают только часть
    критериев WCAG, поэтому ручной аудит остаётся;
  - `next experimental-analyze` экспериментальный и может измениться или сломаться при обновлении
    Next.js; запасной путь — размеры чанков и скрипт бюджета;
  - `web-vitals` работает только локально и на стенде: реальных метрик с POS аптек не будет, пока
    ADR не введёт мониторинг; замеры на эталонном ПК проводятся вручную перед релизами;
  - без виртуализации отдельные экраны (инвентаризация, большие отчёты) могут потребовать доработки
    после замера;
  - пороги покрытия ниже оригинала оставляют меньше страховки в контроллерах и адаптерах (это
    компенсируется e2e) и создают риск, что «временные» значения так и не поднимут — поэтому
    пересмотр на релизе 2 обязателен;
  - бюджеты API опираются на RTT ≤ 150 мс: если место хостинга (вопрос № 1 stack.md) даст
    RTT > 200 мс, бюджет «≤ 1 сек» не сходится, и разложение придётся пересмотреть (буфер
    операций, оптимистичное проведение на клиенте);
  - эталонный POS-ПК заказчика не определён; до его получения замедление CPU 4× — лишь приближение.
- Триггеры пересмотра: рост времени CI (ось А); ADR о деплое (CD); ADR о мониторинге
  (RUM, ось И); решение по месту хостинга (ось М). ADR-0006 (ORM и
