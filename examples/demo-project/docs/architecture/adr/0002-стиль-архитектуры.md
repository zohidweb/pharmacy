# ADR-0002: Стиль архитектуры — модульный монолит

- **Статус:** accepted
- **Дата:** 2026-09-01
- **Авторы:** команда «Сервис уведомлений клиентов» (пример)

## Контекст

Сервис решает одну связную задачу: принять событие по счёту, сформировать уведомление,
отправить его через СМС-шлюз. Команда небольшая, сроки сжаты, текущая нагрузка умеренная
(пик 20 уведомлений/сек на 50 000 клиентов). Нужно решить, как делить систему на компоненты,
не создавая лишней операционной сложности на старте.

## Рассмотренные варианты

1. **Микросервисы** — независимое масштабирование и деплой каждого компонента, но избыточная
   операционная сложность (отдельные конвейеры сборки, мониторинг, сетевые вызовы между
   сервисами) для команды такого размера и текущей нагрузки.
2. **Монолит без разделения на модули** — самый быстрый старт, но по мере роста функциональности
   (шаблоны, история, отправка) код быстро теряет границы ответственности, тяжело тестировать
   и передавать другим разработчикам.
3. **Модульный монолит** — единое решение (.NET solution) с чётким разделением на модули
   (приём событий, формирование, отправка), развёрнутое как два процесса — API и воркер — с
   общими доменными библиотеками.

## Решение

Выбран модульный монолит: единая кодовая база с явными границами модулей, развёрнутая как
два процесса (API уведомлений и воркер отправки, см. c4/container.md) — это даёт независимое
масштабирование самого нагруженного участка (отправки) без операционных издержек полноценных
микросервисов.

## Последствия

- Положительные: быстрая разработка на старте, единая кодовая база и общие доменные модели,
  простой деплой и отладка для команды такого размера.
- **Отрицательные (обязательно):** при росте нагрузки на отправку придётся выделять воркер
  в отдельный сервис (свой репозиторий, свой релизный цикл) — сегодняшнее разделение на модули
  внутри одного solution такой рост не решает само по себе.
