# Возврат поставщику и перемещения — спецификация

Дата: 2026-10-12. Статус: на утверждении архитектора. Связано: модель данных
`docs/architecture/data-model/03-batches-warehouse.md` и `05-purchasing.md` (одобрены 2026-09-30), спецификации
`2026-10-09-inventory-purchasing-design.md` (ядро склада, расчёты с поставщиками, распределение оплат) и
`2026-10-12-write-offs-stock-counts-design.md` (списание, заморозка, правило отмены проведения B2), ADR-0002
(границы модулей), ADR-0006 (блокировка отдельно от подсчёта), ADR-0014 (офлайн-точка; заявки — только облако),
ADR-0018 (права и охват).

## 1. Цель и критерии успеха

Последние складские документы переходят с моков на API (`apps/api`, модуль `inventory`; расчёты — `purchasing`):
брак уходит поставщику и уменьшает долг перед ним, а товар переезжает между точками сети по заявке или без неё.
Экраны «Возврат поставщику» и «Перемещения» `apps/web` работают с API в режиме `partial`.

Успех:
- проведённый возврат уменьшает остаток партий движениями `supplier_return` и долг поставщику — на закупочную
  стоимость возвращённого; если накладная уже оплачена, сумма возврата зачитывается в следующую поставку;
- заявка точки доходит до точки-отправителя, та собирает и отправляет перемещение или отклоняет заявку;
- отправка сразу уменьшает остаток отправителя, приёмка с фактическими количествами — увеличивает остаток
  получателя новыми партиями; недостачу система сама списывает у отправителя;
- отмена проведения возврата и отзыв неполученного перемещения — сторно движений; принятое перемещение не
  отменяется;
- заморозка инвентаризации и правила дат действуют, как у списания; каждое действие — в журнале сети.

## 2. Решения, принятые при обсуждении (2026-10-12)

| # | Вопрос | Решение |
|---|---|---|
| R1 | Деньги возврата | Поставщик **уменьшает долг** (денег не возвращает, замены нет) |
| R2 | Сумма возврата | **Закупочная цена партии**, считается сама: вручную не вводится |
| R3 | Накладная уже оплачена | Сумма возврата **зачитывается в следующую поставку** этого поставщика |
| R4 | Шапка возврата | Один поставщик, одна точка, **одна причина** на документ: брак, срок годности, бой (`defect`, `expired`, `broken`) |
| R5 | Строки возврата | Только партии **этого поставщика** с остатком на точке; количество — в упаковках или штуках; комментарий строки |
| R6 | Права возврата | Черновик — фармацевт (`inventory:create/update`), проведение — заведующий (`inventory:post`), отмена проведения — `inventory:unpost`; суммы — только с `finance:view-cost` |
| R7 | Претензия поставщику | Печать и статусы претензии **отложены**; текст претензии — комментарий документа |
| T1 | Начало перемещения | Обычно **заявка**: её создаёт точка, которой нужен товар (заведующий или сотрудник с доступом) |
| T2 | Заявка и перемещение | **Одна заявка — одно перемещение.** Отправитель может выполнить заявку частично (не хватает товара), но **не больше, чем просили**. После отправки заявка закрывается: «выполнена» / «выполнена частично»; остаток — новой заявкой |
| T3 | Без заявки | Перемещение **без заявки** бывает (излишки) |
| T4 | Отклонение | Отправитель может отклонить заявку с причиной: нет товара, закажите у поставщика, другое |
| T5 | Приёмка | Получатель пересчитывает и вводит **фактические количества** (не больше отправленного) |
| T6 | Недостача | Списывает **отправитель**: система при приёмке сама оформляет проведённое списание у отправителя с причиной `transfer_discrepancy`. Вариант «дослать недостающее» убирается |
| T7 | Отзыв | Отправленное, но не принятое перемещение отправитель может **отозвать** — товар возвращается на его остаток. Принятое перемещение не отменяется |
| T8 | Права перемещений | Заявка — `inventory:create/update`; отправка, отзыв и отклонение заявки — `inventory:post` (отзыв — `inventory:unpost`); приёмка — `inventory:receive` |
| T10 | Цена у получателя | Если у точки-получателя **нет цены** товара, при приёмке ставится **цена отправителя**; есть своя — остаётся |
| T9 | Отложено | Перемещения с офлайн-точками (ждут синхронизации, ADR-0014), закрытие точки через перемещение, сканер на приёмке |
| P1 | Разбиение | Одна спецификация, **два плана и два PR**: PR-1 «Возврат поставщику» (разделы 3.1, 4, web PR-1), PR-2 «Перемещения и заявки» (3.2, 5, web PR-2) |

Решения исполнителя (приняты при обсуждении как догадки и подтверждены): привязка к накладной на экране —
необязательная, для заполнения строк; отзыв — к черновику; права T8.

Решения исполнителя после проверки спецификации (не обсуждались — проверить при чтении):

| # | Вопрос | Решение |
|---|---|---|
| E1 | Точки разных юрлиц | Перемещение между ними разрешено как обычное складское (без продажи между юрлицами, раздел 9). Кредит возврата — в паре «поставщик × юрлицо **прихода**», из которого пришла партия (долг там); у партии без прихода — юрлицо точки возврата |
| E2 | Партии без прихода | Партию начальных остатков с поставщиком вернуть можно; её кредит идёт в общее распределение пары. Нулевая сумма (стартовая партия без цены) — без записи в журнале расчётов |
| E3 | Брошенный черновик перемещения | Не удаляется (после отзыва у него есть движения): **отмена** — статус `cancelled`, конечный, без движений, заявка снова `sent`. Черновик заявки удаляется (`DELETE`) — на него ничего не ссылается |
| E4 | Дата перемещения и заявки | Без ввода и без «задним числом»: дата заявки — бизнес-дата создания; дата перемещения — бизнес-дата отправки (ставится при отправке); номер — при создании черновика. Отзыв — по дате документа (закрытый период → 422), приёмка — по бизнес-дате получателя |

### 2.1 Поправки модели данных (утверждаются вместе со спецификацией)

1. `documents.supplier_return_reason text null` (`defect` / `expired` / `broken`), обязателен для `supplier_return`
   (R4). `claim_text` в этой итерации не используется (R7).
2. `supplier_return_lines` дополняется `product_id`, `unit` (`pack` / `piece`, как у списания), `note text null`;
   `amount_dirams` фиксируется при проведении (в черновике пуст).
3. **Зачёт возврата** (R1, R3; уточнение правила модели 05 «возврат — по исходному приходу, иначе на самый ранний
   неоплаченный, через распределение»): проведённый возврат — **кредит** поставщика в паре «поставщик × юрлицо»
   (E1: юрлицо прихода партии, без прихода — юрлицо точки возврата), который распределяется на приходы, как оплата. Новая таблица `supplier_return_allocations`
   (`return_document_id`, `goods_receipt_document_id`, `amount_dirams > 0`). Сначала кредит гасит остаток приходов,
   из которых пришли возвращённые партии, затем — открытые приходы по общему правилу (ранний срок первым);
   нераспределённый остаток кредита забирает следующий проведённый приход, как предоплату. Остаток по приходу =
   сумма прихода − распределённые оплаты − распределённые возвраты.
4. **Заявка** (`transfer_request`): `store_id` — точка, которой нужен товар (по ней номер `ЗП-…`),
   `destination_store_id` — точка, которую просят отправить. Статусы модели: `draft` → `sent` → `in_progress`
   (создан черновик перемещения) → `done` / `partial` (перемещение отправлено) или `rejected`. Колонки
   `rejection_reason` (`no_stock` / `order_from_supplier` / `other`), `rejection_comment`. Строки — в упаковках.
5. **Перемещение** (`transfer`): `store_id` — отправитель, `destination_store_id` — получатель, `request_document_id`
   — заявка (у заявки не более одного неотменённого перемещения). Статусы `draft` → `in_transit` → `received`;
   отзыв — снова `draft`; `draft` → `cancelled` (E3, конечный). `transfer_lines` дополняется `product_id`, `unit`; `discrepancy_resolution` не используется (T6).
   Комментарий получателя — `documents.received_comment text null`.
6. `documents.source_document_id` (уже в модели для «возврат → приход») получает второе значение: списание
   недостачи → перемещение. Такое списание не редактируется и не отменяется.
7. Недостача (T6) двигает партию отправителя дважды в транзакции приёмки: `reversal` части отправки (+N, ссылка на
   движение `transfer_out` строки) и `write_off` (−N) от автоматического списания. Остаток отправителя не меняется;
   списание недостачи видно в отчётах и журнале ПКУ как обычное.

## 3. Схема

### 3.1 Миграция PR-1 `supplier-returns`

- `documents.type` дополняется `supplier_return`; колонки `supplier_return_reason text null` (`check` по списку R4,
  обязательна для `supplier_return`, пуста для остальных), `source_document_id uuid null` (FK на `documents`;
  индекс). `check`: у `supplier_return` заполнен `supplier_id`.
- `supplier_return_lines` (класс `tenant`): `(tenant_id, id)`, `document_id`, `line_no ≥ 1` (уникален в
  документе), `batch_id`, `product_id`, `qty_pieces > 0`, `unit`, `note text null` (≤ 200), `amount_dirams bigint
  null ≥ 0`, `created_at`; FK и индексы — как у `write_off_lines`; одна партия — не более одной строки.
- `stock_movements.kind` дополняется `supplier_return`.
- `supplier_return_allocations` (класс `tenant`): ключ `(tenant_id, return_document_id, goods_receipt_document_id)`,
  `amount_dirams > 0`, `created_at`; FK на `documents` (оба); индекс по `goods_receipt_document_id`.
- RLS (fail-closed по `app.tenant_id`), гранты `pharmacy_app`, манифест `table-classes.ts`, типы Kysely.

### 3.2 Миграция PR-2 `transfers`

- `documents.type` дополняется `transfer`, `transfer_request`; `documents.status` — `in_transit`, `received`,
  `cancelled` (у `transfer`; `cancelled` — уже есть у инвентаризации, `cancelled_by/at`), `sent`, `in_progress`,
  `partial`, `done`, `rejected` (только `transfer_request`) — `check` статуса по типу; колонки
  `destination_store_id uuid null` (FK на `stores`, ≠ `store_id`, обязательна для обоих типов),
  `request_document_id uuid null` (FK, только у `transfer`; уникальный частичный индекс по неотменённым), `dispatched_at`,
  `dispatched_by`, `received_at`, `received_by`, `received_comment`, `rejection_reason`, `rejection_comment`.
  `posted_by/posted_at` у перемещения и заявки пусты — правило `(status = 'posted') = (posted_at is not null)`
  остаётся.
- `transfer_request_lines` (класс `tenant`): `(tenant_id, id)`, `document_id`, `line_no`, `product_id`,
  `qty_requested_pieces > 0`; товар не повторяется в заявке.
- `transfer_lines` (класс `tenant`): `(tenant_id, id)`, `document_id`, `line_no`, `source_batch_id`, `product_id`,
  `unit`, `qty_sent_pieces > 0`, `qty_received_pieces null ≥ 0` (≤ отправленного), `target_batch_id null`; партия
  не повторяется.
- `batches.origin` дополняется `transfer`; `batches.source_batch_id uuid null` (FK на `batches`; обязательна
  тогда и только тогда, когда `origin = 'transfer'`).
- `stock_movements.kind` дополняется `transfer_out`, `transfer_in`.
- RLS, гранты, манифест, типы — как в 3.1.

## 4. Возврат поставщику (PR-1; `apps/api/src/app/inventory`, только облако)

| Маршрут | Право |
|---|---|
| `GET /supplier-returns?storeId&supplierId&reason&status&limit&offset` (KPI) | `inventory:view` |
| `GET /supplier-returns/{id}` | `inventory:view` |
| `POST /supplier-returns`, `PUT /supplier-returns/{id}` — только черновик | `inventory:create` / `inventory:update` |
| `POST /supplier-returns/{id}/posting` | `inventory:post` |
| `POST /supplier-returns/{id}/unposting` | `inventory:unpost` |
| `GET /stock-documents/supplier-returns/{id}/unposting-check` | `inventory:unpost` |

- **Суммы** (`costMinor` строки, `totalMinor`, сумма в KPI) — только с `finance:view-cost`; запись черновика
  этого права не требует (R6).
- **Черновик:** точка в охвате, облачная, активная (`StoreAccess.writableStore`); поставщик существует и активен
  (как у прихода); номер `ВП-<код точки>-<год>-<6 цифр>` при создании; дата, причина, комментарий ≤ 500;
  `receiptId` — необязательный проведённый приход этого поставщика на этой точке (иначе 400 у `receiptId`);
  строки 1–500: партия этой точки с `supplier_id` поставщика документа (иначе 400 у `lines.i.batchId`,
  `wrong_supplier`), количество > 0 в упаковках или штуках (штуки — только у делимого товара), комментарий строки
  ≤ 200. Остаток при сохранении не проверяется.
- **Проведение — одна транзакция:** заголовок `FOR NO KEY UPDATE`; заморозка (`StockFreeze.guard`); дата — как у
  списания (не в будущем, окно задним числом, закрытый период); партии `FOR UPDATE`, затем остатки, больше остатка
  → 409 `stock_insufficient` у строк; движения `supplier_return` (−штуки); сумма строки =
  `round(штуки × цена упаковки партии / штук в упаковке)` — та же формула, что у суммы прихода (`linesTotal`);
  `total_dirams` = Σ; затем **зачёт** (2.1, п. 3) через `SupplierLedger` модуля `purchasing`; статус `posted`;
  аудит `document.posted`.
- **Зачёт** (`SupplierLedger.returnPosted`, в транзакции вызывающего, под блокировкой расчётов пары
  «поставщик × юрлицо»): приход партии — приход в корне цепочки `source_batch_id` (партия перемещения ведёт к
  партии отправителя); суммы строк группируются по паре (E1: юрлицо прихода партии, без прихода — юрлицо точки
  возврата), на каждую пару — запись журнала `supplier_return` (−сумма; нулевая не пишется, E2); кредит пары сначала
  гасит остаток приходов своих строк (не больше суммы этих строк), остальное — общим распределением; остаток кредита
  ждёт следующего прихода. Проведение прихода забирает кредиты возвратов вместе с предоплатами (старые первыми — по дате документа
  или оплаты).
- **Отмена проведения:** правило B2 (движения партий после проведения → 409 `unpost_blocked`), закрытый период,
  заморозка; сторно движений; `SupplierLedger.returnUnposted` снимает распределения возврата, пишет `reversal` и
  заново распределяет освобождённые оплаты и кредиты; статус `draft`.
- **Отмена проведения прихода** снимает и распределения возвратов на него; освобождённые кредиты распределяются
  заново (как освобождённые оплаты).
- **Долг в карточке и списке поставщиков** учитывает распределённые возвраты; журнал карточки показывает возврат
  видом `return` (в DTO уже есть).
- **Список и KPI:** документы за месяц бизнес-даты, сумма возвращённого за месяц (с правом); поиск по точке,
  поставщику, причине, статусу.
- **Выбор партий:** `GET /stores/{storeId}/stock-products?supplierId=` — только товары и партии этого поставщика с
  остатком (как обычный режим, с поиском и лимитом).

## 5. Перемещения и заявки (PR-2; `apps/api/src/app/inventory`, только облако)

### 5.1 Маршруты и права

| Маршрут | Право |
|---|---|
| `GET /transfers/overview?storeId` | `inventory:view` |
| `GET /transfer-requests/{id}`, `GET /transfers/{id}` | `inventory:view` |
| `POST /transfer-requests`, `PUT /transfer-requests/{id}`, `DELETE /transfer-requests/{id}` — черновик | `inventory:create` / `inventory:update` |
| `POST /transfer-requests/{id}/sending` | `inventory:create` |
| `POST /transfer-requests/{id}/rejection` | `inventory:post` |
| `POST /transfers`, `PUT /transfers/{id}` — черновик | `inventory:create` / `inventory:update` |
| `POST /transfers/{id}/cancellation` — черновик (E3) | `inventory:delete` |
| `POST /transfers/{id}/sending` | `inventory:post` |
| `POST /transfers/{id}/recall` | `inventory:unpost` |
| `POST /transfers/{id}/acceptance` | `inventory:receive` |

Охват: заявку и перемещение видят сотрудники, у которых в охвате **любая** из двух точек. Действия отправителя
(черновик перемещения, отправка, отзыв, отклонение заявки) — только при точке-отправителе в охвате; действия
запросившей точки (заявка) и приёмка — при её точке в охвате. Обе точки — облачные и активные: офлайн-точка с
любой стороны → 409 `offline_store_read_only` (T9). Закупочные цены в перемещениях не показываются.

### 5.2 Заявка

- **Черновик:** точка-заявитель — `writableStore`; точка, которую просят, ≠ заявителю; комментарий ≤ 500; строки
  1–500: активный товар, не повторяется, количество упаковок > 0. Номер `ЗП-<код заявителя>-…`. Можно сразу
  отправить (`send: true`, как в контракте).
- **Отправка:** `draft` → `sent`; аудит. **Удаление** — только черновик.
- **Отклонение** (отправитель): из `sent` или `in_progress` без отправленного перемещения; причина T4, комментарий
  ≤ 500 (обязателен при `other`); черновик перемещения по заявке отменяется (E3); статус `rejected`.
- Дата заявки — бизнес-дата создания (E4).
- Статусы `in_progress`, `done`, `partial` ставит перемещение (5.3).

### 5.3 Перемещение

- **Черновик** (отправитель): `fromStoreId` — `writableStore`, `toStoreId` — другая облачная активная точка;
  `requestId` — заявка в статусе `sent`, адресованная этой точке-отправителю от этой точки-получателя (иначе 409
  `request_not_open`); у заявки уже есть перемещение → 409 `request_has_transfer`; строки 1–500: партия
  отправителя (не повторяется), количество > 0 в упаковках или штуках; по заявке — товары только из заявки и
  **сумма по товару не больше запрошенного** (400 у строк, `not_requested` / `exceeds_request`). Номер
  `ПМ-<код отправителя>-…`. Создание по заявке ставит ей `in_progress`; отмена черновика (E3) возвращает `sent`.
  Можно сразу отправить (`send: true`).
- **Отправка — одна транзакция:** заголовок `FOR NO KEY UPDATE`; заморозка отправителя; дата документа = бизнес-дата
  отправки (E4; закрытый период юрлица отправителя → 422); партии `FOR UPDATE`, затем остатки (409
  `stock_insufficient` у строк); движения `transfer_out` (−штуки) с этой датой у отправителя; статус
  `in_transit`, `dispatched_at/by`; заявка → `done`, если отправлено всё
  запрошенное, иначе `partial`; аудит.
- **Отзыв** (`in_transit` → `draft`): заморозка отправителя, закрытый период по дате документа; сторно движений
  отправки (`reversal`); заявка снова `in_progress`; аудит. Иначе 409 `transfer_not_in_transit`.
- **Приёмка** (`in_transit` → `received`, одна транзакция): точка-получатель в охвате; заголовок `FOR NO KEY
  UPDATE` (гонка с отзывом и второй приёмкой → 409 `transfer_not_in_transit`); `lines` — каждая строка документа
  ровно один раз с количеством 0…отправленного в единицах строки; комментарий ≤ 500; заморозка получателя по
  товарам с количеством > 0 (409 `stock_count_in_progress`); закрытый период юрлица получателя по бизнес-дате;
  для каждой строки с количеством > 0 — **новая партия получателя** (`origin = 'transfer'`, `source_batch_id`,
  товар, срок, серия, закупочная цена и себестоимость штуки, поставщик — как у партии отправителя;
  `source_document_id` — перемещение) и движение `transfer_in` с бизнес-датой приёмки; `received_at/by`.
  **Цена (T10):** по каждому принятому товару без цены упаковки у получателя (`store_products`) — цена упаковки и
  своя цена штуки отправителя; у отправителя цены нет — ничего. Через публичный интерфейс модуля `pricing` (новый
  метод `StorePriceWriter`, например `copyIfMissing`): права на цены у принимающего не требуются — цену выбрал не
  он; `price_version` растёт, аудит `price.changed` с источником «перемещение».
  **Недостача** (отправлено − принято > 0 хотя бы по одной строке): проведённое списание точки-отправителя
  (`СП-…`, причина `transfer_discrepancy`, `source_document_id` — перемещение, дата — бизнес-дата приёмки,
  комментарий — номер перемещения и комментарий получателя, `created_by/posted_by` — принявший) и движения по
  2.1, п. 7. Аудит `transfer.received`.
- Списание недостачи: `PUT`, проведение и отмена проведения → 409 `write_off_from_transfer`.

### 5.4 Обзор

`GET /transfers/overview` (необязательный `storeId` в охвате): заявки и перемещения охвата — открытые (`draft`,
`sent`, `in_progress`; `draft`, `in_transit`) и закрытые за последние 30 дней бизнес-даты, новые первыми, не более
200 каждого вида (решение исполнителя); KPI: новые заявки к моим точкам (`sent`), заявки в работе, в пути к моим
точкам и от них. В ответе и `stores` — активные точки сети (`id`, `name`, `mode`) для выбора второй стороны:
охват сотрудника её не ограничивает, офлайн-точки на экране не предлагаются (решение исполнителя).

## 8. Web (`apps/web`)

- `REAL_API_ROUTES`: PR-1 — `supplierReturns.*`, `documents.unpostCheck` для `supplier-returns`; PR-2 —
  `transfers.*`, `transferRequests.*` (новые маршруты черновиков, отправки, отзыва).
- **Возврат поставщику:** флажок и печать претензии убираются, добавляется комментарий; выбор партий — только
  этого поставщика; «Заполнить из накладной» — строки накладной, которые ещё есть на остатке; суммы скрыты без
  права; ошибки `stock_insufficient`, `stock_count_in_progress` — у строк.
- **Перемещения:**
  - черновики заявки и перемещения открываются, правятся и отправляются; черновик заявки удаляется, черновик
    перемещения отменяется (статус «Отменено»);
  - перемещение по заявке: количества по умолчанию — запрошенные, в пределах остатка, партии по сроку (FEFO);
  - приёмка — фактические количества в единицах строки; после приёмки с недостачей — номер списания со ссылкой;
  - «Отозвать» у отправителя для `in_transit`; «Дослать» убирается;
  - офлайн-точки в выборе точек не предлагаются.
- Списание недостачи в редакторе списания — только просмотр, со ссылкой на перемещение.
- Моки — на новый контракт; полный мок-режим, unit-тесты и web-e2e — зелёные. Тексты RU/TJ.

## 11. Проверка

Новые автотесты не пишутся (тесты отложены до MVP); существующие наборы остаются зелёными. Живая проверка:

- **PR-1, curl:** черновик фармацевтом без сумм; партия чужого поставщика → 400; проведение — движения, остаток,
  сумма по формуле прихода; долг: неоплаченный приход — остаток уменьшился; полностью оплаченный — кредит, который
  забирает следующий проведённый приход; возврат партии, пришедшей перемещением, гасит приход отправителя; больше
  остатка → 409; отмена проведения — долг и распределения вернулись; отмена после продажи по партии → 409;
  заморозка → 409; офлайн-точка → 409.
- **PR-2, curl:** заявка (черновик, правка, отправка, удаление черновика); отклонение; перемещение по заявке — больше
  запрошенного → 400, товар не из заявки → 400; отправка — остаток отправителя, заявка `partial` / `done`; второе
  перемещение по заявке → 409; отзыв — остаток вернулся, заявка `in_progress`; приёмка с недостачей — новые партии
  получателя, списание у отправителя, остаток отправителя не изменился; товар без цены у получателя получил цену
  отправителя, своя цена получателя не изменилась; отзыв и вторая приёмка после приёмки → 409;
  приёмка чужой точкой → 403; заморозка получателя → 409; попытка отменить списание недостачи → 409.
- **Браузер (`partial`):** возврат по накладной — проведение и долг в карточке поставщика; заявка → перемещение →
  приёмка с недостачей двумя сотрудниками разных точек.
