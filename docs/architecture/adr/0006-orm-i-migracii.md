# ADR-0006: Слой доступа к данным и инструмент миграций — Kysely + `pg`, миграции на SQL (node-pg-migrate)

- **Статус:** proposed
- **Дата:** 2026-09-29
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (черновик подготовлен с помощью AI)

## Контекст

`apps/api` (NestJS, ADR-0003) работает с одной мультитенантной PostgreSQL в облаке и с
локальной PostgreSQL офлайн-точки в Docker на ПК аптеки (Windows 10/11 + WSL2 или Linux,
ADR-0005) — схема и цепочка миграций у них одни (ADR-0002). Главные инварианты уже заложены в
скилах `nestjs-api` и `postgres-best-practices`: каждый запрос — в транзакции, которая первым
оператором делает `set_config('app.tenant_id', …, true)` на соединении из пула приложения;
RLS с `FORCE` и прикладная роль `pharmacy_app`, не владеющая таблицами; остаток считается из
движений по партиям, партии блокируются `FOR UPDATE` в стабильном порядке, FEFO; деньги —
`bigint` в дирамах; аудит, журнал ПКУ и движения — append-only (`REVOKE` + триггер);
идемпотентность — `ON CONFLICT DO NOTHING RETURNING`; очереди синхронизации и outbox — таблицы
со `SKIP LOCKED`. CLAUDE.md `pharmacy-app` требует, чтобы ORM и инструмент миграций
зафиксировал первый ADR разработки. Без этого решения нельзя начинать scaffold слоя данных.

## Рассмотренные варианты

Критерии этого проекта (в порядке веса):

- К1. Контекст тенанта: `set_config(…, true)` в явной транзакции на одном соединении пула;
  нет способа выполнить запрос к прикладной таблице мимо tenant-транзакции.
- К2. Явные транзакции и блокировки: `FOR UPDATE`, `SKIP LOCKED`, `ON CONFLICT … RETURNING`,
  advisory xact-локи — без обходных путей.
- К3. Raw SQL для FEFO, отчётов, выгрузки 1С, CTE и оконных функций — параметризованный,
  по возможности типизированный.
- К4. Типобезопасность в TypeScript strict; типы БД не утекают во фронтенды (контракты API —
  только `libs/shared/dto`).
- К5. Миграции на SQL с RLS-политиками, триггерами, `GRANT`/`REVOKE`, `CREATE INDEX
  CONCURRENTLY`; ревью агентом `postgresql-database-reviewer` по читаемому SQL.
- К6. Запуск миграций в офлайн-дистрибутиве: внутри Linux-контейнера, без интернета, без
  лишних рантаймов (JVM) и нативных бинарей под платформу; защита от параллельного запуска.
- К7. Компетенции команды (NestJS/TypeScript), зрелость, лицензия, темп ломающих изменений.

1. **Prisma ORM 7.x** (Prisma Schema + Prisma Migrate). В 7.x клиент по умолчанию без
   Rust-движка (TypeScript + WASM, обязательный driver adapter `@prisma/adapter-pg`), лицензия
   Apache 2.0, лучший DX и популярность в NestJS-сообществе. Минусы для нас: RLS-контекст
   требует интерактивной транзакции `$transaction(async tx => …)` на каждый запрос, включая
   чтения (у интерактивных транзакций свои таймауты и накладные расходы) либо расширения
   клиента; `FOR UPDATE`, `SKIP LOCKED`, `ON CONFLICT DO NOTHING RETURNING` в query API нет —
   критичный код кассы, склада и очередей всё равно уходит в `$queryRaw`/TypedSQL, т.е. две
   парадигмы в одном репозитории; политики RLS, триггеры и гранты не описываются в
   `schema.prisma` — их дописывают вручную в сгенерированный `migration.sql`, а `migrate dev`
   требует теневую БД с правами на создание баз и нужными ролями; отдельный DSL схемы;
   линейка быстро и ломающе меняется (6→7: генератор, `prisma.config.ts`, адаптеры).
   Поставляется ли в 7.x CLI миграций без платформенного бинаря — проверить на пилоте.
2. **TypeORM 1.0** (вышел в мае 2026 после долгого 0.3.x; MIT, официальный `@nestjs/typeorm`,
   вероятно знаком команде). Транзакция через `dataSource.transaction(manager => …)` +
   `manager.query('select set_config…')` реализуема. Минусы: слабая типизация QueryBuilder
   (строковые алиасы) и нетипизированный `query()`; декоратор-сущности и ленивые связи
   провоцируют N+1 и неявные запросы; миграции генерируются диффом сущностей и всё равно
   требуют ручной правки под RLS/триггеры; опасный `synchronize: true` в самом API; история
   застоя проекта до 2024 года, 1.0 — свежий мажор с удалением API.
3. **Drizzle ORM** (Apache 2.0, схема на TypeScript, SQL-подобный типизированный API; есть
   `.for('update', { skipLocked })`, `onConflictDoNothing`, тег `sql`, декларации RLS-политик и
   ролей в схеме; миграции `drizzle-kit generate` в SQL + рантайм-мигратор без CLI в образе).
   Хорошо ложится на К1–К4. Минусы: стабильная линия — 0.45.x, при этом v1 месяцами в
   RC-стадии (на момент написания — v1.0.0-rc.4) с задокументированными ломающими изменениями
   v0→v1: стартовать на 0.x — значит почти сразу мигрировать, на RC — строить продукт на
   нестабильной версии; снапшоты drizzle-kit + вручную написанные «custom»-миграции для
   триггеров/`REVOKE` — два источника правды о схеме. Сильная вторая альтернатива.
4. **Kysely + `pg`** (MIT, типобезопасный query builder без модели и без движков, линия 0.29.x).
   Транзакция `db.transaction().execute(trx => …)` держит одно соединение `pg.Pool` —
   `set_config` первым оператором ложится ровно на контракт скилов (К1); `forUpdate()`,
   `skipLocked()`, `onConflict(…).doNothing()`, `returning()`, CTE — нативно (К2); тег `sql`
   параметризует и типизирует raw-фрагменты (К3); типы БД генерируются из реальной схемы
   после миграций (`kysely-codegen`), т.е. схема — одна, в SQL (К4). Собственный `Migrator`
   Kysely есть, но DDL политик и триггеров в TS-билдере читается хуже чистого SQL — поэтому в
   паре с SQL-мигратором. Минусы: версия 0.x (в минорных бывают ломающие изменения, в работе
   0.30), нет ORM-возможностей (связи, identity map), нет официального NestJS-модуля; сложные
   запросы утяжеляют проверку типов TypeScript.
5. **MikroORM 7.x** (MIT, v7 — март 2026: без knex, zero-dependency core; Data Mapper с Unit
   of Work и identity map). Минусы: неявный `flush` и UoW плохо сочетаются с нашим стилем
   «явная транзакция + явные блокировки + движения append-only»; контекст тенанта надо
   вписывать в `em.transactional` и форки EntityManager; собственный query builder новый (v7);
   самое маленькое сообщество из списка и наименьшие компетенции команды.
6. **Чистый `pg` + SQL-миграции** (node-pg-migrate / dbmate / Flyway). Пример в скиле
   `nestjs-api` уже на `pg`; максимальный контроль, ноль абстракций. Минусы: запросы не
   типизированы (интерфейсы строк пишутся руками, опечатка в колонке ловится только тестом),
   динамические фильтры отчётов и поиска каталога собираются конкатенацией — риск инъекций и
   ошибок. По мигратору: **node-pg-migrate** (MIT, только PostgreSQL, миграции в `.sql` с
   секциями Up/Down, advisory-лок от параллельного запуска, программный `runner()`, живёт в
   том же Node-образе); **dbmate** (MIT, простой SQL, но отдельный Go-бинарь в образе вне
   npm-lock); **Flyway** (JVM в офлайн-образе, часть возможностей — в платных редакциях
   Redgate) — избыточен для ПК аптеки.

## Решение

Выбираем **Kysely (query builder) поверх драйвера `pg`** для всего прикладного доступа к
данным `apps/api` и **node-pg-migrate с миграциями на чистом SQL** как единственный инструмент
версионированных миграций. Определяющие аргументы: наши инварианты (RLS-контекст на
транзакцию, `FOR UPDATE`/`SKIP LOCKED`/`ON CONFLICT`, append-only через `REVOKE` и триггеры)
по природе SQL-first — Kysely даёт на них типизацию без второй парадигмы, а SQL-миграции
остаются единственным источником правды о схеме, который читает ревьюер и одинаково
применяется в облаке и в офлайн-точке без дополнительных рантаймов. Правила применения:
`DatabaseService.tenantTransaction` оборачивает `Transaction<DB>` и `tenantId` (контракт
скилов сохраняется); типы `DB` генерируются `kysely-codegen` из БД после миграций и лежат в
`apps/api` (не в `libs/shared/*`); миграции — `apps/api/migrations/*.sql`, применяются ролью
`pharmacy_owner` отдельным шагом до старта API (облако — job перед выкаткой, офлайн-точка —
шаг скрипта обновления после `pg_dump`), в проде только вперёд (forward-only); версии Kysely и
node-pg-migrate закреплены точно. Если архитектор проекта/команда отвергнут этот выбор —
запасной вариант Drizzle ORM после выхода стабильной v1. Kysely, `pg` и node-pg-migrate —
библиотеки в рамках выбранных NestJS (ADR-0003) и PostgreSQL (stack.md); MIT-лицензии, пакеты
из публичного npm-реестра по lock-файлу.

## Последствия

- Положительные:
  - один путь к данным — tenant-транзакция на одном соединении пула; сессионного состояния и
    неявных запросов (ленивых связей, автосохранения) нет по построению;
  - критичный код кассы и склада (блокировка партий, FEFO, движения, идемпотентность, очереди)
    пишется одним типизированным API, raw-фрагменты — только через параметризованный `sql`;
  - схема, RLS, гранты, триггеры и индексы — в читаемых SQL-файлах; нет DSL схемы, теневой БД
    и дрейфа «модель vs миграции»;
  - офлайн-дистрибутив не получает новых рантаймов и нативных бинарей: мигратор — npm-пакет
    в том же образе, advisory-лок защищает от одновременного запуска несколькими инстансами;
  - нет привязки к вендору ORM со своей коммерческой повесткой; замена query builder не
    затрагивает схему и миграции.
- **Отрицательные (обязательно):**
  - все миграции пишутся вручную — нет автогенерации из модели; больше работы и выше цена
    ошибки в DDL, обязательное ревью `postgresql-database-reviewer` на каждую миграцию;
  - типы БД производны от схемы: шаг «миграции → `kysely-codegen`» в разработке и проверка
    в пайплайне/перед MR, что сгенерированные типы совпадают с закоммиченными; забытая
    регенерация даёт ложную типобезопасность;
  - нет ORM-удобств: связи, вложенные выборки и маппинг строк в доменные объекты пишутся
    руками в репозиториях — больше шаблонного кода, чем с Prisma/TypeORM;
  - Kysely — линия 0.x: минорные обновления могут ломать API (на подходе 0.30); обновления
    только отдельным MR с прогоном e2e; тяжёлые типы сложных запросов замедляют `tsc`;
  - две библиотеки вместо одной и нет официального NestJS-модуля — `DatabaseModule`,
    завершение пула, логирование SQL пишем сами; меньше готовых примеров, чем у Prisma/TypeORM;
    часть команды, привыкшей к ORM, потребует адаптации;
  - `pg` отдаёт `int8` строкой — нужен единый type parser или конвертация через утилиту денег
    из `libs/shared/util`; ошибка здесь бьёт по инварианту «деньги — целые дирамы»;
  - forward-only: откат неудачной миграции в проде — только новой миграцией или
    восстановлением из бэкапа; на офлайн-точке `pg_dump` перед обновлением обязателен, а
    миграции должны быть совместимы с ещё не обновлёнными точками (expand/contract) из-за
    синхронизации;
  - `CREATE INDEX CONCURRENTLY` и иные операции вне транзакции требуют отдельных миграций с
    отключённой транзакцией — поддержку для `.sql`-формата node-pg-migrate проверить на пилоте
    (при отсутствии — TS-миграция с `pgm.noTransaction()` для таких случаев).
- Открытые вопросы для команды: использовать ли `CamelCasePlugin` Kysely или держать
  snake_case в типах БД и маппить в репозиториях; нужен ли вообще `down` в SQL-файлах при
  forward-only; кросс-тенантный путь оператора платформы (отдельная роль БД) — отдельный ADR.
