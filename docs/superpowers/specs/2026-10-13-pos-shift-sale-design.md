# Касса: смена и продажа на API — спецификация

Дата: 2026-10-13. Статус: на утверждении архитектора. Связано: модель данных `docs/architecture/data-model/04-pos.md`,
`03-batches-warehouse.md`, `02-catalog-prices.md`, `06-sync-audit-billing.md` (одобрены 2026-09-30), ADR-0014
(офлайн-точка, «продажа — факт»), ADR-0015 (буфер перебоев кассы, решения архитектора 2026-09-30), ADR-0018 (права и
охват), спецификация `2026-10-12-write-offs-stock-counts-design.md` (инвентаризация, заморозка), ТЗ «Клиентский
продукт» v3.1 (разд. 5, 14), разбор макетов `docs/architecture/reviews/2026-09-30-mockups-tz-review.md`.

## 1. Цель и критерии успеха

Касса облачной точки переходит с моков на API (`apps/api`, модуль `pos`): кассир на привязанном терминале открывает
смену, продаёт, откладывает чеки, вносит и изымает наличные и закрывает смену с Z-отчётом. Экраны «Касса» и «Смена»
`apps/web` работают с API в режиме `partial`, буфер перебоев (outbox-first) досылает операции на настоящий сервер.

Успех:
- продажа уменьшает остаток проданных партий движениями `sale` в одной транзакции с чеком, оплатами и записями ПКУ;
- повтор операции из буфера с тем же ключом не создаёт второй чек и возвращает первый ответ;
- нехватка остатка, изменившаяся цена или скидка не отклоняют чек — он принимается и помечается расхождением;
  партия в минусе видна на экране остатков, чеки с расхождением — на странице смены и в Z-отчёте;
- закрытие смены считает ожидаемые наличные на сервере, требует причину расхождения, сохраняет Z-отчёт и удаляет
  отложенные чеки смены;
- продажа во время инвентаризации больше не даёт ложного излишка (решение I4).

## 2. Решения, принятые при обсуждении (2026-10-12 — 2026-10-13)

| # | Вопрос | Решение |
|---|---|---|
| K1 | Разбиение кассы | Три PR: **(1) смена и продажа + I4** — эта спецификация; (2) возвраты покупателей; (3) журнал ПКУ и офлайн-ограничения буфера (досылка под терминалом, пределы буфера, ПКУ без связи, локальный номер чека) |
| K2 | I4: продажа во время инвентаризации | Учётный остаток строки фиксируется **в момент первого ввода по ней**: всё, что продано после, считается уже посчитанным. В карточке пересчёта видно «продано после пересчёта». Если партию считали в двух местах в разное время, продажи между вводами тоже попадают в «уже посчитанные» — заведующий видит их в той же колонке |
| K3 | Данные рецепта ПКУ | **Все поля необязательны** (состав даёт заказчик, ТЗ разд. 14). Право «Продажа ПКУ» (`pos:sell-controlled`) нужно; запись о продаже ПКУ создаётся всегда, даже без данных |
| K4 | «Продажа — факт» | Нехватка остатка и устаревшая цена или скидка **не отклоняют чек** — он помечается расхождением (ADR-0015). Партия в минусе — на экране остатков (фильтр «Минус»), исправляет инвентаризация; **счётчик чеков с расхождением** — на странице смены и в Z-отчёте |
| K5 | Смена | **Одна открытая смена на терминал** (модель D3), а не на точку, как на моках |
| K6 | Где работает касса | Продажа и смена — **только на привязанном терминале после входа по PIN**: у входа по паролю терминала нет. Заведующему за кассой нужен свой PIN |
| K7 | Права автора при досылке (уточнение ADR-0015) | Истории ролей и блокировок нет, право «на момент продажи» проверить нельзя. Если автор **сейчас** неактивен, вне охвата точки или без права, операция **принимается с пометкой «автор»** и попадает в счётчик расхождений; не отклоняется |

| # | Вопрос | Решение |
|---|---|---|
| E1 | Идентификаторы | `id` смены, чека и операции с наличными = UUIDv7 операции клиента (ключ идемпотентности): касса пользуется id смены до доставки |
| E2 | Номера | Чек `ЧК-<код точки>-<год>-<6 цифр>` (счётчик `receipt`), смена `СМ-<код точки>-<год>-<6 цифр>` (счётчик `z_report`, номер Z-отчёта); год — по бизнес-дате. Номер выдаёт сервер при приёме; чек без связи печатается с «номер — после отправки», как сейчас (локальный номер — PR (3)) |
| E3 | Автор операции | Автор — `employeeId` операции (пока операции ждут в буфере, кассиры на терминале меняются). Сессия запроса — PIN-сессия **того же терминала и точки** с правом маршрута (иначе 403 — буфер на паузе до входа сотрудника с правом). Автор должен быть сотрудником сети (иначе 422 `author_not_allowed`). Права автора на момент операции проверить нельзя — истории ролей нет; если **сейчас** автор неактивен, вне охвата точки или без права операции, операция принимается с пометкой `author` (решение K7). Онлайн-операция (принята в пределах 60 секунд) от имени не того сотрудника, что вошёл, тоже помечается `author`. Досылка после истечения сессии — PR (3) |
| E4 | Время операции | Момент операции = `occurredAt`, исправленный на разницу часов ПК и сервера (касса шлёт момент отправки в заголовке `X-Client-Sent-At`), но не позже приёма сервером, не раньше открытия смены и не старше 30 дней; бизнес-дата — дата этого момента в часовом поясе сети. Закрытый период продажу не блокирует (факт) — чек помечается `closed_period` |
| E5 | Пометки расхождения | `stock` — строка увела партию в минус (сколько штук не хватило); `price` — цена единицы ≠ текущей цене точки; `discount` — скидка ≠ лучшему действующему правилу для суммы чека; `catalog` — карточка товара изменилась после снимка (E23); `author` — автор сейчас неактивен, вне охвата точки или без права операции (E3); `closed_period`. `CreatedReceipt.discrepancies` — число пометок |
| E6 | Что не принимается и после факта | Арифметика чека и оплат по значениям снимка из самого чека (E23), неизвестный товар или партия, партия другой точки или другого товара, просроченная на дату продажи партия, правило скидки, которого в сети не было, автор — не сотрудник сети, смена не открыта или чужого терминала — 400/409/422, операция уходит в карантин буфера (ADR-0015) |
| E23 | Снимок в чеке | Чек несёт значения снимка, по которым касса считала: у строки — `piecesPerPack` и `controlled` (не `null` ⇔ товар был ПКУ в снимке; без данных рецепта — пустой объект), у чека — процент и порог ступени скидки. Сервер считает штуки и арифметику по ним: правку правила скидки, штук в упаковке, делимости или признака ПКУ после снимка он не отклоняет, а помечает (`discount`, `catalog`). Право ПКУ проверяется у строк, помеченных ПКУ в снимке; запись ПКУ создаётся, если товар ПКУ в снимке или сейчас |
| E24 | Закрытие смены — тоже факт | Закрытие открытой своей смены принимается всегда: ожидаемые наличные считает сервер, расхождение = факт − ожидаемые. Если расхождение ≠ 0, а причины нет (касса не видела расхождения из-за операций, ещё ждавших в буфере), закрытие принимается с пометкой «причина не указана» в смене и Z-отчёте — иначе отказ закрытия увёл бы в карантин весь следующий день терминала. Касса считает ожидаемые наличные в окне закрытия с учётом своих неотправленных операций смены |
| E7 | Права по строкам | Сервер FEFO не пересчитывает: касса помечает вручную выбранную партию (`batchChosenManually`), право `pos:choose-batch` проверяется только у неё. Нет у автора права по строке (ПКУ, ручная партия) — пометка `author` по E3, не отказ: на 401/403 буфер встаёт на паузу целиком, а 422 увёл бы проданное в карантин |
| E8 | Цена | Сервер принимает цену из чека. Текущая цена для пометки `price`: упаковка — цена точки; штука — своя цена штуки или `ceil(цена упаковки / штук в упаковке)` до шага `piece_price_rounding_dirams` (модель 02) |
| E9 | Скидка | В снимке одна ступень правила = одно `DiscountRule`, `id` = `<ruleId>:<minSubtotalMinor>`; чек присылает этот `id`, процент и порог ступени (E23). Чек хранит правило, процент и порог. Доли скидки по строкам — пропорционально сумме строки, в сумме равны скидке (остаток округления — на строку с наибольшей суммой) |
| E10 | Способы оплаты | Виды `cash` / `card` / `qr` / `nfc` без таблицы `payment_methods` (экрана способов оплаты нет). Строка оплаты наличными хранит полученную сумму: Σ оплат = итог + сдача (модель 04) |
| E11 | Идемпотентность | Таблица `idempotency_keys` (модель 06), области `receipt`, `shift.open`, `shift.cash`, `shift.close`. Тот же ключ и то же тело — сохранённый ответ; другое тело — 409 `idempotency_conflict`; заголовок `Idempotency-Key` ≠ `id` тела — 400. Срок хранения ключа — 30 дней |
| E12 | Отложенные чеки | Принадлежат открытой смене терминала, где отложены; видны всем кассирам точки; удаляются при оплате (касса), вручную и при закрытии своей смены. Без открытой смены — 409 `no_open_shift`. Только онлайн, не через буфер; повтор `POST` с тем же `id` возвращает тот же чек |
| E13 | Z-отчёт | Снимок `ZReport` сохраняется при закрытии; `GET /shifts/{id}/z-report` — для печати после доставки и повторной печати. История смен — в отчётах (позже) |
| E14 | Отвязка терминала | Отзыв терминала (отвязка или повторная привязка браузера) с открытой сменой — 409 `shift_open`: сначала закрыть смену |
| E15 | Изъятие больше ожидаемого | Принимается; экран только предупреждает, как сейчас |
| E16 | Снимок каталога | Активные товары с ценой упаковки на точке; партии точки с остатком > 0 (просроченные тоже — касса их блокирует). Версия — отметка времени последнего изменения (мс); дельта — товары, изменённые после `sinceVersion` минус перекрытие 2 минуты (карточка, цена, движения партий точки); категории, правила и настройки — каждый раз. Касса онлайн обновляет снимок раз в минуту (было 5) — минус реже |
| E17 | ПКУ в буфере | Буфер пишется до отправки и при связи, поэтому данные рецепта в черновике и буфере **шифруются** AES-GCM (WebCrypto, неэкспортируемый ключ в IndexedDB, ADR-0015) и расшифровываются перед отправкой. **Продажа ПКУ без связи заблокирована** до PR (3), где появятся пределы 20 операций / 8 часов |
| E18 | Пауза буфера | После входа по PIN или паролю очередь возобновляется (сейчас `resume()` никто не вызывает) |
| E19 | Режим точки | `PosModule` регистрируется только в облаке (как `inventory`); касса офлайн-точки — с синхронизацией. Продажа на офлайн-точку через облако — 409 `offline_store_read_only` |
| E20 | Развёртывание | `GET /deployment` (публичный, `{ kind: 'cloud' }`) — для Service Worker; `health.get` и `deployment.get` — в `REAL_API_ROUTES` |
| E21 | Отметка партии | `batches.negative_flagged_at` не вводится: минус виден по движениям (экран остатков), пометка — у строки чека |
| E22 | Фискализация | Не вызывается: `fiscal_status = 'not_required'`, `CreatedReceipt.fiscal = null`. Адаптер и очередь отправки — с ADR о фискализации (stack.md, вопрос 9) |

### 2.1 Поправки модели данных (утверждаются вместе со спецификацией)

1. `shifts`: `id` = id операции открытия (E1); добавляются `received_at` (приём сервером) и `terminal_totals jsonb null`
   (суммы банковского терминала при закрытии: card, qr, nfc); `z_report jsonb` — снимок `ZReport` (E13);
   `discrepancy_reason` при расхождении может быть пустым — тогда смена помечена «причина не указана» (E24).
2. `shift_cash_operations`: `id` = id операции; `kind` `deposit` / `withdrawal`; `reason` — код (`change_fund`, `other`
   / `collection`, `expense`); добавляется `comment text null`, `received_at`.
3. `held_receipts`: `label` не используется; `payload` — строки как в контракте (без данных ПКУ).
4. `receipts`: `id` = id операции, отдельной колонки `operation_id` нет (уникальность — первичный ключ); добавляются
   `received_at`, `discrepancy_kinds text[]` (E5; пусто — без расхождения), `cash_tendered_dirams`; `origin` —
   `online`, если принят в пределах 60 секунд от момента продажи, иначе `offline_buffer`; `fiscal_status` —
   `not_required` (E22); статус в этой итерации только `paid`.
5. `receipt_lines`: добавляются `shortfall_pieces integer not null default 0` (пометка `stock`),
   `current_price_dirams bigint null` (текущая цена при пометке `price`) и `pieces_per_pack integer` (значение
   снимка, E23). `receipts` дополняется `discount_min_total_dirams bigint null` (порог ступени).
6. `payments`: `payment_method_id` не вводится, только `kind` (E10).
7. `controlled_sale_records.prescription_note` — объект с необязательными ключами `prescriptionNumber`,
   `prescriptionDate`, `clinic`, `doctor`, `buyerName`, `buyerDocument` (только непустые); `null`, если данных нет (K3).
8. `idempotency_keys` — как в модели 06 (E11); `stock_movements.source_type` дополняется `receipt`.
9. **Инвентаризация (K2):** снимок старта берёт партии с остатком ≠ 0 (партия в минусе тоже попадает в пересчёт и
   исправляется), `book_qty_pieces` может быть отрицательным; ожидаемый остаток строки при проведении — **остаток
   партии в момент первого ввода по строке** (продажи — по моменту продажи, остальные движения — по моменту
  записи); разница = факт − ожидаемый. Добавляется
   `inventory_lines.sold_after_count_pieces` (фиксируется при проведении). Правило модели 03 «ожидаемый — текущий
   остаток партии» заменяется.
10. Правило модели 03 «Минус запрещён при продаже» уточняется: продажа облачной точки — факт (ADR-0015, K4), минус
    допускается и помечается в строке чека.

## 3. Схема — миграция `pos-shifts-sales`

- `shifts`, `shift_cash_operations`, `held_receipts`, `receipts`, `receipt_lines`, `payments`,
  `controlled_sale_records`, `idempotency_keys` — по модели 04/06 с поправками 2.1. Все — класс `tenant`, RLS
  fail-closed по `app.tenant_id`, гранты `pharmacy_app`, манифест `table-classes.ts`, типы Kysely.
- **Ключи и индексы:** уникальный частичный `(tenant_id, terminal_id) where status = 'open'` у `shifts`; уникальный
  `(tenant_id, store_id, number)` у `receipts` и `shifts`; `(tenant_id, store_id, business_date)` и
  `(tenant_id, shift_id)` у `receipts`; `(tenant_id, receipt_id)` у строк и оплат; `(tenant_id, shift_id)` у операций
  с наличными и отложенных чеков; `(tenant_id, store_id)` у отложенных чеков; уникальный `receipt_line_id` у записей
  ПКУ; FK на `stores`, `terminals`, `employees`, `products`, `batches`, `discount_rules`.
- **Проверки:** `opening_cash_dirams ≥ 0`; `total = subtotal − discount`; `discount ≤ subtotal`; суммы оплат > 0;
  `qty_pieces > 0`; `kind` оплаты по списку E10. Причина расхождения смены `check`-ом не требуется (E24).
- **Только добавление:** `shift_cash_operations`, `receipts`, `receipt_lines`, `payments` — без `DELETE`;
  `controlled_sale_records` — без `UPDATE`/`DELETE` (очистка по сроку — PR (3), тогда же триггер-исключение);
  `shifts` — `UPDATE` только при закрытии; `held_receipts` — единственная таблица кассы с `DELETE` (модель 04).
  `APPEND_ONLY_TABLES` дополняется `shift_cash_operations`, `receipts`, `receipt_lines`, `payments`,
  `controlled_sale_records`.
- `stock_movements.source_type` + `receipt`; `inventory_lines`: снимается `check (book_qty_pieces >= 0)`,
  добавляется `sold_after_count_pieces integer null`.

## 4. Касса (`apps/api/src/app/pos`, только облако)

|---|---|

Сессия без терминала (вход по паролю) на маршрутах смены, чека и отложенных чеков — 403 `terminal_required` (K6);
снимок каталога ей доступен. Точка — облачная, активная, в охвате сессии (PIN-сессия — только своя точка).

### 4.2 Операции буфера: общие правила

Открытие смены, операция с наличными, закрытие и чек:
- `Idempotency-Key` = `id` тела (UUID), иначе 400; первым в транзакции — запись `idempotency_keys` (E11): повтор
  ждёт завершения первой транзакции на уникальном ключе и возвращает её ответ с тем же статусом;
- `storeId` и `terminalId` тела = точка и терминал сессии, иначе 409 `wrong_terminal` (карантин, а не пауза буфера:
  так бывает после перепривязки браузера с непустым буфером); автор — по E3: не сотрудник сети — 422
  `author_not_allowed`; сейчас неактивен, вне охвата точки или без права операции — пометка `author` (у смены и
  операций с наличными — в журнале событий смены);
- момент операции — по E4, `received_at` — время сервера;
- аудит: `shift.opened`, `shift.cash-in` / `shift.cash-out`, `shift.closed`, `receipt.completed` — с терминалом и
  correlation id, без данных рецепта (модель 06).

### 4.3 Снимок каталога

`GET /stores/{storeId}/catalog-snapshot` — контракт `CatalogSnapshot` по E16: `full = true` без `sinceVersion` или
при версии старше 24 часов; `removedProductIds` — товары, архивированные после версии; цена штуки — по E8; закупочная
цена партии — только с `finance:view-cost`; `discountRules` — действующие на бизнес-дату правила точки (уровень сети
и списки точек, период), по ступеням (E9); `settings` — сеть, точка, адрес, ИНН юрлица точки, подвал чека на языке
сессии, `returnWindowDays` = `return_period_days`. Модуль читает каталог, цены и остатки через публичные интерфейсы
`catalog`, `pricing`, `inventory` (без чужих таблиц).

### 4.4 Смена

- **Открытие:** терминал без открытой смены (иначе 409 `shift_open`), наличные на начало ≥ 0; номер по E2;
  ответ — `Shift`.
- **Внесение и изъятие:** смена открыта и принадлежит терминалу сессии (иначе 409 `no_open_shift`); сумма > 0;
  причина по виду (`in`: `change_fund` / `other`, `out`: `collection` / `expense`), комментарий ≤ 200; ответ — `Shift`.
- **`Shift`:** итоги считаются из чеков, оплат и операций смены: число чеков, по способам оплаты, выручка, наличные
  (начало + наличные продажи − сдача + внесения − изъятия), `discrepancyReceipts` — чеки с пометками, журнал событий.
- **Закрытие (E24):** смена открыта и своя; фактические наличные ≥ 0; ожидаемые считает сервер; причина ≤ 500
  символов, при расхождении без причины — пометка «причина не указана»; суммы банковского терминала ≥ 0; статус `closed`,
  `closed_by/at`; снимок `ZReport` (разница банковского терминала = введённая − системная по виду) в `z_report`;
  отложенные чеки смены удаляются; ответ — `ZReport`. Повтор закрытия с тем же ключом — тот же отчёт; закрытие уже
  закрытой смены с другим ключом — 409 `shift_closed`.

### 4.5 Чек

Одна транзакция: ключ идемпотентности; смена открыта, своего терминала и точки (иначе 409 `no_open_shift`, закрыта —
409 `shift_closed`); проверки E6 (поля и коды раздела 7); права автора по строкам E7; партии `FOR UPDATE` (по
возрастанию id), затем остатки партий; номер по E2; строки (одна партия — одна строка, штуки = упаковки × штук в
упаковке или штуки), себестоимость строки = штуки × себестоимость штуки партии, доли скидки (E9); оплаты (E10);
записи ПКУ по E23 (K3); движения `sale` (−штуки, `source_type = 'receipt'`, бизнес-дата продажи); пометки E5:
остаток партии после продажи < 0 → `stock` и `shortfall_pieces` (не больше штук строки), цена ≠ текущей → `price`,
скидка ≠ лучшему действующему правилу → `discount`, штук в упаковке, делимость или признак ПКУ ≠ текущим →
`catalog`, автор сейчас неактивен, вне охвата или без права → `author`, дата в закрытом периоде юрлица точки →
`closed_period`; аудит. Ответ — `CreatedReceipt` (`fiscal: null`).

Арифметика (400 `validation_failed`) — по значениям снимка из чека (E23): штуки строки = количество × `piecesPerPack`
строки (упаковки) или количество (штуки); `amount` строки = количество × цена; `subtotal` = Σ строк; правило скидки
существует в сети в любом статусе (иначе `unknown_discount`), скидка = присланный процент от `subtotal` (округление
как `discountAmount`; без правила — 0) и `subtotal` ≥ присланного порога; `total` = `subtotal − discount`; Σ оплат
(наличные — чистая часть) = `total`;
полученные наличные ≥ наличной части; сдача = полученные − наличная часть; сдача только при наличной части. Ступень
архивирована, вне периода или точки, порог не достигнут, есть ступень выгоднее (или скидки нет, а правило
действует) — не отказ, а пометка `discount`.

### 4.6 Отложенные чеки

`POST /held-receipts` — по E12, строки 1–100, товары и партии точки; `heldBy` — сотрудник сессии. Список — чеки
точки по времени. `DELETE` — чек точки охвата; уже удалённый — 204.

### 4.7 Отвязка терминала

`terminals` спрашивает открытую смену терминала через публичный интерфейс `pos` (E14); в офлайн-режиме, где
`pos` не зарегистрирован, проверки нет.

## 5. Инвентаризация (K2; `apps/api/src/app/inventory`)

- Старт: снимок — партии охвата с остатком ≠ 0 (2.1, п. 9).
- Ожидаемый остаток строки при проведении = сумма движений партии, случившихся не позже первого ввода по строке
  (`entered_at` самого раннего ввода). Момент движения продажи — момент продажи чека (`receipts.sold_at`, E4): чек,
  пробитый при перебое до пересчёта и доставленный после первого ввода, — «продано до пересчёта»; у остальных
  движений — `recorded_at`. Разница = факт − ожидаемый; движения `inventory_gain` / `inventory_loss` на
  разницу; `sold_since_start_pieces` = учёт на начало − ожидаемый, `sold_after_count_pieces` = ожидаемый − текущий
  остаток при проведении.
- Карточка идущего пересчёта: «продано до пересчёта» = учёт − остаток на момент первого ввода (у строки без вводов —
  учёт − текущий), «продано после пересчёта» = остаток на момент первого ввода − текущий (у строки без вводов — 0).

## 8. Web (`apps/web`)

- `REAL_API_ROUTES`: `catalog.snapshot`, `receipts.create`, `heldReceipts.*`, `shifts.*` (с новым `shifts.zReport`),
  `deployment.get`, `health.get`.
- **Сессия без терминала:** «Касса» и «Смена» показывают «Касса работает на привязанном терминале после входа по
  PIN» без кнопок продажи и смены.
- **Касса:** окно ПКУ сохраняется с пустыми полями и оплату не блокирует; ПКУ без связи — блокировка с сообщением
  (E17); данные рецепта в черновике и буфере зашифрованы (E17); в строке чека — `batchChosenManually`, в чеке —
  `language`; снимок обновляется раз в минуту (E16).
- **Смена:** номер — строка (до доставки «…»); после закрытия — Z-отчёт сервера, если закрытие доставлено за 1,5 с,
  иначе локальный с пометкой «предварительный, итог — после отправки»; счётчик «чеков с расхождением» на странице и в
  Z-отчёте; ошибки `shift_open`, `no_open_shift`, `shift_closed`, `idempotency_conflict`, `author_not_allowed` —
  понятным текстом в «Требует разбора».
- **Буфер:** возобновление после входа (E18).
- **Инвентаризация:** колонки «Учёт на начало», «Продано до пересчёта», «Продано после пересчёта», «Факт»,
  «Расхождение» = факт − (учёт − продано до пересчёта).
- **Сотрудники → терминалы:** ошибка `shift_open` при отвязке — понятным текстом.
- Моки и фейковый API web-e2e — на новый контракт (смена на терминал, номера-строки, пометки); полный мок-режим,
  unit-тесты и web-e2e — зелёные. Тексты RU/TJ.

## 11. Проверка

Новые автотесты не пишутся (тесты отложены до MVP); существующие наборы остаются зелёными, моки и спеки web
адаптируются к контракту. Живая проверка:

- **curl:** вход по PIN на терминале; открытие смены, повтор с тем же ключом — та же смена, другое тело — 409; вторая
  смена терминала — 409; продажа — номер, движения, итоги смены; продажа партии сверх остатка — принята, пометка
  `stock`, партия в фильтре «Минус»; цена не та — пометка `price`; просроченная партия — 400; ПКУ или ручная партия
  без права у автора — принят с пометкой `author`; автор не из сети — 422; чек с пустыми данными ПКУ — запись ПКУ без
  данных; внесение и
  изъятие; правка ступени скидки и штук в упаковке после снимка — чек принят с пометками `discount` / `catalog`;
  закрытие — ожидаемые наличные, без причины при расхождении — принято с пометкой «причина не указана», Z-отчёт,
  отложенные чеки удалены; чек при перебое до первого ввода инвентаризации, доставленный после, — без ложной
  недостачи;
  сессия по паролю — 403 `terminal_required`; отвязка терминала с открытой сменой — 409; инвентаризация: продажа
  после первого ввода — нет ложного излишка, партия в минусе попадает в пересчёт и исправляется.
- **Браузер (`partial`):** вход по PIN → открытие смены → скан → смешанная оплата → номер чека → отложенный чек →
  закрытие смены с Z-отчётом; продажа при отключённом API уходит в буфер и доставляется после включения.
