# ADR-0017: Архитектура фронтенда — Feature-Sliced Design для `apps/web` и `apps/admin`

- **Статус:** accepted (2026-09-30, архитектор проекта — APPROVAL.md)
- **Дата:** 2026-09-30
- **Авторы:** Zohid Saidov (z.saidov@eskhata.com), команда проекта Pharmacy (текст подготовлен с помощью AI)
- **Принимает:** архитектор проекта (docs/architecture/APPROVAL.md)

## Контекст

`apps/web` (касса, склад, закупки, каталог, отчёты, кабинет владельца — около 25 экранов по макетам,
docs/architecture/reviews/2026-09-30-mockups-tz-review.md) и `apps/admin` (админка оператора) — Next.js
App Router в режиме static export (ADR-0004), общий UI-кит `libs/ui` (ADR-0007), общие `libs/shared/*`.
Нужна единая архитектура кода внутри приложений, понятная команде и проверяемая автоматически: сейчас
скил `react-dev` описывает упрощённую схему `features/ · shared/ · app/`, а Nx-границы
(`@nx/enforce-module-boundaries`) работают только между проектами, не внутри приложения. Архитектор
проекта выбрал Feature-Sliced Design (FSD) для обоих фронтендов.

## Рассмотренные варианты

1. **Схема `features/ · shared/ · app/` из скила `react-dev`** — проста, но не определяет слои сущностей,
   виджетов и страниц, правила импортов между фичами держатся только на ревью.
2. **Feature-Sliced Design внутри каждого приложения, общий `shared` — Nx-библиотеки** — стандартизированная
   методология со слоями, срезами, сегментами и public API; официальный гайд для Next.js; официальный
   линтер Steiger.
3. **FSD, где каждый слой или срез — отдельная Nx-библиотека** (`libs/web/features/*`…) — границы держит
   Nx, кэш сборки по срезам; но десятки Nx-проектов для небольшой команды.
4. **FSD с общими `entities` в `libs/entities/*` для обоих приложений** — меньше дублей, но больше
   проектов и риск, что сущность «точка» для оператора и для владельца окажется разной.

## Решение

Выбран вариант 2: **FSD внутри каждого приложения, общий слой `shared` — существующие Nx-библиотеки**.

1. **Структура приложения** (поправка 2026-09-30 — см. «Поправка» ниже):

   ```
   apps/<web|admin>/
   ├── app/            # маршрутизация Next.js: только тонкие реэкспорты страниц из src/pages
   ├── pages/          # пустая, только README: не даёт Next.js считать src/pages маршрутами
   └── src/            # FSD — канонические имена слоёв
       ├── app/        # провайдеры, глобальные стили, i18n, инициализация приложения
       ├── pages/      # страницы — композиция виджетов и фич; один срез = один маршрут
       ├── widgets/    # крупные самостоятельные блоки UI (шапка, сайдбар, панель чека)
       ├── features/   # действия пользователя с бизнес-ценностью (пробить чек, принять перемещение)
       ├── entities/   # бизнес-сущности (товар, партия, чек, сотрудник, точка)
       └── shared/     # своё для приложения: базовый API-клиент, config, i18n-ключи
   ```

   Папка маршрутов `app/` и пустая `pages/` — в корне приложения; при их наличии Next.js не трогает
   `src/app` и `src/pages`, поэтому слои FSD сохраняют канонические имена. Слой `processes` не используется
   (устарел в FSD). Файл маршрута: `export { ReceiptViewPage as default } from '@/pages/receipt-view'`. API routes и
   middleware не используются (ADR-0004).
2. **Общий `shared` для обоих приложений** — Nx-библиотеки: `libs/ui` (shared/ui), `libs/shared/util`
   (shared/lib: деньги, даты, i18n-форматирование), `libs/shared/dto` и `libs/shared/domain` (типы API и
   домена). Они импортируются с любого слоя. **Типы API и домена (DTO, `Tenant`, `LicenseKey`, `Receipt`…)
   объявляются только в `libs/shared/dto` и `libs/shared/domain`** — это единственный источник моделей
   для бэкенда и фронтендов; срезы `entities` их не переопределяют, а держат UI и состояние вокруг них.
   Сущности, нужные обоим приложениям, пока дублируются на уровне UI; выносятся в `libs/` отдельным
   решением, когда дублирование станет реальным. Новых Nx-проектов это решение не добавляет.
3. **Правила импортов:** слой импортирует только слои ниже себя (`app → pages → widgets → features →
   entities → shared`); срезы одного слоя друг друга не импортируют; связь между срезами `entities` —
   только через кросс-импорт `@x` в public API; у каждого среза есть public API (`index.ts`), глубокие
   импорты в срез запрещены.
4. **«Pages first»** (практика FSD 2.1): код экрана сначала живёт в срезе страницы (`pages/<экран>`) и
   опускается в `widgets`, `features` или `entities` только тогда, когда он понадобился второму экрану.
   Так в небольшом `apps/admin` не появляются пустые слои, а структура остаётся той же, что в `apps/web`.
   Рассмотренные для `apps/admin` альтернативы — модули по доменам и Nx-библиотеки «домен × тип» —
   отклонены 2026-09-30: одна архитектура на оба фронтенда важнее, а общие модели уже решены
   `libs/shared/dto`.
5. **Сегменты среза:** `ui`, `model`, `api`, `lib`, `config`. Библиотеки для `model` (состояние) и `api`
   (данные) — ADR-0015.
6. **Маршруты статические**, идентификаторы — в query (`/receipts/view?id=…`, ADR-0015, ADR-0012):
   совместимо со static export.
7. **Проверка:** Steiger (`steiger` 0.7, `@feature-sliced/steiger-plugin` 0.8, MIT) — Nx-таргет `fsd` для
   обоих приложений, запускается в job **checks** CI (ADR-0009) и перед PR; в редакторе — встроенное правило
   ESLint `no-restricted-imports` по слоям (без новых плагинов). Nx-границы между проектами не меняются.
   Правило Steiger `fsd/insignificant-slice` понижено до предупреждения: при «pages first» срез с одной
   ссылкой на старте — норма.

**Поправка 2026-09-30.** Первоначально слои назывались `_app` и `_pages` (гайд FSD для Next.js). Проверка
на Steiger 0.7 / `@feature-sliced/steiger-plugin` 0.8 показала, что переименованные слои он считает
опечаткой (`fsd/typo-in-layer-name`) и **не проверяет как слои** — запрещённый импорт «фича → страница»
не был обнаружен. С каноническими именами `src/app` / `src/pages`, корневыми `app/` (маршруты) и пустой
`pages/` сборка `nx build web` (static export) прошла, а Steiger нашёл тот же запрещённый импорт.
Решение принято архитектором проекта (APPROVAL.md).

## Последствия

- Положительные:
  - единая понятная структура обоих фронтендов; новые экраны из макетов ложатся на слои предсказуемо;
  - нарушения слоёв и public API ловятся автоматически (Steiger в CI, ESLint в редакторе);
  - бизнес-логика отделена от страниц и UI-кита; `libs/ui` остаётся без бизнес-знаний.
- **Отрицательные (обязательно):**
  - команде нужно освоить FSD (слои, срезы, `@x`, public API) — обучение и примеры в скиле `react-dev`;
  - правило «срезы одного слоя не видят друг друга» поначалу мешает, особенно на `entities`; споры
    «это feature или widget» — нужны примеры и решения в скиле;
  - Steiger — линия 0.x: возможны ломающие изменения и ложные срабатывания; версия закрепляется точно;
  - две папки `app/` (маршруты Next.js в корне) и `src/app` (слой FSD) с одинаковым именем, плюс пустая
    служебная `pages/` — легко перепутать новичку; README в корневых папках объясняет назначение;
  - дублирование сущностей между `web` и `admin`, пока они не вынесены в `libs/`.
- После перевода в `accepted`:
  - перенести маршруты из `apps/*/src/app` в корневую `app/`, добавить пустую `pages/` с README, настроить алиас
    `@/*` → `src/*`, добавить Nx-таргет `fsd` (Steiger) и правила ESLint по слоям;
  - переписать скил `.claude/skills/react-dev/SKILL.md` под FSD (раздел «Структура проекта»);
  - обновить агента `ui-standards-expert`, CLAUDE.md («Project structure»), ADR-0015 (раскладка по
    сегментам), скилы `web-performance-optimization` и `ui-standards-tokens` (пути примеров).
