# Аутентификация, часть 4 — офлайн-точка. План реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Новые тесты не пишутся до готовности MVP** (решение пользователя 2026-10-05). Существующие
> тесты должны оставаться зелёными: тест, сломанный изменением сигнатуры, исправляется, а не
> удаляется. Что осталось без тестов — в разделе «Долг по тестам».
>
> **Порядок.** Реализация начинается после слияния части 3, от свежего `main`. Задача 3 опирается
> на модули оператора из части 3.

**Goal:** API запускается на ПК офлайн-точки с `STORE_MODE=offline`, без Redis. Вход по паролю,
вход по PIN, терминалы и `/me` работают так же, как в облаке, а сессии хранятся в PostgreSQL точки.

**Architecture:**
- Порты части 1 получают PostgreSQL-реализации:
  - `PgSessionStore` — таблица `sessions` класса `tenant`, RLS;
  - `PgPermissionsVersionCache` — читает `employees`;
  - лимиты попыток — в памяти единственного процесса.
- DI выбирает реализацию по `STORE_MODE`.
- Модули оператора не регистрируются.
- Cookie — `sid` и `term`, без префикса `__Host-`.

**Tech Stack:** NestJS 11, Kysely + pg, node-pg-migrate (только Up), `@nestjs/config`
`ConditionalModule`; новых зависимостей нет.

**Spec:** `docs/superpowers/specs/2026-10-02-auth-design.md`:
- §10 — офлайн-точка;
- §4 — порты;
- §5 и §7 — запись сессии и проверка запроса;
- §11 — конфигурация.

## Global Constraints

- **Ветка:** `feature/auth-part4` от `main`, в который уже слита часть 3. Conventional Commits. Подпись GPG не обходить.
- **Таблица `sessions`:**
  - класс `tenant`, ключ `(tenant_id, jti)`;
  - чтение и запись только через `TenantDatabase.withTenant(tid)` под RLS;
  - в строке нет секретов: только идентификаторы, снимок прав, хеш device-cookie.
- **Redis в офлайне не трогается:** при `STORE_MODE=offline` ни один провайдер не обращается к
  `REDIS_CLIENT`, а `REDIS_URL` не нужен.
- **Cookie офлайн-точки:** `sid` и `term` с атрибутами `Secure; HttpOnly; SameSite=Strict; Path=/`,
  без `__Host-`. Режим `AUTH_TEST_COOKIES` по-прежнему снимает `Secure`.
- **Лимиты в памяти:**
  - действуют те же значения `LOGIN_*` и `TERMINAL_PIN_*`;
  - после перезапуска процесса счётчики обнуляются (ADR-0008: один процесс);
  - блокировка PIN сотрудника хранится в `employee_credentials`, поэтому перезапуск её не снимает.
- **Без побочных действий:** Docker-контейнеры не создаются; `.env` не читается и не правится.
- **Проверки:**
  - в каждой задаче — `lint`, `tsc -b apps/api/tsconfig.spec.json`, `nx test api`;
  - в задаче с миграцией дополнительно — `api:migrate`, `api:db-types`, `api:integration`.

## Review Focus

Тестов нет, поэтому это список для финального ревью и для ручной проверки (задача 4):

1. **Чужая сеть.** JWT с `tid`, отличным от `OFFLINE_TENANT_ID`, или запись другой сети → гость (401).
2. **Просроченная сессия.** Строка с истёкшим `idle_expires_at` или `absolute_expires_at` не
   авторизует, даже пока её не удалили.
3. **Без Redis.** Процесс стартует без `REDIS_URL` и при остановленном Redis; вход, PIN, `/me`,
   выбор точки и выход работают.
4. **Контур оператора.** `/api/v1/operator/*` → 404: маршрутов нет, контур оператора в middleware
   всегда даёт гостя.
5. **Лимиты.** 5 неудачных входов → `429 login_locked`; 10 неверных PIN на терминале →
   `423 terminal_locked`; после перезапуска счётчики пусты, а блокировка PIN сотрудника остаётся.

## Решения, принятые при составлении плана

- **P1. Одна сеть на точку.** Офлайн-точка обслуживает ровно одну сеть: новая обязательная при
  `offline` переменная `OFFLINE_TENANT_ID`. `PgSessionStore` работает в её контексте, а токен с
  другим `tid` даёт гостя.
  - **Почему так.** Методам порта `update`/`touch`/`destroy` не передаётся `tenantId`, а
    middleware вызывает их до создания контекста запроса. Менять сигнатуры порта ради офлайна
    значило бы трогать всех вызывающих.
  - **С чем сверить.** Как это согласуется с лицензионным ключом точки, проверить при реализации
    синхронизации (ADR-0014).
- **P2. Очистка просроченных сессий.** Отдельной плановой задачи нет (планировщика пока нет).
  Просроченные строки удаляются при каждом `create`, а `lookup` их не принимает (Review Focus 2).
  Спека (§10, «плановая задача») правится в задаче 4.
- **P3. Флаг отзыва терминала.** Источник правды — `terminals.revoked_at`, который `lookup` читает
  тем же запросом. `markTerminalRevoked` в офлайне ничего не делает; `destroyForTerminal` удаляет
  строки по `terminal_id`.
- **P4. Версия прав.** `PgPermissionsVersionCache.get` читает `employees.permissions_version`, а
  `setIfGreater` ничего не делает. `lookup` берёт версию тем же запросом — один запрос к БД на
  запрос API, как в §7, шаг 3.
- **P5. Лимитер.** `LoginLimiter` становится абстрактным классом, существующая реализация
  переименовывается в `RedisLoginLimiter`. Потребители по-прежнему внедряют `LoginLimiter`.
