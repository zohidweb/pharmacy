# Закрытие точки на API — спецификация

Дата: 2026-10-15. Статус: утверждена архитектором 2026-10-15 (вместе с решениями автора E1–E15).

Связано:
- модель данных: `docs/architecture/data-model/01-platform-org.md` (`stores`, `employee_stores`, `terminals`),
  `03-batches-warehouse.md` (`documents`, перемещения), `02-catalog-prices.md` (`discount_rule_stores`);
- ADR-0013 (классы таблиц), ADR-0014 (офлайн-точки), ADR-0018 (права, охват, `finance:view-cost`);
- спецификации: точек `2026-10-06-owner-stores-design.md` (409 `store_closed`), перемещений
  `2026-10-12-supplier-returns-transfers-design.md` (T9 откладывал закрытие точки через перемещение), кассы
  `2026-10-13-pos-shift-sale-design.md`;
- макет клиента «Закрытие точки» (экран сделан на моках: `CloseStoreDialog`).

## 1. Цель и критерии успеха

Владелец закрывает аптеку или склад сети. Весь товар точки уходит перемещением на другую точку. Пока товар в пути,
точка «закрывается»: продавать и проводить на ней складские документы нельзя. Закрытой точка становится, когда
получатель примет товар. Закрытая точка пропадает из рабочих списков, а её история продаж и движений остаётся в отчётах.

Успех:
- после закрытия остаток закрытой точки — ноль, у получателя — всё, что принято. Недостача при приёмке списывается
  на закрытой точке (как у любого перемещения);
- на «закрывающейся» точке не проходит ни продажа, ни открытие смены, ни возврат, ни складской документ;
- закрыть нельзя, пока на точке открыта смена, идёт инвентаризация, к ней или с неё едет перемещение, по ней есть
  открытая заявка на перемещение или есть отрицательный остаток. Экран заранее показывает, что мешает;
- точку без товара закрывают сразу, без получателя; последнюю работающую точку сети закрыть нельзя;
- закрытие можно отменить, пока получатель ничего не принял: товар возвращается, точка снова работает;
- терминалы и скидочные правила закрытой точки отвязываются от неё. Сотрудники сохраняют её в своём охвате как
  историю: в рабочих списках её нет, а редактирование сотрудника или правила после закрытия не падает;
- отчёты за период, который захватывает время работы закрытой точки, её показывают — и владельцу, и управляющим,
  у которых она была в охвате;
- экран «Закрытие точки» и карточка точки работают с API в режиме `partial`.

## 2. Решения, принятые при обсуждении (2026-10-15)

| # | Вопрос | Решение |
|---|---|---|
| Z1 | Куда товар | Весь остаток переводится на другую точку сети перемещением |
| Z2 | Смена | Смену перед закрытием закрывают: открытая смена не даёт закрыть точку (не закрывается автоматически — кассиру нужно пересчитать деньги) |
| Z3 | Пока товар в пути | Статус «Закрывается»: продажи и складские документы на точке запрещены; «Закрыта» — когда получатель принял перемещение. В карточке — дата закрытия и куда ушёл товар |
| Z4 | Точка без товара | Закрывается сразу, без перемещения |
| Z5 | Офлайн-точки | Не закрываются, пока нет синхронизации (ADR-0014) |
| Z6 | Вскрытые упаковки | Уходят тем же перемещением, штуками — не списываются |

## 3. Решения автора (на утверждение вместе со спецификацией)

| # | Тема | Решение |
|---|---|---|
| E1 | Кто закрывает | Право `stores:delete` (по умолчанию только у владельца), точка — в охвате сотрудника; вход подтверждается паролем (свежий вход, `@RequireFreshAuth`, в web — `withFreshAuth`): действие разрушительное |
| E2 | Какие точки | Закрывается точка в статусе `active` и режиме `online`. Офлайн и `offline_pending` → 409 `offline_store_read_only`; уже закрывающаяся → 409 `store_closing`; закрытая → 409 `store_closed` |
| E3 | Получатель | Нужен, только если у точки есть товар. Другая точка сети в статусе `active` и режиме `online` — аптека или склад, охват не проверяется (как у получателя перемещения). Иначе 422 `validation_failed` (`receiverStoreId`, `invalid`; без товара получатель игнорируется). Последнюю точку сети в статусе `active` (любого режима) закрыть нельзя → 409 `last_store`: закрытие всей сети — дело оператора платформы |
| E4 | Дата закрытия | Поля даты в запросе нет: перемещение отправляется сегодняшней бизнес-датой (перемещения не делаются задним числом, спецификация перемещений E4). Дата закрытия `closedOn` — бизнес-дата, когда точка стала закрытой (приёмка последнего перемещения или сразу для пустой точки). Поле «Дата закрытия» уходит с экрана и из `CloseStoreRequest` |
| E5 | Строки перемещения | Одна строка на каждую партию с положительным остатком. Остаток кратен упаковке — строка в упаковках, иначе — в штуках (вскрытая упаковка, Z6). Внутренний вызов: проверка `not_divisible` для штук не применяется — это не ввод пользователя |
| E6 | Больше 500 партий | Приёмка принимает не больше 500 строк (DTO, тело запроса ≤ 100 КБ). Закрытие режет строки на перемещения по 500 (порядок — по товару и партии) и отправляет все в одной транзакции. Точка закрывается, когда не осталось ни одного перемещения закрытия в пути и принято хотя бы одно |
| E7 | Блокеры | Закрытие и предпросмотр проверяют: открытые смены точки; идущая инвентаризация; перемещения в пути **на** точку — любые, в том числе перемещения закрытия другой точки (поправка 2026-10-15 по итоговому ревью: закрытая точка не смогла бы их принять), — и обычные **с** неё (исходящие пока можно отозвать, а недостача по ним после закрытия легла бы на закрытую точку вне отчётов); открытые заявки на перемещение, где точка — любая сторона (`draft`, `sent`, `in_progress`); партии с отрицательным остатком; закрытый период на сегодня (`closed_until` ≥ сегодня). Любой блокер → 409 `store_not_closable` с `errors[]` (`field` — код блокера, `code` — `blocked`) |
| E8 | Не блокирует, но предупреждает | Черновики складских документов точки (остаются черновиками — провести их будет нельзя); открытые заказы поставщикам точки; неоплаченные приходы точки (долг остаётся у поставщика, оплаты распределяются как раньше). Предпросмотр отдаёт их счётчики (сумму долга — только с `finance:view-cost`) |
| E9 | Пока «Закрывается» | Статус `closing` в БД. Все существующие проверки `status = 'active'` его уже не пускают: касса (`cloudStore` → 404), складские документы (`writableStore` → 404), цены, скидки, сотрудники, выбор точки в сессии, расходы. Обычный отзыв перемещения со стороны точки недоступен (`writableStore`) — только «Отменить закрытие» (E10) |
| E10 | Отмена закрытия | `POST /stores/{id}/closing/cancellation`, право `stores:delete` + свежий вход. Можно, пока ни одно перемещение закрытия не принято: все отзываются (движения сторнируются) и отменяются (`cancelled`), точка снова `active`. Если хоть одно принято → 409 `closing_partly_received` — закрытие идёт до конца |
| E11 | Когда точка закрылась | В транзакции приёмки последнего перемещения закрытия (через порт модуля `inventory`, который заполняет модуль `stores`): статус `closed`, `closed_at = now()`; затем отвязка (E12). Для пустой точки — то же сразу при закрытии |
| E12 | Отвязка при закрытии | Строки `employee_stores` точки **остаются**: это охват сотрудника, по которому он видит историю точки в отчётах, журнале и списках документов. Рабочие списки (выбор точки в сессии, фильтры, кассы) её уже не показывают — они берут активные точки. Назначить закрытую точку нельзя (400 `unknown_store`, как сейчас), а закрытые точки, уже бывшие в охвате, сохраняются при любом сохранении сотрудника, даже если их нет в запросе (экран их не показывает). Сотрудник, у которого остались только закрытые точки, работать не может — владелец назначит другую или заблокирует. Терминалы точки отзываются (`revoked_at`, `revoked_by` — кто начал закрытие); точка убирается из списков скидочных правил, правило со списком точек, где не осталось ни одной, архивируется. Цены точки (`store_products`) остаются как история. Каждое действие — через экспорт модуля-владельца таблицы |
| E13 | Отчёты | Отчёты и главная берут точки охвата (у управляющего — вместе с закрытыми из E12), которые активны, закрываются или закрыты не раньше начала периода (`closed_at` в бизнес-дату ≥ `from`). Так история закрытой точки видна за прошлые периоды, а за периоды после закрытия её строки нет. Фильтр точки на экранах — только рабочие точки сессии (как сейчас). «Долги поставщикам» владельца без фильтра учитывают и закрытые точки (минорное замечание PR 2 № 1) |
| E14 | Аудит | `store.closing-started` (получатель, номера перемещений, число партий), `store.closing-cancelled`, `store.closed` (число отвязанных сотрудников, терминалов, правил). Группа журнала `store` (префикс `store.`) — без изменений. Перемещения пишут свои события как обычно |
| E15 | Что не трогаем | Закрытая точка не открывается снова. Оплата и лицензии (биллинга нет). Заказы поставщикам и черновики не отменяются автоматически |

## 4. Схема

Миграция `store-closing` (после `1791991049879_operator-language`):
- `stores.status`: проверка `('active', 'closing', 'closed')`;
- `stores`: `closing_started_at timestamptz null`, `closing_started_by uuid null` (FK сотрудник),
  `closing_receiver_store_id uuid null` (FK точка); проверка: при `status = 'closing'` эти три поля заданы;
- `documents`: `store_closing boolean not null default false` — перемещение создано закрытием точки
  `documents.store_id`; проверка: `store_closing` только у `type = 'transfer'`;
- частичный индекс `documents (tenant_id, store_id) where store_closing`;
- роль `pharmacy_platform`: грант `select` на новые колонки не нужен (платформа видит `status`, `closed_at`); статус
  `closing` платформа показывает как `active` (точка ещё работает с лицензией) — маппинг реестра сетей;
- данные: изменения не нужны (ни одна точка не закрыта).

## 5. API

| Маршрут | Модуль | Право |
|---|---|---|
| `GET /stores/{id}/closing-preview` | `stores` | `stores:delete` |
| `POST /stores/{id}/closing` | `stores` | `stores:delete` + свежий вход |
| `POST /stores/{id}/closing/cancellation` | `stores` | `stores:delete` + свежий вход |

- **Предпросмотр:** партии с остатком (товар, партия, срок, штуки, `piecesPerPack`, себестоимость — с
  `finance:view-cost`), число позиций, итог по себестоимости (с правом), число перемещений (E6), `blockers[]` (E7),
  `warnings[]` (E8). Для точки не в статусе `active`/`online` — те же 409, что у закрытия.
- **Закрытие:** проверки E2, E3, E7 в одной транзакции под блокировкой строки точки (`FOR UPDATE`) и партий (как
  отправка перемещения); создание и отправка перемещений (E5, E6) через экспорт модуля `inventory`; статус `closing`,
  поля `closing_*`; для пустой точки — сразу E11. Ответ: `{ transferNumbers: string[], store: OwnerStore }`.
- **Отмена:** E10 в одной транзакции.
- **Порт приёмки:** модуль `inventory` вызывает зарегистрированных слушателей в транзакции приёмки перемещения
  (`transferAccepted(trx, tenantId, transferId)`); модуль `stores` проверяет, что это перемещение закрытия, и закрывает
  точку, если в пути их больше нет (E11). Граф модулей: `inventory`, `pos`, `terminals`, `staff`, `pricing` ← `stores`.
- **`OwnerStore`:** `status` — `closing` для закрывающейся; `closedOn` — бизнес-дата `closed_at` в часовом поясе
  сети (сейчас — дата UTC, исправить); `stockMovedTo` — имя точки-получателя; новое `closingTransfers:
  { number, status }[]` для `closing`/`closed`; новое `closingCancellable: boolean`.

## 6. Контракт (`libs/shared/dto`, `tenant-owner.ts`)

- `StoreClosingPreview`: + `transfers: number`, `blockers: StoreClosingBlocker[]`, `warnings: StoreClosingWarning[]`;
  `StoreClosingLine` — без изменений.
- `StoreClosingBlocker = { code: 'open_shift' | 'stock_count' | 'incoming_transfer' | 'outgoing_transfer' |
  'transfer_request' | 'negative_stock' | 'period_closed'; count: number }`.
- `StoreClosingWarning = { code: 'draft_documents' | 'open_purchase_orders' | 'unpaid_receipts'; count: number;
  amountMinor?: number }`.
- `CloseStoreRequest = { receiverStoreId: string | null }` (без `closeOn`, E4; `null` — только для точки без
  товара, E3).
- `CloseStoreResponse = { transferNumbers: string[]; store: OwnerStore }`.
- `OwnerStore`: + `closingTransfers`, `closingCancellable` (раздел 5).

## 8. Web (`apps/web`)

- `REAL_API_ROUTES`: `stores.closingPreview`, `stores.close`, новый `stores.cancelClosing`.
- `CloseStoreDialog`: убрать поле даты; список блокеров (`Alert` с текстом на каждый код и числом) — кнопка закрытия

## 11. Проверка

Новых автотестов нет (решение «тесты до MVP»). Существующие наборы — зелёные, включая `nx test api`; `npm run
check` — у пользователя.

Живая проверка на dev-API (curl и браузер, режим `partial`):
- точка A с товаром (целые и вскрытые упаковки делимого товара): предпросмотр без блокеров; закрытие → перемещение в
  пути, A «Закрывается», продажа и открытие смены на A — 404, складской документ — 404; приёмка у получателя с
  недостачей → A «Закрыта», остаток A — ноль, у получателя — принятое, недостача списана на A; сотрудник A без точек,
  терминал A отозван, правило «только A» архивировано; отчёт за период до закрытия показывает A владельцу и
  управляющему A и B; сохранение управляющего A и B не теряет A и не падает;
- блокеры по одному: открытая смена, инвентаризация, перемещение в пути на A и с A, заявка, отрицательный остаток —
  409 с кодом; предпросмотр показывает тот же блокер;
- отмена закрытия до приёмки: остаток вернулся, A снова работает; после частичной приёмки — 409
  `closing_partly_received`;
- пустая точка закрывается сразу без получателя; последняя работающая точка — 409 `last_store`; офлайн — 409; без свежего входа — 403 `fresh_auth_required`; управляющий без
  `stores:delete` — 403;
- больше 500 партий: синтетический сценарий — два перемещения, точка закрывается после приёмки обоих.
