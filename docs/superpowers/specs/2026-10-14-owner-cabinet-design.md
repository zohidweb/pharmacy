# Кабинет владельца на API — спецификация

Дата: 2026-10-14. Статус: утверждена архитектором 2026-10-14 (вместе с решениями автора E1–E20 и поправками 3.1). Связано: модель данных
`docs/architecture/data-model/01-platform-org.md` (`tenant_settings`), `06-sync-audit-billing.md` (`audit_log`,
`notifications`), `04-pos.md`, `03-batches-warehouse.md`, `05-purchasing.md`; ADR-0008 (сессии, PIN), ADR-0013
(классы таблиц), ADR-0015 (web), ADR-0016 (сомони), ADR-0018 (права, охват, `finance:view-cost`); спецификации
кассы `2026-10-13-pos-shift-sale-design.md` и возвратов `2026-10-13-customer-returns-design.md`; макеты клиента
(экраны «Дашборд», «Отчёты», «Журнал действий», «Настройки»).

## 1. Цель и критерии успеха

Кабинет владельца `apps/web` переходит с моков на API. Владелец и управляющие видят настоящие цифры сети: главную за
выбранный период, отчёты о продажах, прибыли, остатках, движении, долгах, кассирах, потерях и ПКУ, уведомления и
журнал действий. Владелец меняет настройки сети, и они действуют. Владелец раз в месяц вносит прочие расходы и видит
чистую прибыль точек.

Успех:
- выручка точки (продажи минус возвраты покупателей) за любой период одинакова на главной и в отчёте «Продажи по
  точкам» (`revenue` + `returns`); для смен, открытых и закрытых в одну бизнес-дату, — ещё и с суммой выручки этих
  смен (у смены нет своей бизнес-даты, смена через полночь в сверку не входит);
- прибыль точки = выручка − возвраты − себестоимость проданного (за вычетом себестоимости возвращённого) − списания и
  недостачи (+ излишки); на тестовом сценарии сходится с расчётом вручную до дирама;
- строка отчёта «Движение товара» и строка сводки ПКУ сходятся: на начало + приход − расход = на конец;
- расходы месяца входят в отчёт за часть месяца пропорционально дням, изъятия из кассы «на расходы» — отдельной
  колонкой без ручного ввода;
- управляющий видит только точки своего охвата — на главной, в отчётах, уведомлениях и журнале; без
  `finance:view-cost` колонок себестоимости, прибыли, долгов и сумм потерь в ответах нет;
- изменённые настройки действуют: новый тайм-аут — для новых сессий, новая длина PIN — при следующей установке PIN,
  порог сроков — в уведомлениях, на главной и в остатках, предупреждение «ниже закупочной» — на экране цен;
- уведомление видят владелец и управляющие точки; отключённый в настройках вид не видит никто;
- экраны «Дашборд», «Отчёты», «Журнал действий», «Настройки», колокольчик и новый экран «Расходы» работают с API в
  режиме `partial`, пометка «Демо-данные» на них исчезает.

## 2. Решения, принятые при обсуждении (2026-10-14)

| # | Вопрос | Решение |
|---|---|---|
| O1 | Главная | По макету клиента, перерисовывать не нужно: выручка с изменением к прошлому периоду, чеки и средний чек, «Мало на складе», «Истекает срок», продажи по точкам, выручка по дням, напоминания, журнал действий. В список периода «Сегодня / Неделя / Месяц» добавляется «Свой период…» с двумя датами (обе включительно) — единственное изменение экрана |
| O2 | Главный вопрос отчётов | «Сколько продали и какая прибыль по точкам за месяц» — отчёт «Продажи по точкам» |
| O3 | Списания | Уменьшают прибыль точки |
| O4 | Прочие расходы | Аренда, зарплата, коммуналка; вносит владелец раз в месяц |
| O5 | Расходы за неполный месяц | Пропорционально дням периода (1–14 октября — 14/31 расходов октября) |

| O7 | Кто получает уведомления | Владелец и управляющие — по своим точкам |
| O8 | Объём | Одна спецификация, три PR: (1) настройки, уведомления, главная, журнал действий; (2) отчёты; (3) прочие расходы |

## 3. Решения автора (на утверждение вместе со спецификацией)

| # | Тема | Решение |
|---|---|---|
| E1 | Периоды | Бизнес-даты сети (`tenant_settings.timezone`). «Сегодня» — текущая бизнес-дата; «Неделя» — последние 7 дней с сегодняшним; «Месяц» — с 1-го числа текущего месяца по сегодня; «Свой период» — `from`…`to` включительно, `to` ≤ сегодня, не длиннее 92 дней на главной и 366 дней в отчётах. Сравнение — с отрезком той же длины непосредственно перед периодом; процент с одним знаком, `null`, если там выручка 0 |
| E2 | Выручка | Σ `receipts.total_dirams` по бизнес-дате продажи − Σ `customer_returns.refund_dirams` по бизнес-дате возврата, по точке возврата. Чеки — число чеков продажи (возвраты их не уменьшают); средний чек = Σ продаж / число чеков, без возвратов. В отчётах «Продажи по точкам» и «Кассиры» колонка `revenue` — продажи, возвраты — отдельной отрицательной колонкой `returns` (как в макете); выручка главной = `revenue` + `returns` |
| E3 | Себестоимость и прибыль | Себестоимость проданного — `receipt_lines.cost_dirams` (снимок при продаже); возвращённого — штуки возврата × `batches.cost_per_piece_dirams` партии строки. Списания — `documents.total_dirams` проведённых списаний (по себестоимости, в т. ч. автосписания брака и истёкшего из возвратов и недостачи перемещения у отправителя), по `document_date`; инвентаризация — подписанная разница по себестоимости (недостача уменьшает, излишек увеличивает), по дате документа. Отменённое проведение не учитывается. Перемещения и возвраты поставщику прибыль не меняют. Это валовая прибыль; в PR 3 — ещё и чистая (E16) |
| E4 | «Мало на складе» и «Истекает срок» | Всегда на текущую бизнес-дату, от периода не зависят. Мало — пары точка×товар из ассортимента точки (как на экране остатков: у точки есть партии товара или цена в `store_products`), где у активного товара `default_min_stock_pieces` > 0 и остаток точки (все партии) меньше минимума (ноль тоже). Истекает — партии с остатком > 0 и сроком ≤ `expiry_reminder_days` дней от сегодня, включая уже истёкшие; «критично» — ≤ 7 дней |
| E5 | Продажи по точкам на главной | Все активные точки охвата, включая точки без продаж. У офлайн-точек `lastSyncAt` = null («нет синхронизации»), пока нет синхронизации (ADR-0014) |
| E6 | Выручка по дням | «Сегодня» и «Неделя» — последние 7 дней (как в макете, сегодня выделено); «Месяц» и «Свой период» — каждый день периода. Заголовок графика — «Выручка по дням» |
| E7 | Журнал действий | `GET /audit-log` в модуле `audit`. События `audit_log` сводятся в группы фильтра (раздел 6.4); текст записи строит клиент из кода события и параметров на языке пользователя, сервер не пишет готовых фраз. Записи без точки видит только сотрудник с охватом «вся сеть». На главной — 8 последних записей охвата без групп «Вход» и «Отказ в доступе» |
| E8 | Дата документа в журнале | События документов (`document.*`, `transfer.*`) начинают писать `documentDate` в `details`; для старых записей «документ от …» не показывается |
| E9 | Уведомления: модель | Таблица `notifications` (поправка 2.1): вид, точка (или вся сеть), ключ дедупликации, параметры, время появления, время снятия. Отметки «прочитано» — по сотруднику в `notification_reads`. Получатели не хранятся — их определяет право вида + охват (E10) |
| E10 | Уведомления: получатели | Новое право `notifications:view` (шаблоны владельца и управляющего; миграция выдаёт его существующим ролям, у которых есть `settings:view` — это роли «Заведующий точкой»). Плюс право раздела вида: сроки, мало на складе, продажа в минус, перемещения — `inventory:view`; оплата поставщику — `purchasing:view`; расхождение смены — `shifts:view`. Уведомление точки видит сотрудник с точкой в охвате, уведомление без точки — с охватом «вся сеть». Суммы — только с `finance:view-cost` |
| E11 | Уведомления: когда появляются | Фоновых задач в API нет (и `job_queue` не создан), поэтому уведомления **обновляются при чтении**: `GET /notifications` и `GET /dashboard` перед ответом запускают обновление сети, если прошлое было больше 5 минут назад (`notification_refresh`), под `pg_try_advisory_xact_lock` по тенанту — параллельный запрос обновление пропускает. Состояния (сроки, мало, оплата поставщику, перемещение в пути) создаются, обновляют параметры и снимаются, когда состояние ушло; события (расхождение смены, продажа в минус) берутся из фактов после отметки прошлого обновления. Новой библиотеки и ADR не нужно |
| E12 | Уведомления: список | Колокольчик — неснятые уведомления-состояния и уведомления-события за 30 дней, новые сверху; «прочитать все» отмечает все видимые сотруднику. Напоминания главной — до 5 видимых, непрочитанные первыми. Колокольчик скрыт без `notifications:view` (API — 403) |
| E13 | Виды уведомлений | Один список видов для переключателей и для уведомлений (раздел 6.3). `sync_conflict` и `license_expiry` в настройках остаются, но не создаются, пока нет синхронизации и тарифов; `impersonation` убирается (вход «от имени» не реализуется, ADR-0008) |
| E14 | Настройки сети | `GET/PUT /settings` в модуле `stores` (настройки организации — модель 01). Название сети только для чтения (`tenants.name` — платформенная таблица, меняет оператор). Тайм-аут сессии — 5…240 мин (нижняя граница API — 5 мин), действует для новых сессий и применяется ко всем сессиям сотрудников, как сейчас. Длина PIN — 4…8, действует при следующей установке PIN, старые PIN работают. Порог сроков — 1…365. `PUT` требует свежего входа (`@RequireFreshAuth`: тайм-аут и PIN — настройки безопасности). Аудит — `settings.updated` с `{before, after}` |
| E15 | «Предупреждать о цене ниже закупочной» | Колонка `warn_below_cost` (по умолчанию true). Экран цен получает `costMinor` — закупочную цену упаковки партии последнего проведённого прихода товара в сети (`batches.origin = 'goods_receipt'`, последний по времени проведения; начальные остатки, излишки и перемещения не в счёт), с `finance:view-cost`; сейчас API отдаёт `null`. Предупреждение `below_cost` появляется только при включённой настройке. `pricing` не может импортировать `inventory` (обратная зависимость `StorePriceWriter`), поэтому цену отдаёт порт `PurchasePrices` модуля `pricing`, который заполняет `inventory` (как `ShiftReturns`). Флаг приходит в профиле сессии (`tenant.warnBelowCost`). Подсказка настройки — «при изменении цены» (в приходе предупреждения нет) |
| E16 | Расходы (PR 3) | Запись: месяц, точка или вся сеть, вид (`rent`, `salary`, `utilities`, `other`), сумма > 0, комментарий. Новые права `expenses:view`, `expenses:create`, `expenses:update`, `expenses:delete` — только у владельца по умолчанию. Правка и удаление разрешены, в аудит (`expense.created/updated/deleted` с прежними значениями). В отчёт за период расход месяца входит долей `amount × дни пересечения / дни месяца` с округлением половины вверх по каждой записи (функция `prorateExpense` в `libs/shared/domain`). Расходы сети не делятся по точкам: входят только в итог и только у сотрудника с охватом «вся сеть» без фильтра по точке. Изъятия из кассы с причиной `expense` (O9) входят в расходы точки отдельной колонкой `cashExpenses` — по бизнес-дате `occurred_at` и точке смены, целиком (не делятся по дням). Чистая прибыль = прибыль (E3) − `expenses` − `cashExpenses`. Колонки `expenses`, `cashExpenses` и `netProfit` в отчёте — только с `finance:view-cost` **и** `expenses:view` (зарплаты и аренда не видны управляющему, пока владелец не выдаст право) |
| E17 | Модули | Новые облачные модули `notifications` и `reports`; данные других доменов они читают через экспорты владельцев (новые читатели в `pos`, `returns`, `inventory`, `purchasing`), не через их таблицы; к справочным таблицам (точки, сотрудники, товары, категории, партии) для названий допускается join. `audit` получает контроллер журнала. Граф без циклов: `pos`, `returns`, `inventory`, `purchasing` ← `notifications` ← `reports`; `audit` ← все; порт `PurchasePrices` (`pricing`, заполняет `inventory`, E15) |
| E18 | Отчёт «Долги поставщикам» | На текущий момент: период не влияет (долг на прошлую дату потребовал бы переигрывания распределений оплат). Экран показывает пометку. Фильтр точки — приходы этой точки |
| E19 | Количества в отчётах | «Движение товара», «Потери», ПКУ — в штуках с показом «N уп. M шт.»: новый тип колонки `pieces`, строка несёт `piecesPerPack` |
| E20 | Выгрузка в Excel | Вне объёма: кнопки остаются неактивными, как сейчас |

### 3.1 Поправки модели данных (утверждаются вместе со спецификацией)

1. `tenant_settings` (модель 01): `warn_below_cost boolean not null default true`; `disabled_notifications text[] not null
   default '{}'` с проверкой «только известные виды» (раздел 6.3).
2. `notifications` (модель 06) — вместо `recipient_employee_id` / `recipient_permission`: `id`, `kind`, `store_id null`,
   `dedupe_key`, `entity_type null`, `entity_id null`, `params jsonb`, `created_at`, `resolved_at null`; уникальность
   `(tenant_id, dedupe_key)` среди неснятых. Новые `notification_reads` (`notification_id`, `employee_id`, `read_at`;
   ключ `(tenant_id, notification_id, employee_id)`) и `notification_refresh` (`tenant_id`, `refreshed_at`,
   `events_after timestamptz`). Класс `tenant`, не только добавление.
3. `expenses` (модель 01, PR 3): `id`, `month date` (1-е число), `store_id null`, `kind`, `amount_dirams > 0`,
   `comment null`, `created_by`, `created_at`, `updated_by null`, `updated_at null`. Класс `tenant`.
4. Каталог прав (ADR-0018): `notifications:view`; модуль `expenses` с действиями `view`, `create`, `update`,
   `delete` (PR 3).

## 4. Схема

**PR 1 — миграция `owner-cabinet`:** поправки 3.1 п. 1, 2; RLS и гранты `pharmacy_app` (SELECT/INSERT/UPDATE на
`notifications`, `notification_refresh`; SELECT/INSERT на `notification_reads`); индексы `notifications (tenant_id,
store_id, created_at)`, частичный уникальный по `dedupe_key`; `notifications:view` — существующим ролям с
`settings:view`. Манифест `table-classes.ts`.

**PR 2** — без миграции, если планы запросов отчётов на dev-данных не покажут нужды в индексах (проверить `EXPLAIN`;
есть `receipts (tenant_id, store_id, business_date)`, `customer_returns` по точке и дате, `stock_movements (tenant_id,
store_id, business_date)`, `documents (tenant_id, store_id, type, document_date)`).

**PR 3 — миграция `expenses`:** таблица, RLS, гранты (SELECT/INSERT/UPDATE/DELETE), индекс `(tenant_id, month)`.

## 5. API

### 5.1 Маршруты и права

| Маршрут | Модуль | Право |
|---|---|---|
| `GET /settings` | `stores` | `settings:view` |
| `PUT /settings` | `stores` | `settings:update` + свежий вход |
| `GET /notifications?limit=&offset=` | `notifications` | `notifications:view` |
| `POST /notifications/read-all` | `notifications` | `notifications:view` |
| `GET /dashboard?period=&from=&to=` | `reports` | `reports:view` |
| `GET /audit-log?from=&to=&employeeId=&storeId=&action=&q=&limit=&offset=` | `audit` | `audit:view` |
| `GET /reports/{kind}?from=&to=&storeId=` (PR 2) | `reports` | `reports:view` |
| `GET /expenses?month=YYYY-MM&storeId=` (PR 3) | `reports` | `expenses:view` |
| `POST /expenses`, `PUT /expenses/{id}`, `DELETE /expenses/{id}` (PR 3) | `reports` | `expenses:create` / `update` / `delete` |

Охват: точка запроса (`storeId`) вне охвата — 403 `store_not_in_scope`; без `storeId` — все точки охвата. Расход без
точки создаёт и меняет только сотрудник с охватом «вся сеть».

### 5.2 Главная

`TenantDashboard` за период (E1–E6): `kpi`, `stores`, `revenueByDay`, `reminders` (E12), `recentActivity` (E7).
`period=custom` требует `from` и `to`.

### 5.3 Отчёты (PR 2)

Колонки — ключи `ReportColumn`; в скобках — только с `finance:view-cost`. Последняя строка `total` — итог, где он есть
(первая текстовая ячейка — `'total'`, как ждёт экран).

| Вид | Строка | Колонки | Итог |
|---|---|---|---|
| `sales_by_store` | точка | `store`, `receipts`, `revenue` (продажи), `returns` (отрицательная), (`cost`, `writeOffs` — списания и инвентаризация по E3, отрицательные, `margin` — прибыль, `marginPercent` — от выручки за вычетом возвратов); PR 3: (`expenses`, `cashExpenses`, `netProfit` — с `expenses:view`, E16) | да |
| `sales_by_category` | категория (текущая категория товара) | `category`, `revenue` (за вычетом возвратов: строки за вычетом доли скидки чека минус суммы возвратов строк — колонки возвратов в макете нет), (`cost`, `margin`, `marginPercent`) | да |
| `stock` | точка | на конец дня `to`: `positions`, (`cost`), `retail` (по текущим ценам точки), `low`, `expiring` (порог от даты `to`) | да |
| `movement` | товар (по выбранным точкам) | `product`, `opening`, `receipt` (приход и начальные остатки), `transfers` (сальдо), `sales` (продажи минус возвраты покупателей), `supplierReturns`, `writeOffs`, `stockCount`, `closing` — тип `pieces`; сторно относится к виду исходного движения на дату сторно | нет |
| `supplier_debts` | поставщик | `supplier`, (`debt`, `overdue`), `nextDueOn` — на сегодня (E18) | с правом |
| `cashiers` | кассир × точка | `cashier`, `store`, `receipts`, `cash` (продажи наличными за вычетом сдачи), `card`, `qr`, `nfc` (продажи по способам), `returns` (все возвраты, проведённые кассиром, отрицательные), `revenue` = способы + `returns` | да |
| `losses` | строка документа | `number`, `date`, `store`, `product`, `reason` (`WriteOffReason` или `stock_count`), `quantity` (`pieces`), (`amount`) — проведённые списания, в т. ч. автосписания, и недостачи инвентаризаций, по себестоимости | да (сумма) |
| `controlled` | продажа строки ПКУ | `at`, `store`, `product`, `batch`, `quantity` (`pieces`), `cashier`, `receipt`, `prescription` (данные рецепта; очищенные по сроку — пометка) | нет |
| `controlled_summary` (новый) | препарат ПКУ × точка | `product`, `store`, `opening`, `received` (приход, начальные остатки, перемещения на точку, возвраты покупателей, излишки), `issued` (продажи, списания, перемещения с точки, возвраты поставщику, недостачи), `closing` — `pieces`; препарат — по текущему признаку `is_controlled` | нет |

Без `finance:view-cost` колонки в скобках отсутствуют и в `columns`, и в строках; итог по деньгам — тоже.

### 5.4 Уведомления

Правила создания (E11), ключи дедупликации и параметры:

| Вид | Источник | Ключ | Снимается |
|---|---|---|---|
| `batch_expiring` | партия с остатком в пределах порога (E4) | `batch_expiring:<batchId>` | остаток 0 или партия вне порога (порог уменьшили) |
| `low_stock` | точка, где есть товары ниже минимума; `positions` — их число | `low_stock:<storeId>` | ниже минимума ничего нет |
| `supplier_payment_due` | поставщик × точка, у приходов которой срок оплаты ≤ сегодня + `supplier_payment_reminder_days`, долг > 0 | `supplier_payment_due:<supplierId>:<storeId>:<dueDate>` | долг по этим приходам закрыт |
| `transfer_in_transit` | перемещение `in_transit`; точка — получатель | `transfer:<documentId>` | принято или отозвано |
| `shift_discrepancy` | закрытая смена с расхождением ≠ 0 | `shift:<shiftId>` | не снимается (событие) |
| `negative_stock` | чеки с пометкой `stock` за бизнес-дату; `positions` — число строк | `negative_stock:<storeId>:<date>` | не снимается (событие) |

`days` в `batch_expiring` считается при чтении от `expiresOn` из параметров. Выключенный в настройках вид не создаётся
и не показывается.

### 5.5 Журнал действий

`TenantAuditEntry` (раздел 6.4): время, дата документа (E8), сотрудник, точка, группа, код события, объект, параметры,
«оператор» (`acting_operator_id`). Поиск `q` — по объекту и номеру. Порядок — новые сверху, `limit` ≤ 100.

### 5.6 Расходы (PR 3)

`GET` возвращает записи месяца, их сумму и изъятия «на расходы» месяца по точкам (только чтение: точка, сумма, число
изъятий); `POST` / `PUT` — месяц, точка или `null`, вид, сумма, комментарий; `DELETE` — удаление записи. Все изменения —
в аудит.

## 11. Проверка

Новых автотестов нет (решение «тесты до MVP»), кроме unit-теста `prorateExpense` в `libs/shared/domain` (как правило
суммы возврата). Существующие наборы — зелёные; `npm run check` — у пользователя.

Живая проверка на dev-API (curl и браузер, режим `partial`):
- сценарий сети из двух точек: продажи со скидкой, возврат по желанию и брака, списание, инвентаризация с недостачей и
  излишком, перемещение, возврат поставщику, ПКУ — затем сверка вручную: выручка главной = отчёт = смены; прибыль по
  формуле E3; строки «Движение» и «ПКУ: сводка» сходятся;
- периоды: сегодня, неделя, месяц, свой период; `from` > `to`, будущая дата, 93 дня на главной — 422;
- управляющий одной точки: главная, отчёты, журнал и уведомления — только его точка; чужая `storeId` — 403;
- без `finance:view-cost`: нет колонок денег в отчётах и сумм в уведомлениях;
- настройки: тайм-аут действует для новой сессии; длина PIN — при смене PIN, старый PIN входит; выключенный вид
  уведомлений исчезает; `PUT` без свежего входа — 403 `fresh_auth_required`; цена ниже закупочной — предупреждение
  только при включённой настройке;
- уведомления: партия в пороге появляется и снимается после списания; повторный запрос в течение 5 минут не
  обновляет; «прочитать все» — счётчик 0 только у этого сотрудника; кассир — 403;
- расходы (PR 3): аренда октября за 1–14.10 входит долей 14/31; расход сети — только в итоге; изъятие «на расходы»
  из кассы — в `cashExpenses` точки за дату изъятия, инкассация — нет; правка и удаление — в журнале действий;
  управляющий без `expenses:view` колонок расходов не видит.
