## 1. Профиль проекта

| Параметр | Значение |
|---|---|
| Класс проекта | Full — продуктовая система |
| Тип проекта | Веб-приложение: клиентский продукт (касса, склад, кабинет владельца) и административный продукт (админка оператора платформы). Офлайн-дистрибутив точки — та же система, разворачиваемая локально (Docker) |
| Репозитории кода | Единый репозиторий `pharmacy` (ADR-0010, 2026-09-29): Nx-монорепо в корне — `apps/api` (NestJS, единый бэкенд обоих продуктов), `apps/web` (клиентский продукт), `apps/admin` (админка оператора), `libs/*` (общие типы, DTO, доменная логика, UI-кит) — и архитектурные артефакты (`docs/architecture/`: stack.md, C4, ADR, APPROVAL). Отступление от практики «один деплой-юнит = один репозиторий» обосновывается в ADR-0002 и ADR-0010. ~~Отдельный кодовый репозиторий `pharmacy-app`~~ — заменено ADR-0010 |
| Назначение (1–2 предложения) | Мультитенантная SaaS-платформа автоматизации аптечных сетей Таджикистана: складской учёт по партиям (FEFO, сроки годности), касса с офлайн-режимом, закупки и долги поставщикам, цены/скидки, возвраты, отчёты, выгрузка в 1С — плюс административный контур оператора (тенанты, биллинг, лицензионные ключи офлайн-точек, услуги) |
| Пользователи и пиковая нагрузка | Из ТЗ: на старте 3 тенанта, ~30 точек, до 50 одновременно работающих кассиров; операции кассы ≤ 1 сек; архитектура обязана выдержать рост ×5 без переработки |
| Критичность | Tier 2 — при простое облака в течение дня облачные аптеки не могут штатно продавать (смягчается буфером перебоев связи), владельцы не видят отчёты; офлайн-точки продолжают работать. Подтверждено командой |
| Категория данных | Персональные данные: ФИО и учётные записи сотрудников тенантов, контакты поставщиков, поля рецептов ПКУ (состав уточняется заказчиком). Розничный покупатель анонимен. |
| Объём данных и срок хранения | Оценка (подтверждена командой): ~3–9 тыс. чеков/день на платформу; за 3 года ~5–10 млн чеков и ~30–50 млн строк движений по партиям; суммарно десятки ГБ, до ~100 ГБ с учётом роста ×5. Аудит-журналы неизменяемы, хранение ≥ 3 лет; бэкапы облачной БД ежедневно, хранение 30 дней |
| Доступность (SLA) | 99,5% в рабочие часы тенантов; плановые работы ночью с уведомлением (из ТЗ) |
| RTO / RPO | RTO 4 часа / RPO 24 часа (из ТЗ) |
| Ограничения | Срок — запуск до конца 2026 года. Компетенции команды: NestJS, Next.js, Angular (нет .NET/PHP). Валюта TJS, автозагрузка курсов НБТ; локализация RU/TJ; фискализация РТ (в MVP — адаптер-заглушка); место хостинга — открытый юридический вопрос; офлайн-точки требуют Docker (ADR-0005) |

## 2. Чек-лист безопасности

| Вопрос | Ответ |
|---|---|
| Какие категории данных обрабатываются? | Персональные данные (сотрудники тенантов, контакты поставщиков, поля рецептов ПКУ); финансовые данные тенантов (продажи, долги, счета). Покупатель анонимен |
| Где хранятся секреты (пароли, ключи, строки подключения)? | НЕ в коде и не в git; на MVP — env-файлы на хосте среды (`docker/env/*.env`). Хранилище секретов не выбрано — через ADR (открытый вопрос № 8) |
| Как аутентифицируются пользователи? | Самописная аутентификация по ТЗ: логин + пароль (хеш), PIN ≥ 4 цифр для переключения кассира на привязанном к точке терминале, таймаут сессии (настройка сети). Реализация — ADR-0008; самописная криптография запрещена (ADR-0011) |
| Как аутентифицируются сервисы между собой? | Внутри облака — модульный монолит, внешних межсервисных вызовов нет. Синхронизация офлайн-точка ↔ облако — HTTPS + уникальный лицензионный ключ точки |
| Что уходит за контур платформы (данные, вызовы)? | Продукт — внешняя SaaS-платформа для аптек; данные тенантов живут в облаке платформы, место хостинга — открытый вопрос № 1. Исходящие внешние вызовы — только закрытый список интеграций (раздел 4); ПДн и клиентские данные во внешние LLM/SaaS не передаются (ADR-0011) |
| Что шифруется (при передаче / при хранении)? | При передаче — HTTPS на всех соединениях (из ТЗ). При хранении — пароли/PIN хешируются; шифрование БД и бэкапов — решить до prod (вместе с вопросом № 1) |
| Хранение данных на устройстве (для мобильных) | Не применимо (веб). Для офлайн-точки: локальная БД на ПК точки; ответственность за сохранность несёт тенант (фиксируется в договоре, из ТЗ) |
| Биометрия и fallback-вход (для мобильных) | Не применимо |
| Certificate pinning (для мобильных) | Не применимо |
| Root/jailbreak-детект (для мобильных) | Не применимо |
| Удалённый сброс при утере устройства, MDM (для мобильных) | Не применимо. Аналог для терминалов: отвязка терминала заведующим/владельцем, мгновенная блокировка сотрудника (из ТЗ) |

**Ревью безопасности:** обрабатываются персональные данные и используется самописная
аутентификация — архитектор проекта проверяет ADR-0008 и изоляцию тенантов до prod (APPROVAL.md).

## 3. Выбор стека

Стек фиксируется здесь и в ADR (ADR-0001, 0003–0005); новая технология — только через ADR
(ADR-0011); внешних согласований нет.

| Слой | Технология | Решение | Обоснование | Рассмотренные альтернативы |
|---|---|---|---|---|
| Backend | NestJS (Node.js, TypeScript) | ADR-0003 | Единственный бэкенд-стек, которым владеет команда; срок до конца 2026; единый TypeScript и общие типы с фронтендом в Nx-монорепо | C# (.NET), PHP — команда ими не владеет, обучение с нуля срывает срок |
| Frontend | Next.js (React, TypeScript), static export | ADR-0004 | Единая TS/React-экосистема с бэкендом, компетенции команды | Angular (команда владеет), чистый React — отклонены в пользу единой Next.js-экосистемы |
| БД | PostgreSQL | ADR-0001 | Реляционная модель из ТЗ (партии, движения, документы), мультитенантная изоляция (RLS), та же БД в Docker-дистрибутиве офлайн-точки | Другая СУБД — не рассматривалась, PostgreSQL подходит полностью |
| Кэш | Redis | ADR-0001 | Сессии и PIN-сессии терминалов, кэш каталога/цен для скорости кассы (≤ 1 сек) | — |
| API-стиль | REST | ADR-0001 | Браузерные клиенты и синхронизация офлайн-точек; простота отладки | gRPC — не нужен: нет внешних высоконагруженных потребителей |
| Аутентификация | Самописная (логин+пароль, PIN, привязка терминала) | ADR-0001; реализация — ADR-0008 | Требования ТЗ не ложатся на SSO: PIN-переключение кассиров на терминале, мультитенантные кастомные роли «модуль × действие × охват точек», офлайн-вход на автономной точке | Внешний IdP (Keycloak и т.п.) — офлайн-точка без интернета не может ходить в централизованный IdP |
| Язык фронтенда | TypeScript | ADR-0001 | Обязателен для всего кода фронтенда | — |
| Организация кода | Nx (монорепо), единый репозиторий | ADR-0002, ADR-0010 | Общие типы и библиотеки между `api`, `web`, `admin`; кэширование сборок | Отдельные репозитории — см. ADR-0010 |
| UI и стили | Tailwind CSS v4 поверх токенов `--ph-*`; собственный UI-кит `libs/ui` на нативной платформе | ADR-0007 | Свой дизайн-язык и эргономика кассы; ноль UI-кода рантайма на слабых POS; команда знает Tailwind | Готовые киты (MUI, Mantine, PrimeReact), headless (Base UI, Radix), shadcn/ui — см. ADR-0007 |
| Доступ к данным / миграции | Kysely + `pg`, SQL-миграции node-pg-migrate | ADR-0006 | Инварианты (RLS на транзакцию, FOR UPDATE, ON CONFLICT, append-only) SQL-природные; spike: нет путей утечки данных чужого тенанта, чистый JS для офлайн-образа | Prisma 7, TypeORM 1.x, MikroORM 7 — сравнены spike'ом, см. ADR-0006 |
| Контейнеризация | Docker (офлайн-дистрибутив, test/prod, локальная среда) | ADR-0005 | Требование ТЗ: офлайн-точка = Docker-образ на ПК точки (Windows 10/11 + WSL2, Linux); воспроизводимые среды | Нативная установка служб — хрупкая, противоречит ТЗ |

## 4. Интеграции

Правила: закрытый список интеграций (ADR-0011), новая — через ADR;
для финансовых операций — идемпотентность и correlation ID.

| Система | Протокол | Формат | Владелец | SLA |
|---|---|---|---|---|
| 1С:Бухгалтерия 8 для Таджикистана | Файловый обмен, выгрузка вручную за период | CommerceML/XML | Бухгалтерия заказчика | Нет (офлайн-обмен); тестовая база заказчика нужна к приёмке W2-05 |
| Фискализация (онлайн-ККМ / виртуальная касса) | Адаптер отправки чека; в MVP — заглушка (логирует и возвращает успех) | По требованиям вендора ККМ | Вендор не выбран (открытый вопрос № 9) | Замена заглушки на реального вендора не должна менять кассу |
| Курсы валют НБТ | Исходящий запрос курса на дату операции (REST/HTML — уточнить при реализации) | JSON/HTML | Национальный банк Таджикистана | Ежедневная загрузка; ручная корректировка при недоступности |
| Банковский эквайринг | БЕЗ интеграции в MVP: отдельный банковский терминал, кассир указывает способ оплаты; сверка вручную по итогам смены | — | Банк-эквайер заказчика | — |
| Синхронизация офлайн-точек | HTTPS, очередь операций, идемпотентность (из ТЗ: повторная отправка без дублей) | JSON | Собственный компонент платформы | Расписание по умолчанию раз в сутки + ручной запуск |
