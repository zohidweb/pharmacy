# Governance техрадара

## Роли

- **Владелец радара**: главный архитектор банка (роль, не человек).
- **Апрув исключений**: Архитектурный комитет; для security-категорий — совместно с ИБ.
- **Эскалация**: архитектурный комитет / CTO.

## Цикл пересмотра

- Плановый пересмотр — **ежеквартально**.
- Внеочередной — при накоплении **2+ одинаковых** запросов на исключение.
- Каждое изменение статуса — строка в «Changelog радара» (RADAR.md) с датой,
  версия радара увеличивается.

## Как команды получают обновления

- Радар живёт копией в каждом проекте. Канонический источник — центральный репозиторий
  ai-project-start (URL в шапке RADAR.md).
- Команда обновляет копию командой `/update-radar` (или вручную, см. docs/guides).
- О релизах радара и шаблона владелец сообщает в канал «Архитектура».
- Проекты не обязаны мигрировать на новые версии, КРОМЕ случая перевода их технологии
  в «Запрещено» — тогда владелец радара уведомляет команду и согласует план миграции.

## Реестр post-factum ревью (Lite)

Заполняется командой проекта при финализации (`/04-generate-claude-md` или ручной шаг 5),
если `APPROVAL.md` содержит `Статус: APPROVED (post-factum)`. Столбец «Дедлайн ревью»
переносится из строки APPROVAL.md `Дедлайн фактического ревью: YYYY-MM-DD` (обязательна для
post-factum, иначе финализация запрещена). Комитет проверяет реестр на каждом квартальном
пересмотре радара (см. «Цикл пересмотра» выше). Просроченный дедлайн без проведённого
ревью — эскалация владельцу радара.
