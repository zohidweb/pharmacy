## Deduplicate Receipts and Sync Operations with Idempotency Keys

Касса досылает операции из буфера перебоев связи, офлайн-точка повторяет пакеты синхронизации,
сеть рвётся после COMMIT, но до ответа. Повтор обязан вернуть **тот же** результат, а не создать
второй чек и второе списание партий. Конвенция проекта: финансовые операции и синхронизация —
idempotency key + correlation ID.

Ключ генерирует **клиент** (браузер кассы / офлайн-точка) при создании операции (UUID) и
передаёт при каждой попытке. Уникальность обеспечивает БД, а не проверка «select, потом insert».

**Incorrect:**

```sql
-- Check-then-insert: two concurrent retries both see "nothing" and both insert
select id from receipts where tenant_id = $1 and idempotency_key = $2;
insert into receipts (...) values (...);

-- Upsert that overwrites a financial document on retry
insert into receipts (...) values (...)
on conflict (tenant_id, idempotency_key) do update set total_dirams = excluded.total_dirams;
```

**Correct (уникальный ключ + `ON CONFLICT DO NOTHING RETURNING` как «ворота» транзакции):**

```sql
create table receipts (
  tenant_id uuid not null references tenants (id),
  id uuid not null,                    -- UUIDv7 from the application
  store_id uuid not null,
  operation_id uuid not null,          -- idempotency key (UUIDv7 generated by the client / store)
  request_hash bytea not null,         -- SHA-256 of the normalized request payload
  correlation_id text not null,        -- tracing only, NOT a dedup key
  total_dirams bigint not null check (total_dirams >= 0),
  created_at timestamptz not null default now(),
  primary key (tenant_id, id),
  constraint receipts_operation_uq unique (tenant_id, operation_id)
);

begin;
select set_config('app.tenant_id', $1, true);

insert into receipts (tenant_id, id, store_id, operation_id, request_hash, correlation_id, total_dirams)
values ($1, $2, $3, $4, $5, $6, $7)
on conflict (tenant_id, operation_id) do nothing
returning id;

-- Row returned  → first attempt: lock batches, write lines + movements + audit, COMMIT.
-- No row        → duplicate: do NOT write movements; COMMIT/ROLLBACK and return the stored result:
select id, request_hash, total_dirams from receipts
where tenant_id = $1 and operation_id = $4;
-- request_hash differs → same key reused for a different payload → 409/422 problem+json
commit;
```

Конкурентный повтор с тем же ключом блокируется на уникальном индексе до завершения первой
транзакции и затем получает `DO NOTHING` — дубля не будет даже при одновременной досылке.

Синхронизация офлайн-точек (приёмная сторона в облаке, ADR-0014; таблица — модель данных
`06-sync-audit-billing.md`, месячные секции по `received_at`):

```sql
create table sync_inbox (
  tenant_id uuid not null,
  store_id uuid not null,
  operation_id uuid not null,          -- UUIDv7 generated on the store when the operation was created
  store_seq bigint not null,           -- the store's own order of operations
  type text not null,
  type_version integer not null,
  payload_hash bytea not null,         -- SHA-256: the same id with another hash is rejected
  envelope jsonb not null,             -- raw envelope for quarantine re-apply
  status text not null check (status in ('applied', 'duplicate', 'quarantined', 'rejected', 'pending_dependency')),
  reason text,
  received_at timestamptz not null default now(),
  primary key (tenant_id, store_id, operation_id, received_at)
) partition by range (received_at);

begin;
select set_config('app.tenant_id', $1, true);
select pg_advisory_xact_lock(hashtext('sync-apply'), hashtext($2::text));  -- one applier per store
-- duplicate check across partitions: the id may arrive again months later
select payload_hash from sync_inbox where tenant_id = $1 and store_id = $2 and operation_id = $3;
-- found, same hash  → status 'duplicate', ack;  found, other hash → 'rejected: id-reused'
-- not found         → validate (sums, signs, dependency) → apply operation + movements in THIS
--                     transaction and insert the inbox row as 'applied' — or 'quarantined'
commit;
```

Секционированная таблица не может иметь уникальный ключ без ключа секции, поэтому повтор
`operation_id` проверяется запросом под advisory-локом точки (операции одной точки применяются
последовательно).

Правила:

- Ключ и применение операции — в одной транзакции; запись ключа «заранее» отдельной транзакцией
  при сбое оставит ключ без операции.
- `store_id` и `tenant_id` для синхронизации берутся из лицензионного ключа точки
  (`LicenseKeyGuard` + резолвер `resolve_license_key`), не из тела пакета.
- Срок хранения ключей ≥ максимального окна повторов (офлайн-точка может быть без связи днями) —
  ключи чеков не удаляются вместе с чеками.
- `ON CONFLICT DO UPDATE` для финансовых документов запрещён; он уместен для настроек и
  справочников (см. `data-upsert.md`).

Reference: [INSERT … ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT)
